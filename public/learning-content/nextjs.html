Next.js — Comprehensive Learning Reference

1. Overview & Rendering Modes

Next.js is a React meta-framework built by Vercel that provides production-grade features: file-based routing, multiple rendering strategies, API routes, image optimization, and more — out of the box.

Why Next.js? Pure React is a UI library — it doesn't prescribe routing, data fetching, or rendering strategy. Next.js provides these opinionated, optimized solutions, letting you focus on your app rather than configuration.

2. Version History

Next.js 13 (October 2022)

  • App Router (beta) — new app/ directory, React Server Components by default
  • Layouts — persistent UI between routes with layout.tsx
  • Server Components — zero-bundle UI components, run only on server
  • Server Actions (preview) — mutations via async functions with 'use server'
  • Turbopack (alpha) — Rust-based bundler, 700x faster HMR claim
  • New next/image — improved API, lazy loading by default
  • New next/font — automatic font optimization, zero layout shift
  • New next/link — no need for nested <a> tag

Next.js 14 (October 2023)

  • Server Actions stable — form actions, revalidation, redirect in production
  • Partial Prerendering (PPR) preview — static shell + dynamic streaming holes, single request
  • Improved Metadata API — generateMetadata, viewport, themeColor as separate export
  • Turbopack improvements — 53% faster local dev server cold starts
  • Minimum Node.js version: 18.17
  • Form component (preview) for progressive enhancement

Next.js 15 (October 2024)

  • React 19 support — useActionState, useOptimistic, new form actions
  • Async Request APIs — cookies(), headers(), params, searchParams are now async (breaking change)
  • Turbopack stable — now default for next dev --turbopack
  • Caching changes — fetch requests and route handlers no longer cached by default (opt-in caching)
  • after() API — run code after response is sent (analytics, logging)
  • forbidden() / unauthorized() — new error functions (like notFound())
  • Static Indicator in dev mode
  • next/form component stable — client-side navigation + prefetching for forms

Migration Guide (Pages → App Router)

// BEFORE (Pages Router): pages/blog/[slug].tsx
import { GetStaticProps, GetStaticPaths } from 'next'

export const getStaticPaths: GetStaticPaths = async () => {
  const posts = await getPosts()
  return {
    paths: posts.map(p => ({ params: { slug: p.slug } })),
    fallback: 'blocking'
  }
}

export const getStaticProps: GetStaticProps = async ({ params }) => {
  const post = await getPost(params!.slug as string)
  return {
    props: { post },
    revalidate: 3600  // ISR
  }
}

export default function BlogPost({ post }: { post: Post }) {
  return <article>{post.title}</article>
}

// AFTER (App Router): app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation'

export async function generateStaticParams() {
  const posts = await getPosts()
  return posts.map(p => ({ slug: p.slug }))
}

export const revalidate = 3600  // ISR equivalent

export default async function BlogPost({
  params
}: {
  params: Promise<{ slug: string }>  // Next.js 15: async params
}) {
  const { slug } = await params
  const post = await getPost(slug)
  if (!post) notFound()
  return <article>{post.title}</article>
}

Middleware

// middleware.ts (at project root or inside src/)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  const token = request.cookies.get('auth-token')?.value

  // Auth protection
  if (request.nextUrl.pathname.startsWith('/dashboard')) {
    if (!token) {
      return NextResponse.redirect(new URL('/login', request.url))
    }
  }

  // Rewrite
  if (request.nextUrl.pathname === '/old-path') {
    return NextResponse.rewrite(new URL('/new-path', request.url))
  }

  // Add headers
  const response = NextResponse.next()
  response.headers.set('x-custom-header', 'my-value')
  return response
}

// Configure which paths middleware runs on
export const config = {
  matcher: [
    '/dashboard/:path*',
    '/api/:path*',
    '/((?!_next/static|_next/image|favicon.ico).*)'
  ]
}

5. Server Components & Client Components

In the App Router, all components are Server Components by default. You opt into client-side behavior with 'use client' at the top of a file.

Rules & Capabilities

CapabilityServer ComponentClient Component
Access server resources (DB, files, secrets)YesNo
useState, useEffect, hooksNoYes
Browser APIs (window, localStorage)NoYes
Event listeners (onClick, etc.)NoYes
Keep sensitive data (API keys) off client bundleYesNo
Async/await at component levelYesNo (use hooks)
Stream progressivelyYesNo
Access cookies, headers directlyYes (await cookies(), headers())No (only via API)

Server Component (default)

// app/users/page.tsx — Server Component (no 'use client')
import { db } from '@/lib/database'

// Direct database access, no API layer needed
export default async function UsersPage() {
  // This runs on the server — never sent to client
  const users = await db.user.findMany({
    select: { id: true, name: true, email: true }
  })

  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>
          {user.name} — {user.email}
        </li>
      ))}
    </ul>
  )
}

Client Component

'use client'
// Add at the top — marks this file and all imports as client-side

import { useState, useEffect } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)

  useEffect(() => {
    document.title = `Count: ${count}`
  }, [count])

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
    </div>
  )
}

Passing Server Components as Children to Client Components

// WRONG: importing Server Component inside Client Component
'use client'
import ServerComponent from './ServerComponent' // This becomes a Client Component!

// CORRECT: pass Server Components as children/props
// Parent (Server Component)
import ClientWrapper from './ClientWrapper'
import ServerContent from './ServerContent'

export default function Page() {
  return (
    <ClientWrapper>
      <ServerContent />  {/* Passed as children prop — stays Server */}
    </ClientWrapper>
  )
}

// ClientWrapper.tsx
'use client'
export default function ClientWrapper({
  children
}: {
  children: React.ReactNode
}) {
  const [isOpen, setIsOpen] = useState(true)
  return isOpen ? <div>{children}</div> : null
}

6. Server Actions

Server Actions are async functions that run on the server, called from the client. They're the recommended way to handle form submissions and data mutations in the App Router.

Basic Server Action

// app/actions.ts
'use server'  // All exports from this file are Server Actions

import { revalidatePath, revalidateTag } from 'next/cache'
import { redirect } from 'next/navigation'
import { cookies, headers } from 'next/headers'

export async function createPost(formData: FormData) {
  // Server-side validation
  const title = formData.get('title') as string
  const content = formData.get('content') as string

  if (!title || title.length < 3) {
    return { error: 'Title must be at least 3 characters' }
  }

  // Direct DB access
  const post = await db.post.create({
    data: { title, content }
  })

  // Revalidate cached data
  revalidatePath('/blog')
  revalidateTag('posts')  // Invalidate all fetches tagged with 'posts'

  // Redirect (throws internally, must not be in try/catch)
  redirect(`/blog/${post.slug}`)
}

export async function deletePost(postId: string) {
  const cookieStore = await cookies()
  const userId = cookieStore.get('userId')?.value
  if (!userId) throw new Error('Unauthorized')

  await db.post.delete({ where: { id: postId, userId } })
  revalidatePath('/blog')
}

Form Actions & useActionState (React 19)

'use client'
import { useActionState } from 'react'
import { createPost } from '@/app/actions'

type FormState = {
  error?: string
  success?: boolean
}

export default function CreatePostForm() {
  const [state, formAction, isPending] = useActionState<FormState, FormData>(
    createPost,
    {}  // Initial state
  )

  return (
    <form action={formAction}>
      <input name="title" required />
      <textarea name="content" />
      {state.error && <p className="error">{state.error}</p>}
      <button type="submit" disabled={isPending}>
        {isPending ? 'Saving...' : 'Create Post'}
      </button>
    </form>
  )
}

// after() — Next.js 15: run code after response is finalized
import { after } from 'next/server'

export async function processOrder(formData: FormData) {
  'use server'
  const order = await db.order.create({ data: parseOrder(formData) })

  // Response is sent to user, THEN this runs
  after(async () => {
    await sendConfirmationEmail(order)
    await updateInventory(order.items)
    await logAnalytics('order_created', order.id)
  })

  redirect('/order-confirmation')
}

Streaming

// Streaming — send static shell immediately, stream dynamic parts
import { Suspense } from 'react'

export default function Dashboard() {
  // Static content renders and sends immediately
  return (
    <div>
      <h1>Dashboard</h1>  {/* Sent immediately */}
      <Suspense fallback={<ChartSkeleton />}>
        <SlowChart />         {/* Streamed when ready */}
      </Suspense>

      </Suspense>

}

// Each Suspense boundary streams independently — no waterfall
async function SlowChart() {
  const data = await fetchChartData()  // 2s
  return <Chart data={data} />
}

async function DataTable() {
  const rows = await fetchTableData()  // 500ms — arrives before SlowChart
  return <Table rows={rows} />
}

9. Route Handlers

// app/api/users/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { cookies, headers } from 'next/headers'

// GET /api/users?page=1&limit=10
export async function GET(request: NextRequest) {
  const { searchParams } = request.nextUrl
  const page = parseInt(searchParams.get('page') ?? '1')
  const limit = parseInt(searchParams.get('limit') ?? '10')

  // Next.js 15: cookies/headers are async
  const cookieStore = await cookies()
  const token = cookieStore.get('auth-token')?.value

  if (!token) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }

  const users = await db.user.findMany({
    skip: (page - 1) * limit,
    take: limit
  })

  return NextResponse.json({ users, page, limit })
}

// POST /api/users
export async function POST(request: NextRequest) {
  const body = await request.json()

  // Validation
  if (!body.email || !body.name) {
    return NextResponse.json(
      { error: 'Email and name are required' },
      { status: 400 }
    )
  }

  const user = await db.user.create({ data: body })
  return NextResponse.json(user, { status: 201 })
}

// Dynamic route: app/api/users/[id]/route.ts
export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ id: string }> }  // Next.js 15: async params
) {
  const { id } = await params
  const user = await db.user.findUnique({ where: { id } })
  if (!user) return NextResponse.json({ error: 'Not found' }, { status: 404 })
  return NextResponse.json(user)
}

export async function DELETE(
  request: NextRequest,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params
  await db.user.delete({ where: { id } })
  return new NextResponse(null, { status: 204 })
}

Streaming Response

// app/api/stream/route.ts
export async function GET() {
  const stream = new ReadableStream({
    async start(controller) {
      const encoder = new TextEncoder()

      for (let i = 0; i < 10; i++) {
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ i })}\n\n`))
        await new Promise(resolve => setTimeout(resolve, 100))
      }

      controller.close()
    }
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive'
    }
  })
}

13. Interview Q&A

Easy Questions

Q1. What is the difference between SSR, SSG, and ISR in Next.js? Easy

SSG (Static Site Generation) — HTML is generated at build time. The same HTML is served to all users. Best for content that rarely changes (blogs, marketing pages).

SSR (Server-Side Rendering) — HTML is generated on the server for each request. Fresh data per user. Best for user-specific content (dashboards, logged-in pages).

ISR (Incremental Static Regeneration) — Pages are generated statically but revalidated in the background after a time interval. Best of both: fast static serving + fresh data.

// SSG — cache forever (or build-time only)
const data = await fetch(url, { cache: 'force-cache' })

// SSR — no cache, fresh per request
const data = await fetch(url, { cache: 'no-store' })

// ISR — revalidate every hour
const data = await fetch(url, { next: { revalidate: 3600 } })
// Or at route level:
export const revalidate = 3600
SSGSSRISR
SpeedFastest (CDN)Slower (server per request)Fast (CDN + background refresh)
Data freshnessBuild-time onlyAlways freshUp to N seconds stale
ScaleUnlimited (CDN)Limited by serverUnlimited (CDN)
Q2. What is the App Router and how is it different from the Pages Router? Easy

The App Router (app/ directory, introduced in Next.js 13) uses React Server Components by default, supports nested layouts, loading states, error boundaries, and Server Actions. It's the current recommended approach.

The Pages Router (pages/ directory) is the legacy approach where all components run on the client, and data fetching is done via getStaticProps / getServerSideProps.

Key differences:

  • App Router: Server Components by default. Pages Router: Client Components by default.
  • App Router: Layouts via layout.tsx that persist across navigations. Pages Router: Layouts via custom wrappers in _app.tsx.
  • App Router: loading.tsx automatically wraps pages in Suspense. Pages Router: Manual loading states.
  • App Router: Server Actions for mutations. Pages Router: No equivalent.

Both can coexist in the same application during migration.

Q3. What are Server Components and why are they useful? Easy

Server Components are React components that run only on the server — their code never ships to the client browser.

Benefits:

  • Direct access to databases, file system, and secrets without API layer
  • Reduced client JavaScript bundle (component code stays on server)
  • Improved initial page load and Core Web Vitals
  • No hydration cost for static content
// Server Component — database access, no API needed
export default async function ProductPage({ params }: { params: { id: string } }) {
  // This code never runs in the browser
  const product = await db.product.findUnique({ where: { id: params.id } })
  const SECRET_KEY = process.env.INTERNAL_API_KEY  // Safe, server-only

  return <div>{product.name}</div>
}

Limitations: Cannot use useState, useEffect, event handlers, or browser APIs. For those, use Client Components with 'use client'.

Q4. How does the Next.js Image component optimize images? Easy

The next/image component provides automatic image optimization:

  • Format conversion: Automatically serves WebP/AVIF where supported (smaller file sizes)
  • Resizing: Serves correctly sized images for each device viewport
  • Lazy loading: Images below the fold load only when needed (default behavior)
  • Blur placeholder: Shows a blurred preview while the image loads
  • Priority: priority prop preloads above-the-fold images (important for LCP)
  • Prevents layout shift: Requires width/height or fill — prevents CLS

Q5. What is middleware in Next.js and when would you use it? Easy

Middleware runs before a request is completed, on every matched route. It runs at the Edge (close to the user, not on the origin server).

Common use cases:

  • Authentication and authorization — redirect to login if no session
  • A/B testing — serve different variants
  • Internationalization — redirect based on locale
  • Rate limiting (with external store like Upstash Redis)
  • Request logging and analytics
  • Rewriting URLs or setting headers
// middleware.ts
export function middleware(request: NextRequest) {
  const token = request.cookies.get('session')?.value
  if (!token && request.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
}

export const config = {
  matcher: '/dashboard/:path*'  // Only run on dashboard routes
}

Note: Middleware runs on every matched request — keep it fast and lightweight. Don't do heavy DB queries here.

Intermediate Questions

Q6. Explain Next.js caching layers and how they interact. Intermediate

Next.js has 4 caching layers that work together:

  1. Request Memoization — Per-render deduplication using React cache(). Identical fetch calls in the same render tree make ONE request. Automatically cleared between requests.
  2. Data Cache — Persistent server-side cache for fetch() calls. Controlled by cache and next.revalidate options. Persists across deployments (until revalidated).
  3. Full Route Cache — Cached rendered HTML+RSC payload for static routes. Built at deploy time. Invalidated when data cache invalidates.
  4. Router Cache — Client-side in-memory cache of route segments. Prefetched and visited routes are cached. Lasts 30s (dynamic) or 5min (static).
// Opt out of Data Cache (all fetches uncached)
export const dynamic = 'force-dynamic'
// or
fetch(url, { cache: 'no-store' })

// Tag-based invalidation — invalidates Data Cache + Full Route Cache
revalidateTag('products')
revalidatePath('/products')

// Next.js 15 change: fetch no longer cached by default
// Must explicitly opt in with cache: 'force-cache'
Q7. How do Server Actions work and what are their security considerations? Intermediate

Server Actions are async functions marked with 'use server'. They're called from the client but run exclusively on the server. Under the hood, they create POST endpoints automatically.

// actions.ts
'use server'
export async function updateUser(formData: FormData) {
  const name = formData.get('name') as string
  // Runs on server, can access DB directly
  await db.user.update({ where: { id: userId }, data: { name } })
  revalidatePath('/profile')
}

Security considerations:

  • Always validate and sanitize inputs — treat Server Actions like public API endpoints, not internal functions
  • Authentication: Always verify the user's session inside the action — the action can be called directly
  • Authorization: Check that the user has permission to perform the action on the specific resource
  • CSRF: Next.js adds CSRF protection automatically (Origin header checks)
  • Never trust client data: Even though it "looks" like server code, clients call it — validate everything
export async function deletePost(postId: string) {
  'use server'
  // Always authenticate
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')

  // Always authorize — check ownership
  const post = await db.post.findUnique({ where: { id: postId } })
  if (post?.authorId !== session.user.id) throw new Error('Forbidden')

  // Input validation
  if (!z.string().uuid().safeParse(postId).success) {
    throw new Error('Invalid ID')
  }

  await db.post.delete({ where: { id: postId } })
  revalidatePath('/blog')
}
Q8. How does streaming work in Next.js and what are the benefits? Intermediate

Streaming allows the server to progressively send HTML to the browser as it's generated, rather than waiting for all data to be ready. This uses HTTP chunked transfer encoding + React's concurrent rendering.

Traditional SSR waterfall: Wait for ALL data → Generate full HTML → Send response (user sees nothing for 2 seconds)

Streaming: Send static shell immediately → Stream each Suspense boundary as its data becomes available (user sees content progressively)

// Dashboard with streaming
export default function Dashboard() {
  return (
    <div>
      {/* Sent immediately — no data needed */}
      <h1>Dashboard</h1>
      <nav>...</nav>

      {/* Streamed when revenue data is ready (~100ms) */}
      <Suspense fallback={<KPISkeleton />}>
        <KPICards />
      </Suspense>

      {/* Streamed when analytics data is ready (~2s) */}
      {/* Doesn't block KPICards from appearing! */}
      <Suspense fallback={<ChartSkeleton />}>
        <AnalyticsChart />
      </Suspense>
    </div>
  )
}

Benefits:

  • Improved Time to First Byte (TTFB) — shell arrives instantly
  • Improved First Contentful Paint (FCP)
  • No sequential waterfall — slow data doesn't block fast data
  • Better perceived performance with skeleton UI during loading
Q9. Explain Partial Prerendering (PPR) and how it differs from regular SSG/SSR. Intermediate

PPR is a new rendering model (Next.js 14+) that combines static and dynamic in a single request:

  • The static shell (layout, nav, static content) is pre-rendered at build time and served from CDN
  • Dynamic holes (Suspense boundaries containing dynamic content) are streamed from the server

This is different from SSG/SSR:

SSGSSRPPR
Static contentCDNServer (slow)CDN (fast)
Dynamic contentNot possibleServer (per-request)Streamed from server
Requests1 (CDN)1 (Server)1 (CDN shell + stream)

Advanced Questions

Q11. How does Next.js handle React Server Component serialization and the RSC payload? Advanced

When Next.js renders Server Components, it produces an RSC payload — a special binary/text format that describes the rendered UI tree. This is separate from HTML.

The RSC payload contains:

  • The rendered output of Server Components (as tree references)
  • Placeholders for Client Components (with their props serialized)
  • References to JavaScript files needed for Client Components
// Simplified RSC wire format (JSON-like):
0:["$","div",null,{
  "children":[
    ["$","h1",null,{"children":"Server Component"}],
    ["$","$L1",null,{"initialCount":5}]  // $L1 = Client Component lazy ref
  ]
}]
1:I["path/to/Counter.js",["Counter"],"default"]  // Client Component reference

Navigation flow:

  1. Initial load: Server renders HTML + RSC payload → Sent to browser → React hydrates using RSC payload
  2. Client navigation: Browser requests RSC payload only (no full HTML) → React merges into existing tree

This is why layouts persist across navigations — React uses the RSC payload to update only changed segments, preserving Client Component state in unchanged parts.

Serialization constraints: Props passed to Client Components must be serializable (no functions, no class instances, no Sets/Maps without serialization).

  }

Q13. Explain how to implement optimistic updates with Server Actions and useOptimistic. Advanced

useOptimistic (React 19) allows you to immediately show the expected result of a mutation before the server confirms it, then revert if the action fails.

'use client'
import { useOptimistic, useTransition } from 'react'
import { toggleLike } from '@/app/actions'

interface Post {
  id: string
  likes: number
  liked: boolean
}

export default function LikeButton({ post }: { post: Post }) {
  const [isPending, startTransition] = useTransition()

  // useOptimistic: [optimistic state, dispatch function]
  const [optimisticPost, setOptimisticPost] = useOptimistic(
    post,
    (currentPost, liked: boolean) => ({
      ...currentPost,
      liked,
      likes: liked ? currentPost.likes + 1 : currentPost.likes - 1
    })
  )

  function handleLike() {
    startTransition(async () => {
      // Immediately show optimistic state
      setOptimisticPost(!optimisticPost.liked)

      // Run server action (may take time)
      try {
        await toggleLike(post.id)
        // On success: real data from server will update state
      } catch {
        // On failure: optimistic state automatically reverts
      }
    })
  }

  return (
    <button onClick={handleLike} disabled={isPending}>
      {optimisticPost.liked ? '❤️' : '🤍'} {optimisticPost.likes}
    </button>
  )
}
Q14. How would you implement a multi-tenant Next.js application? Advanced

Multi-tenancy in Next.js is typically implemented using middleware to detect the tenant from subdomain/path, then serving tenant-specific content.

// middleware.ts
export function middleware(request: NextRequest) {
  const hostname = request.headers.get('host')!
  const subdomain = hostname.split('.')[0]

  // app.example.com → rewrite to /app
  // tenant.example.com → rewrite to /tenants/tenant
  const rootDomain = 'example.com'

  if (hostname === `app.${rootDomain}` || hostname === `www.${rootDomain}`) {
    return NextResponse.next()
  }

  // Custom subdomain — rewrite URL to include tenant segment
  const url = request.nextUrl.clone()
  url.pathname = `/tenants/${subdomain}${url.pathname}`
  return NextResponse.rewrite(url)
}

// app/tenants/[tenant]/layout.tsx

Q15. How does Turbopack differ from Webpack and what does it change about the development experience? Advanced

Turbopack is a next-generation JavaScript bundler written in Rust, designed as a replacement for Webpack. It became stable for next dev in Next.js 15.

FeatureWebpackTurbopack
LanguageJavaScriptRust
Incremental computationLimitedFine-grained (function-level)
Cold startSlow (full bundle)Fast (lazy compilation)
HMRSeconds on large appsMilliseconds
Build (next build)StableBeta/not yet default

Key architecture difference: Turbopack uses a demand-driven computation engine. It only compiles what's actually needed (requested by the browser), rather than bundling everything upfront. Changes invalidate only the specific functions/modules that changed, not entire files.

Q17. How would you implement a real-time collaborative feature (like Google Docs) in Next.js? Very Advanced

Real-time collaboration requires WebSockets or Server-Sent Events, which are beyond typical Next.js rendering. The architecture combines Next.js for the UI with a separate real-time server.

// app/docs/[id]/page.tsx — Server Component for initial load
export default async function DocPage({
  params

// CollaborativeEditor.tsx — Client Component with Yjs + WebSocket
'use client'
import { useEffect, useRef } from 'react'
import * as Y from 'yjs'
import { WebsocketProvider } from 'y-websocket'
import { Editor } from '@tiptap/react'

export default function CollaborativeEditor({ documentId, initialContent, userId }) {
  const editorRef = useRef(null)

  useEffect(() => {
    // Yjs CRDT document for conflict-free merging
    const ydoc = new Y.Doc()
    const ytext = ydoc.getText('content')

    // Connect to WebSocket server (separate from Next.js)
    const provider = new WebsocketProvider(
      process.env.NEXT_PUBLIC_WS_URL!,
      documentId,
      ydoc,
      { params: { userId } }
    )

    provider.awareness.setLocalStateField('user', {
      name: 'User Name',
      color: '#' + Math.floor(Math.random() * 0xFFFFFF).toString(16)
    })

    // Sync initial content
    if (ytext.toString() === '') {
      ytext.insert(0, initialContent)
    }

    // Persist to DB on change (debounced)
    const saveTimeout = { current: null }
    ytext.observe(() => {
      clearTimeout(saveTimeout.current)
      saveTimeout.current = setTimeout(() => {
        saveDocument(documentId, ytext.toString())
      }, 1000)
    })

    return () => {
      provider.destroy()
      ydoc.destroy()
    }
  }, [documentId])

  return <div ref={editorRef}>...</div>
}

// Server Action for periodic persistence
async function saveDocument(id: string, content: string) {
  'use server'
  await db.document.update({ where: { id }, data: { content } })
  // Don't revalidate path — we don't want to reload the page
}
Q18. How do you handle database connection pooling and prevent connection exhaustion in serverless Next.js? Very Advanced

Serverless functions create a new instance per invocation, potentially opening a new DB connection each time. With 100 concurrent requests, you'd have 100 DB connections — exhausting the pool quickly (PostgreSQL default: 100 max connections).

Solutions:

  1. Connection pooler — Use PgBouncer, Prisma Accelerate, or Neon's built-in pooler
  2. Singleton pattern — Reuse the connection across hot function restarts
  3. Edge-compatible ORMs — Drizzle + HTTP driver, Kysely + HTTP

Q19. How would you implement a custom Next.js plugin system that modifies the Webpack/Turbopack config? Very Advanced 
// next.config.ts — composable plugin pattern
import type { NextConfig } from 'next'
import { Configuration as WebpackConfig } from 'webpack'

// Plugin factory type
type NextPlugin = (config: NextConfig) => NextConfig

// Plugin 1: SVG as React components
const withSVG: NextPlugin = (config) => ({
  ...config,
  webpack(webpackConfig: WebpackConfig, options) {
    webpackConfig.module?.rules?.push({
      test: /\.svg$/,
      use: [
        options.defaultLoaders.babel,
        { loader: '@svgr/webpack', options: { icon: true } }
      ]
    })
    // Always call existing webpack config
    return typeof config.webpack === 'function'
      ? config.webpack(webpackConfig, options)
      : webpackConfig
  }
})

// Plugin 2: Bundle analysis
const withAnalyzer: NextPlugin = (config) => {
  const enabled = process.env.ANALYZE === 'true'
  if (!enabled) return config

  const bundleAnalyzer = require('@next/bundle-analyzer')({ enabled: true })
  return bundleAnalyzer(config)
}

// Plugin 3: Feature flags at build time
const withFeatureFlags: NextPlugin = (config) => ({
  ...config,
  webpack(webpackConfig, options) {
    webpackConfig.plugins?.push(
      new (require('webpack').DefinePlugin)({
        'process.env.FEATURE_NEW_CHECKOUT': JSON.stringify(
          process.env.FEATURE_NEW_CHECKOUT ?? 'false'
        )
      })
    )
    return typeof config.webpack === 'function'
      ? config.webpack(webpackConfig, options)
      : webpackConfig
  }
})

// Compose plugins (right-to-left, like Redux compose)
function compose(...plugins: NextPlugin[]): NextPlugin {
  return (config) => plugins.reduceRight((acc, plugin) => plugin(acc), config)
}

const baseConfig: NextConfig = {
  reactStrictMode: true,
  experimental: { ppr: 'incremental' }
}

export default compose(withAnalyzer, withFeatureFlags, withSVG)(baseConfig)
Q20. Describe a strategy for migrating a large Next.js Pages Router app to the App Router with zero downtime. Very Advanced

Large-scale migrations require an incremental, route-by-route strategy. Next.js supports coexistence of both routers simultaneously.

Migration Strategy:

  1. Audit and categorize — inventory all pages by complexity: simple (no data fetching), moderate (getStaticProps), complex (getServerSideProps + custom logic)
  2. Create app/ directory — Start with the root layout mirroring _app.tsx
  3. Migrate simple routes first — Static pages with minimal logic
  4. Shared infrastructure — Set up auth, i18n, theme providers in app/ layouts
  5. Feature flag per route — Use middleware to route traffic to old vs new
  6. Migrate complex routes last — Heavily data-dependent pages
  7. Remove pages/ directory — After all routes are migrated and verified
// Step 1: Both routers coexist

// app/blog/page.tsx — new App Router page
