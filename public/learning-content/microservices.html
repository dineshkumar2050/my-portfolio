Decomposition Strategies

1. Decompose by Business Capability

Identify what the business does, not how the software is built. Each service owns a business capability end-to-end.

graph LR subgraph "E-Commerce Business Capabilities" UC[User Management] CAT[Catalog Management] ORD[Order Management] PAY[Payment Processing] INV[Inventory Management] SHIP[Shipping & Fulfillment] NOTIF[Notifications] end

2. Decompose by Subdomain (DDD Bounded Contexts)

Domain-Driven Design identifies bounded contexts — each context has its own ubiquitous language and owns its domain model.

graph TD subgraph "Bounded Context: Orders" O_Order[Order] O_LineItem[LineItem] O_Customer[Customer - just an ID] end subgraph "Bounded Context: Customers" C_Customer[Customer - full profile] C_Address[Address] C_Preferences[Preferences] end subgraph "Bounded Context: Payments" P_Payment[Payment] P_Invoice[Invoice] P_Charge[Charge] end O_Order -->|OrderPlaced event| P_Payment O_Order -->|CustomerID reference| C_Customer
Key DDD Insight: The same concept (e.g., "Customer") means different things in different bounded contexts. In Orders, Customer is just an ID. In CRM, Customer has a rich profile. Don't share the model — share only IDs and events.

Kafka: Event Publishing Example (Java/Spring)

// Producer
@Service
public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void publishOrderPlaced(Order order) {
        OrderPlacedEvent event = new OrderPlacedEvent(
            order.getId(), order.getCustomerId(),
            order.getTotal(), Instant.now()
        );
        kafkaTemplate.send("order.placed", order.getId(), event)
            .addCallback(
                result -> log.info("Published: {}", event),
                ex -> log.error("Failed to publish", ex)
            );
    }
}

// Consumer
@Component
public class InventoryEventConsumer {

    @KafkaListener(topics = "order.placed", groupId = "inventory-service")
    public void handleOrderPlaced(OrderPlacedEvent event,
                                  @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                                  @Header(KafkaHeaders.OFFSET) long offset) {
        log.info("Received order {} from partition {} offset {}", event.getOrderId(), partition, offset);
        inventoryService.reserveItems(event.getOrderId(), event.getItems());
    }
}

API Gateway & BFF Pattern

API Gateway — Cross-Cutting Concerns

Backend for Frontend (BFF) Pattern

Instead of one generic API gateway, create a dedicated backend per client type. Each BFF optimizes for its client's specific needs.

graph LR MOB[Mobile App] --> MOBILE_BFF[Mobile BFF] WEB[Web App] --> WEB_BFF[Web BFF] THIRD[3rd Party] --> PUBLIC_BFF[Public API Gateway] MOBILE_BFF --> US[User Service] MOBILE_BFF --> OS[Order Service] WEB_BFF --> US WEB_BFF --> OS WEB_BFF --> PS[Product Service] PUBLIC_BFF --> OS
BFF Benefits: Mobile BFF can aggregate 5 service calls into 1 (reduce chattiness), compress responses, omit heavy fields. Web BFF can return richer data. Public BFF can throttle heavily. Each BFF evolves independently.

Inter-Service Authentication

JWT Propagation

// API Gateway validates the JWT from external client and propagates it downstream
// Downstream services verify the JWT themselves (no central validation bottleneck)

@Component
public class JwtPropagationFilter implements WebFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String authHeader = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (authHeader != null) {
            // Forward the original JWT to downstream services
            return chain.filter(exchange.mutate()
                .request(r -> r.header("Authorization", authHeader))
                .build());
        }
        return chain.filter(exchange);
    }
}

// Each downstream service validates
@Component
public class JwtAuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String token = req.getHeader("Authorization");
        if (token != null && jwtService.isValid(token)) {
            Authentication auth = jwtService.getAuthentication(token);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res);
    }
}

mTLS (Mutual TLS)

Both client and server present certificates. Used in service mesh (Istio) — each service has a certificate, and only services with valid certs can communicate. mTLS provides encryption + mutual authentication without token overhead.

Service Mesh Security

Istio automatically issues SPIFFE/SPIRE identities to each pod. mTLS is enforced transparently without application code changes. PeerAuthentication and AuthorizationPolicy define which services can talk to which.

Circuit Breaker Pattern

Prevents cascading failures by stopping calls to a failing service and providing fast-fail behavior.

stateDiagram-v2 [*] --> Closed Closed --> Open : failure threshold exceeded\n(e.g., 50% errors in 10s) Open --> HalfOpen : timeout elapsed\n(e.g., wait 30s) HalfOpen --> Closed : probe request succeeds HalfOpen --> Open : probe request fails Closed --> Closed : requests succeed normally Open --> Open : all requests fail-fast\n(no call to service)

Resilience4j Circuit Breaker (Java)

@Configuration
public class Resilience4jConfig {

    @Bean
    public CircuitBreakerConfig circuitBreakerConfig() {
        return CircuitBreakerConfig.custom()
            .failureRateThreshold(50)              // Open when 50% of calls fail
            .waitDurationInOpenState(Duration.ofSeconds(30)) // Wait 30s before half-open
            .slidingWindowSize(10)                 // Track last 10 calls
            .permittedNumberOfCallsInHalfOpenState(3) // 3 probes in half-open
            .slowCallRateThreshold(70)             // Also open if 70% of calls are slow
            .slowCallDurationThreshold(Duration.ofSeconds(2)) // "slow" = >2s
            .build();
    }
}

@Service
public class OrderService {
    private final CircuitBreaker circuitBreaker;
    private final PaymentServiceClient paymentClient;

    public PaymentResult processPayment(Order order) {
        return circuitBreaker.executeSupplier(() ->
            paymentClient.charge(order.getTotal(), order.getCustomerId())
        );
    }

    // Fallback when circuit is OPEN
    @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
    public PaymentResult chargeWithFallback(Order order) {
        return paymentClient.charge(order.getTotal(), order.getCustomerId());
    }

    private PaymentResult paymentFallback(Order order, Exception ex) {
        log.warn("Payment service unavailable, queuing for retry: {}", ex.getMessage());
        retryQueue.enqueue(order);
        return PaymentResult.queued(order.getId());
    }
}

Bulkhead Pattern & Retry with Exponential Backoff

Bulkhead Pattern

Isolate thread pools/connections per downstream service. Failures in one service don't exhaust resources for others.

// Resilience4j Bulkhead — limits concurrent calls to a service
BulkheadConfig bulkheadConfig = BulkheadConfig.custom()
    .maxConcurrentCalls(20)        // Max 20 concurrent calls to payment-service
    .maxWaitDuration(Duration.ofMillis(100)) // Wait max 100ms for a permit
    .build();

// Thread pool isolation (separate executor per service)
ThreadPoolBulkheadConfig tpConfig = ThreadPoolBulkheadConfig.custom()
    .maxThreadPoolSize(10)
    .coreThreadPoolSize(5)
    .queueCapacity(50)
    .build();

Retry with Exponential Backoff + Jitter

RetryConfig retryConfig = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(500))
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(500, 2.0, 0.3, 10_000))
    // Base 500ms, multiplier 2x, jitter 30%, max 10s
    // Attempts: ~500ms, ~1000ms±jitter, ~2000ms±jitter
    .retryExceptions(IOException.class, TimeoutException.class)
    .ignoreExceptions(BusinessValidationException.class)
    .build();
Why Jitter? Without jitter, all retrying clients retry simultaneously ("thundering herd"), overwhelming the recovering service. Jitter spreads retries over time.

Timeout & Sidecar / Ambassador Pattern

Timeout

Every inter-service call must have a timeout. Without timeouts, slow dependencies cause thread pool exhaustion.

// Resilience4j TimeLimiter
TimeLimiterConfig config = TimeLimiterConfig.custom()
    .timeoutDuration(Duration.ofSeconds(2)) // Fail after 2 seconds
    .cancelRunningFuture(true)
    .build();

// WebClient (reactive) timeout
WebClient.builder()
    .baseUrl("http://payment-service")
    .build()
    .post()
    .uri("/charge")
    .bodyValue(request)
    .retrieve()
    .bodyToMono(PaymentResponse.class)
    .timeout(Duration.ofSeconds(2))  // Overall timeout
    .onErrorReturn(TimeoutException.class, PaymentResponse.timeout())
    .block();

A specialized sidecar that acts as a proxy for outbound communication — connection pooling, retry, logging for calls made BY the service.

SAGA Pattern

A SAGA is a sequence of local transactions where each transaction publishes events/messages that trigger the next transaction. If one fails, compensating transactions undo previous steps.

Outbox Pattern & Idempotency

Outbox Pattern

Atomically write to the DB AND publish an event — without distributed transactions — by writing the event to an "outbox" table in the same local transaction, then having a separate process publish it.

@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    // 1. Save order to orders table
    Order order = orderRepository.save(new Order(cmd));

    // 2. Save event to outbox table — SAME local transaction!
    // No risk of "order saved but event not published"
    OutboxEvent event = new OutboxEvent(
        UUID.randomUUID(),
        "ORDER_PLACED",
        objectMapper.writeValueAsString(new OrderPlacedEvent(order)),
        Instant.now(),
        false // not yet published
    );
    outboxRepository.save(event);

    return order;
    // Both saved atomically — or both rolled back
}

// Separate "outbox relay" process polls and publishes
@Scheduled(fixedDelay = 1000) // every 1 second
@Transactional
public void publishPendingEvents() {
    List<OutboxEvent> pending = outboxRepository.findByPublishedFalse();
    for (OutboxEvent event : pending) {
        kafkaTemplate.send(event.getTopic(), event.getPayload());
        event.setPublished(true);
        outboxRepository.save(event);
    }
    // Debezium CDC is a better alternative — reads DB transaction log
}

Idempotency

An operation is idempotent if calling it multiple times produces the same result as calling it once. Critical for retry-safe APIs.

// Idempotency Key pattern — client sends unique key per logical operation
@PostMapping("/payments")
public ResponseEntity<PaymentResponse> processPayment(
        @RequestBody PaymentRequest request,
        @RequestHeader("Idempotency-Key") String idempotencyKey) {

    // Check if we've already processed this exact operation
    Optional<PaymentResponse> cached = idempotencyStore.get(idempotencyKey);
    if (cached.isPresent()) {
        log.info("Returning cached response for idempotency key: {}", idempotencyKey);
        return ResponseEntity.ok(cached.get()); // Same response, no side effects
    }

    // Lock to prevent concurrent duplicate processing
    try (IdempotencyLock lock = idempotencyStore.lock(idempotencyKey)) {
        // Double-check after lock
        cached = idempotencyStore.get(idempotencyKey);
        if (cached.isPresent()) return ResponseEntity.ok(cached.get());

        PaymentResponse response = paymentService.processPayment(request);
        idempotencyStore.store(idempotencyKey, response, Duration.ofHours(24));
        return ResponseEntity.ok(response);
    }
}

Event Sourcing & CQRS in Microservices

Event Sourcing

Instead of storing current state, store a sequence of events. Current state is derived by replaying events. The event log is the source of truth.

CQRS (Command Query Responsibility Segregation)

Separate the read model (queries, optimized for reads) from the write model (commands, optimized for consistency).

graph LR CLIENT[Client] --> CMD[Command Handler] CLIENT --> QUERY[Query Handler] CMD --> ES[Event Store\nAppend-only] ES --> PROJ[Event Projector] PROJ --> READ_DB[Read Model DB\nDenormalized views] QUERY --> READ_DB ES --> KAFKA[Kafka: publish events\nto other services] 
// Event Sourcing with Axon Framework
@Aggregate
public class BankAccount {
    @AggregateIdentifier
    private String accountId;
    private BigDecimal balance;

    // Command handler — validates, then applies event
    @CommandHandler
    public void handle(WithdrawMoneyCommand cmd) {
        if (balance.compareTo(cmd.getAmount()) < 0) {
            throw new InsufficientFundsException();
        }
        apply(new MoneyWithdrawnEvent(accountId, cmd.getAmount()));
    }

    // Event handler — only mutates state, no side effects
    @EventSourcingHandler
    public void on(MoneyWithdrawnEvent event) {
        this.balance = balance.subtract(event.getAmount());
    }
    // State is rebuilt by replaying all events from the event store
}

// Read model projection
@Component
public class AccountProjection {
    @EventHandler
    public void on(MoneyWithdrawnEvent event) {
        AccountView view = repo.findById(event.getAccountId());
        view.setBalance(view.getBalance().subtract(event.getAmount()));
        repo.save(view); // denormalized read model updated
    }
}

Database per Service & API Composition

Database per Service

Each service owns its data exclusively. Other services access it only via the service's API, never directly connecting to the DB.

  • Why: Independent schema evolution, technology choice, deployment, failure isolation
  • Cross-service queries: Handled via API composition, CQRS read models (materialized views), or event-driven data replication
  • Shared Database anti-pattern: Services sharing DB leads to tight coupling, schema changes breaking multiple services, deployment coupling

API Composition Pattern

// Aggregate data from multiple services in a composite/BFF service
@Service
public class OrderDetailsComposer {

    public OrderDetailsDTO getOrderDetails(String orderId) {
        // Execute calls in parallel for performance
        CompletableFuture<Order> orderFuture = CompletableFuture
            .supplyAsync(() -> orderService.getOrder(orderId));

        CompletableFuture<Customer> customerFuture = orderFuture
            .thenCompose(order -> CompletableFuture
                .supplyAsync(() -> customerService.getCustomer(order.getCustomerId())));

        CompletableFuture<List<Product>> productsFuture = orderFuture
            .thenCompose(order -> CompletableFuture
                .supplyAsync(() -> productService.getProducts(order.getProductIds())));

        CompletableFuture.allOf(orderFuture, customerFuture, productsFuture).join();

        return OrderDetailsDTO.from(
            orderFuture.join(),
            customerFuture.join(),
            productsFuture.join()
        );
    }
}

Strangler Fig Pattern — Monolith Migration

Gradually migrate a monolith to microservices by extracting capabilities piece by piece, using a proxy to route traffic.

graph LR CLIENT[Client] --> PROXY[Reverse Proxy\nNginx/API Gateway] PROXY -->|/users| US[NEW: User Microservice] PROXY -->|/orders| OS[NEW: Order Microservice] PROXY -->|/legacy/*| MONO[Remaining Monolith\nShrinking over time] style US fill:#1a4731 style OS fill:#1a4731 style MONO fill:#3d1f00
  1. Add a proxy/facade in front of the monolith
  2. Extract one service (e.g., User Service) with its own DB
  3. Route /users/* traffic to the new service; rest goes to monolith
  4. Delete the user code from the monolith
  5. Repeat for next capability until monolith is gone

Testing Microservices

Contract Testing with Pact

Consumer-driven contract testing: the consumer defines what it expects from the provider API. The provider verifies it can satisfy all consumer contracts.

// Consumer side: defines the contract
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "UserService")
class OrderServiceConsumerTest {

    @Pact(consumer = "OrderService")
    public RequestResponsePact getUserPact(PactDslWithProvider builder) {
        return builder
            .given("user with id 123 exists")
            .uponReceiving("GET user by id")
            .path("/users/123")
            .method("GET")
            .willRespondWith()
            .status(200)
            .body(new PactDslJsonBody()
                .stringValue("id", "123")
                .stringValue("name", "Alice")
                .stringValue("email", "alice@example.com"))
            .toPact();
    }

    @Test
    @PactTestFor(pactMethod = "getUserPact")
    void testGetUser(MockServer mockServer) {
        UserClient client = new UserClient(mockServer.getUrl());
        User user = client.getUser("123");
        assertEquals("Alice", user.getName());
    }
}

// Provider side: verifies the contract is satisfied
@Provider("UserService")
@PactBroker(host = "pact-broker.example.com")
class UserServiceProviderTest {
    @TestTarget
    public final Target target = new HttpTarget(8080);

    @State("user with id 123 exists")
    public void userExists() {
        // seed test data
        userRepository.save(new User("123", "Alice", "alice@example.com"));
    }
}

Interview Questions & Answers

Q1. What is the main difference between a monolith and microservices? Easy

A monolith is a single deployable unit where all components share the same process, memory, and database. All features are deployed together.

Microservices decompose the application into small, independently deployable services, each responsible for a business capability, with its own data store, running in its own process.

Key differences:

  • Deployment: All-or-nothing vs independent per service
  • Scaling: Scale the whole app vs scale individual hot services
  • Technology: Single stack vs polyglot
  • Failures: Whole app down vs isolated failures
  • Complexity: Simple initially vs distributed systems complexity always

Don't always choose microservices: For a small team or new product, start with a modular monolith and migrate when scale or team size requires it.

Q2. How do you handle data consistency across microservices? Intermediate

You accept eventual consistency in most cases. True ACID across services requires distributed transactions (2PC) which are impractical at scale.

Patterns:

  • SAGA Pattern: Chain of local transactions with compensating transactions on failure
  • Outbox Pattern: Atomically write state + event in same DB transaction; relay publishes event
  • Event Sourcing: Append-only event log is the truth; read models are derived (eventually consistent)
  • CQRS: Separate write model (consistent) from read model (may be slightly stale)

Embrace eventual consistency: Define acceptable consistency windows (e.g., "inventory shown to user can be up to 1 minute stale"). Use optimistic locking to handle conflicts.

Q3. Explain the SAGA pattern and when to use orchestration vs choreography. Intermediate

A SAGA is a distributed transaction implemented as a sequence of local transactions, each publishing an event or message to trigger the next step. Failed steps trigger compensating transactions.

Use Orchestration when:

  • Business flows are complex with many steps
  • You need clear visibility of saga progress
  • Many error scenarios and compensations
  • Compliance/audit requirements (all decisions in one place)

Use Choreography when:

  • Simple flows with few steps
  • Services should be highly autonomous
  • You want to avoid a central coordinator SPOF
  • Event-driven architecture is already in place

Real example: e-commerce order flow (charge payment → reserve inventory → create shipment) maps well to SAGA with compensations (refund payment, release inventory).

Q4. What is the Outbox Pattern and why is it needed? Intermediate

The core problem: saving to a DB AND publishing an event are two separate operations. Either can fail independently:

  • DB saved but Kafka publish failed → lost event
  • Kafka published but DB transaction rolled back → phantom event

Outbox solution: Write both the state change and the event to the SAME local DB transaction. A separate "relay" process (polling or CDC via Debezium) reads unpublished events and publishes them to Kafka.

Debezium (preferred): Reads the DB transaction log (CDC — Change Data Capture). No polling overhead. Guarantees at-least-once delivery. Used in production at scale.

Guarantee: "At-least-once" delivery (event may be published multiple times if relay crashes after publish but before marking as sent). Consumers must be idempotent.

Q5. How does a circuit breaker work? What happens in each state? Intermediate

Circuit breaker prevents cascading failures by monitoring call success rates:

  • CLOSED: Normal operation. All calls pass through. Failure rate tracked via sliding window. If rate exceeds threshold (e.g., 50%), transition to OPEN.
  • OPEN: All calls fail immediately without touching the downstream service (fast-fail). After a configured wait period (e.g., 30s), transitions to HALF-OPEN.
  • HALF-OPEN: A limited number of probe requests are let through. If they succeed, transition to CLOSED. If they fail, go back to OPEN.

Why fast-fail matters: If Order Service calls Payment Service and Payment is slow, threads pile up waiting. Circuit breaker in OPEN state returns immediately, freeing threads for other work.

Fallback strategies: Return cached data, return default value, queue for later processing, return user-friendly error.

Q6. What is service discovery and when would you use client-side vs server-side? Intermediate

Service discovery solves the problem of finding service instances in a dynamic environment where IPs change (containers scale up/down).

Client-side (Eureka/Ribbon): Client queries the registry and load-balances itself. Pros: no extra hop, client controls LB algorithm. Cons: language-specific library needed (Ribbon is JVM-only).

Server-side (AWS ALB, K8s Service): Client sends to a single endpoint; infrastructure handles discovery and LB. Pros: language-agnostic, simple client. Cons: extra infrastructure hop.

Kubernetes default: DNS-based service discovery. http://payment-service resolves to the ClusterIP, which routes to healthy pods. Kube-proxy handles the LB. This is the most common pattern in modern deployments.

Q7. Explain the Strangler Fig pattern for migrating a monolith. Intermediate

Named after the strangler fig tree that wraps around a host tree and eventually replaces it.

Steps:

  1. Put a reverse proxy/API gateway in front of the monolith
  2. Identify the best first service to extract (high value, clear boundaries, low coupling)
  3. Build the new service with its own DB, deploy it
  4. Route the relevant traffic to the new service via the proxy
  5. Migrate data if needed (dual-write phase + data migration)
  6. Remove the functionality from the monolith
  7. Repeat until monolith is gone

Key success factors: Never cut over all-at-once. Start with a low-risk service (e.g., notification service). The monolith and new service may need to share data temporarily — use the Anti-Corruption Layer pattern to translate between the two models.

Q8. What is contract testing and how does Pact work? Advanced

Contract testing verifies that a consumer's expectations of a provider's API are met, without requiring both services to be running simultaneously.

Pact workflow:

  1. Consumer writes tests defining what it expects from the provider (interactions)
  2. Pact generates a "pact file" (JSON contract) from these tests
  3. Consumer publishes the pact to Pact Broker
  4. Provider runs verification: starts its service, replays each interaction from the pact, verifies responses match expectations
  5. Both teams can release independently — as long as provider tests pass

vs Integration tests: Integration tests require both services running simultaneously (slow, flaky, environment-dependent). Pact tests run per-service and can be part of CI.

Can I deploy? Pact Broker provides a can-i-deploy CLI command that checks if a service version can safely deploy given all its consumers' pacts.

Q9. How does the Bulkhead pattern prevent cascading failures? Advanced

Named after ship bulkheads that prevent flooding from spreading. The pattern isolates resources (thread pools, connections) per downstream service.

Without Bulkhead: Order Service has 100 threads. Payment Service becomes slow. All 100 threads wait for Payment. Now Inventory calls (using the same pool) also hang. Order Service is dead even though Inventory is fine.

With Bulkhead: Payment Service pool: 20 threads. Inventory Service pool: 20 threads. Others: 60 threads. Payment slowness exhausts only its 20 threads — Inventory calls continue normally.

Implementation: Resilience4j Bulkhead (semaphore-based, limits concurrency) or ThreadPoolBulkhead (dedicated thread pool). Also applies to connection pool sizes per downstream DB/service.

Q10. What is the Database per Service pattern? What are the challenges? Intermediate

Each microservice has exclusive ownership of its data — other services cannot directly query or modify it. Access is only through the service's API.

Benefits: Independent schema evolution, technology choice (SQL vs NoSQL per need), independent scaling, failure isolation.

Challenges:

  • Cross-service queries: Can't JOIN across service DBs. Use API Composition (orchestrate multiple API calls) or CQRS (maintain a read-only materialized view)
  • Distributed transactions: Use SAGA pattern
  • Data duplication: Some data replicated across services for local querying (eventual consistency)
  • Reporting: Dedicated reporting service aggregates data from all services (event-driven, separate DB)
Q11. How does Event Sourcing differ from a traditional DB? What are the trade-offs? Advanced

Traditional DB: Stores current state. UPDATE overwrites previous values. No history.

Event Sourcing: Stores all events (immutable, append-only). Current state is derived by replaying events. Full audit trail built-in.

Pros:

  • Complete audit log — "what happened and when" — regulatory compliance
  • Time travel — replay events to see state at any point in time
  • Event-driven integration — other services consume events directly
  • Debugging — replay production events in staging

Cons:

  • Complexity — replaying events to reconstruct state can be slow for large histories (use snapshots)
  • Eventual consistency — read models built by projections may lag
  • Schema evolution — changing event schemas is hard (versioned events needed)
  • Learning curve — different mental model from CRUD
Q12. What is CQRS and when should you use it? Advanced

CQRS separates write operations (Commands — change state) from read operations (Queries — return data). Separate models, potentially separate data stores.

When to use CQRS:

  • Read and write patterns have very different performance requirements (scale reads independently)
  • Complex domain logic on writes vs simple, denormalized reads
  • Event Sourcing (they complement each other naturally)
  • Multiple read models needed (mobile API, web API, reporting)

When NOT to use CQRS:

  • Simple CRUD apps — massive over-engineering
  • Small teams without expertise in eventually consistent systems
  • When read-after-write consistency is strictly required everywhere

Trade-off: Eventual consistency between write model and read models. A write may not be immediately visible in the read model (usually milliseconds, but noticeable if showing data immediately after an action).

Q13. How do you handle inter-service authentication securely? Advanced

Multiple approaches, often combined:

  • JWT propagation: API Gateway validates external JWT; passes it to downstream services. Services re-validate the JWT locally. Pros: no central session store. Cons: JWTs can't be revoked (short expiry needed).
  • Service-to-service JWTs: Each service has its own JWT (issued by auth service) for internal calls. Separate from user JWTs.
  • mTLS (Mutual TLS): Both services present certificates. In service mesh (Istio/Linkerd), this is automatic. Pros: strong authentication, encrypted traffic. No token overhead.
  • API Keys: Simple but hard to rotate; not suitable for dynamic microservices
  • SPIFFE/SPIRE: Identity framework for services. Issues short-lived SVIDs (SPIFFE Verifiable Identity Documents) as X.509 certs. Foundation for Istio mTLS.

Best practice: Use Istio mTLS for service-to-service authentication + authorization. For calls that need user context, propagate the user's JWT via a header.

Q15. How do you trace a request across multiple microservices? Advanced

Distributed tracing tracks a request as it propagates through multiple services. Each service adds span information to a shared trace context.

Key concepts:

  • Trace ID: Unique ID for the entire request journey
  • Span: A single unit of work (e.g., one service processing), has parent span ID
  • Context propagation: Trace ID passed via HTTP headers (X-B3-TraceId, traceparent in W3C standard)

Tools: Jaeger, Zipkin, AWS X-Ray, Datadog APM. Spring Sleuth/Micrometer auto-instruments Spring services. Istio auto-instruments all pod-to-pod calls.

// Spring Boot with Micrometer Tracing (auto-configured)
@Service
public class OrderService {
    private final Tracer tracer;

    public Order createOrder(OrderRequest req) {
        Span span = tracer.nextSpan().name("createOrder").start();
        try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
            // trace ID automatically propagated to downstream HTTP calls
            return processOrder(req);
        } finally {
            span.end();
        }
    }
}
Q16. What are the challenges with blue/green vs canary deployments? Intermediate

Blue/Green challenges:

  • Double the infrastructure cost during switchover
  • DB schema changes are tricky — new schema must be compatible with both versions simultaneously during cutover
  • All-or-nothing traffic switch — if v2 has issues, ALL users are affected before rollback

Canary challenges:

  • Two versions live simultaneously — must be backward-compatible (API, DB schema, events)
  • Requires metrics to determine if canary is healthy (error rate, latency, business metrics)
  • Sticky sessions — if a user hits v1 then v2, their session must be compatible
  • Data migrations — canary pods may write data in a new format that v1 pods can't read

DB migration strategy for canary: Expand/contract pattern — first migration adds new columns (backward compatible), canary uses new schema, rollout completes, second migration removes old columns.

Q17. How would you design a notification service in a microservices architecture? Advanced

Design principles:

  • Notification Service consumes events (async) — doesn't get called synchronously
  • Other services don't know about the Notification Service — they just publish domain events
  • Notification Service subscribes to relevant events (OrderPlaced → send order confirmation)

Architecture:

  1. Services publish domain events to Kafka topics (order.placed, payment.failed, etc.)
  2. Notification Service has a consumer group subscribed to all relevant topics
  3. Maps events to notification templates
  4. Dispatches via Email (SendGrid), SMS (Twilio), Push (FCM), or in-app
  5. Own DB for notification history, preferences, delivery status

Idempotency: Must be idempotent — use event ID as idempotency key to avoid duplicate notifications on re-delivery.

User preferences: Respect do-not-disturb times, channel preferences (email vs SMS), frequency limits.

Use REST when: You need an immediate response (get user profile before rendering), simple CRUD, the caller must react to the result right away.

Use Events when: Notifying multiple consumers, fire-and-forget operations, long-running processes (order fulfillment), decoupling services that don't need to know about each other, audit/history (event log).

Hybrid: Most real systems use both. REST for queries and synchronous commands. Events for domain changes that trigger workflows in other services.

Q19. How do you handle schema evolution in event-driven microservices? Very Advanced

Event schemas are a critical contract between producers and consumers. Breaking changes are dangerous because consumers may have old code.

Strategies:

  • Backward-compatible changes only: Add optional fields (never remove/rename). Consumers ignore unknown fields.
  • Event versioning: Include version in event ({"version": 2, ...} or topic naming order.placed.v2). Consumers handle multiple versions during migration.
  • Consumer-driven evolution: Before removing a field, check all consumers via Pact/schema registry
  • Schema Registry (Confluent): Centralizes Avro/Protobuf schemas. Enforces compatibility rules (BACKWARD, FORWARD, FULL). Producers and consumers must register schemas.

Avro + Schema Registry example:

{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "com.example.events",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "amount", "type": "double"},
    {"name": "discountCode", "type": ["null", "string"], "default": null}
  ]
}

Adding discountCode as nullable with a default is backward compatible — old consumers that don't know about it will use the default.

Q20. How do you prevent a distributed system from suffering from "death by a thousand timeouts"? Very Advanced

Timeout cascades: A → B → C → D. D is slow (30s timeout). C waits 30s then times out. B already timed out waiting for C (set to 25s). A already gave up (set to 20s). User gets an error after 20s but D was processing for 30s wasted.

Solutions:

  • Deadline propagation: Pass remaining deadline in requests. Each service knows the overall deadline and can fail fast if not enough time remains. gRPC has built-in deadline propagation.
  • Context cancellation: Pass Context/CancellationToken through call chains. When API Gateway cancels (client gave up), downstream services detect cancellation and stop work.
  • Circuit breaker: Fail fast when a service is known to be slow — don't even attempt the call.
  • Budget timeout: API Gateway sets overall budget (e.g., 5s). Each service checks remaining budget before making downstream calls.
// gRPC deadline propagation
Channel channel = ManagedChannelBuilder.forAddress("payment-service", 443).build();
PaymentServiceGrpc.PaymentServiceBlockingStub stub = PaymentServiceGrpc.newBlockingStub(channel)
    .withDeadlineAfter(2, TimeUnit.SECONDS); // Deadline propagated to server

// Server checks if deadline exceeded before expensive operations
if (Context.current().getDeadline() != null &&
    Context.current().getDeadline().isExpired()) {
    throw Status.DEADLINE_EXCEEDED.asRuntimeException();
}
Q21. What is the API Composition pattern and when does it fail? Advanced

API Composition assembles data from multiple services to fulfill a client request. A BFF or aggregator service calls multiple services in parallel and combines results.

When it fails:

  • Performance: If you must call 10 services to render one page, the slowest call determines latency. Mitigate: caching, parallelism, GraphQL data loaders.
  • Consistency: Data from different services may be at different points in time (Customer from t1, Orders from t2). Unavoidable in microservices.
  • Large datasets: Complex joins/filters across datasets from different services are inefficient — you'd need to fetch all data and filter in memory. Prefer CQRS read model for complex queries.
  • Transactions: You can read data from many services via composition but can't atomically write across them.

Better alternative for complex queries: CQRS read model — a dedicated service that subscribes to events from all relevant services and maintains a denormalized, queryable view. Complex queries run on this local DB with zero API calls.

Q22. How do you design for observability in microservices? Very Advanced

Observability = the ability to understand the internal state of a system from external outputs. Three pillars:

  • Metrics: Quantitative measurements over time (request rate, error rate, latency percentiles, resource utilization). Tools: Prometheus + Grafana. Key metrics: RED (Rate, Errors, Duration) per service.
  • Logs: Timestamped records of events. Must be structured (JSON), include trace ID, correlation ID, service name. Aggregated via ELK (Elasticsearch/Logstash/Kibana) or Datadog.
  • Traces: End-to-end request journey across services. Tools: Jaeger, Zipkin, AWS X-Ray. Identifies latency bottlenecks and error sources in distributed flows.

Practices:

  • Every log line includes traceId, spanId, serviceName, version
  • Standardize health check endpoints (/health/live, /health/ready)
  • Expose business metrics (orders/sec, payment success rate) not just technical ones
  • Alert on SLOs (Service Level Objectives) not just raw error rates
  • Istio/service mesh auto-instruments service mesh metrics without code changes
