React — Comprehensive Learning Reference

1. Overview

React is a declarative, component-based JavaScript library for building user interfaces, created by Meta (Facebook). It focuses solely on the View layer and can integrate with any architecture or stack.

Core Concepts

  • Declarative: Describe what the UI should look like; React handles how to update the DOM efficiently
  • Component-based: Build encapsulated components that manage their own state, then compose them to build complex UIs
  • Learn once, write anywhere: Render to DOM, native mobile (React Native), server (SSR), canvas, VR (React 360)

Virtual DOM

React maintains a lightweight in-memory representation of the real DOM called the Virtual DOM (VDOM). When state/props change:

  1. React creates a new VDOM tree by calling your component functions
  2. Diffing: Compares new tree vs previous tree using an O(n) heuristic algorithm
  3. Reconciliation: Computes the minimal set of mutations needed
  4. Commit: Applies only the necessary changes to the actual DOM in a batch

Reconciliation Heuristics

  • Elements of different types produce entirely different trees (full subtree replace)
  • Same type DOM elements: React updates changed attributes only, recurses on children
  • Same type component elements: React keeps the instance alive, updates props, re-renders
  • key prop signals stable identity across renders — critical for lists

2. Version History

React 16 — Fiber Architecture (Sept 2017)

Complete rewrite of React's core using the Fiber reconciler, enabling incremental rendering.

  • Fiber: Unit of work that can be paused, prioritized, reused, or aborted. Enables future concurrent features
  • Error Boundaries: componentDidCatch + getDerivedStateFromError — catch JS errors in component trees
  • Portals: ReactDOM.createPortal(child, container) — render outside parent DOM hierarchy (modals, tooltips)
  • Fragments: <React.Fragment> / <></> — return multiple sibling elements without extra DOM node
  • Return arrays and strings from render methods
  • Streaming SSR: renderToNodeStream() for faster TTFB
  • Custom DOM attributes: unknown attributes pass through to DOM instead of being ignored

React 16.8 — Hooks (Feb 2019)

The most significant addition since React's creation. Hooks allow function components to use state and lifecycle features without classes.

  • Basic: useState, useEffect, useContext, useReducer
  • Performance: useMemo, useCallback
  • DOM/Ref: useRef, useLayoutEffect, useImperativeHandle
  • Dev: useDebugValue
  • Fully backwards-compatible — class components continue to work

React 17 — Platform Release (Oct 2020)

Focused on upgrading React itself rather than adding developer features.

  • Gradual upgrade support: Multiple React versions on the same page
  • New JSX Transform: No longer need import React from 'react' — compiler handles the import
  • Event delegation moved to root: Events attach to the React root container, not document
  • Removed event pooling: SyntheticEvent objects are no longer reused/nullified
  • useEffect cleanup timing: Cleanup functions run asynchronously (matching mount behavior)

React 18 — Concurrent React (Mar 2022)

The most transformative release since Hooks. Introduces Concurrent Mode — React can prepare multiple versions of the UI simultaneously and interrupt/prioritize work.

  • New Root API: ReactDOM.createRoot() replaces ReactDOM.render() to opt into concurrent features
  • Automatic Batching: State updates in timeouts, promises, native events now batched (previously only React synthetic events)
  • startTransition: Mark updates as non-urgent so React can deprioritize them
  • useTransition: Hook providing isPending flag + startTransition
  • useDeferredValue: Defer rerendering of a value during high-priority updates
  • useId: Generate stable IDs consistent between SSR and hydration
  • useSyncExternalStore: Subscribe to external stores safely (prevents tearing)
  • useInsertionEffect: For CSS-in-JS libraries to inject styles before DOM mutations
  • Suspense SSR Streaming: Stream HTML with renderToPipeableStream, selective hydration
  • Strict Mode: Double-invokes effects to surface concurrency bugs

React 18.2 / 18.3

  • Improved act() for async tests in concurrent mode
  • Deprecation warnings for legacy patterns (ReactDOM.render, findDOMNode, string refs)
  • React Compiler (React Forget) announced — automatically memoizes components
  • React 19 prep: server components integration improvements

State Immutability

// WRONG — direct mutation
const [user, setUser] = useState({ name: 'Alice', age: 25 });
user.age = 26;      // mutating object
setUser(user);      // same reference, React may skip re-render

// CORRECT — always create new references
setUser(prev => ({ ...prev, age: 26 }));

// Arrays — use non-mutating methods
const [list, setList] = useState([1, 2, 3]);
setList(prev => [...prev, 4]);                          // add
setList(prev => prev.filter(x => x !== 2));            // remove
setList(prev => prev.map(x => x === 2 ? 99 : x));      // update
setList(prev => [...prev].sort());                       // sort (copy first!)

// Deeply nested — use immer or manual spread
import produce from 'immer';
setConfig(produce(draft => { draft.server.port = 8080; }));

Controlled vs Uncontrolled Components

// Controlled: React state is the single source of truth
function ControlledForm() {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');

  const handleSubmit = (e) => {
    e.preventDefault();
    console.log({ email, password });
  };

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" value={email} onChange={e => setEmail(e.target.value)} />
      <input type="password" value={password} onChange={e => setPassword(e.target.value)} />
      <button>Submit</button>
    </form>
  );
}

// Uncontrolled: DOM is the source of truth, read via ref
function UncontrolledForm() {
  const emailRef = useRef(null);
  const passwordRef = useRef(null);

  const handleSubmit = (e) => {
    e.preventDefault();
    console.log({ email: emailRef.current.value, password: passwordRef.current.value });
  };

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" ref={emailRef} defaultValue="" />
      <input type="password" ref={passwordRef} />
      <button>Submit</button>
    </form>
  );
}
// Prefer controlled for: validation, conditional fields, real-time feedback
// Prefer uncontrolled for: simple forms, file inputs, integrating with non-React libs

useReducer

// Define actions as constants
const TODO_ACTIONS = {
  ADD: 'ADD',
  TOGGLE: 'TOGGLE',
  DELETE: 'DELETE',
  EDIT: 'EDIT',
};

// Pure reducer function — easy to test in isolation
function todoReducer(state, action) {
  switch (action.type) {
    case TODO_ACTIONS.ADD:
      return {
        ...state,
        todos: [...state.todos, { id: Date.now(), text: action.payload, done: false }]
      };
    case TODO_ACTIONS.TOGGLE:
      return {
        ...state,
        todos: state.todos.map(t =>
          t.id === action.payload ? { ...t, done: !t.done } : t
        )
      };
    case TODO_ACTIONS.DELETE:
      return { ...state, todos: state.todos.filter(t => t.id !== action.payload) };
    case TODO_ACTIONS.EDIT:
      return {
        ...state,
        todos: state.todos.map(t =>
          t.id === action.payload.id ? { ...t, text: action.payload.text } : t
        )
      };
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

function TodoApp() {
  const [state, dispatch] = useReducer(todoReducer, { todos: [] });
  const [input, setInput] = useState('');

  const addTodo = () => {
    if (!input.trim()) return;
    dispatch({ type: TODO_ACTIONS.ADD, payload: input });
    setInput('');
  };

  return (
    <div>
      <input value={input} onChange={e => setInput(e.target.value)} />
      <button onClick={addTodo}>Add</button>
      {state.todos.map(todo => (
        <div key={todo.id}>
          <span style={{ textDecoration: todo.done ? 'line-through' : 'none' }}>
            {todo.text}
          </span>
          <button onClick={() => dispatch({ type: TODO_ACTIONS.TOGGLE, payload: todo.id })}>
            Toggle
          </button>
          <button onClick={() => dispatch({ type: TODO_ACTIONS.DELETE, payload: todo.id })}>
            Delete
          </button>
        </div>
      ))}
    </div>
  );
}

// Memoize expensive calculation
function SearchResults({ data, query, sortKey }) {
  const results = useMemo(() => {
    if (!query) return data;
    const lower = query.toLowerCase();
    return data
      .filter(item => item.name.toLowerCase().includes(lower) ||
                      item.description.toLowerCase().includes(lower))
      .sort((a, b) => {
        if (sortKey === 'name') return a.name.localeCompare(b.name);
        if (sortKey === 'price') return a.price - b.price;
        return 0;
      });
  }, [data, query, sortKey]);  // recompute only when these change

  return <ResultGrid items={results} />;
}

// useCallback(fn, deps) === useMemo(() => fn, deps)
// Returns the same function reference unless deps change

function TaskManager() {
  const [tasks, setTasks] = useState([]);
  const [filter, setFilter] = useState('all');

  // Stable reference — deps never change (setTasks is always stable)
  const addTask = useCallback((text) => {
    setTasks(prev => [...prev, { id: crypto.randomUUID(), text, done: false }]);
  }, []);

  // Depends on nothing mutable — stable
  const toggleTask = useCallback((id) => {
    setTasks(prev => prev.map(t => t.id === id ? { ...t, done: !t.done } : t));
  }, []);

  // Depends on filter — new function when filter changes
  const deleteTask = useCallback((id) => {
    setTasks(prev => prev.filter(t => t.id !== id));
    if (filter === 'done') console.log('Removing done task');
  }, [filter]);

  return (
    <div>
      {/* TaskList is memoized — won't re-render unless callbacks or tasks change */}
      <TaskList tasks={tasks} onAdd={addTask} onToggle={toggleTask} onDelete={deleteTask} />
    </div>
  );
}

useLayoutEffect

// Fires synchronously AFTER DOM mutations but BEFORE browser paint
// Prevents visual flicker when reading layout dimensions

function MeasuredDiv({ children }) {
  const ref = useRef(null);
  const [height, setHeight] = useState(0);

  useLayoutEffect(() => {
    // Safe to read layout here — DOM is updated, browser hasn't painted yet
    setHeight(ref.current.getBoundingClientRect().height);
  });  // runs after every render to track height changes

  return (
    <div>
      <div ref={ref}>{children}</div>
      <p>Height: {height}px</p>
    </div>
  );
}

// Popover positioning — avoid flicker by measuring before paint
function Popover({ anchor, children }) {
  const popoverRef = useRef(null);
  const [style, setStyle] = useState({});

  useLayoutEffect(() => {
    if (!anchor || !popoverRef.current) return;
    const anchorRect = anchor.getBoundingClientRect();
    const popoverRect = popoverRef.current.getBoundingClientRect();
    setStyle({
      position: 'fixed',
      top: anchorRect.bottom + 4,
      left: Math.min(anchorRect.left, window.innerWidth - popoverRect.width - 8),
    });
  }, [anchor]);

  return <div ref={popoverRef} style={style}>{children}</div>;
}

// RULE: Start with useEffect; switch to useLayoutEffect only if you see visual flicker

useImperativeHandle

// Expose a limited, custom API to parent via ref
// Must be used with React.forwardRef

const RichEditor = React.forwardRef(function RichEditor(props, ref) {
  const editorRef = useRef(null);
  const [content, setContent] = useState('');

  useImperativeHandle(ref, () => ({
    // Expose these methods to the parent
    clear() { setContent(''); },
    focus() { editorRef.current?.focus(); },
    getContent() { return content; },
    insertText(text) {
      setContent(prev => prev + text);
    },
  }), [content]);  // recreate if content changes (getContent needs current content)

  return (
    <textarea

// 1. useFetch — fetch with loading/error/abort
function useFetch(url, options) {
  const [state, setState] = useState({ data: null, loading: true, error: null });

  useEffect(() => {
    if (!url) return;
    const controller = new AbortController();
    setState({ data: null, loading: true, error: null });

    fetch(url, { ...options, signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(`${r.status} ${r.statusText}`); return r.json(); })
      .then(data => setState({ data, loading: false, error: null }))
      .catch(err => {
        if (err.name !== 'AbortError') setState({ data: null, loading: false, error: err.message });
      });

    return () => controller.abort();
  }, [url]);

  return state;
}

// 2. useLocalStorage — persistent state
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try { return JSON.parse(localStorage.getItem(key) ?? 'null') ?? initialValue; }
    catch { return initialValue; }
  });

  const setStoredValue = useCallback((newValue) => {
    const resolved = typeof newValue === 'function' ? newValue(value) : newValue;
    setValue(resolved);
    try { localStorage.setItem(key, JSON.stringify(resolved)); }
    catch (e) { console.error('localStorage write failed:', e); }
  }, [key, value]);

  return [value, setStoredValue];
}

// 3. useDebounce — delay value update
function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

// 4. useIntersectionObserver — lazy loading / infinite scroll
function useIntersection(options = {}) {
  const [entry, setEntry] = useState(null);
  const ref = useRef(null);

  useEffect(() => {
    if (!ref.current) return;
    const observer = new IntersectionObserver(([e]) => setEntry(e), options);
    observer.observe(ref.current);
    return () => observer.disconnect();
  // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [options.threshold, options.rootMargin]);

  return [ref, entry?.isIntersecting ?? false];
}

6. React Rendering & Reconciliation

Render Phases

React rendering is split into two distinct phases:

  • Render Phase (can be paused, resumed, aborted in concurrent mode): React calls your component function, builds the new VDOM tree, runs the diffing algorithm. Must be pure — no side effects.
  • Commit Phase (synchronous, cannot be interrupted): React applies the computed DOM changes, runs useLayoutEffect (synchronous), then schedules useEffect (asynchronous) after paint.
flowchart TD A[State or Prop Change] --> B[Render Phase] B --> C{Output changed?} C -->|No - bailout| D[Skip Commit - no DOM change] C -->|Yes| E[Reconciliation / Diffing] E --> F[Commit Phase] F --> G[Apply DOM Mutations] G --> H[Run useLayoutEffect cleanup] H --> I[Run useLayoutEffect setup] I --> J[Browser Paint] J --> K[Run useEffect cleanup] K --> L[Run useEffect setup]

When Do Components Re-Render?

  • Its own state changes (useState / useReducer dispatch)
  • Its parent re-renders (even if props didn't change — unless wrapped in React.memo)
  • Its context value changes
  • Custom hooks it uses return new values

Reconciliation Algorithm

  • Same element type at same position: React updates the existing DOM node's attributes/props
  • Different element type: React destroys old subtree (including state), mounts new subtree from scratch
  • Lists: React compares by key; without keys uses index; key mismatch = destroy + remount
// React.memo — skip re-render if props are shallowly equal
const ExpensiveList = React.memo(function ExpensiveList({ items }) {
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
});

// Custom comparison
const SmartComponent = React.memo(MyComponent, (prevProps, nextProps) => {
  return prevProps.data.id === nextProps.data.id;  // return true to skip render
});

// Batching — React 18 batches ALL state updates
function handleClick() {
  setA(1);  // these 3 updates are batched into one render
  setB(2);
  setC(3);
}

// To opt out of batching (rarely needed)

// Class-based error boundary (only way in React currently)
class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false, error: null };
  }

  // Called during render phase — use to update state
  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  // Called in commit phase — use for logging
  componentDidCatch(error, errorInfo) {
    console.error('Caught error:', error, errorInfo.componentStack);
    logErrorToService(error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback || <div>Something went wrong.</div>;
    }
    return this.props.children;
  }
}

13. Interview Q&A — Easy Easy

Q1. What is the difference between state and props in React?

Props are read-only inputs passed from a parent component to a child. They are immutable from the child's perspective — a component cannot change its own props.

State is mutable data managed inside a component. When state changes, React re-renders the component and its children.

function ParentCounter() {
  const [count, setCount] = useState(0);  // state — mutable, owned by Parent

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      {/* count passed as prop — read-only inside DisplayCount */}
      <DisplayCount count={count} />
    </div>
  );
}

function DisplayCount({ count }) {
  // count is a prop — cannot do count++ here
  return <p>Current count: {count}</p>;
}

Key rules: Props flow down (parent to child). State stays local. To share state between siblings, lift state up to their common parent.

Q2. What is the Virtual DOM and why does React use it?

The Virtual DOM (VDOM) is a lightweight JavaScript object tree that mirrors the real DOM structure. React keeps this in memory to minimize expensive real DOM operations.

Why it matters: Real DOM manipulation is slow (triggers layout, paint, composite). React batches all necessary changes and applies them in one operation by:

  1. Rendering to VDOM (cheap JS operations)
  2. Diffing new VDOM vs previous VDOM (O(n) algorithm)
  3. Computing minimal DOM mutations
  4. Applying only those changes to the real DOM
// React computes the diff and only updates what changed
// Before:
<ul>
  <li>Alice</li>
  <li>Bob</li>
</ul>

// After state change (added Charlie):
<ul>
  <li>Alice</li>
  <li>Bob</li>
  <li>Charlie</li>  {/* only this DOM node is added */}
</ul>
Q3. What are React Hooks and why were they introduced?

Hooks are functions that let function components use React features that previously required class components.

Problems hooks solved:

  • Complex class components: Lifecycle methods mixed unrelated logic (subscriptions in componentDidMount AND componentWillUnmount)
  • Logic reuse: HOCs and render props created "wrapper hell" and made component trees hard to follow
  • Class confusion: this binding was a constant source of bugs
// Class: subscription logic split across lifecycle methods
class Timer extends React.Component {
  componentDidMount() { this.interval = setInterval(this.tick, 1000); }
  componentWillUnmount() { clearInterval(this.interval); }
  tick = () => this.setState(s => ({ count: s.count + 1 }));
  render() { return <div>{this.state.count}</div>; }
}

// Hook: subscription logic co-located
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(c => c + 1), 1000);
    return () => clearInterval(id);  // cleanup right next to setup
  }, []);
  return <div>{count}</div>;
}

Q1. Explain React's reconciliation algorithm. How does React decide what to update?

React's reconciliation uses a heuristic O(n) algorithm with two key assumptions:

  1. Two elements of different types produce different trees
  2. Developers can hint at stable identities with key

Algorithm steps:

  • Comparing root elements: If types differ (e.g., <div> → <span>), React tears down the entire old tree and builds new one from scratch. Component state is destroyed.
  • Same type DOM elements: React keeps the DOM node and only updates changed attributes. Then recurses on children.
  • Same type component elements: React keeps the component instance alive (preserving state), updates its props, and calls render. Then recurses on children.
  • Lists: React compares by position (or key if provided). Keys allow React to match elements across positions — critical for reordering.
// Example: React's decision tree
// Before:
<Counter color="blue" />   // instance A, state = 5

// After (same type): instance A kept, props updated, re-rendered
<Counter color="red" />    // same instance A, state still = 5!

// After (different type): instance A destroyed, new instance B created
<Timer color="red" />      // new instance B, state reset to initial

Why O(n) instead of O(n³): A general tree edit distance algorithm is O(n³). React's two assumptions allow an O(n) heuristic — React only compares at the same level, never across levels.

Q1. How does React Fiber work? What problems did it solve?

Before Fiber (Stack Reconciler): React used a recursive, synchronous algorithm. Once started, it couldn't be paused. On large component trees, this would block the main thread for 100ms+ causing dropped frames and unresponsive UIs.

Fiber is a reimplementation of the reconciler using a linked list of "fiber nodes" instead of the call stack. Each fiber represents a unit of work.

Key capabilities unlocked:

  • Incremental rendering: Break work into chunks, pause between chunks
  • Prioritization: Assign priority to different updates (user input > data fetch > background)
  • Reuse work: Pause and resume where left off
  • Abort work: Discard partially done work if a newer update supersedes it
// Each fiber node has:
// type: component function or DOM tag
// key: for reconciliation
// child, sibling, return: linked list pointers
// pendingProps, memoizedProps: props
// memoizedState: hooks state
// effectTag: what DOM mutation is needed
// lanes: priority bitmask

// React processes fibers using a work loop:
function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield(deadline)) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork) {
    requestIdleCallback(workLoop);  // yield, schedule continuation
  } else {
    commitRoot();  // no more work — commit to DOM
  }
}

Two trees: Fiber maintains a "work-in-progress" tree alongside the current tree. Only when work completes does it swap (double buffering), ensuring the UI never shows a half-finished state.

Q4. How does React Suspense work with data fetching? Explain the "render-as-you-fetch" pattern.

Suspense works through a throwing promises mechanism. When a component is not ready to render, it throws a Promise. React catches it, shows the nearest Suspense fallback, and re-renders when the promise resolves.

// HOW SUSPENSE WORKS INTERNALLY
// 1. Component throws a Promise (the "suspend" signal)
// 2. React catches it at the nearest Suspense boundary
// 3. Renders fallback UI
// 4. Promise resolves → React re-renders the suspended component
// 5. Component returns JSX → replaced in tree

// Simple suspense-compatible resource factory
function createResource(promise) {
  let status = 'pending';
  let result;
  const suspender = promise.then(
    data => { status = 'success'; result = data; },
    error => { status = 'error'; result = error; }
  );
  return {
    read() {
      if (status === 'pending') throw suspender;  // tell React "not ready"
      if (status === 'error') throw result;        // throw to Error Boundary
      return result;                               // return data when ready
    }
  };
}
