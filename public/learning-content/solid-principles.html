SOLID Principles & Design Guidelines

S — Single Responsibility Principle

Definition: A class should have only one reason to change. This means each class should be responsible for a single piece of functionality.

Real-World Analogy: A chef cooks food. A waiter takes orders. You wouldn't want one person to cook, take orders, handle billing, AND wash dishes — each person has a single responsibility so the restaurant runs efficiently.

Java — Bad Example (Violation)

// BAD: One class doing too much — multiple reasons to change
public class UserService {
    public void createUser(String name, String email) {
        // 1. Validate email
        if (!email.contains("@")) throw new IllegalArgumentException("Invalid email");

        // 2. Save to DB — reason to change: DB schema changes
        String sql = "INSERT INTO users (name, email) VALUES (?, ?)";
        // ... jdbc code ...

        // 3. Send welcome email — reason to change: email template changes
        String body = "Welcome " + name + "! Thanks for registering.";
        // ... smtp code ...

        // 4. Generate PDF report — reason to change: report format changes
        // ... pdf generation code ...

        // 4 reasons to change = 4 responsibilities = SRP violation!
    }
}

Java — Good Example (Fixed)

// GOOD: Each class has exactly one responsibility
public class EmailValidator {
    public boolean isValid(String email) {
        return email != null && email.contains("@") && email.contains(".");
    }
}

public class UserRepository {
    private final DataSource dataSource;

    public UserRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void save(User user) {
        String sql = "INSERT INTO users (name, email) VALUES (?, ?)";
        // ... only DB concern here
    }
}

public class EmailService {
    private final MailSender mailSender;

    public EmailService(MailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendWelcomeEmail(User user) {
        String body = "Welcome " + user.getName() + "!";
        mailSender.send(user.getEmail(), "Welcome!", body);
    }
}

public class UserService {
    private final EmailValidator emailValidator;
    private final UserRepository userRepository;
    private final EmailService emailService;

    public UserService(EmailValidator emailValidator,
                       UserRepository userRepository,
                       EmailService emailService) {
        this.emailValidator = emailValidator;
        this.userRepository = userRepository;
        this.emailService = emailService;
    }

    public void createUser(String name, String email) {
        if (!emailValidator.isValid(email)) {
            throw new IllegalArgumentException("Invalid email: " + email);
        }
        User user = new User(name, email);
        userRepository.save(user);
        emailService.sendWelcomeEmail(user);
    }
    // UserService now has only ONE reason to change: user creation workflow
}

When Is It OK to Bend SRP?

  • Tiny utility/script where over-engineering adds no value
  • Prototype code where separation is premature
  • Framework-generated code (Entity classes with some annotations)
  • When two "responsibilities" genuinely change together always (cohesion)

O — Open/Closed Principle

Definition: Software entities (classes, modules, functions) should be open for extension but closed for modification. Add new behavior by adding new code, not by editing existing tested code.

Real-World Analogy: A power strip is closed for modification (you can't rewire it), but open for extension — you plug in new devices without modifying the strip itself.

Connection to Strategy Pattern: OCP is best implemented via the Strategy Pattern — define a family of algorithms, encapsulate each one, and make them interchangeable.

Java — Bad Example (Violation)

// BAD: Must modify this class every time we add a new shape
public class AreaCalculator {
    public double calculate(Object shape) {
        if (shape instanceof Circle) {
            Circle c = (Circle) shape;
            return Math.PI * c.getRadius() * c.getRadius();
        } else if (shape instanceof Rectangle) {
            Rectangle r = (Rectangle) shape;
            return r.getWidth() * r.getHeight();
        }
        // Need to add Triangle? Must MODIFY this class — OCP violation!
        throw new UnsupportedOperationException("Unknown shape");
    }
}

Java — Good Example (Fixed)

// GOOD: Open for extension (new shapes), closed for modification
public interface Shape {
    double area();
}

public class Circle implements Shape {
    private final double radius;
    public Circle(double radius) { this.radius = radius; }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle implements Shape {
    private final double width, height;
    public Rectangle(double width, double height) {
        this.width = width; this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}

// Adding Triangle? Zero changes to existing code!
public class Triangle implements Shape {
    private final double base, height;
    public Triangle(double base, double height) {
        this.base = base; this.height = height;
    }

    @Override
    public double area() { return 0.5 * base * height; }
}

// This class is truly CLOSED for modification
public class AreaCalculator {
    public double calculate(Shape shape) {
        return shape.area();  // polymorphism handles everything
    }

    public double totalArea(List<Shape> shapes) {
        return shapes.stream().mapToDouble(Shape::area).sum();
    }
}

TypeScript — Strategy Pattern (OCP)

// BAD: Conditional logic that grows with every new payment type
class PaymentProcessor_BAD {
  process(amount: number, type: string): void {
    if (type === 'stripe') { /* stripe logic */ }
    else if (type === 'paypal') { /* paypal logic */ }
    else if (type === 'crypto') { /* must modify this every time */ }
  }
}

// GOOD: Strategy Pattern — closed for modification, open for extension
interface PaymentStrategy {
  process(amount: number): Promise<PaymentResult>;
  getName(): string;
}

class StripePayment implements PaymentStrategy {
  async process(amount: number): Promise<PaymentResult> {
    // Stripe-specific logic
    return { success: true, transactionId: 'stripe_txn_123' };
  }
  getName() { return 'stripe'; }
}

class PayPalPayment implements PaymentStrategy {
  async process(amount: number): Promise<PaymentResult> {
    return { success: true, transactionId: 'pp_txn_456' };
  }
  getName() { return 'paypal'; }
}

// Adding CryptoPayment? Zero changes to PaymentProcessor!
class CryptoPayment implements PaymentStrategy {
  async process(amount: number): Promise<PaymentResult> {
    return { success: true, transactionId: 'crypto_txn_789' };
  }
  getName() { return 'crypto'; }
}

class PaymentProcessor {
  private strategies = new Map<string, PaymentStrategy>();

  register(strategy: PaymentStrategy): void {
    this.strategies.set(strategy.getName(), strategy);
  }

  async process(amount: number, type: string): Promise<PaymentResult> {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error(`Unknown payment type: ${type}`);
    return strategy.process(amount);
  }
}

When Is It OK to Bend OCP?

  • Small, stable codebases where extensions rarely happen
  • When over-abstraction would create indirection without benefit
  • During initial development before patterns emerge (avoid premature abstraction)

L — Liskov Substitution Principle

Definition: Objects of a subclass must be substitutable for objects of the superclass without breaking the program. If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering any of the desirable properties of the program.

Key Rules: Subtypes must not strengthen preconditions, must not weaken postconditions, and must not throw new exceptions not declared in the supertype.
Real-World Analogy: If you can drive any sedan, you should be able to drive ANY sedan (Toyota, Honda, BMW) without reading a new manual. A subclass "SportsCar" that requires special controls violates LSP.

Java — Bad Example (Square/Rectangle Violation)

// BAD: Classic LSP violation
public class Rectangle {
    protected int width, height;

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int area() { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        // Square must keep sides equal — CHANGES BEHAVIOR!
        this.width = width;
        this.height = width; // violates Rectangle's contract
    }

    @Override
    public void setHeight(int height) {
        this.width = height;
        this.height = height;
    }
}

// This code breaks when we substitute Square for Rectangle
public class LSPTest {
    static void increaseWidth(Rectangle r) {
        int originalHeight = r.height;
        r.setWidth(r.width + 10); // expects only width to change
        // FAILS for Square! height also changes
        assert r.area() == (r.width) * originalHeight : "LSP violated!";
    }

    public static void main(String[] args) {
        Rectangle rect = new Rectangle();
        rect.setWidth(5); rect.setHeight(10);
        increaseWidth(rect); // works fine

        Square sq = new Square();
        sq.setWidth(5);
        increaseWidth(sq); // AssertionError! LSP broken
    }
}

Java — Good Example (Fixed)

// GOOD: Don't force Square to extend Rectangle
// Both are shapes, but Square is NOT a behavioral subtype of Rectangle
public interface Shape {
    int area();
    int perimeter();
}

public class Rectangle implements Shape {
    private final int width, height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    @Override public int area() { return width * height; }
    @Override public int perimeter() { return 2 * (width + height); }
    public int getWidth() { return width; }
    public int getHeight() { return height; }
}

public class Square implements Shape {
    private final int side;

    public Square(int side) { this.side = side; }

    @Override public int area() { return side * side; }
    @Override public int perimeter() { return 4 * side; }
    public int getSide() { return side; }
}

// Now LSP holds: any Shape can be used where Shape is expected
public class AreaPrinter {
    public void print(Shape shape) {
        System.out.println("Area: " + shape.area()); // works for ALL shapes
    }
}

TypeScript — LSP with Preconditions/Postconditions

// BAD: Subclass strengthens precondition (requires more) — LSP violation
class FileReader {
  read(path: string): string {
    // reads any valid path
    return fs.readFileSync(path, 'utf8');
  }
}

class SecureFileReader extends FileReader {
  read(path: string): string {
    // Strengthening precondition: requires path to start with /secure/
    if (!path.startsWith('/secure/')) {
      throw new Error('Can only read from /secure/ directory!');
    }
    return super.read(path);
  }
}
// Code that uses FileReader now breaks with SecureFileReader — LSP violated!

// GOOD: Subclass can only weaken preconditions, strengthen postconditions
abstract class UserFinder {
  abstract findById(id: number): User | null;
}

class DatabaseUserFinder extends UserFinder {
  findById(id: number): User | null {
    return db.query(`SELECT * FROM users WHERE id = ?`, [id]);
  }
}

class CachingUserFinder extends UserFinder {
  constructor(private inner: UserFinder, private cache: Map<number, User>) {
    super();
  }

  findById(id: number): User | null {
    // Postcondition: still returns User | null (contract maintained)
    // Behavior enriched (caching) without breaking contract
    if (this.cache.has(id)) return this.cache.get(id)!;
    const user = this.inner.findById(id);
    if (user) this.cache.set(id, user);
    return user;
  }
}

// Perfectly substitutable — LSP holds
function displayUser(finder: UserFinder, id: number): void {
  const user = finder.findById(id); // works with ANY UserFinder implementation
  if (user) console.log(user.name);
}

When Is It OK to Bend LSP?

  • When the superclass is intentionally abstract and never used directly
  • When documentation explicitly states certain overrides change behavior (template method pattern with documented extension points)
  • When using override methods only for performance optimization (same observable behavior, different implementation)

I — Interface Segregation Principle

Definition: Clients should not be forced to depend on interfaces they do not use. Prefer many specific interfaces (role interfaces) over one fat/general interface.

Real-World Analogy: A TV remote has specific buttons per function. You wouldn't want a single remote that also controls your car, microwave, and AC — you'd accidentally press buttons meant for other devices.

// BAD: Fat interface forces all implementors to implement all methods
public interface Animal {
    void eat();
    void sleep();
    void fly();    // Dogs can't fly!
    void swim();   // Not all animals swim
    void bark();   // Only dogs bark
    void meow();   // Only cats meow
}

public class Dog implements Animal {

    @Override public void sleep() { System.out.println("Dog sleeping"); }
    @Override public void fly() { throw new UnsupportedOperationException("Dogs can't fly!"); }
    @Override public void swim() { System.out.println("Dog paddling"); }
    @Override public void bark() { System.out.println("Woof!"); }
    @Override public void meow() { throw new UnsupportedOperationException("Dogs don't meow!"); }
}

D — Dependency Inversion Principle

Definition: (1) High-level modules should not depend on low-level modules. Both should depend on abstractions. (2) Abstractions should not depend on details. Details (concrete implementations) should depend on abstractions.

Real-World Analogy: An electrical outlet (abstraction) doesn't care what you plug in. Your lamp (high-level) plugs into the outlet (abstraction), not directly into the power station (low-level). You can switch power providers without rewiring your lamp.

// GOOD: Abstractions (interfaces) decouple high-level from low-level
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(String id);
}

public interface NotificationService {
    void notifyOrderCreated(Order order);
}

// Low-level modules depend on the abstraction
public class MySQLOrderRepository implements OrderRepository {
    @Override public void save(Order order) { /* MySQL code */ }
    @Override public Optional<Order> findById(String id) { return Optional.empty(); }
}

public class MongoOrderRepository implements OrderRepository {
    @Override public void save(Order order) { /* MongoDB code */ }
    @Override public Optional<Order> findById(String id) { return Optional.empty(); }
}

public class EmailNotificationService implements NotificationService {
    @Override public void notifyOrderCreated(Order order) { /* email code */ }
}

public class SMSNotificationService implements NotificationService {
    @Override public void notifyOrderCreated(Order order) { /* SMS code */ }
}

// High-level module depends on abstractions, NOT concretions
public class OrderService {
    private final OrderRepository repository;
    private final NotificationService notificationService;

    // Injection via constructor (Spring, Guice, manual DI)
    public OrderService(OrderRepository repository, NotificationService notificationService) {

        this.notificationService = notificationService;

    public void processOrder(Order order) {
        repository.save(order);
        notificationService.notifyOrderCreated(order);
        // Switch to MongoDB? Just inject MongoOrderRepository — zero code change here!
    }
}

@Configuration
public class AppConfig {

TypeScript — DIP with IoC Container

import 'reflect-metadata';
import { injectable, inject, Container } from 'inversify';

  IUserRepository: Symbol.for('IUserRepository'),
  IEmailService: Symbol.for('IEmailService'),
  UserService: Symbol.for('UserService'),

interface IUserRepository {

}

interface IEmailService {
  send(to: string, subject: string, body: string): Promise<void>;
}

@injectable()
class PostgresUserRepository implements IUserRepository {
  async findById(id: string) { /* postgres logic */ return null; }
  async save(user: User) { /* postgres logic */ }
}

@injectable()
class SendGridEmailService implements IEmailService {
  async send(to: string, subject: string, body: string) { /* sendgrid logic */ }
}

@injectable()
class UserService {
  constructor(
    @inject(TYPES.IUserRepository) private repo: IUserRepository,
    @inject(TYPES.IEmailService) private email: IEmailService

    await this.email.send(user.email, 'Welcome!', `Hi ${user.name}!`);

}

// IoC Container configuration

container.bind<IUserRepository>(TYPES.IUserRepository).to(PostgresUserRepository);
container.bind<IEmailService>(TYPES.IEmailService).to(SendGridEmailService);
container.bind<UserService>(TYPES.UserService).to(UserService);

const userService = container.get<UserService>(TYPES.UserService);

DRY — Don't Repeat Yourself

Definition: Every piece of knowledge must have a single, unambiguous, authoritative representation within a system. Duplication is the root of all maintenance nightmares.

// BAD: Duplicated validation logic
function createUser(name: string, email: string) {
  if (!email.includes('@')) throw new Error('Invalid email');
  if (name.length < 2) throw new Error('Name too short');
  // ... create user
}

function updateUser(id: string, name: string, email: string) {
  if (!email.includes('@')) throw new Error('Invalid email'); // duplicated!
  if (name.length < 2) throw new Error('Name too short');    // duplicated!
  // ... update user
}

// GOOD: Single source of truth
class UserValidator {
  static validate(name: string, email: string): void {
    if (!email.includes('@')) throw new Error('Invalid email');
    if (name.length < 2) throw new Error('Name too short');
  }
}

function createUser(name: string, email: string) {
  UserValidator.validate(name, email);
  // ... create user
}

function updateUser(id: string, name: string, email: string) {
  UserValidator.validate(name, email); // single reference
  // ... update user
}
Warning: DRY applies to knowledge/logic, not just identical-looking code. Two identical code blocks that represent different concepts should NOT be merged (accidental duplication). Premature DRY can lead to wrong abstractions.

KISS — Keep It Simple, Stupid

Definition: Most systems work best if they are kept simple rather than made complicated. Avoid unnecessary complexity. The simplest solution that works is usually the best.

// BAD: Over-engineered
public class NumberEvenChecker {
    private final NumberParityStrategy strategy;
    public NumberEvenChecker(NumberParityStrategy strategy) { this.strategy = strategy; }
    public boolean evaluate(int n) { return strategy.check(n); }
}
interface NumberParityStrategy { boolean check(int n); }
class ModuloEvenStrategy implements NumberParityStrategy {
    public boolean check(int n) { return n % 2 == 0; }
}
// Usage: new NumberEvenChecker(new ModuloEvenStrategy()).evaluate(4)

// GOOD: KISS — just write the function
public boolean isEven(int n) { return n % 2 == 0; }

YAGNI — You Ain't Gonna Need It

Definition: Don't implement functionality until you actually need it. Implement things when you need them, not when you just foresee that you might need them. Every feature you write that's never used is pure waste.

// BAD: Building features "just in case"
class UserService {
  createUser(data: UserDTO) { /* ... */ }
  createUserBulk(users: UserDTO[]) { /* ... needed? not now */ }
  createUserFromCSV(file: File) { /* ... needed? not now */ }
  createUserFromXML(xml: string) { /* ... definitely premature */ }
  createUserWithMultiTenancy(data: UserDTO, tenant: string) { /* ... */ }
}

// GOOD: Only implement what's currently needed
class UserService {
  createUser(data: UserDTO): Promise<User> {
    // Only what the current feature requires
    return this.userRepo.save(new User(data));
  }
  // Add createUserBulk WHEN bulk import feature is actually requested
}

Law of Demeter (Principle of Least Knowledge)

Definition: A module should not know about the internal workings of the objects it manipulates. Don't talk to strangers. A method should only call methods on: itself, its parameters, objects it creates, its direct component objects.

Rule of Thumb: Avoid "train wrecks" — chains like order.getCustomer().getAddress().getCity() 
// BAD: Violates LoD — deep traversal (train wreck)
public class OrderService {
    public String getOrderCity(Order order) {
        // Knows too much about Order's internals
        return order.getCustomer().getAddress().getCity().toUpperCase();
        // OrderService now depends on: Order, Customer, Address, City
    }

    public double calculateShipping(Order order) {
        double weight = order.getItems().get(0).getProduct().getWeight(); // fragile chain
        return weight * 2.5;
    }
}

// GOOD: Respects LoD — Order exposes what you need
public class Order {
    private Customer customer;
    private List<OrderItem> items;

    // Convenience method — Order knows its own internals
    public String getCustomerCity() {
        return customer.getCity(); // Customer knows its own address
    }

    public double getTotalWeight() {
        return items.stream().mapToDouble(OrderItem::getWeight).sum();
    }
}

public class Customer {
    private Address address;
    public String getCity() { return address.getCity(); } // Customer delegates to Address
}

public class OrderService {
    public String getOrderCity(Order order) {
        return order.getCustomerCity(); // Only talks to direct collaborator
    }

    public double calculateShipping(Order order) {
        return order.getTotalWeight() * 2.5; // Only talks to Order
    }
}

Composition over Inheritance

Definition: Prefer composing objects with desired behaviors over inheriting from a base class. Inheritance models an "is-a" relationship; composition models a "has-a" relationship. Composition gives you flexibility at runtime.

classDiagram class Character_INHERITANCE { +swim() +fly() +shoot() note: "Explosion of subclasses: SwimmingFlyingCharacter, SwimmingShootingCharacter, etc." } class Character_COMPOSITION { -locomotion: LocomotionAbility -attack: AttackAbility +move() +attack() } class LocomotionAbility { <> +move() } class Swimming { +move() } class Flying { +move() } class AttackAbility { <> +attack() } class ShootingAttack { +attack() } class MeleeAttack { +attack() } LocomotionAbility <|.. Swimming LocomotionAbility <|.. Flying AttackAbility <|.. ShootingAttack AttackAbility <|.. MeleeAttack Character_COMPOSITION --> LocomotionAbility Character_COMPOSITION --> AttackAbility 
// BAD: Deep inheritance hierarchy — fragile, inflexible
class Animal {
  breathe() {}
}
class SwimmingAnimal extends Animal {
  swim() {}
}
class FlyingSwimmingAnimal extends SwimmingAnimal {
  fly() {}
  // What about an animal that only flies? We need another branch...
  // Explosion of subclasses as behaviors multiply!
}

// GOOD: Composition — behaviors as pluggable components
interface SwimBehavior { swim(): void; }
interface FlyBehavior { fly(): void; }
interface EatBehavior { eat(food: string): void; }

class CanSwim implements SwimBehavior {
  swim() { console.log('Swimming with fins'); }
}
class CanFly implements FlyBehavior {
  fly() { console.log('Flying with wings'); }
}
class CantFly implements FlyBehavior {
  fly() { console.log("I can't fly"); }
}

class Duck {
  private swimBehavior: SwimBehavior = new CanSwim();
  private flyBehavior: FlyBehavior = new CanFly();

  swim() { this.swimBehavior.swim(); }
  fly() { this.flyBehavior.fly(); }

  // Can CHANGE behavior at runtime — impossible with inheritance
  setFlyBehavior(behavior: FlyBehavior) { this.flyBehavior = behavior; }
}

class RubberDuck {
  private swimBehavior: SwimBehavior = new CanSwim();
  private flyBehavior: FlyBehavior = new CantFly();

  swim() { this.swimBehavior.swim(); }
  fly() { this.flyBehavior.fly(); }
}

// React: Composition over Inheritance in UI
// BAD: Extending base components
class EnhancedButton extends Button {
  render() {
    return super.render() + ' (enhanced)';
  }
}

// GOOD: Compose via HOC / wrapping
const withLogging = (WrappedComponent: React.ComponentType<any>) =>
  (props: any) => {
    console.log('Rendering with props:', props);
    return <WrappedComponent {...props} />;
  };

const LoggedButton = withLogging(Button);

Interview Questions & Answers

Q1. What is the Single Responsibility Principle and how do you identify violations? Easy

SRP states a class should have only one reason to change. A class has multiple responsibilities if you can describe its purpose with "AND" — e.g., "UserService creates users AND sends emails AND generates reports."

Signs of SRP violation:

  • Class imports from many different packages (DB, email, PDF, logging)
  • Class has more than ~10 methods
  • Test file needs mocks for 5+ different dependencies
  • Small change to one feature requires changing/retesting unrelated code

Fix: Extract each responsibility into its own class. Use composition (inject the separated classes) to maintain behavior.

Q2. Can you give an example where following SRP might be wrong? Intermediate

Yes. A Money value object that stores an amount AND currency AND formats itself as a string is technically doing two things (storing + formatting), but splitting it might be over-engineering. When two responsibilities are cohesive and always change together, separating them creates unnecessary indirection.

Another case: a Name class with firstName, lastName, and fullName(). The formatting is intrinsically part of the Name concept.

Key insight: SRP is about reasons to change, not counting methods. If two things change together for the same reason, they belong together.

Q3. How does the Open/Closed Principle relate to the Strategy Pattern? Intermediate

The Strategy Pattern is the primary mechanism for achieving OCP. Instead of using if/else or switch on a type field, you define a strategy interface and pass in the desired strategy at runtime.

Without Strategy (OCP violation): Every new payment type requires modifying PaymentProcessor.

With Strategy (OCP satisfied): Each payment type is a new class implementing PaymentStrategy. PaymentProcessor never changes.

Other OCP patterns: Template Method, Decorator, Plugin architecture, Event-Driven systems (emitting events lets extensions react without the source changing).

Q4. Why is the Square/Rectangle problem an LSP violation? Intermediate

In mathematics, a square IS a rectangle (all squares are rectangles). But in OOP with mutable state, Square extends Rectangle violates LSP because:

  1. Rectangle's contract: setWidth(5) only changes width; height is unchanged
  2. Square must keep sides equal, so setWidth(5) also sets height to 5
  3. Code that assumes Rectangle behavior (checks area after setting one dimension) breaks when a Square is substituted

Solution: Use a common interface (Shape with area()), or use immutable value objects — Square.withSide(5) and Rectangle.withDimensions(4, 5) are both Shapes.

Lesson: "Is-a" in mathematics ≠ "is-a" in OOP. Behavioral compatibility matters, not taxonomic classification.

Q5. What are preconditions and postconditions in the context of LSP? Advanced

From Bertrand Meyer's Design by Contract:

  • Precondition: What must be true BEFORE calling a method (caller's obligation)
  • Postcondition: What must be true AFTER the method returns (callee's guarantee)
  • Invariant: What must always be true about the object's state

LSP rules:

  • Subclass must NOT strengthen preconditions (cannot require MORE from callers)
  • Subclass must NOT weaken postconditions (cannot guarantee LESS to callers)

Example violation: FileReader.read(path) accepts any valid path (weak precondition). SecureFileReader.read(path) requires path to start with /secure/ (stronger precondition). Code using FileReader breaks with SecureFileReader.

Q6. What is the difference between Interface Segregation and Single Responsibility? Intermediate

SRP is about a class having only one reason to change — it's about the implementation.

ISP is about clients not being forced to depend on methods they don't use — it's about the interface/contract.

A class can follow SRP but still expose a fat interface that forces clients to depend on methods they don't need. Conversely, a class could violate SRP internally while ISP is preserved from the client's perspective.

Example: A UserRepository with findById, findAll, save, delete follows SRP (all DB concerns), but violates ISP if a read-only service is forced to depend on save and delete — fix: split into UserReader and UserWriter.

Q7. How does Dependency Inversion differ from Dependency Injection? Intermediate

Dependency Inversion Principle (DIP) is an architectural rule: high-level modules shouldn't depend on low-level modules; both should depend on abstractions.

Dependency Injection (DI) is a technique/pattern used to achieve DIP — it provides dependencies to a class from the outside rather than having the class create them.

Analogy: DIP is the design rule ("use a plug socket"). DI is the mechanism ("plug in the device from outside, don't hardwire it").

You can violate DIP even with DI: if you inject a concrete MySQLRepository instead of an IRepository interface, you're using DI but not DIP.

IoC (Inversion of Control) is a broader concept — the framework controls the flow of the application, not your code. Spring, Angular, and NestJS IoC containers implement DI to achieve DIP.

Q8. What is the Law of Demeter and when does it conflict with performance? Advanced

The Law of Demeter (LoD) says a method should only call methods on: itself, parameters, objects it creates, and its direct fields. This prevents "train wrecks" like a.getB().getC().doSomething().

Conflict with performance: Following LoD sometimes means adding wrapper methods that add indirection, or loading extra data you don't need. For example, if you only need a city name but LoD says order.getCustomerCity() (not order.getCustomer().getAddress().getCity()), Order.getCustomerCity() might load the full Customer and Address from DB unnecessarily.

Resolution: Use projections/DTOs — a OrderSummaryDTO that already contains the needed fields without navigation. LoD then holds naturally (no chains, just flat data).

Practical advice: LoD is a guideline, not a law. 2-level chains (user.getAddress().getCity()) are generally OK. 3+ level chains are code smells.

Q9. When should you prefer inheritance over composition? Intermediate

Composition is generally preferred, but inheritance has valid use cases:

  • True "is-a" relationships with stable hierarchies: IllegalArgumentException extends RuntimeException — this is stable and correct
  • Template Method Pattern: Base class defines algorithm skeleton, subclasses fill in steps
  • Framework base classes: AbstractController, JpaRepository — you extend to reuse infrastructure
  • When subclass truly IS the same type and needs to be substitutable everywhere the parent is used

Prefer composition when:

  • Behaviors need to change at runtime
  • You want to combine multiple behaviors
  • The hierarchy would become deep or wide
  • Java/TypeScript can only extend one class (multiple inheritance problem)
Q10. How do you apply SOLID principles in a microservices architecture? Advanced

SOLID applies at both class level AND service level:

  • SRP: Each microservice owns one business capability (User Service, Order Service). Services don't mix concerns.
  • OCP: Services communicate via stable contracts (APIs, events). Adding a new consumer doesn't require changing the producer.
  • LSP: If services implement the same contract (e.g., all payment providers expose the same REST API), they must be substitutable.
  • ISP: Don't expose one giant API. BFF pattern creates focused APIs per client type. Event schemas contain only what subscribers need.
  • DIP: Services depend on abstractions (API contracts, message schemas), not concrete implementations. Service mesh (Istio) or API Gateway provides this indirection layer.
Q11. What is the difference between DRY and the Wrong Abstraction? Advanced

DRY says "don't repeat yourself." But blindly applying DRY can create the wrong abstraction — merging code that looks the same but represents different concepts.

Example: Order validation and User registration both check if an email is unique. They look similar but have different business rules (orders can share emails, users cannot). If you extract one isEmailUnique() function and add flags to handle both cases, you've created a wrong abstraction that's harder to modify than duplication.

Sandi Metz's rule: "Duplication is far cheaper than the wrong abstraction." Wait for the third occurrence of identical logic before abstracting, and ensure they represent the same concept, not just similar code.

Q12. How do you explain YAGNI to a team that keeps adding "future-proof" features? Intermediate

Cost of unused features:

  • Development time spent building something never used
  • Maintenance burden: every line of code has a maintenance cost
  • Testing complexity: must test code paths never exercised
  • Cognitive overhead: new developers must understand features that serve no current purpose
  • Wrong abstractions: guessing future requirements leads to abstractions that don't fit when the future arrives

Studies: In many codebases, 45-64% of features are rarely or never used (based on feature usage analytics from companies like Microsoft and others).

YAGNI doesn't mean: Don't plan at all. Design for change (OCP), write clean code, leave extension points. But don't implement the extension before it's needed.

Q13. Describe a real scenario where you had to choose between following SOLID and pragmatism. Advanced

Scenario: A startup needs a quick feature for a demo next week. Proper DIP would require creating interfaces, DI container configuration, and separate implementations. The team has two engineers and three days.

Pragmatic approach:

  1. Write the feature with direct instantiation (new MySQLRepo())
  2. Isolate in a separate class/module so refactoring is localized
  3. Write a TODO/tech debt ticket
  4. Refactor to proper DIP when the second implementation is actually needed (YAGNI-aligned)

Key insight: SOLID is about managing complexity at scale. For a 2-person team with no foreseeable need for multiple DB implementations, full DIP is over-engineering. Apply principles proportionally to the team size, codebase complexity, and rate of change.

Q14. How does the Decorator Pattern relate to OCP and composition? Advanced

The Decorator Pattern is a perfect example of OCP via composition. You wrap an existing class to add new behavior without modifying the original.

// Interface
public interface Logger {
    void log(String message);
}

// Core implementation (closed for modification)
public class ConsoleLogger implements Logger {
    public void log(String message) {
        System.out.println(message);
    }
}

// Extension via decoration (open for extension)
public class TimestampLogger implements Logger {
    private final Logger inner;
    public TimestampLogger(Logger inner) { this.inner = inner; }

    public void log(String message) {
        inner.log(LocalDateTime.now() + " " + message);
    }
}

public class MetricsLogger implements Logger {
    private final Logger inner;
    private final MetricsRegistry metrics;

    public MetricsLogger(Logger inner, MetricsRegistry metrics) {
        this.inner = inner; this.metrics = metrics;
    }

    public void log(String message) {
        metrics.increment("log.count");
        inner.log(message);
    }
}

// Chain decorators — zero modification to existing classes
Logger logger = new MetricsLogger(new TimestampLogger(new ConsoleLogger()), registry);

This is also composition over inheritance — each decorator wraps instead of extends.

Q15. How does ISP apply to REST API design? Advanced

In REST APIs, ISP manifests as avoiding "fat" endpoints that return more data than any single client needs.

  • Problem: GET /users/{id} returns 50 fields. Mobile clients only need 5 fields — they're forced to transfer/parse unnecessary data.
  • ISP Solution 1 — BFF Pattern: Create separate API gateways for mobile vs web, each returning only what its client needs
  • ISP Solution 2 — GraphQL: Let clients specify exactly which fields they need
  • ISP Solution 3 — Sparse fieldsets: GET /users/{id}?fields=id,name,email (JSON:API spec)
  • ISP Solution 4 — View Models: Different endpoints for different client needs — GET /users/{id}/summary vs GET /users/{id}/profile
Q16. What are the drawbacks of over-applying SOLID? Very Advanced

SOLID principles, over-applied, lead to:

  • Abstraction overload: Interfaces for everything, even classes with only one implementation — unnecessary complexity
  • Indirection maze: Following a call requires jumping through 10 files — cognitive overhead
  • Premature generalization: Strategy Pattern for logic with only one variant — wasted effort
  • Anemic domain model: Extreme SRP + DIP can lead to domain objects with no behavior (just getters/setters), all logic in service classes — loses OOP benefits
  • Verbose DI configuration: Large IoC container setup for simple apps

Counter-principles to balance: KISS, YAGNI. Apply SOLID where complexity exists or is anticipated. For simple, stable code, simpler is better.

Q17. Explain the "fragile base class problem" and how composition solves it. Very Advanced

The fragile base class problem: when a base class changes, subclasses break in unexpected ways, even when the change seems safe. This is a consequence of deep inheritance hierarchies.

Example: HashSet extends AbstractSet. If addAll() in AbstractSet internally calls add() for each element, and a subclass overrides add() to count insertions, then calling addAll(5 items) will count 5 insertions from addAll PLUS 5 more from the internal add() calls = double counting. The subclass is fragile to the superclass's internal implementation.

Composition fix: Instead of extending, wrap (has-a HashSet). Your class calls the wrapped HashSet.add() directly without being affected by internal delegation chains.

This is why Java's Effective Java (Bloch) recommends "Favor composition over inheritance" and "Design and document for inheritance, or else prohibit it."

Q18. How would you refactor a God Class? Advanced

A God Class is a massive class that knows and does everything — the ultimate SRP violation. Refactoring strategy:

  1. Add tests first — characterization tests to capture current behavior
  2. Identify responsibilities — list what the class does; group by concern
  3. Extract value objects — pure data clusters with no external dependencies
  4. Extract service classes — one by one, move methods to focused classes
  5. Introduce interfaces — abstract extracted classes behind interfaces (DIP)
  6. Wire with DI — inject the new collaborators
  7. Delete dead code — remove methods now delegated to extracted classes

Tools: IntelliJ's "Extract Class" refactoring, "Move Method," "Pull Up/Push Down." Eclipse Che, VS Code with language servers support similar refactoring.

Key: Do it incrementally. Each PR is one extracted class, always leaving tests green. Don't try to refactor the whole thing at once.

Q19. Can SOLID apply to functional programming? Very Advanced

SOLID was coined for OOP but most principles translate to FP:

  • SRP → Single-purpose functions: Each function does one thing. Compose functions with pipe/compose
  • OCP → Higher-order functions: Pass functions as parameters instead of if/else. A map function is open for extension (any transform function) and closed for modification
  • LSP → Algebraic types/type classes: Any type implementing a type class contract is substitutable
  • ISP → Small, focused modules: Export only what consumers need. Tree-shaking benefits
  • DIP → Dependency injection as function parameters: Pass dependencies as higher-order function arguments rather than importing concretions directly
// FP-style DIP: dependencies as function parameters
const createUserService = (
  findUser: (id: string) => Promise<User | null>,
  saveUser: (user: User) => Promise<void>,
  sendEmail: (to: string, body: string) => Promise<void>
) => ({
  register: async (data: UserDTO) => {
    const user = new User(data);
    await saveUser(user);
    await sendEmail(user.email, 'Welcome!');
  }
});
Q20. What is the "Tell, Don't Ask" principle and how does it relate to SOLID? Advanced

Tell, Don't Ask: Instead of asking an object for its state and then making decisions based on that state (procedural), tell the object to do something and let it decide how (OOP).

// ASK (procedural, bad)
if (user.getAge() >= 18 && user.isEmailVerified() && !user.isBanned()) {
    // do something
}

// TELL (OOP, good)
if (user.canAccess()) {
    user.grantAccess();
}
// User encapsulates the logic for what "canAccess" means

Relation to SOLID:

  • Supports SRP: Logic for access rules lives in User, not scattered across callers
  • Supports OCP: Adding a new access condition only requires changing User.canAccess()
  • Supports LoD: You're not drilling into user.getAccount().getStatus()
  • Supports rich domain models over anemic ones
Q21. How do you write unit tests that reinforce SOLID principles? Advanced

Good unit tests enforce SOLID:

  • SRP: If your test needs 5+ mocks, the class under test has too many responsibilities. Tests act as a smell detector.
  • OCP: If adding a test for a new case requires modifying the production class, OCP is violated. New behaviors should be testable by adding new test cases (not modifying existing ones)
  • LSP: Write shared test suites that run against all implementations of an interface. If any implementation fails the suite, LSP is violated.
  • ISP: Test classes should only depend on the interface they're testing. If a mock needs to stub methods not used in the test, the interface is too fat.
  • DIP: Tests naturally enforce DIP — you inject mocks of interfaces, not concretions. If you can't easily mock a dependency, it's likely a concrete class dependency (DIP violation).
// LSP contract test
@RunWith(Parameterized.class)
public class OrderRepositoryContractTest {
    private final OrderRepository repo;

    @Parameters
    public static Collection<OrderRepository> repos() {
        return Arrays.asList(new MySQLOrderRepository(), new InMemoryOrderRepository());
    }

    @Test
    public void savedOrderCanBeRetrieved() {
        Order order = new Order("id-1");
        repo.save(order);
        assertEquals(order, repo.findById("id-1").orElseThrow());
    }
}
Q22. What's the relationship between SOLID and Clean Architecture? Very Advanced

Clean Architecture (Robert C. Martin) is essentially SOLID applied at the architectural level:

  • SRP: Each layer (Entity, Use Case, Interface Adapter, Framework) has one responsibility — Entities encode enterprise business rules, Use Cases encode app-specific rules, etc.
  • OCP: Inner layers don't know about outer layers. Adding a new delivery mechanism (REST, GraphQL, CLI) doesn't change use cases.
  • LSP: Frameworks are substitutable — switch from Spring to Quarkus without changing domain logic.
  • ISP: Port interfaces (in hexagonal architecture) are narrow and focused on what the use case needs.
  • DIP: The Dependency Rule — source code dependencies point inward. Use cases define repository interfaces; outer layers implement them. The dependency arrow is inverted.

Hexagonal Architecture (Ports and Adapters) is a concrete implementation of these same ideas: ports are ISP-compliant interfaces, adapters implement them, and the domain (use cases) only depends on ports (DIP).
