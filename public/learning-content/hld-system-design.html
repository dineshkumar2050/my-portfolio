Interview Framework

5-Step System Design Process

  1. Clarify Requirements (5 min) — functional vs non-functional, scale estimates (DAU, QPS, storage), SLAs. Ask before assuming.
  2. Capacity Estimation (5 min) — QPS = DAU × actions / 86400. Storage = writes/day × record_size × retention. Identify read/write ratio.
  3. High-Level Design (10 min) — draw client → API gateway → services → DB → cache → CDN. Keep it broad, identify hotspots.
  4. Deep Dive (15 min) — pick 2-3 critical components the interviewer cares about. Database schema, sharding strategy, cache invalidation, async flows.
  5. Trade-offs & Wrap-up (5 min) — bottlenecks, failure scenarios, what you'd do with more time, monitoring strategy.
Always ask: "What should I prioritize?" — interviewers want to see structured thinking, not a perfect design.

CAP Theorem & Consistency Models

CAP Triangle

Consistency: every read gets the most recent write. Availability: every request gets a response (not necessarily latest). Partition Tolerance: system continues despite network partitions.

In a distributed system, P is mandatory — so the real choice is CP vs AP. During a partition: choose consistency (block/error) or availability (serve stale data).

SystemTypeExample
Zookeeper, HBaseCPCoordination, banking
Cassandra, DynamoDBAPShopping cart, DNS
RDBMS (single node)CANo partition tolerance

Consistency Levels

  • Strong: linearizability — reads always see latest write
  • Sequential: operations appear in some sequential order consistent with program order
  • Eventual: replicas converge given no new updates (DNS, caches)
  • Read-your-writes: user always sees own updates (session consistency)
  • Monotonic reads: never read older data after reading newer

PACELC Extension

If partition (P): choose A or C. Else (E): choose Latency or Consistency. Cassandra: PA/EL (low latency). MySQL: PC/EC (strong consistency).

Core Building Blocks

Load Balancer

Distributes traffic across servers. L4 LB (TCP/UDP level) is faster; L7 LB (HTTP level) enables content-based routing, SSL termination, cookie-based affinity.

Algorithms

  • Round Robin: equal distribution, ignores server load
  • Weighted RR: proportional to server capacity
  • Least Connections: best for variable request duration
  • IP Hash: sticky sessions — same client → same server
  • Consistent Hash: minimal reshuffling on server changes
  • Active-passive HA: failover delay ~30s; active-active: no failover but complex state sync
  • Session stickiness breaks horizontal scaling; prefer stateless services + external session store

CDN (Content Delivery Network)

Caches static/dynamic content at edge PoPs close to users. Reduces origin load and latency. Push CDN: you upload content proactively (good for small, infrequently changed assets). Pull CDN: edge fetches from origin on first miss (simpler, origin must handle bursts).

Cache Control Headers

  • Cache-Control: max-age=86400 — browser + CDN TTL
  • s-maxage — CDN-only TTL override
  • Surrogate-Key / Cache-Tag — tag-based purge
  • Stale content risk: use versioned URLs (hash in filename) for zero-TTL invalidation overhead
  • Dynamic content CDN (edge compute) adds complexity but dramatically cuts TTFB globally

Caching

Strategies

  • Cache-Aside (Lazy): app checks cache → miss → load DB → populate cache. Simple, resilient to cache failure. Risk: cache stampede on cold start.
  • Write-Through: write to cache and DB together. Always consistent but write latency doubles.
  • Write-Behind (Write-Back): write to cache only, async flush to DB. Low write latency, risk of data loss on cache crash.
  • Read-Through: cache handles DB load transparently. Simpler app code.

Eviction Policies

LRU (most common), LFU (frequency-based), FIFO, TTL-based. Redis supports LRU, LFU, volatile-lru.

  • Cache invalidation is hard: use event-driven invalidation or short TTLs + background refresh
  • Hot key problem: one key gets 90% traffic — use local in-process cache or key sharding

Sharding Strategies

  • Range: simple, hotspots on sequential keys
  • Hash: even distribution, range queries hard
  • Directory: flexible, lookup table is SPOF
  • Consistent Hash: minimal data movement on rebalance

Message Queues

Decouple producers from consumers, absorb traffic spikes, enable async processing. Kafka: append-only log, high throughput, replay, ordered within partition. RabbitMQ: traditional broker, routing/fanout, message TTL, DLQ. SQS: managed, at-least-once, visibility timeout.

Key Concepts

  • At-most-once: fire-and-forget, possible loss
  • At-least-once: retry on failure, idempotent consumers required
  • Exactly-once: hardest — Kafka transactions, idempotent producers
  • Consumer groups: scale consumers independently per partition
  • Dead Letter Queue: capture failed messages for inspection

API Gateway & Consistent Hashing

API Gateway

Single entry point for microservices. Handles: auth/authz, rate limiting, SSL termination, request routing, request/response transformation, circuit breaking, observability. Examples: Kong, AWS API GW, Nginx.

Consistent Hashing

Map both servers and keys onto a ring (0–2³²). Each key is served by the first server clockwise. Adding/removing a server affects only ~K/N keys (K=keys, N=nodes). Virtual nodes (vnodes) improve distribution — each server gets 100-200 positions on the ring.

  • More vnodes = better load balance but higher memory for the ring lookup
  • Without vnodes, uneven data distribution when N is small

System Design: URL Shortener

Scale: 100M URLs shortened/day, 100:1 read:write ratio → 10B redirects/day → ~116K read QPS, 1.16K write QPS. Storage: 500 bytes × 100M/day × 5 years ≈ 90 TB.

graph LR C[Client] --> AG[API Gateway / LB] AG --> WS[Write Service] AG --> RS[Read Service] WS --> DB[(PostgreSQL\nURL Mapping)] WS --> KG[ID Generator\nSnowflake] RS --> RC[(Redis Cache\nshort→long)] RC -- miss --> DB RS --> CDN[CDN Edge\nRedirect Cache]

Key Components

  • ID Generation: Snowflake ID → base62 encode (a-z, A-Z, 0-9 = 62 chars). 7-char string = 62⁷ ≈ 3.5T unique URLs. Alternatively: MD5(url) → first 7 chars (collision risk ~0.1% at 365M URLs).
  • Redirect: HTTP 301 (permanent, browser caches — reduces server load) vs 302 (temporary, every request hits server — enables analytics). Choose 302 if analytics matter.
  • Redis Cache: shortCode → longURL, TTL 24h, LRU eviction. 20% of URLs drive 80% of traffic — cache hit rate ~90%+.
  • Read path: CDN edge → Redis → DB (cascading cache layers).
  • Base62 vs base58 (no 0, O, I, l): base58 avoids user confusion for manually typed URLs but reduces address space slightly
  • Counter-based IDs are predictable (enumerable); hash-based adds privacy but risks collisions requiring retry logic
  • 301 vs 302 redirect: 301 saves bandwidth but loses click analytics; 302 enables tracking but increases server load 10×

System Design: Twitter Timeline

Scale: 300M DAU, 600M tweets/day, average 200 followers. Timeline load = top 20 tweets from 200 followees → fan-out challenge at scale.

graph TD TW[Tweet Service] --> MQ[Kafka\nTweet Events] MQ --> FO[Fan-out Service] FO -->|push to| TL[(Redis Timeline\nCache per user)] MQ --> SR[Search Indexer] FO -->|celebrities >1M followers| PA[Pull-on-read\nfor mega accounts] Client --> AG[API Gateway] AG --> TS[Timeline Service] TS --> TL TS --> PA TS --> DB[(Cassandra\nTweet Store)]

Fan-out Strategies

  • Fan-out on Write (Push): when tweet is posted, pre-compute and push to each follower's timeline cache. Fast reads (O(1)), but costly writes for users with millions of followers (Lady Gaga's tweet → 80M writes).
  • Fan-out on Read (Pull): fetch tweets from all followees at read time, merge/rank. No write amplification, but slow reads requiring N DB calls per timeline load.
  • Hybrid: Push for regular users (< 1M followers), pull for celebrities. Merge at read time. Twitter uses this approach.

Timeline Ranking

Raw chronological: simple, no ML needed. Engagement-ranked: ML model scores tweets (likes, retweets, dwell time). Store only tweet IDs in timeline cache; hydrate tweet content from tweet service to reduce storage.

  • Push model: celebrity with 100M followers × 1 tweet = 100M Redis writes. Unfollow doesn't clean cache — serve stale but use tombstones
  • Pull model: N=200 followees, each DB query must be fast. Cassandra partition per user + time range query works well
  • Caching tweet IDs vs full tweet objects: IDs are tiny (8 bytes) vs full tweet (300 bytes); hydration adds a second RTT but keeps cache fresh for edits

System Design: YouTube

Scale: 500 hours of video uploaded/minute, 1B hours watched/day. Massive asymmetry: read-heavy (views vs uploads ~1000:1). Storage: 500h/min × 60min × 24h × 365 × 10GB/h ≈ 2.6 EB/year raw (before transcoding).

graph LR U[User Upload] --> UPS[Upload Service] UPS --> S3_RAW[(S3\nRaw Storage)] S3_RAW --> MQ[Kafka\nUpload Events] MQ --> TS[Transcoding\nWorkers] TS -->|360p/720p/1080p/4K| S3_CDN[(S3\nTranscoded)] S3_CDN --> CDN[CDN PoPs] CDN --> Viewer[Viewer] UPS --> DB[(MySQL\nVideo Metadata)] DB --> MC[(Memcached)]

Upload & Transcoding Pipeline

  • Chunked upload: split video into 5-10MB chunks, upload with resumable protocol. On failure, resume from last successful chunk. Store chunks in blob storage (S3).
  • Transcoding workers: stateless, horizontally scalable workers pull from queue. Produce multiple renditions: 360p, 480p, 720p, 1080p, 4K. Container formats: MP4 (H.264) for broad compatibility, WebM (VP9) for open-source.
  • Adaptive Bitrate (ABR): HLS or DASH segments video into 2-10s chunks at multiple bitrates. Player selects quality based on bandwidth. Segments cached aggressively at CDN (immutable once created).
  • Metadata: MySQL for structured video metadata (title, description, views). Denormalize read-heavy fields. Cassandra or BigTable for view counts at scale.
  • Transcoding is CPU-intensive; use spot instances for cost efficiency but require checkpointing for preemption resilience
  • HLS (Apple) vs DASH (MPEG): HLS has broader device support; DASH is codec-agnostic and better for DRM flexibility
  • View count consistency: exact counts require distributed counters (HyperLogLog for uniques, Kafka aggregation for total) — eventual consistency is acceptable for display

System Design: Uber

Scale: 5M trips/day, 20M active drivers globally. Location updates every 4 seconds per active driver → ~500K location updates/sec peak. Real-time matching latency < 2s.

graph TD D[Driver App] -->|WebSocket| LS[Location Service] LS --> GS[(GeoHash Store\nRedis)] Rider[Rider App] --> MS[Match Service] MS --> GS MS --> PS[Pricing Service\nSurge] MS --> TS[Trip Service] TS --> DB[(PostgreSQL\nTrips)] TS --> NS[Notification\nService] NS --> D NS --> Rider

Key Components

  • Geohash: encode lat/lng as a string (e.g., "9q8yy"). Nearby cells share a prefix. Precision 6 = ~1.2km cells. Store driver locations as geohash → [driverIds] in Redis Sorted Set with expiry. On match request, search current + 8 neighboring cells.
  • Driver Location Updates: WebSocket for persistent bidirectional connection. Driver sends location every 4s; server updates Redis with TTL of ~30s (driver considered offline if no update).
  • Matching: find N nearest drivers → filter by availability → rank by ETA (actual routing, not straight-line). ETA from precomputed road graph (OSRM or Google Maps API).
  • Surge Pricing: demand/supply ratio per geohash cell. If demand > supply × threshold → surge multiplier. Updated every 60s. Stored in Redis, cached on API gateway.
  • Geohash vs S2 cells: S2 cells have equal area (no polar distortion), better for global consistency, but more complex to implement; geohash is simpler with good tooling
  • WebSocket vs polling: WebSocket reduces location update overhead 10× but requires sticky sessions or a pub/sub fan-out layer (Redis pub/sub per driver)
  • Match latency vs optimality: greedy nearest-driver match is fast O(log N) but suboptimal; Hungarian algorithm is optimal but O(N³) — use greedy with constraints

System Design: WhatsApp

Scale: 2B users, 100B messages/day → 1.16M messages/sec. Most traffic is 1:1 chat. Storage: 100B × 100 bytes avg ≈ 10 TB/day. Delivery latency target: < 500ms for online users.

graph LR SA[Sender App] -->|WebSocket| CS1[Chat Server 1] CS1 --> MQ[Kafka\nMessage Router] MQ --> CS2[Chat Server 2] CS2 -->|WebSocket| RA[Receiver App] CS1 --> MS[(Cassandra\nMessage Store)] CS2 --> MS MQ --> PS[Push Service\nAPNS/FCM] PS -->|offline user| RA CS1 --> PRS[Presence Service\nRedis]

Key Components

  • WebSocket Connection: each client maintains persistent WebSocket to a chat server. Connection layer is stateful — use consistent hashing to map user → chat server. Chat servers are stateless in logic but stateful in connections.
  • Message Flow: Sender → Chat Server A → Kafka → Chat Server B (if receiver online via WebSocket) OR Push Notification (FCM/APNS) if offline → Receiver pulls unread on reconnect.
  • Cassandra for Messages: partition key = conversation_id, clustering key = message_id (time-ordered). Wide rows enable efficient range queries for chat history. Replication factor 3 for HA.
  • E2E Encryption: Signal Protocol — each message encrypted with a one-time pre-key. Server stores only ciphertext; cannot read messages. Key exchange during first message in a conversation.
  • Message Status: single tick (sent to server), double tick (delivered to device), blue tick (read). Stored as events, not denormalized on message row to avoid hot spots.
  • Cassandra append-only model is ideal for messages (no updates), but message deletion requires tombstones and compaction tuning to reclaim space
  • E2E encryption prevents server-side spam filtering and content moderation — WhatsApp uses metadata analysis and user reports instead
  • Group chat fan-out: 1 message → N members. At 256 members, server-side fan-out; at thousands, push-to-member-service with partitioned delivery

System Design: Google Drive

Scale: 1B users, 15 GB free quota. 10M files uploaded/day → ~116 uploads/sec. Files range from 1KB to 5GB. Key challenge: sync across multiple devices with conflict resolution.

graph TD Client -->|Chunked Upload| US[Upload Service] US --> S3[(Blob Storage\nS3/GCS)] US --> MDB[(Metadata DB\nMySQL)] US --> MQ[Kafka\nSync Events] MQ --> NS[Notification Service] NS -->|long-poll/SSE| OtherDevices[Other Devices] OtherDevices --> DS[Download Service] DS --> CDN[CDN] CDN --> S3 MDB --> MC[(Memcached\nMetadata Cache)]

Key Components

  • Chunked Upload: split file into 4-10MB chunks. Hash each chunk (SHA-256). If same hash exists in blob store, skip upload (deduplication). Resume interrupted uploads from last successful chunk. Store chunk manifest in metadata DB.
  • Delta Sync: on file change, compute diff at block level (rsync algorithm). Upload only changed blocks. A 100MB file with 1KB change → upload 1KB not 100MB. Reduces bandwidth 99%+ for edits.
  • Conflict Resolution: Last-write-wins (LWW) with vector clocks for detecting conflicts. If two devices edit offline simultaneously, detect via vector clock divergence → create a "conflict copy" and notify user. Google Docs uses OT (Operational Transformation) for real-time collaborative editing.
  • Metadata DB: MySQL stores file hierarchy (path, parent_id), version history, chunk list per version, ACL (sharing permissions). Partition by user_id.
  • Sync Protocol: clients maintain local state DB. On reconnect, compare local version with server version using sync tokens. Long-polling or Server-Sent Events for push notifications of remote changes.
  • Deduplication at block level saves storage but requires cryptographically strong hashing (SHA-256) to avoid hash collision attacks that could leak data
  • Strong consistency for metadata (you must see your own upload immediately) vs eventual consistency for sync events to other devices (acceptable 1-5s delay)
  • Version history storage cost: keep N versions or time-based retention — trade storage cost vs user expectation of recovery window

Design Patterns

Saga Pattern

Manages distributed transactions across microservices without 2PC. A saga is a sequence of local transactions; each step publishes an event to trigger the next. On failure, compensating transactions roll back prior steps.

Choreography vs Orchestration

  • Choreography: services react to events. Decoupled, but hard to track flow and debug.
  • Orchestration: a central saga orchestrator directs each step. Easier to monitor, but orchestrator is a coupling point.
Use case: e-commerce order — reserve inventory → charge payment → dispatch. Compensating: release inventory if payment fails.

Circuit Breaker

Prevents cascading failures by stopping calls to a failing service. Three states: Closed (normal), Open (failing, reject calls fast), Half-Open (probe with limited traffic to test recovery).

Thresholds: open after N failures in T seconds. Half-open probe: allow 1 request; if success → close; if fail → open again. Libraries: Hystrix (deprecated), Resilience4j, Polly (.NET).

  • Fast failure improves UX (immediate error) over hanging requests that consume threads and memory
  • Combine with retry + exponential backoff + jitter to avoid thundering herd on recovery

Transactional Outbox Pattern

Solves the dual-write problem: writing to DB and publishing to message broker atomically. Solution: write the event to an outbox table in the same DB transaction. A separate message relay (Debezium CDC or polling) reads the outbox and publishes to Kafka.

Guarantees at-least-once delivery. Consumers must be idempotent (deduplicate via event_id). Inbox pattern at consumer side for exactly-once semantics.

CQRS (Command Query Responsibility Segregation)

Separate the write model (commands) from the read model (queries). Write side: normalized, strongly consistent, optimized for integrity. Read side: denormalized, eventually consistent, optimized for query patterns.

Often paired with Event Sourcing: store all state changes as an immutable event log; derive read models by replaying events. Enables audit trails, temporal queries, and rebuilding projections.

  • Adds complexity: two models to maintain, eventual consistency between write and read side
  • Excellent for high-read systems where read patterns differ significantly from write structure

Rate Limiting Algorithms

Token Bucket

Bucket holds max N tokens; replenished at rate R/sec. Each request consumes 1 token. Allows bursts up to N. Redis: INCR + TTL or Lua script for atomic check-and-decrement.

Leaky Bucket

Requests enter a queue (bucket) and are processed at a fixed rate R. Smooths out bursts — no burst allowed. If queue full, request is dropped. Good for network traffic shaping.

Sliding Window Log

Store timestamp of each request in a sorted set. On request, remove timestamps older than window, count remaining. If count < limit, allow. Accurate but memory-intensive.

Sliding Window Counter

Approximate: current_window_count + previous_window_count × (1 - elapsed/window). ~0.003% error rate but O(1) memory. Best accuracy-to-memory tradeoff.

Fixed Window Counter

Simple: counter per time window (e.g., per minute). INCR in Redis with EXPIRE. Weakness: burst at window boundary (2× limit in 1s straddling two windows).

Distributed Rate Limiting

Multiple API gateway nodes share a central Redis counter. Lua script for atomic check-and-increment. Alternative: each node enforces N/num_nodes limit locally (less accurate but no Redis hop).

Interview Q&A

Easy

Easy What is the difference between horizontal and vertical scaling?

Vertical scaling (scale up): add more CPU/RAM/disk to a single machine. Simple (no code changes), but limited by hardware max, single point of failure, and expensive at the top end. Good for stateful systems that are hard to distribute (legacy DBs).

Horizontal scaling (scale out): add more machines, distribute load. Theoretically unlimited, fault-tolerant, cost-effective with commodity hardware. Requires stateless services, load balancing, and distributed state management (harder to implement).

In practice: vertical scale first (cheaper and simpler), then horizontal when you hit the wall. Databases often use vertical scaling + read replicas before sharding horizontally.

Easy What is a CDN and when would you use one?

A CDN (Content Delivery Network) is a geographically distributed network of proxy servers that cache content close to users. It reduces latency (data travels shorter distance), reduces origin server load, and improves availability (edge serves content even if origin is down).

Use when: serving static assets (images, JS, CSS, videos), globally distributed users, high read QPS on public content, need for DDoS protection at edge. Don't use when: content is personalized/private (requires cache-bypass), real-time data (WebSockets), or you have a strictly regional user base with low scale.

Key decision: push vs pull CDN. Push is better for large files you control the update cycle for. Pull is better for unpredictable traffic patterns where you can't pre-populate.

Easy Explain the difference between SQL and NoSQL databases. When would you choose each?

SQL databases (PostgreSQL, MySQL): structured schema, ACID transactions, powerful join queries, vertical scaling + read replicas. Choose for: financial systems, user accounts, anything requiring strong consistency and complex relational queries. Mature tooling, well-understood failure modes.

NoSQL databases: flexible schema, horizontal scaling, BASE consistency. Types: Document (MongoDB — flexible JSON), Key-Value (Redis, DynamoDB — ultra-fast simple lookups), Wide-column (Cassandra — time-series, write-heavy), Graph (Neo4j — relationship traversal).

Choose NoSQL for: massive scale (billions of records), flexible/evolving schema, specific access patterns (time-series, graph), high write throughput. In most real systems you use both: PostgreSQL for user data + Cassandra for events + Redis for cache.

Intermediate

Medium How do you handle database hotspots / hot keys?

A hot key occurs when a small subset of keys receives disproportionate traffic — e.g., a celebrity's profile page or a viral post. Common causes: hash-based sharding with a key that maps to one shard, or a single Redis key for a popular counter.

Solutions: (1) Key splitting: append a random suffix (counter_1, counter_2 … counter_100), read all and aggregate. (2) Local in-process cache: each app server caches hot keys for 1-5s, dramatically reducing Redis load. (3) Read replicas: distribute hot reads across replicas. (4) Cache warming: preload known hot keys before traffic spike. (5) Consistent hashing with vnodes: distributes load more evenly across shards.

For counters specifically: use approximate counting (HyperLogLog for uniques), batched updates (buffer in memory, flush every N seconds), or probabilistic sampling.

Medium How does consistent hashing work and why is it preferred over simple modulo hashing?

Simple modulo hashing: key % N where N is number of servers. Problem: when N changes (server added/removed), almost all keys remap. Adding 1 server to 10 reshuffles ~90% of keys — catastrophic for cache invalidation.

Consistent hashing: map servers and keys onto a hash ring [0, 2³²). A key is assigned to the first server clockwise from its position. Adding/removing a server only affects keys between it and its predecessor — typically K/N keys (1/N of all keys). With 10 servers, adding 1 remaps ~9% of keys.

Virtual nodes: each physical server gets 100-200 positions on the ring (e.g., server1_0, server1_1 … server1_150). This improves load distribution when N is small and allows weighted assignment (more powerful servers get more vnodes). Used by Cassandra, DynamoDB, Memcached (ketama).

Medium Design a rate limiter for an API with 1M requests/second.

Requirements: limit per user/IP, distributed across 100 API servers, respond with 429 on limit breach, minimal latency overhead (< 5ms).

Algorithm: Sliding Window Counter (best accuracy-to-performance tradeoff). Store in Redis: rate:{userId}:{windowMin} with INCR and 2-minute TTL. Check: current_count + (previous_count × overlap_fraction) < limit.

Architecture: API gateway → Redis cluster (sharded by user_id). Use Lua script for atomic check-and-increment to avoid race conditions. Redis pipeline reduces RTT. For 1M RPS across 100 servers = 10K RPS/server → Redis at 100K ops/sec (well within Redis limits of 500K-1M ops/sec). Add Redis replica for read offload. If Redis is down, fail open (allow traffic) or fail closed (block) — business decision. Local in-process cache for burst absorption: allow 10 requests without Redis check, sync periodically.

Medium How do you design a notification system for 100M users?

A notification system must handle multiple channels (push, email, SMS), prioritize notifications, handle failures gracefully, and respect user preferences.

Architecture: Event sources → Kafka topics (one per notification type or priority tier) → Notification Service (fan-out, template rendering, user preference lookup) → Channel-specific senders (FCM/APNS for push, SES for email, Twilio for SMS) → Delivery tracking in Cassandra.

Key considerations: (1) User preferences DB (opt-outs per channel/type) checked before sending. (2) Rate limit notifications per user (max N per hour) to avoid spam. (3) Retry with exponential backoff for failed deliveries. (4) Dead Letter Queue for persistently failed messages. (5) Idempotency: store notification_id; skip if already sent (handles Kafka at-least-once). (6) Batching: group low-priority notifications into digest emails. (7) Priority queues: critical notifications (OTP, password reset) skip queues and send directly.

Advanced

Hard How would you design a globally distributed database with strong consistency?

Strong consistency globally means all readers see the same data as soon as a write commits, regardless of geographic location. This conflicts directly with the CAP theorem — network partitions between regions mean you must choose: block writes until all regions confirm (strong consistency) or allow divergence (availability).

Google Spanner approach: uses TrueTime API (GPS + atomic clocks, uncertainty ± 7ms) to assign globally ordered transaction timestamps. Two-phase commit across regions with Paxos per shard. Guarantees external consistency (linearizability). External commits wait for TrueTime uncertainty to pass. High latency (50-150ms for cross-region transactions) but strongest guarantees available.

Practical approach without atomic clocks: Hybrid Logical Clocks (HLC) combine physical time and logical counters. Use multi-region Paxos (CockroachDB) or Raft (etcd) with a leader per shard. For cross-shard transactions, use two-phase commit with a transaction coordinator. Read from local replica for non-critical reads (potential stale), force leader reads for critical data. Accept 100-300ms write latency for cross-region commits as the fundamental physics cost.

Hard Explain how you'd implement distributed tracing for a microservices system with 500 services.

Distributed tracing tracks a request as it flows through multiple services, each adding a span. A trace = tree of spans. Each span captures: service name, operation, start time, duration, parent span ID, status, and custom tags.

Implementation: Propagate a trace context header (W3C TraceContext standard: traceparent: 00-{traceId}-{spanId}-{flags}) through HTTP headers, Kafka message headers, and gRPC metadata. Each service SDK (OpenTelemetry) creates child spans and forwards context downstream. Spans are sent asynchronously (UDP or fire-and-forget HTTP) to a local agent (Jaeger agent, OTel collector) to avoid impacting request latency.

At scale: 500 services × 1000 RPS each = 500K spans/sec. Sampling is critical: head-based sampling (decide at trace root, propagate decision) at 1% for normal traffic; tail-based sampling (buffer all spans, decide after trace completes based on error/latency) preserves all error traces. Storage: Cassandra for span data (write-heavy, time-series access patterns), Elasticsearch for tag-based search. Retention: full detail 7 days, aggregated metrics 90 days.

Hard How would you design a search autocomplete system for 10B queries/day?

Autocomplete must return top-N suggestions in < 100ms for a partial query string. 10B queries/day = ~116K QPS globally. Most queries are reads; index updates lag writes by acceptable minutes.

Data structure: Trie (prefix tree) stores all query strings. Each node stores the top K (e.g., 10) queries with their scores for that prefix. This allows O(L) lookup (L = query length) returning pre-sorted suggestions. Problem: in-memory trie for web-scale is huge. Solution: serialize to sorted string table (SST) or use Elasticsearch prefix queries with edge n-gram analyzer.

Architecture: Query logs → Kafka → Aggregation service (count by query, 1-hour windows) → Score update service (computes trending score = freq × recency × quality) → Trie builder (periodic full rebuild or incremental update) → Distributed trie servers (consistent hash by prefix prefix, e.g., first 2 chars). API layer checks Redis cache for hot prefixes (< 2ms), falls back to trie servers (< 20ms), falls back to Elasticsearch (< 100ms). CDN caches top 10K prefixes at edge. Personalization: blend global results with user-specific query history at serving time.

Hard Design a real-time collaborative document editor (like Google Docs).

The core challenge: multiple users editing the same document simultaneously, each seeing others' changes in real-time, with no conflicts and correct merge semantics. Network latency means users apply operations locally before receiving remote operations — these can conflict.

Operational Transformation (OT): Transform incoming operations against concurrent operations. Example: User A inserts 'X' at position 5; User B deletes char at position 3. If B's op arrives at A's server, transform it to account for A's insert: adjust position. OT requires a central server to serialize and transform operations (Google Docs uses this). Server is the source of truth; clients speculatively apply operations locally and reconcile on acknowledgment.

CRDT (Conflict-free Replicated Data Type): Alternative — no coordination needed. Yjs, Automerge use sequence CRDTs where each character has a unique ID (site + counter). Concurrent inserts are deterministically ordered by ID. Deletes mark characters as tombstones. Merge is always convergent. Enables peer-to-peer collaboration. Tradeoff: higher memory (tombstones accumulate), more complex implementation.

System architecture: WebSocket connections to document server. Operations stored in Kafka (ordered log per document). Presence service (Redis pub/sub) broadcasts cursor positions. Document snapshot stored in PostgreSQL; op log in Cassandra. Periodic checkpointing (snapshot + compact old ops). Rate limit ops per user (max 50 ops/sec) to prevent flooding. Conflict window after network partition: buffer ops, replay on reconnect using OT/CRDT merge.

Very Advanced

Very Advanced How would you design a distributed transaction system that handles partial failures across microservices without 2PC?

Two-Phase Commit (2PC) is synchronous and blocks if the coordinator fails mid-transaction — unacceptable in microservices with independent deployments and network unreliability. The goal: achieve transaction semantics without a blocking coordinator.

Saga Pattern with Outbox: decompose into local transactions with compensating actions. Each service writes to a local outbox table atomically with its business data. A CDC relay (Debezium) publishes outbox events to Kafka. Downstream services consume events and either complete or publish failure events. Orchestrated saga: a saga coordinator service manages state machine, retries, and triggers compensations. Choreographed: services react to events directly.

Idempotency is non-negotiable: all operations must be idempotent (safe to retry). Use idempotency keys (event_id) stored in a deduplicate table per service. Check before processing, insert after. TTL the dedup table to bounded size.

Handling partial failure: stuck saga (compensating failed too) → Dead Letter Queue → human intervention or retry with exponential backoff. Semantic locks: while saga is in-progress, mark resource as "pending" to prevent concurrent sagas conflicting. Forward recovery (retry failed step) is preferred over backward recovery (compensate) when possible — compensations are business-logic-heavy and often imperfect (cannot un-send an email).

Very Advanced Design a system to detect duplicate events in a stream of 10M events/second.

Exact deduplication at 10M events/sec requires O(1) lookup. If events must be deduplicated within a 24-hour window, that's 10M × 86400 = 864B events — storing all event IDs is ~8.6 TB for 10-byte IDs. Not feasible for exact matching at low latency.

Probabilistic: Bloom Filter: bit array of size M with K hash functions. False positive rate ~1% at M=10M bits per million elements. For 864B events, bloom filter size: 10B bits ≈ 1.25 GB at 1% FPR. Bloom filters never have false negatives (if it says "not seen", it hasn't been seen). Use a rotating bloom filter — two filters, switch every 12 hours, clear the older one. Implement in Redis with RedisBloom module: BF.ADD key event_id.

Exact with bounded window: if window is 1 hour not 24h: 36B events × 10 bytes = 360 GB — still large. Partition event stream by event_id hash across 100 Kafka partitions → each partition handles 100K events/sec. Each consumer maintains an in-process LRU cache of seen event IDs for last N seconds. LRU of 36M entries × 10 bytes = 360 MB per partition — feasible. Persist to Redis for cross-instance deduplication. Key insight: partition by event_id ensures the same event always goes to the same consumer, enabling purely local deduplication without coordination.

Very Advanced How would you build a system to handle thundering herd problems at cache layer?

Thundering herd: a popular cache key expires; thousands of simultaneous requests all miss the cache and hit the DB simultaneously. DB gets spike that can be 100-1000× normal load. Classic scenario: product launch page, viral content, market open.

Solution 1 — Mutex/Probabilistic Lock: first request to detect a miss acquires a distributed lock (Redis SET NX EX), fetches from DB, populates cache, releases lock. All other requests either wait or return stale data. Redis SETNX + GETEX pattern. Risk: lock holder fails, other requests starve. Mitigate with lock TTL.

Solution 2 — Probabilistic Early Expiration (XFetch): before a key expires, probabilistically refresh it. Formula: currentTime - (delta × beta × log(rand())) > expiry_time. As expiry approaches, probability of early refresh increases. The first requester to trigger early refresh re-populates. No locking needed, works at any scale, smooth repopulation.

Solution 3 — Stale-While-Revalidate: serve stale data immediately, trigger async background refresh. Cache-Control HTTP header supports this natively. Zero latency impact; stale window = max staleness acceptable. Combine with background queue: when stale threshold crossed, enqueue exactly one refresh job (check-and-set to avoid duplicate jobs). This is the recommended approach for most systems — decouple cache refresh from request path entirely.

Additional mitigations: jitter on TTLs (instead of 3600s, use 3600 ± 300s random) to stagger mass expiration. Warm cache proactively before anticipated traffic spikes. Use layered caches (L1 in-process → L2 Redis → DB) so L1 miss doesn't always mean Redis miss.

Very Advanced Design a multi-region active-active database architecture with conflict resolution.

Active-active multi-region means users in any region can write, and writes are replicated to other regions. No region is a replica — all are primaries. Challenges: write conflicts (same record updated in two regions before sync), replication lag (50-200ms cross-region), and maintaining consistency guarantees users expect.

Conflict Detection: use vector clocks or hybrid logical clocks to track causality. Each write is stamped with {region, timestamp, counter}. On receiving a remote write, compare versions: if local version happened-before remote → accept remote. If concurrent (neither happened-before the other) → conflict.

Conflict Resolution Strategies: (1) LWW (Last Write Wins): highest timestamp wins. Simple, but clock skew can cause recent writes to lose. Use with NTP + bounded drift. (2) CRDT-based: data structures that always merge correctly (counters: add both; sets: union; registers: LWW or MV-register). DynamoDB uses CRDTs for counters. (3) Application-level merge: surface conflict to application; shopping cart merges items, document editor merges edits via OT/CRDT. (4) Write to primary region, async replicate: for user profile updates, route writes to "home region" (consistent hashing by user_id → region). Eliminates conflicts at the cost of cross-region write latency for traveling users.

Practical architecture (CockroachDB/Spanner model): partition data by region locality. Each row has a "home region." Writes to home region are single-Paxos-group (low latency). Writes to a non-home region go cross-region (higher latency). Reads from any region: local reads for home-region data (stale-ok), cross-region reads for other data. Global secondary indexes require fan-out to all regions. Accept that some data (e.g., global leaderboard, inventory count) cannot be active-active without coordination cost — use centralized single-region service for those hotspots with async replication for display purposes.
