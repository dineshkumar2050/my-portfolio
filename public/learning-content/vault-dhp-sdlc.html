HashiCorp Vault, DHP & SDLC

What is HashiCorp Vault

HashiCorp Vault is an identity-based secrets and encryption management system. It provides a unified interface to any secret while providing tight access control and recording a detailed audit log. Vault solves the problem of how to securely store, access, and distribute secrets (API keys, passwords, certificates, encryption keys) across distributed systems.

Core capabilities: Secrets management · Encryption as a service · Identity-based access · Dynamic secrets · Key management · PKI/certificate management

Key Concepts

  • Secret: Anything that you want to tightly control access to — API keys, passwords, certificates, encryption keys
  • Dynamic secrets: Generated on-demand, short-lived credentials (never reused)
  • Encryption as a service (EaaS): Apps encrypt/decrypt data without ever handling the encryption key
  • Lease: Time-to-live (TTL) associated with a secret; Vault revokes it when the lease expires

Barrier: AES-256-GCM Encryption

The barrier is Vault's encryption layer. All data stored in the backend is encrypted using AES-256-GCM (authenticated encryption). The barrier key is derived from the master key during unseal. Even if someone gains access to the storage backend, all data is encrypted and unreadable without the unseal keys.

Database Secret Engine

Generates dynamic, short-lived credentials for databases. Vault creates a new user on each request, with a configurable TTL. The credential is automatically revoked when the lease expires.

# Enable and configure database engine
vault secrets enable database
vault write database/config/my-postgresql-database \
  plugin_name=postgresql-database-plugin \
  allowed_roles="readonly" \
  connection_url="postgresql://{{username}}:{{password}}@localhost:5432/mydb" \
  username="vault-admin" password="vault-pass"

# Create a role with SQL to run on credential creation
vault write database/roles/readonly \
  db_name=my-postgresql-database \
  creation_statements="CREATE ROLE '{{name}}' WITH LOGIN PASSWORD '{{password}}' \
    VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO '{{name}}';" \
  default_ttl="1h" max_ttl="24h"

# Generate credentials
vault read database/creds/readonly
# Returns: username (vault-readonly-xxxx), password (dynamic), lease_duration 1h

Supported databases: PostgreSQL, MySQL/MariaDB, MongoDB, MSSQL, Oracle, Cassandra, Redis, Elasticsearch, Snowflake.

PKI Secret Engine

Vault acts as a Certificate Authority (CA). It can issue X.509 certificates, sign CSRs, and manage certificate revocation.

# Enable PKI engine
vault secrets enable pki
vault secrets tune -max-lease-ttl=87600h pki  # 10 years

# Generate root CA
vault write pki/root/generate/internal \
  common_name="example.com" ttl="87600h"

# Configure URLs (CRL, OCSP)
vault write pki/config/urls \
  issuing_certificates="http://vault.example.com:8200/v1/pki/ca" \
  crl_distribution_points="http://vault.example.com:8200/v1/pki/crl" \
  ocsp_servers="http://vault.example.com:8200/v1/pki/ocsp"

# Create intermediate CA (recommended pattern)
vault secrets enable -path=pki_int pki
vault write pki_int/intermediate/generate/internal common_name="example.com Intermediate"
# Sign with root, then set signed cert in pki_int/intermediate/set-signed

# Create role for issuing certs
vault write pki_int/roles/example-dot-com \
  allowed_domains="example.com" allow_subdomains=true \
  max_ttl="720h"

# Issue certificate
vault write pki_int/issue/example-dot-com \
  common_name="app.example.com" ttl="24h"

# Revoke a certificate
vault write pki/revoke serial_number="39:dd:2e:..."

AWS Secret Engine

Generates dynamic AWS IAM credentials (access key + secret key) or STS credentials on demand.

vault secrets enable aws
vault write aws/config/root access_key=AKIAIOSFODNN7 secret_key=... region=ap-southeast-2

# Create role (IAM user with inline policy)
vault write aws/roles/s3-readonly \
  credential_type=iam_user \
  policy_document='{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["s3:GetObject"],"Resource":"*"}]}'

# Or using STS assumed role
vault write aws/roles/deploy \
  credential_type=assumed_role \
  role_arns="arn:aws:iam::123456789012:role/my-role"

vault read aws/creds/s3-readonly  # returns access_key, secret_key, lease_duration

Transit Secret Engine (Encryption as a Service)

Provides cryptographic operations without storing data. Applications encrypt/decrypt data using Vault's API — the plaintext never leaves the app, only ciphertext is stored in your database.

vault secrets enable transit

# Create an encryption key
vault write -f transit/keys/my-app-key  # AES-256-GCM96 default
# Or specify type: aes128-gcm96, chacha20-poly1305, ed25519, ecdsa-p256, rsa-2048, rsa-4096

# Encrypt data (plaintext must be base64-encoded)
vault write transit/encrypt/my-app-key \
  plaintext=$(echo -n "sensitive-data" | base64)
# Returns: ciphertext: vault:v1:8SDd3WHDOjf7mq6...

# Decrypt data
vault write transit/decrypt/my-app-key \
  ciphertext="vault:v1:8SDd3WHDOjf7mq6..."
# Returns: plaintext (base64-encoded)

# Key rotation (new ciphertext uses v2, old still decryptable)
vault write -f transit/keys/my-app-key/rotate

# Rewrap old ciphertext to use latest key version
vault write transit/rewrap/my-app-key ciphertext="vault:v1:..."

# Signing (ed25519/ECDSA keys)
vault write transit/sign/my-signing-key input=$(echo -n "message" | base64)
vault write transit/verify/my-signing-key input=... signature=...

SSH Secret Engine

Two modes: OTP (one-time password per session) and Signed Certificates (CA-signed SSH keys).

# Signed certificates mode (preferred)
vault secrets enable ssh
vault write ssh/config/ca generate_signing_key=true
# Add Vault's public key to SSH servers: TrustedUserCAKeys /etc/ssh/trusted-user-ca-keys.pem

vault write ssh/roles/my-role \
  key_type=ca \
  allowed_users="ubuntu,ec2-user" \
  default_extensions='{"permit-pty":""}' \
  ttl="30m"

# Sign a public key
vault write ssh/sign/my-role public_key=@~/.ssh/id_rsa.pub
# SSH using signed cert: ssh -i vault-signed-cert.pub -i ~/.ssh/id_rsa ubuntu@host

Auth Methods

Token Auth (Default)

Every auth method generates a token. Tokens are Vault's native auth mechanism. The root token is created at initialization and should be revoked after initial setup.

# Token properties
vault token create -policy="my-policy" -ttl=24h -use-limit=5
vault token lookup <token>
vault token renew <token>
vault token revoke <token>

# Periodic tokens (no TTL expiry but must be renewed)
vault token create -policy="worker" -period=24h

# Token roles (templates for creating tokens)
vault write auth/token/roles/worker \
  allowed_policies="worker-policy" period=24h orphan=true

AppRole Auth (Machine-to-Machine)

The recommended method for applications. The app knows its RoleID (public, like a username) and must fetch a SecretID (private, like a password). Response wrapping adds an extra layer of security.

vault auth enable approle
vault write auth/approle/role/my-app \
  secret_id_ttl=10m \
  secret_id_num_uses=1 \
  token_ttl=20m \
  token_max_ttl=4h \
  policies="my-app-policy"

# Get RoleID (embed in app config/image)
vault read auth/approle/role/my-app/role-id

# Get SecretID via response wrapping (CI/CD passes wrapped token)
vault write -wrap-ttl=120s -f auth/approle/role/my-app/secret-id
# Returns: wrapping_token (valid 120s, single-use)

# App unwraps to get SecretID
vault unwrap <wrapping_token>

# App logs in
vault write auth/approle/login role_id="..." secret_id="..."

AWS IAM Auth

EC2 instances or Lambda functions authenticate using AWS-signed API calls or instance identity documents.

vault auth enable aws
vault write auth/aws/config/client \
  access_key=AKIA... secret_key=...

# IAM method: iam auth type (recommended for ECS/Lambda)
vault write auth/aws/role/my-ecs-role \
  auth_type=iam \
  bound_iam_principal_arn="arn:aws:iam::123456789:role/my-ecs-task-role" \
  policies="my-policy" ttl=1h

# EC2 method: uses PKCS7-signed instance identity document
vault write auth/aws/role/my-ec2-role \
  auth_type=ec2 \
  bound_ami_id="ami-12345678" \
  bound_account_id="123456789012" \
  policies="my-policy" ttl=1h

Kubernetes Auth

Pods authenticate using their ServiceAccount JWT token. The vault-agent injector uses this method automatically.

vault auth enable kubernetes

vault write auth/kubernetes/role/my-app \

Policies

Policies are written in HCL (HashiCorp Configuration Language) and control access to paths in Vault. Every token has one or more policies attached.

# Capabilities: create, read, update, delete, list, sudo, deny
path "secret/data/myapp/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}

path "secret/data/myapp/shared" {
  capabilities = ["read"]
}

# Deny overrides all other capabilities
path "secret/data/myapp/admin-only" {
  capabilities = ["deny"]
}

# Database dynamic credentials
path "database/creds/readonly" {
  capabilities = ["read"]
}

# Allow renewing own token
path "auth/token/renew-self" {
  capabilities = ["update"]
}

# Policy templating with identity
path "secret/data/users/{{identity.entity.name}}/*" {
  capabilities = ["create", "read", "update", "delete"]
}

# Group-based templating
path "secret/data/teams/{{identity.groups.names.engineering.id}}/*" {
  capabilities = ["read", "list"]
}
# CRUD policy operations
vault policy write my-policy policy.hcl
vault policy read my-policy
vault policy list
vault policy delete my-policy

# Token with multiple policies
vault token create -policy=read-only -policy=kv-writer

Sentinel Policies (Enterprise)

Endpoint Governing Policies (EGP) and Role Governing Policies (RGP) allow fine-grained control using Sentinel language — e.g., restrict access to business hours, require MFA, enforce IP-based access.

Vault Agent & Vault Injector

Vault Agent

A client-side daemon that handles auto-auth, secret rendering to files, and response wrapping. Runs alongside your application.

# vault-agent-config.hcl
vault {
  address = "https://vault.example.com:8200"
}

auto_auth {
  method "aws" {
    mount_path = "auth/aws"
    config = {
      type = "iam"
      role = "my-role"
    }
  }
  sink "file" {
    config = { path = "/tmp/vault-token" }
  }
}

template {
  source      = "/etc/vault/templates/db-config.ctmpl"
  destination = "/etc/app/db-config.yaml"
  perms       = 0640
}

cache {
  use_auto_auth_token = true
}
# db-config.ctmpl (Consul Template syntax)
{{- with secret "database/creds/readonly" -}}
DB_USERNAME={{ .Data.username }}
DB_PASSWORD={{ .Data.password }}
{{- end }}

Vault Injector (Kubernetes)

A Kubernetes mutating admission webhook that automatically injects Vault secrets into pods via annotations. Creates an init container (fetch secrets at startup) and a sidecar (keep secrets up-to-date).

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "my-app"
        vault.hashicorp.com/agent-inject-secret-config.yaml: "secret/data/myapp/config"
        vault.hashicorp.com/agent-inject-template-config.yaml: |
          {{- with secret "secret/data/myapp/config" -}}
          DB_URL: {{ .Data.data.db_url }}
          API_KEY: {{ .Data.data.api_key }}
          {{- end }}
        vault.hashicorp.com/agent-inject-secret-db-creds.yaml: "database/creds/readonly"
        vault.hashicorp.com/agent-pre-populate-only: "false"  # keep sidecar running
        vault.hashicorp.com/agent-cache-enable: "true"

Seal / Unseal

When Vault starts, it is sealed — it knows where to find storage but cannot read any of it (barrier key not in memory). Unsealing loads the barrier key into memory.

Shamir's Secret Sharing (Default)

The master key is split into N shares, requiring K shares to reconstruct (e.g., 5 shares, threshold 3). Key holders each hold one share. On restart, K holders must provide their share to unseal.

vault operator init -key-shares=5 -key-threshold=3
# Saves 5 unseal keys + 1 initial root token

vault operator unseal <key-1>  # run 3 times with different keys
vault status  # shows sealed: false once unsealed

Auto-Unseal

# AWS KMS auto-unseal
seal "awskms" {
  region     = "ap-southeast-2"
  kms_key_id = "arn:aws:kms:ap-southeast-2:123456789:key/abc123"
}

Vault Interview Q&A

Q1: Explain Vault's architecture and how the barrier works. Advanced

Answer: Vault has a layered architecture: the HTTP API layer receives requests, which pass through the auth layer for identity verification, then the core coordinates with secret engines to serve data. All persistent data goes through the barrier — a cryptographic seal implemented with AES-256-GCM. The barrier key is derived from the master key during the unseal process and is only ever held in memory (never written to disk). Even if an attacker gets the storage backend (Raft, Consul, S3), all data is encrypted ciphertext they cannot read without the barrier key. This is why Vault must be explicitly unsealed on every restart — the process reconstitutes the barrier key in memory from unseal key shares.

Q2: What is the difference between KV v1 and KV v2, and when would you use each? Intermediate

Answer: KV v1 is a simple key-value store — write overwrites, delete destroys. KV v2 adds versioning (up to N versions stored, configurable via max-versions), metadata, soft-delete (marking a version deleted without destroying data), hard destroy (permanent removal), and check-and-set for atomic updates. In practice, always use KV v2 for production as it gives you audit history and the ability to recover accidentally overwritten secrets. Use v1 only for high-throughput use cases where version history creates unacceptable storage overhead, or when migrating from a legacy system that doesn't support the v2 data path (secret/data/ prefix).

Q3: How do dynamic secrets improve security compared to static credentials? Intermediate

Answer: Static credentials (e.g., a DB password shared in config) are permanent, often shared between services, hard to rotate, and a significant blast radius if leaked. Dynamic secrets are generated on-demand and short-lived (e.g., 1-hour DB credentials). Each app instance gets unique credentials, making it easy to identify which service used a credential. When the lease expires, Vault automatically revokes the credential. Even if a credential is compromised, it expires quickly. There's no shared secret — every request generates fresh credentials. This also eliminates the "secret zero" problem for the DB credentials themselves (though Vault auth credentials still need bootstrapping via AppRole/K8s auth).

Q4: How does AppRole authentication work and why is SecretID wrapping important? Advanced

Answer: AppRole is a two-factor machine auth: RoleID (public, like a username — embedded in app config/Docker image) + SecretID (private, like a password — must be securely delivered). The challenge is secure SecretID delivery (the "secret zero problem"). Response wrapping solves this: instead of CI/CD receiving the SecretID directly, it receives a single-use, short-TTL "wrapping token" that can only be unwrapped once. The app unwraps it to get the SecretID. If the wrapping token is intercepted, the legitimate app will fail to unwrap (already used), alerting to the compromise. This shifts the trust boundary to: the CI/CD pipeline only needs permission to generate wrapped SecretIDs, not to access the actual secrets.

Q5: Explain Vault's Raft storage HA model and what happens during a leader failure. Advanced

Answer: Integrated Raft storage gives Vault built-in HA without an external dependency. Raft uses a consensus protocol: one node is the Leader (handles all writes and reads by default), others are Followers. The Leader sends heartbeats; if Followers don't receive a heartbeat within the election timeout, they become Candidates and call for election. A node wins the election with a majority vote (quorum). For a 3-node cluster, quorum = 2, so you can tolerate 1 failure. All Vault data is replicated via Raft log entries. During leader failure: a new leader is elected in seconds (election timeout 100-500ms typically), brief unavailability (the new leader must be elected and catch up). Clients get a 503 and must retry. Load balancers should be configured to redirect to the new leader (Vault's health endpoint returns 200 only for the active leader).

Q6: What is the Transit secret engine and how does it enable encryption as a service? Advanced

Answer: Transit allows applications to encrypt and decrypt data via Vault's API without Vault ever storing the data itself. The app sends plaintext → gets back ciphertext → stores ciphertext in its own database. To read, it sends the ciphertext → gets plaintext back. The encryption key never leaves Vault. Key benefits: centralized key management, easy key rotation (old data auto-upgradeable with rewrap), comprehensive audit log of every encrypt/decrypt call, no encryption code in the app. It supports multiple key types: AES-GCM for symmetric encryption, RSA/ECDSA for asymmetric, Ed25519 for signing. A common pattern is encrypting PII in a database — even if the DB is breached, data is unreadable without Vault access.

Q7: How does Vault Injector work in Kubernetes? Advanced

Answer: Vault Injector is a Kubernetes mutating admission webhook — it intercepts Pod creation requests and mutates the Pod spec to inject Vault sidecar containers. When a Pod is created with the vault.hashicorp.com/agent-inject: "true" annotation, the webhook adds: (1) an init container (vault-agent-init) that authenticates to Vault using the Pod's ServiceAccount JWT (Kubernetes auth method), fetches specified secrets, renders them to files in a shared volume (typically /vault/secrets/), and exits; (2) a sidecar container (vault-agent) that keeps running, renewing leases, and re-rendering secrets when they change. The app container reads secrets from the shared in-memory volume. The annotation vault.hashicorp.com/agent-pre-populate-only: "true" disables the sidecar (init-only mode).

Q8: How do you handle Vault in a disaster recovery scenario? Very Advanced

Answer: With Vault Enterprise DR Replication, a secondary cluster in another region continuously receives replicated data from the primary. In a disaster: promote the secondary to primary with vault operator replication dr promote — this requires a DR operation token (generated from the primary or using a DR secondary batch token). All data is available immediately. For open-source Vault: periodic snapshots of Raft storage (vault operator raft snapshot save backup.snap), restore with vault operator raft snapshot restore on a new cluster. RPO = time since last snapshot. Additionally: maintain unseal keys securely (HSM or distributed key holders), pre-configure auto-unseal in the DR region, test DR procedures quarterly, document runbooks for leader re-election and certificate rotation post-failover.

Q9: What are Vault Policies and how do you use policy templating? Intermediate

Answer: Vault Policies are HCL documents that define which paths a token can access and with what capabilities (create/read/update/delete/list/sudo/deny). Policy templating allows policies to reference the authenticated entity's identity using variables like {{identity.entity.id}}, {{identity.entity.name}}, or {{identity.groups.names.<groupname>.id}}. This enables tenant-isolation patterns: e.g., path "secret/data/users/{{identity.entity.name}}/*" means each user can only access their own secrets using a single shared policy. Without templating, you'd need one policy per user. This is essential for multi-tenant Vault deployments where you don't want to manage thousands of individual policies.

Q10: Compare Vault PKI with a traditional CA. When would you use Vault for certificate management? Advanced

Answer: Traditional CA (e.g., internal Microsoft CA, cfssl): certificate issuance is manual or semi-automated, long TTLs (1-3 years), revocation via CRL/OCSP that clients often don't check promptly. Vault PKI enables short-lived certificates (hours or days) which reduces the need for revocation (certificates expire before they become a problem), full automation via API, tight integration with service mesh (cert rotation without restart), and per-service certificates with appropriate SANs. Use Vault PKI when: mTLS between microservices (rotate certs every 24h), developer environments (issue personal certs on demand), zero-trust architectures (no long-lived credentials). Combine with cert-manager (K8s) for automatic rotation. The golden rule: Vault PKI certificates should be short-lived enough that CRL becomes irrelevant.

What is DHP (Digital Hosting Platform)

DHP is Commonwealth Bank of Australia's internal platform engineering initiative — a standardized, self-service infrastructure and deployment platform that enables engineering teams to deploy, operate, and scale services without managing the underlying infrastructure complexity. It is CBA's implementation of "platform as a product" thinking.

Core purpose: Standardize how CBA's 200+ engineering teams deploy services · Enable self-service infrastructure · Reduce time-to-production · Enforce security and compliance guardrails · Provide observability out of the box

Key Principles

  • GitOps: All environment definitions are YAML in Git — PRs to change infrastructure
  • Self-service: Teams define their own service configuration within guardrails
  • Paved road: Platform provides opinionated, secure defaults — teams opt into complexity only when needed
  • Guardrails over gates: Automated policy enforcement (not slow manual approval) where possible
  • Shift-left security: Security validation at PR time, not after deployment

Swimlanes Concept

Swimlanes are CBA's term for isolated deployment environments. Each swimlane has its own namespace, resource quotas, network policies, and IAM boundaries. Think of them as lightweight "mini-environments" within the larger DHP platform.

Swimlane Characteristics

  • Namespace isolation: Each swimlane has its own ECS cluster namespace or K8s namespace
  • Resource quotas: CPU/memory limits enforced per swimlane to prevent noisy-neighbor issues
  • Network isolation: Security groups and NACLs isolate swimlane-to-swimlane traffic
  • IAM boundaries: ECS task roles scoped to the swimlane — prod roles have production-only DB access
  • Environment-specific config: Vault paths, ALB hostnames, log destinations differ per swimlane
  • Job Template Definitions: YAML files defining Temporal worker jobs, ECS task configs per swimlane

Environment Definition Repos (GitOps)

DHP uses a GitOps pattern where all environment configuration lives in YAML files in a dedicated repository (e.g., DHP-InstBanking-EnvironmentDefinition). Changes to infrastructure are made via Pull Requests — the CI/CD pipeline validates and applies changes automatically on merge.

DHP Interview Q&A

Q1: What is the purpose of swimlanes in DHP and how do they enable environment isolation? Intermediate

Answer: Swimlanes provide namespace-level isolation of deployment environments within the DHP platform. Each swimlane (dev/test2/stg/prod) has its own ECS cluster namespace, IAM task roles scoped to that environment, Vault secret paths, network security groups, and resource quotas. This means a dev deployment of Service A cannot accidentally access prod data — the IAM role only has dev database permissions. It also prevents resource starvation: a runaway dev service hitting CPU limits doesn't affect prod. From an operational perspective, swimlanes enable a promotion model — the same container image is promoted through swimlanes with only configuration changing (dev DB → prod DB via swimlane-specific Vault paths), enforcing that prod runs the exact same artifact tested in lower environments.

Q2: How does GitOps work in DHP's environment definition repositories? Intermediate

Answer: DHP uses GitOps where the desired state of each swimlane is declared in YAML files in the environment definition repo. All infrastructure changes go through a PR workflow — no one SSHes into servers or runs ad-hoc Terraform. When a PR is merged: the CI/CD pipeline detects the change, validates against platform schemas and security policies (e.g., ensuring image comes from approved ECR, task role has acceptable permissions), then applies the change to AWS via Terraform/CDK. The Git history becomes the audit trail for all infrastructure changes. Drift detection can periodically reconcile actual state against the declared state. This gives compliance benefits (all changes reviewed, traceability) and operational benefits (environment reproducibility — recreate any swimlane from the YAML).

Q3: How are secrets securely delivered to ECS tasks running in DHP? Advanced

Answer: In DHP, secrets flow from HashiCorp Vault to ECS tasks via two mechanisms: (1) ECS Secrets Manager integration — ECS can reference Vault or AWS Secrets Manager paths in the task definition, injecting them as environment variables at container start; (2) Vault Agent sidecar — a Vault Agent container runs alongside the app, authenticates using the ECS task's IAM role (AWS IAM auth method), fetches secrets, and writes them to a shared volume as files. The ECS task role must have an IAM policy allowing the specific sts:AssumeRole action, and a Vault AWS auth role must map that IAM role to a Vault policy. Secrets are per-swimlane (different Vault paths for dev/prod), ensuring a dev task cannot fetch prod secrets. Dynamic database credentials via Vault's DB engine are preferred over static credentials for databases.

Q4: How does Temporal integrate with DHP swimlanes at CBA? Advanced

Answer: Temporal workers are deployed as ECS Fargate tasks within each DHP swimlane. Each swimlane corresponds to a separate Temporal namespace (e.g., dev-payments, prod-payments), providing workflow isolation — a bug in a dev workflow cannot affect prod workflow execution history or task queue polling. Worker configuration is defined in Job Template Definition YAML files in the environment definition repo. The worker connects to a shared Temporal cluster (or separate per-environment cluster for prod) using mTLS certificates issued by Vault's PKI engine, rotated via Vault Agent. Scaling of workers is managed by DHP's ECS autoscaling based on CPU/memory metrics or custom CloudWatch metrics (e.g., Temporal task queue backlog depth). This allows teams to scale payment processing workers independently of other services in the same swimlane.

Q5: What are the trade-offs of a platform engineering approach like DHP? Very Advanced

Answer: Benefits: Standardization reduces cognitive load for teams (don't need to know Terraform/AWS deeply), faster onboarding (golden path), built-in security and compliance guardrails, economies of scale (one platform team serves hundreds of product teams), consistent observability, centralized security updates. Trade-offs: Platform teams become a bottleneck if not adequately resourced; the "paved road" may not fit edge cases (teams sometimes need escape hatches); abstraction can obscure real complexity (teams don't understand what's happening under the hood when things break); version upgrades (e.g., ECS runtime, K8s version) must be coordinated across all teams simultaneously; over-opinionation can stifle innovation. The key success factor is the platform team treating their internal teams as customers, measuring platform adoption and developer satisfaction (DORA metrics + developer NPS), and providing clear escape valves for teams with legitimate unusual requirements.

Scrum Roles

  • Sprint Backlog: Selected items for the sprint + plan for how to deliver them. Dev team owns it, updated daily

  • Definition of Done (DoD): Shared understanding of "done" — code complete + unit tests + code reviewed + CI passes + documentation + deployed to staging

Scrum Metrics

  • Velocity: Story points completed per sprint (used for capacity planning, not performance measurement)

Technical Practices

TDD (Test-Driven Development)

Red-Green-Refactor cycle:

  1. Red: Write a failing test for the new behavior (test doesn't pass — expected)
  2. Green: Write the minimum code to make the test pass (no gold-plating)
  3. Refactor: Improve code quality without breaking tests (clean up duplication, improve naming)
TDD is not about testing — it's about design. Tests drive the API design of your code. The result is code that is inherently testable, with high test coverage, and a fast test suite.

BDD (Behaviour-Driven Development)

BDD extends TDD with a business-readable test format using Gherkin syntax:

Feature: User account transfer
  As a CBA customer
  I want to transfer money between my accounts
  So that I can manage my finances

  Scenario: Successful transfer between own accounts
    Given I have a savings account with balance $1000
    And I have a checking account with balance $500
    When I transfer $200 from savings to checking
    Then my savings account should have balance $800
    And my checking account should have balance $700
    And I should see a transfer confirmation

  Scenario: Transfer with insufficient funds
    Given I have a savings account with balance $100
    When I transfer $200 from savings to checking
    Then the transfer should fail
    And I should see "Insufficient funds" error

SDLC Interview Q&A

Q1: Compare Scrum and Kanban. When would you choose one over the other? Intermediate

Answer: Scrum works best for feature development teams where work arrives in planned batches and you need regular stakeholder alignment (sprint reviews). The sprint cadence creates predictability and forces prioritization. Kanban works best for support/operations/maintenance work where demand is unpredictable and can't be batched into sprints. WIP limits in Kanban prevent multitasking and surface bottlenecks. The cumulative flow diagram is more useful than a burndown chart for continuous flow work. In practice, many teams use a hybrid ("Scrumban") — Scrum ceremonies for alignment with Kanban WIP limits to improve flow. Key question: can your work be planned in sprint-sized batches, or is it primarily reactive? At CBA, a payment platform team doing feature development fits Scrum; the incident response team fits Kanban.

Q2: What are DORA metrics and how have you used them to improve your team? Advanced

Answer: DORA metrics (Deployment Frequency, Lead Time, MTTR, Change Failure Rate) measure software delivery and operational performance. They're research-backed predictors of organizational performance. In a previous role, I used them diagnostically: our change failure rate was 25% — high for our targets. Root cause analysis showed insufficient integration testing in CI. We invested in expanding our test coverage and adding contract testing between services. Three months later, CFR dropped to 8% and deployment frequency increased because teams were more confident deploying. Lead time was also long (2 weeks) due to a slow Terraform apply step — we optimized the pipeline with targeted plan/apply on changed modules, dropping it to 2 days. The key is using DORA as a system diagnostic, not as performance targets for individual engineers.

Q3: How do you handle technical debt in a fast-moving product team? Advanced

Answer: Technical debt is unavoidable — the question is managing it intentionally. My approach: first, make it visible by tracking debt as first-class backlog items with business impact descriptions (not just "refactor X"). Second, use the Boy Scout Rule — any time someone touches a module, leave it better (rename confusing variables, add a missing test, extract a helper). Third, reserve 15-20% of sprint capacity explicitly for debt reduction — negotiate this with the PO upfront as an investment in sustained velocity, using the metaphor "if we don't change the oil, the engine seizes." Fourth, for large-scale debt, pitch it as an enabler: "Migrating from our monolith to the event-driven model will cut our lead time for new payment types from 3 months to 2 weeks." Data-driven framing converts debt from a "nice to have" to a business priority.

Q4: Explain TDD and its trade-offs. Do you practice it? Intermediate

Answer: TDD (Red-Green-Refactor) means writing a failing test before writing production code. Benefits: forces you to design the API before implementation (better interfaces), provides a safety net for refactoring, creates living documentation, high coverage by default, faster debugging (failures localized immediately). Trade-offs: upfront time investment (though studies show net-positive ROI over 3+ months), requires discipline, doesn't work well for exploratory/prototype code where the design is unknown, UI testing is hard to TDD (use BDD/E2E for that layer). My practice: I apply TDD strictly for business logic and service layer code, less strictly for glue code and infrastructure config. For complex algorithms or financial calculations (e.g., interest rate computation at CBA), TDD is non-negotiable — the test suite is the specification.

Q5: How do you manage a release in a continuous delivery pipeline? Advanced

Answer: With CD, every merge to main is a potential release — the pipeline validates and deploys automatically. Key practices: (1) Feature flags decouple deployment from release — code ships to prod but is hidden behind a flag, enabled for canary users first; (2) Trunk-based development — short-lived branches or direct commits to main, no long-running feature branches causing merge hell; (3) Deployment strategies — rolling deploys (gradual pod replacement), blue/green (instant traffic switch with instant rollback), canary (route 5% traffic to new version, monitor, then ramp up); (4) Pipeline gates — automated quality gates (test pass rate, coverage threshold, security scan clean) that must pass before promotion to next environment; (5) Automated rollback — if error rate spikes post-deploy, the pipeline auto-reverts. At CBA in DHP, this translates to promoting the same container image through swimlanes (dev → test → stg → prod) with automated validation at each gate.

Q6: What is DevSecOps and how do you implement it? Advanced

Answer: DevSecOps integrates security into every phase of development rather than a post-development gate. Implementation: at the IDE/coding level, tools like Snyk VS Code extension catch vulnerable dependencies and SAST issues in real-time. In CI, SAST (SonarQube, CodeQL), dependency scanning (OWASP Dependency Check), container image scanning (Trivy), IaC security scanning (Checkov), and secret detection (GitGuardian, truffleHog) run on every PR. In staging, DAST (OWASP ZAP, Burp Suite) and penetration testing. In production, runtime security monitoring (Falco for container anomalies), WAF rules, and SIEM integration for threat detection. Cultural shift: security team moves from blocker to enabler — they define policies as code, not review gates. Security champions within each team champion secure coding practices. At CBA, this is baked into the DHP pipeline — the platform enforces image scanning and IaC security as non-negotiable pipeline stages.

Q7: How do you ensure quality when working in a short sprint cycle? Intermediate

Answer: Quality in short cycles requires shifting left: don't write code then test — build quality in as you go. Practices: (1) Strong Definition of Done that includes unit tests, code review, and CI passing — not an afterthought; (2) Three amigos (PO/Dev/Tester) session before coding to align on acceptance criteria and edge cases; (3) BDD scenarios written before development begins; (4) Test pyramid discipline — many fast unit tests, fewer integration, minimal E2E; (5) Pair programming or mob programming for complex or high-risk stories; (6) No "testing sprint" or "hardening sprint" — a sign of insufficient quality discipline in development; (7) Automated regression suite that runs in <10 minutes. If quality requires a longer cycle, the solution is better practices, not longer sprints.

Q8: What is the difference between a user story and a task? How do you write good acceptance criteria? Easy

Answer: A user story is a vertical slice of value from the user's perspective: "As a [persona] I want [goal] so that [benefit]." It's the unit of sprint planning and reflects business value. A task is a technical work item within a story (e.g., "create DB migration," "write API endpoint," "update frontend") — horizontal technical slices. Good acceptance criteria (AC): use Given-When-Then (BDD) or bulleted conditions of satisfaction. Good AC is: testable (binary pass/fail), specific (not "works correctly"), complete (covers happy path + error cases), agreed upon (PO + team). Bad AC: "Should be fast" (not measurable). Good AC: "API response time must be <200ms at p95 under 100 concurrent users." Write AC before starting development — it's the contract that defines "done."

Q9: How do you handle scope creep during a sprint? Intermediate

Answer: The sprint goal is a commitment — mid-sprint scope additions break predictability and disrespect the team's planning. My approach: (1) Distinguish urgency from importance — true production-critical bugs get a separate track, not sprint injection; (2) Log new requests in the backlog for next sprint; (3) If something truly must come in, negotiate out an equivalent-sized item with the PO (keep sprint capacity constant); (4) Daily standup transparency — flag immediately if new work is being taken on; (5) Retrospective discussion if scope creep is chronic — often signals that POs don't trust the team's backlog capacity, or requirements aren't being clarified enough upfront. The Scrum Master's role is to protect the team's ability to meet the sprint goal — "Yes, that's important, it goes to the top of the next sprint backlog."

Q10: Explain the SAFe framework and when it is appropriate. Advanced

Answer: SAFe (Scaled Agile Framework) addresses the challenge of coordinating agile across many teams working on interconnected systems. Core concepts: Agile Release Trains (ARTs) — groups of 50-125 people aligned to a value stream; PI (Program Increment) Planning — quarterly face-to-face event where all teams plan together and identify dependencies; Epics → Features → Stories hierarchy. Use SAFe when: genuinely large-scale (50+ engineers), multiple teams must coordinate releases (shared platform, regulatory dependencies), enterprise governance requirements need to be met. Criticism: SAFe can become heavyweight bureaucracy that reintroduces waterfall at the program level. Success requires genuine executive commitment and proper Scrum practices at team level first. At CBA, a bank-wide digital transformation with regulatory dependencies on shared banking systems is a legitimate SAFe use case — independent startup-style teams are not.

Q11: What is the role of a Scrum Master vs. a Project Manager? Easy

Answer: A Project Manager is accountable for delivering a defined scope on time and within budget — they plan, track, report status, manage risks, and coordinate resources. Authority flows top-down. A Scrum Master is a servant-leader who coaches the team and organization on Scrum values, removes impediments to the team's self-organization, facilitates ceremonies, shields the team from distractions, and helps the organization adopt agile ways of working. A Scrum Master has no authority over the team or what gets built (that's the PO). The SM's success metric is the team's improved performance and self-sufficiency over time — a great SM works to make themselves redundant. In practice, conflating the two roles (PM/SM hybrid) usually produces poor outcomes — the authority dynamic undermines psychological safety needed for self-organization.

Q12: How do you measure team velocity and why should you be careful using it as a performance metric? Intermediate

Answer: Velocity = story points completed per sprint (based on agreed DoD). It's used for capacity planning: if a team averages 40 points/sprint, they can commit to ~40 points for next sprint. Dangers of misusing velocity: (1) Comparing velocity between teams is meaningless (teams define their own story point scales); (2) Optimizing for velocity by inflating story points ("point farming") — teams learn to estimate high to show "improvement"; (3) Using velocity as a performance score creates pressure that reduces quality and psychological safety; (4) Velocity fluctuates legitimately (holidays, incidents, onboarding new members, refactoring sprints). Use velocity for planning (what can we take on?), not evaluation (how hard is this team working?). Better team health metrics: sprint goal completion rate, deployment frequency, MTTR, team satisfaction scores.

Q13: What is Shape Up and how does it differ from Scrum? Advanced

Answer: Shape Up (Basecamp's methodology) uses 6-week cycles with a "betting table" instead of a backlog. Before a cycle, senior staff "shape" raw ideas into fully designed pitches that specify the appetite (max time to spend), solution, risks, and rabbit holes. The betting table reviews pitches and bets on which to build in the next cycle. During the 6-week cycle, cross-functional teams (designer + 1-2 engineers) work autonomously without daily standups or sprint reviews. At 6 weeks, unfinished work is "cut" (no carry-over) — this creates accountability. A 2-week "cool-down" follows for bugs and exploration. Key differences from Scrum: no product backlog (old ideas die; if important they get re-pitched), no velocity tracking, 6-week cycles vs 2-week sprints, teams decide how to implement (no task breakdown by PO). Works well for stable product teams with experienced engineers; less suited for large enterprises needing coordination.

Q14: How does continuous integration differ from continuous delivery and continuous deployment? Intermediate

Answer: Continuous Integration (CI): Developers merge code to a shared branch multiple times per day; every merge triggers automated build and test — catches integration issues quickly. Continuous Delivery (CD): Extends CI — after passing tests, the artifact is automatically deployed to staging/pre-prod environments and is always in a releasable state. Deployment to production requires a manual trigger/approval. Continuous Deployment: Extends CD further — every passing build is automatically deployed to production without human intervention. Requires high confidence in the test suite, feature flags for risk management, and good rollback capabilities. At CBA with DHP, most teams practice Continuous Delivery (automatic deployment to lower swimlanes, manual approval gate to prod) rather than full Continuous Deployment, due to regulatory and compliance requirements for production changes.

Q15: Describe a time when you improved a team's SDLC process. Advanced

Answer (STAR format): Situation: Our team was shipping features but with high bug rates in production — about 30% of deployments required hotfixes. Deploys were infrequent (monthly) because they were "events" that required days of manual regression. Task: As tech lead, I identified this as a systemic process issue, not individual failures. Action: I ran a process retrospective — root causes: no automated integration tests (unit tests only), long-lived feature branches causing huge merge conflicts, no staging environment. I proposed: (1) automated API integration test suite (2-week investment), (2) trunk-based development with feature flags, (3) a staging swimlane in DHP. I framed it to the PO as "reducing our maintenance overhead by 40% based on current hotfix rates." Got buy-in for a "quality sprint." Result: Within 2 months: change failure rate dropped from 30% to 8%, deploy frequency increased from monthly to weekly (then daily). The team's confidence in deploying drove more frequent, smaller releases.
