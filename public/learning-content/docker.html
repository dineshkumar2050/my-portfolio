VM vs Container

Virtual Machines virtualise the entire hardware stack including the OS kernel, while containers share the host OS kernel and isolate only the user-space process.

Key Linux primitives behind containers:
  • Namespaces — isolate PID, network, mount, UTS, IPC, user namespaces
  • cgroups — limit and account CPU, memory, I/O, network bandwidth
  • Union filesystem — overlay layers (OverlayFS) for efficient image storage

Components

  • Docker Client — CLI tool that sends REST API calls to the daemon
  • Docker Daemon (dockerd) — Long-running background service managing images, containers, networks, volumes
  • containerd — Industry-standard container runtime managing container lifecycle
  • runc — Low-level OCI-compliant runtime that actually creates containers (uses namespaces/cgroups)
  • Docker Registry — Stores and distributes images (Docker Hub, ECR, GCR, Nexus, Harbor)

Images & Union Filesystem

A Docker image is a read-only stack of layers. Each layer represents a filesystem delta. Layers are content-addressable (identified by SHA256 digest) and shared across images.

graph BT L0[Layer 0: scratch/base OS - Read Only] L1[Layer 1: apt install curl - Read Only] L2[Layer 2: COPY app/ - Read Only] L3[Layer 3: Container RW layer] L0 --> L1 --> L2 --> L3

When a container is started, Docker adds a thin read-write layer on top. Writes use Copy-on-Write (CoW): the file is copied from a lower layer to the RW layer before modification.

Dockerfile Instructions

# === Dockerfile Reference ===

# FROM — base image (required, must be first)
FROM ubuntu:22.04
FROM node:20-alpine AS builder   # named stage for multi-stage

# ARG — build-time variable (available ONLY during build)
ARG NODE_ENV=production
ARG APP_VERSION

# ENV — runtime environment variable (persists in container)
ENV NODE_ENV=production \
    PORT=3000

# LABEL — metadata (OCI annotations)
LABEL maintainer="team@example.com" \
      version="1.0"

# WORKDIR — sets working directory (creates if absent)
WORKDIR /app

# COPY — copies from build context into image
COPY package*.json ./
COPY --chown=node:node src/ ./src/
COPY --from=builder /app/dist ./dist   # from another stage

# ADD — like COPY but also: extracts tar archives, fetches URLs
# Prefer COPY unless you need tar extraction
ADD archive.tar.gz /app/
ADD https://example.com/file.txt /tmp/  # NOT recommended (no caching)

# RUN — executes command in a new layer (shell or exec form)
RUN apt-get update && apt-get install -y \
    curl \
    vim \
  && rm -rf /var/lib/apt/lists/*   # clean up in SAME layer!

# Exec form (preferred - no shell processing)
RUN ["apt-get", "update"]

# USER — sets the user/group for subsequent instructions
RUN groupadd -r appuser && useradd -r -g appuser appuser
USER appuser

# EXPOSE — documents the port (does NOT publish it)
EXPOSE 3000
EXPOSE 3000/udp

# VOLUME — creates a mount point (anonymous volume)
VOLUME ["/data", "/logs"]

# HEALTHCHECK — tells Docker how to test container health
HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

# CMD — default command to run (can be overridden at runtime)
# Only ONE CMD allowed; last one wins
CMD ["node", "server.js"]
CMD node server.js           # shell form (wraps in /bin/sh -c)

# ENTRYPOINT — container's main executable (harder to override)
ENTRYPOINT ["node"]
CMD ["server.js"]            # CMD becomes default argument to ENTRYPOINT
# docker run myapp other.js  -> runs: node other.js

Multi-Stage Builds

Multi-stage builds produce small final images by using intermediate stages for building/compiling while copying only necessary artifacts to the final image.

# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

# Stage 2: Test (optional)
FROM builder AS tester
RUN npm run test

# Stage 3: Production image (minimal)
FROM node:20-alpine AS production
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app

# Copy ONLY what's needed
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package.json .

USER appuser
EXPOSE 3000
HEALTHCHECK --interval=30s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "dist/server.js"]
# Build specific stage
docker build --target builder -t myapp:builder .
docker build --target production -t myapp:prod .

Result: Instead of a ~1.2GB Node.js dev image, production image can be ~80MB with Alpine.

Optimization Tips

  1. Use slim/alpine base images — node:20-alpine (~50MB) vs node:20 (~1GB)
  2. Minimize layers — Chain RUN commands with && to reduce layer count
  3. Clean up in same RUN — apt-get clean && rm -rf /var/lib/apt/lists/*
  4. Order layers by change frequency — Put frequently changing code last (leverage cache)
  5. Use multi-stage builds — Don't include build tools in production image
  6. Don't run as root — Create dedicated user
  7. Use .dockerignore — Exclude unnecessary files from build context
  8. Combine COPY + RUN — Copy only package.json first, install, then copy source
  9. Use specific image tags — Never use latest in production
  10. Use distroless — gcr.io/distroless/nodejs20-debian11 for smallest footprint
# Optimized layer caching pattern
FROM node:20-alpine
WORKDIR /app
# Dependencies change less often than source code
COPY package*.json ./
RUN npm ci --only=production
# Source code copied last (cache-friendly)
COPY . .
CMD ["node", "server.js"]

User-Defined Bridge (Recommended)

docker network create --driver bridge \
  --subnet 172.20.0.0/16 \
  --ip-range 172.20.240.0/20 \
  mynetwork

docker run -d --name web --network mynetwork nginx
docker run -d --name db --network mynetwork postgres

# Containers on user-defined networks can reach each other by NAME
# docker exec web curl http://db:5432  ← works! (DNS resolution)
# Default bridge network does NOT support container DNS

    depends_on:

        condition: service_started

      retries: 3

BuildKit Features

BuildKit is the modern build engine (default since Docker 23.0). Enable with DOCKER_BUILDKIT=1 for older versions.

# syntax=docker/dockerfile:1.6
FROM node:20-alpine

# Cache mount — persist cache between builds (huge speedup)
RUN --mount=type=cache,target=/root/.npm \
    npm ci

# Secret mount — access secrets during build WITHOUT embedding them
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) \
    npm install --legacy-peer-deps

# SSH forwarding — use host SSH keys during build (git clone private repos)
RUN --mount=type=ssh \
    git clone git@github.com:private/repo.git

# Bind mount — read files from context without copying
RUN --mount=type=bind,source=package.json,target=package.json \
    node -e "require('./package.json')"
# Build with secret
docker build \
  --secret id=npm_token,env=NPM_TOKEN \
  -t myapp .

# Build with SSH forwarding
docker build \
  --ssh default \
  -t myapp .

# Inline cache (push cache to registry)
docker build \
  --cache-from type=registry,ref=myregistry/myapp:cache \
  --cache-to type=registry,ref=myregistry/myapp:cache,mode=max \
  -t myregistry/myapp:latest .

# Build for multiple platforms
docker buildx create --use --name multiarch
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --push \
  -t myregistry/myapp:latest .

Interview Q&A

Q1: What is the difference between a Docker image and a container? Easy

An image is a read-only, immutable template containing the application code, runtime, libraries, and filesystem. It's like a class in OOP.

A container is a running (or stopped) instance of an image — a writable layer added on top. Like an object instantiated from a class.

Multiple containers can be started from the same image. Stopping/removing a container doesn't affect the image. Container writes (in the RW layer) are lost unless committed or stored in a volume.

Q2: What happens when you run "docker run nginx"? Easy
  1. Docker CLI sends request to Docker daemon (via REST API)
  2. Daemon checks if nginx:latest exists locally
  3. If not found, pulls from Docker Hub (registry)
  4. Daemon passes request to containerd
  5. containerd calls runc (OCI runtime)
  6. runc creates namespaces (PID, network, mount, UTS, IPC) and cgroups
  7. OverlayFS layers are assembled (read-only layers + RW layer)
  8. Container process starts
Q3: What is a multi-stage build and why would you use it? Easy

A multi-stage build uses multiple FROM statements in a single Dockerfile. Each FROM creates a new build stage. You can COPY --from=<stage> only the artifacts you need from previous stages.

Benefits:

  • Dramatically smaller production images (no build tools, compilers, dev dependencies)
  • Better security (smaller attack surface)
  • Single Dockerfile — no need for separate build scripts
  • Example: Go app compile image ~1GB → final binary image ~15MB
Q4: Difference between CMD and ENTRYPOINT? Easy

ENTRYPOINT sets the command that always runs when the container starts. It defines the container's purpose.

CMD provides default arguments. When used alone, it's the default command. When used with ENTRYPOINT, it provides default arguments to ENTRYPOINT.

At runtime: docker run myimage arg1 — if ENTRYPOINT is set, arg1 replaces CMD. If only CMD is set, arg1 replaces CMD entirely.

Use ENTRYPOINT for containers with a fixed purpose (e.g., always run nginx). Use CMD alone for flexible containers.

Q5: What is Docker layer caching and how does it work? Intermediate

Each Dockerfile instruction creates a layer. Docker caches layers and reuses them if:

  • The instruction hasn't changed
  • The base layer hash hasn't changed
  • For COPY/ADD: the file contents haven't changed

Cache is invalidated for a layer and ALL subsequent layers when any of these change. This is why you should:

  1. Put rarely-changing instructions early (base image, install system deps)
  2. Copy dependency files (package.json) before source code
  3. Copy source code last (changes most frequently)
Q6: What are Docker networking modes and when would you use each? Intermediate
  • bridge — Default. Containers get their own network namespace, communicate via virtual bridge. Use for most single-host scenarios.
  • host — No network isolation; container uses host's network stack. Use for maximum performance or when you need to directly bind host ports. Ports aren't mapped.
  • none — Complete isolation. Only loopback. Use for batch jobs that don't need network.
  • overlay — Multi-host networking for Docker Swarm. Uses VXLAN tunneling. Use for distributed services.
  • macvlan — Container gets its own MAC address and appears as a physical device. Use when integrating with existing network infrastructure that requires direct L2 access.

Key insight: User-defined bridge networks provide automatic DNS resolution between containers by name. Default bridge does NOT.

Q7: Difference between COPY and ADD in Dockerfile? Easy

COPY — Copies files/directories from build context to image. Transparent and predictable. Preferred.

ADD — Does everything COPY does, plus: automatically extracts local tar archives, and can fetch from URLs (though URL fetching is not recommended as it bypasses cache).

Best practice: Use COPY for regular file copying. Only use ADD when you specifically need tar auto-extraction. Never use ADD for URLs — use RUN wget/curl instead (better caching control).

Q8: What is Docker Compose and when is it not enough? Intermediate

Docker Compose is a tool for defining and running multi-container applications on a single host using a YAML file.

When it falls short:

  • Multi-host deployment (use Docker Swarm or Kubernetes)
  • Auto-healing in production (Kubernetes handles this better)
  • Fine-grained auto-scaling (HPA in K8s)
  • Complex traffic routing (Kubernetes Ingress + Service Mesh)
  • Enterprise-grade RBAC and policy management

Compose is excellent for local development, CI environments, and simple single-host deployments.

Q9: How do you reduce Docker image size? Intermediate
  1. Use Alpine or distroless base images
  2. Multi-stage builds — don't include build tools in final image
  3. Clean package manager caches in same RUN instruction
  4. Use .dockerignore to exclude unnecessary files
  5. Minimize the number of layers (chain RUN commands)
  6. Don't install debug tools in production
  7. Use specific minimal base — e.g., python:3.11-slim not python:3.11
  8. Remove temporary files in same layer they're created
Q10: What is the difference between a bind mount, named volume, and tmpfs? Intermediate

Bind mount: Maps a specific host directory/file into the container. Host controls the path. Data persists on host after container removal. Great for development (live code reloading).

Named volume: Docker manages the storage location (typically /var/lib/docker/volumes). Portable, easier to backup, works with volume drivers. Preferred for databases and production.

tmpfs: Stored in host memory only. Never written to disk. Ideal for sensitive data (secrets, session tokens) that shouldn't persist. Lost on container stop.

Q11: What are Docker namespaces and cgroups? Advanced

Namespaces provide isolation — each container gets its own view of the system:

  • PID — Container process tree isolation (PID 1 in container)
  • Network — Separate network interfaces, IP addresses, routing
  • Mount — Separate filesystem mount tree
  • UTS — Separate hostname and domain name
  • IPC — Separate inter-process communication (message queues, semaphores)
  • User — Map host UIDs to container UIDs (rootless containers)

cgroups (Control Groups) provide resource limits and accounting:

  • CPU: --cpus, --cpu-shares
  • Memory: --memory, --memory-swap
  • Block I/O: device read/write rate limits
  • Network: bandwidth limits
Q12: What is BuildKit and what advantages does it provide? Advanced
  • Parallel stage execution — Independent build stages run concurrently
  • Better caching — More granular cache, --mount=type=cache persists caches between builds
  • Secret mounts — Pass secrets during build without embedding in layers
  • SSH forwarding — Use host SSH keys without exposing private keys
  • Multi-platform builds — Build for multiple architectures with buildx
  • Garbage collection — Configurable build cache pruning
  • Inline cache — Export/import cache from/to registry
  • SBOM and provenance — Generate software bill of materials
Q13: How would you handle secrets in Docker? Advanced

Wrong approaches:

  • Hardcoding in Dockerfile (visible in image history)
  • Passing via ENV (visible in image metadata)
  • COPY-ing secret files into image

Correct approaches:

  • Runtime environment variables — Pass via -e or --env-file, or inject via orchestration (Kubernetes Secrets, AWS SSM)
  • Docker Secrets (Swarm) — Secrets stored in Swarm's distributed Raft log, mounted at /run/secrets/
  • BuildKit secret mounts — --mount=type=secret for build-time secrets (not embedded in layers)
  • Volume-mounted secrets — Vault agent sidecar writes secrets to shared volume
  • External secret managers — HashiCorp Vault, AWS Secrets Manager, K8s Sealed Secrets
Q14: What is Docker Content Trust and why is it important? Advanced

Docker Content Trust (DCT) uses Notary to provide cryptographic signing and verification of image tags. When enabled (DOCKER_CONTENT_TRUST=1), Docker only pulls/runs signed images.

Why important:

  • Prevents pulling tampered or malicious images
  • Provides supply chain security
  • Guarantees image integrity and publisher identity
  • Modern alternative: Sigstore/Cosign (docker scout integrates with it)
Q15: What is the Docker overlay filesystem and how does Copy-on-Write work? Advanced

OverlayFS (overlay2 storage driver) presents a unified view of multiple directories:

  • lowerdir — Read-only image layers (stacked)
  • upperdir — Read-write container layer
  • workdir — Temporary work area for OverlayFS
  • merged — The unified view presented to the container

Copy-on-Write: When a container modifies a file that exists in a lower (read-only) layer:

  1. The file is copied from the lower layer to the upper (RW) layer
  2. The modification is applied to the copy in the upper layer
  3. The upper layer file shadows the lower layer file

This means the first write to a large file is slow (copy overhead), but subsequent writes are fast. Small containers don't affect large shared base layers.

Q17: What is a distroless image? Advanced

Distroless images (from Google) contain only the application runtime and its dependencies — no shell, no package manager, no utilities. They use a minimal layer derived from Debian/Ubuntu but strip everything non-essential.

Benefits: Smaller size, dramatically reduced attack surface, no shell means attackers can't easily explore the container.

Drawback: Harder to debug (no shell). Use debug variants for debugging: gcr.io/distroless/java17-debian11:debug

FROM gcr.io/distroless/nodejs20-debian11
COPY --from=builder /app/dist /app
CMD ["/app/server.js"]

Q20: How do you optimize Docker build times in CI/CD? Advanced
  • Registry-based caching: --cache-from type=registry with BuildKit
  • Cache mounts: --mount=type=cache for npm, Maven, pip caches
  • Layer ordering: Dependencies before source code

docker buildx build \

Q21: What is the difference between docker stop and docker kill? Easy

docker stop: Sends SIGTERM to the main process, waits for a grace period (default 10s), then sends SIGKILL. This allows graceful shutdown.

docker kill: Sends SIGKILL immediately (or a specified signal with -s). No grace period.

Always prefer docker stop for graceful shutdown. Use docker kill only when a container is unresponsive. You can customize the signal: docker kill -s SIGUSR1 mycontainer

Q22: How does Docker handle IPv6 and network isolation? Advanced

Docker's network isolation uses Linux network namespaces. Each container gets its own network namespace with its own interfaces, routing table, and iptables rules.

IPv6: Disabled by default. Enable in daemon.json: "ipv6": true, "fixed-cidr-v6": "2001:db8:1::/64"

Inter-container traffic (ICC): Controlled by --icc=false in daemon config — prevents containers on the same bridge from communicating unless explicitly linked.

iptables: Docker manages iptables rules automatically. Use --iptables=false if you manage iptables yourself.

Q23: What is a health check in Docker and how does it affect container scheduling? Intermediate

A HEALTHCHECK instruction defines how Docker tests if a container is working correctly. States: starting → healthy → unhealthy.

In Docker Compose: depends_on with condition: service_healthy waits for healthy status before starting dependent services.

In Docker Swarm: Swarm replaces unhealthy containers automatically.

In Kubernetes: K8s has its own probes (liveness/readiness/startup) — Docker HEALTHCHECK is not used.

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/actuator/health || exit 1
