API Gateway, REST, GraphQL & gRPC

What Is an API Gateway?

An API Gateway is a single entry point for all client requests to backend services. It acts as a reverse proxy, routing requests to the appropriate services while handling cross-cutting concerns centrally.

2. Rate Limiting

# Kong rate limiting plugin
plugins:
  - name: rate-limiting
    config:
      minute: 100        # 100 requests per minute per consumer
      hour: 2000         # 2000 per hour
      day: 10000         # 10000 per day
      policy: redis      # shared across multiple gateway instances
      limit_by: consumer # or ip, credential, service
      hide_client_headers: false
      # Response headers added: X-RateLimit-Limit-Minute, X-RateLimit-Remaining-Minute

3. SSL Termination

The gateway handles HTTPS from clients and communicates with backend services over HTTP (or mTLS for zero-trust). Offloads TLS processing from application servers.

4. Request/Response Transformation

# Kong request transformer
plugins:
  - name: request-transformer
    config:
      add:
        headers:
          - "X-Internal-Service:true"
          - "X-Gateway-Version:2.0"
      remove:
        headers:
          - "Authorization"   # strip before forwarding to internal service
      rename:
        querystring:
          - "page_num:page"   # rename query param

5. Request Aggregation

The gateway (or BFF) can aggregate multiple downstream calls into a single API response, reducing client chattiness.

// AWS API Gateway Lambda integration for aggregation
exports.handler = async (event) => {
  const orderId = event.pathParameters.orderId;

  // Parallel calls to internal services
  const [order, customer, shipment] = await Promise.all([
    fetch(`http://order-service/orders/${orderId}`).then(r => r.json()),
    fetch(`http://customer-service/customers/${order?.customerId}`).then(r => r.json()),
    fetch(`http://shipping-service/shipments/${orderId}`).then(r => r.json())
  ]);

  return {
    statusCode: 200,
    body: JSON.stringify({ order, customer, shipment })
  };
};

Backend for Frontend (BFF) Pattern

Instead of one generic API gateway, create a dedicated backend API per client type. Each BFF is a thin layer that aggregates, filters, and shapes data specifically for its client.

graph LR subgraph Clients MOB[iOS / Android] WEB[Web SPA] THIRD[Third-Party API] end subgraph BFFs MB[Mobile BFF\nNode.js\nAggregates, compresses] WB[Web BFF\nNode.js\nRich data, SSR support] PB[Partner BFF\nJava\nStrict auth, limited endpoints] end subgraph Services US[User Service] OS[Order Service] PS[Product Service] INV[Inventory] end MOB --> MB WEB --> WB THIRD --> PB MB --> US MB --> OS WB --> US WB --> OS WB --> PS PB --> OS PB --> INV

When to Use BFF

  • Different clients have significantly different data requirements
  • Mobile must minimize payload size and number of requests
  • Different teams own different client frontends
  • Different security requirements per client (public API vs internal web app)

REST Design Best Practices

RESTful URL Conventions

## Collections and Resources
GET    /api/v1/users              # List users (collection)
POST   /api/v1/users              # Create user
GET    /api/v1/users/{id}         # Get user by ID
PUT    /api/v1/users/{id}         # Full update (replace)
PATCH  /api/v1/users/{id}         # Partial update
DELETE /api/v1/users/{id}         # Delete user

GET    /api/v1/users/{userId}/orders         # Orders for a user
POST   /api/v1/users/{userId}/orders         # Create order for user

// Spring Boot global exception handler
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex, HttpServletRequest req) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST, "The request body contains invalid fields.");
        pd.setType(URI.create("https://api.example.com/errors/validation-error"));
        pd.setTitle("Validation Error");
        pd.setProperty("traceId", MDC.get("traceId"));
        pd.setProperty("timestamp", Instant.now());

        List<FieldError> errors = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> new FieldError(e.getField(), e.getCode(), e.getDefaultMessage(), e.getRejectedValue()))
            .collect(Collectors.toList());
        pd.setProperty("errors", errors);

        return pd;
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://api.example.com/errors/not-found"));
        pd.setProperty("traceId", MDC.get("traceId"));
        return pd;
    }
}

N+1 Problem & DataLoader

// N+1 Problem: fetching orders for users
// If 10 users each have orders, this fires 10+1 DB queries!
const resolvers = {
  Query: {
    users: () => db.query('SELECT * FROM users LIMIT 10'), // 1 query
  },
  User: {
    orders: (user) => db.query('SELECT * FROM orders WHERE user_id = ?', [user.id])
    // Called 10 times = 10 queries! Total: 11 queries
  }
};

// SOLUTION: DataLoader batches and caches
const DataLoader = require('dataloader');

const ordersByUserLoader = new DataLoader(async (userIds) => {
  // Called ONCE with all 10 userIds batched!
  const orders = await db.query(
    'SELECT * FROM orders WHERE user_id IN (?)',
    [userIds]
  );
  // Group by userId and return in same order as userIds
  const orderMap = orders.reduce((map, order) => {
    if (!map[order.userId]) map[order.userId] = [];
    map[order.userId].push(order);
    return map;
  }, {});
  return userIds.map(id => orderMap[id] || []);
});

const resolvers = {
  User: {
    orders: (user) => ordersByUserLoader.load(user.id) // batched!
    // 10 calls to .load() → 1 DB query
  }
};

gRPC Java Implementation

// Server implementation
@GrpcService
public class PaymentGrpcService extends PaymentServiceGrpc.PaymentServiceImplBase {

    @Override
    public void processPayment(PaymentRequest request, StreamObserver<PaymentResponse> responseObserver) {
        try {
            PaymentResult result = paymentService.process(
                request.getOrderId(),
                request.getAmount(),
                request.getCurrency()
            );

            PaymentResponse response = PaymentResponse.newBuilder()
                .setTransactionId(result.getTransactionId())
                .setStatus(PaymentStatus.PAYMENT_STATUS_SUCCESS)
                .setProcessedAt(Timestamps.fromMillis(System.currentTimeMillis()))
                .build();

            responseObserver.onNext(response);
            responseObserver.onCompleted();

        } catch (PaymentException e) {
            responseObserver.onError(
                Status.FAILED_PRECONDITION
                    .withDescription(e.getMessage())
                    .asRuntimeException()
            );
        }
    }

    // Server streaming: status updates
    @Override
    public void getPaymentStatus(PaymentStatusRequest request,
                                  StreamObserver<PaymentStatusUpdate> responseObserver) {
        // Stream multiple updates to client
        paymentStatusSubscriber.subscribe(request.getTransactionId(), update -> {
            responseObserver.onNext(PaymentStatusUpdate.newBuilder()
                .setStatus(update.getStatus())
                .setTimestamp(Timestamps.fromMillis(update.getTime()))
                .build());

            if (update.isFinal()) responseObserver.onCompleted();
        });
    }
}

OAuth 2.0 Flows

Authorization Code Flow (with PKCE)

For web and native apps where users grant access. PKCE (Proof Key for Code Exchange) prevents authorization code interception.

sequenceDiagram participant User participant Client as Browser/App participant AuthServer as Auth Server participant API as Resource Server Client->>Client: Generate code_verifier + code_challenge Client->>AuthServer: GET /authorize?response_type=code&client_id=...&code_challenge=...&redirect_uri=... AuthServer->>User: Show login/consent screen User->>AuthServer: Authenticate + grant consent AuthServer->>Client: Redirect to redirect_uri?code=AUTH_CODE Client->>AuthServer: POST /token\n{code, code_verifier, client_id} AuthServer->>AuthServer: Verify code_verifier matches code_challenge AuthServer-->>Client: {access_token, refresh_token, id_token} Client->>API: GET /resource\nAuthorization: Bearer ACCESS_TOKEN API->>API: Validate JWT / introspect token API-->>Client: Protected resource

Client Credentials Flow

For machine-to-machine (service-to-service) authentication. No user involved.

// Service requesting a token for M2M communication
@Service
public class TokenService {
    private final WebClient authClient;
    private volatile String cachedToken;
    private volatile Instant tokenExpiry;

    public String getServiceToken() {
        if (cachedToken != null && Instant.now().isBefore(tokenExpiry.minusSeconds(60))) {
            return cachedToken; // Return cached token (with 60s buffer)
        }
        return refreshToken();
    }

    private String refreshToken() {
        TokenResponse response = authClient.post()
            .uri("/oauth2/token")
            .contentType(MediaType.APPLICATION_FORM_URLENCODED)
            .bodyValue(Map.of(
                "grant_type", "client_credentials",
                "client_id", clientId,
                "client_secret", clientSecret,
                "scope", "payment:write inventory:read"
            ))
            .retrieve()
            .bodyToMono(TokenResponse.class)
            .block();

        this.cachedToken = response.getAccessToken();
        this.tokenExpiry = Instant.now().plusSeconds(response.getExpiresIn());
        return cachedToken;
    }
}

JWT Deep Dive

JWT Structure

JWT = Base64URL(Header) . Base64URL(Payload) . Base64URL(Signature)

// Header
{
  "alg": "RS256",   // RSA-SHA256 (asymmetric — recommended over HS256)
  "typ": "JWT",
  "kid": "key-id-2025" // key ID for rotation
}

// Payload (Claims)
{
  // Registered claims
  "iss": "https://auth.example.com",    // issuer
  "sub": "user-id-123",                 // subject (user ID)
  "aud": ["api.example.com"],           // audience (intended recipient)
  "exp": 1756000000,                    // expiration (Unix timestamp)
  "iat": 1755996400,                    // issued at
  "jti": "unique-token-id",             // JWT ID (for revocation tracking)

  // Custom claims
  "email": "alice@example.com",
  "roles": ["user", "admin"],
  "org_id": "org-456",
  "scope": "read:orders write:orders"
}

JWT Validation Checklist

@Component
public class JwtValidator {

    public Claims validate(String token) {
        try {
            return Jwts.parserBuilder()
                // 1. Verify signature using public key (RS256)
                .setSigningKeyResolver(keyResolver) // handles key rotation via kid

                // 2. Verify issuer
                .requireIssuer("https://auth.example.com")

                // 3. Verify audience
                .requireAudience("api.example.com")

                .build()
                .parseClaimsJws(token)
                .getBody();

            // Library also checks:
            // 4. exp (not expired)
            // 5. iat (not in future)
            // 6. nbf (not before, if present)

        } catch (ExpiredJwtException e) {
            throw new TokenExpiredException("Token expired at: " + e.getClaims().getExpiration());
        } catch (JwtException e) {
            throw new InvalidTokenException("Invalid token: " + e.getMessage());
        }
    }

    // Refresh token flow
    public TokenPair refresh(String refreshToken) {
        // Validate refresh token (longer-lived, stored in DB)
        RefreshTokenEntity stored = refreshTokenRepo.findByToken(refreshToken)
            .orElseThrow(() -> new InvalidTokenException("Unknown refresh token"));

        if (stored.isRevoked()) throw new InvalidTokenException("Token revoked");
        if (stored.getExpiry().isBefore(Instant.now())) throw new TokenExpiredException();

        // Rotate refresh token (one-time use)
        refreshTokenRepo.revoke(refreshToken);
        String newRefreshToken = generateRefreshToken(stored.getUserId());

        return new TokenPair(
            generateAccessToken(stored.getUserId()), // short-lived (15min)
            newRefreshToken // long-lived (7 days), stored in HttpOnly cookie
        );
    }
}

// Token Bucket implementation with Redis
@Service
public class TokenBucketRateLimiter {
    private final RedisScript<Long> rateLimitScript;

    // Lua script for atomic token bucket check in Redis
    private static final String SCRIPT = """
        local key = KEYS[1]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])
        local now = tonumber(ARGV[3])
        local tokens_requested = tonumber(ARGV[4])

        local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
        local tokens = tonumber(bucket[1]) or capacity
        local last_refill = tonumber(bucket[2]) or now

        -- Refill tokens based on elapsed time
        local elapsed = now - last_refill
        tokens = math.min(capacity, tokens + elapsed * refill_rate)

        if tokens >= tokens_requested then
            tokens = tokens - tokens_requested
            redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
            redis.call('EXPIRE', key, 3600)
            return 1  -- allowed
        else
            return 0  -- rejected
        end
        """;

    public boolean isAllowed(String clientId, int tokensRequested) {
        Long result = redisTemplate.execute(rateLimitScript,
            List.of("ratelimit:" + clientId),
            String.valueOf(100),  // capacity: 100 tokens
            String.valueOf(10),   // refill rate: 10 tokens/second
            String.valueOf(System.currentTimeMillis() / 1000),
            String.valueOf(tokensRequested)
        );
        return Long.valueOf(1).equals(result);
    }
}

Webhook Design Patterns

Webhooks are HTTP callbacks — the server calls YOUR endpoint when something happens. Inverse of polling.

// Webhook delivery with retry
@Service
public class WebhookDeliveryService {

    @Async
    @Retryable(maxAttempts = 5, backoff = @Backoff(delay = 1000, multiplier = 2, maxDelay = 30000))
    public void deliver(WebhookEndpoint endpoint, WebhookEvent event) {
        String payload = objectMapper.writeValueAsString(event);
        String signature = signPayload(payload, endpoint.getSecret());

        ResponseEntity<Void> response = restTemplate.exchange(
            RequestEntity.post(endpoint.getUrl())
                .header("Content-Type", "application/json")
                .header("X-Webhook-Signature", signature) // HMAC-SHA256
                .header("X-Event-Type", event.getType())
                .header("X-Delivery-ID", UUID.randomUUID().toString())
                .header("X-Timestamp", String.valueOf(Instant.now().getEpochSecond()))
                .body(payload),
            Void.class
        );

        if (!response.getStatusCode().is2xxSuccessful()) {
            throw new WebhookDeliveryException("Webhook returned: " + response.getStatusCode());
        }
    }

    // Receiver-side: verify signature
    private String signPayload(String payload, String secret) {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret.getBytes(), "HmacSHA256"));
        return "sha256=" + Hex.encode(mac.doFinal(payload.getBytes()));
    }
}

// Receiver validates signature
@PostMapping("/webhooks/orders")
public ResponseEntity<Void> handleWebhook(
        @RequestBody String payload,
        @RequestHeader("X-Webhook-Signature") String signature,
        @RequestHeader("X-Timestamp") long timestamp) {

    // 1. Prevent replay attacks — reject if too old
    if (Math.abs(Instant.now().getEpochSecond() - timestamp) > 300) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
    }

    // 2. Verify HMAC signature
    String expectedSig = "sha256=" + computeHmac(payload, webhookSecret);
    if (!MessageDigest.isEqual(signature.getBytes(), expectedSig.getBytes())) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
    }

    // 3. Process idempotently
    webhookProcessor.processAsync(payload);
    return ResponseEntity.ok().build(); // Return 200 immediately, process async
}

// API Key generation and hashing (never store plaintext)
@Service
public class ApiKeyService {

    public ApiKeyResult generateApiKey(String customerId) {
        // Generate cryptographically secure random key
        byte[] keyBytes = new byte[32];
        new SecureRandom().nextBytes(keyBytes);
        String rawKey = "sk_" + Base64.getUrlEncoder().withoutPadding().encodeToString(keyBytes);

        // Store only the hash
        String hashedKey = BCrypt.hashpw(rawKey, BCrypt.gensalt(12));
        apiKeyRepo.save(new ApiKey(customerId, hashedKey, Instant.now()));

        // Return raw key ONCE to customer — never seen again
        return new ApiKeyResult(rawKey, "Store this securely — it will not be shown again");
    }

    public Optional<Customer> validate(String providedKey) {
        // Brute-force: scan all keys and BCrypt check — use prefix to narrow
        String prefix = providedKey.substring(0, 7); // "sk_xxxx"
        List<ApiKey> candidates = apiKeyRepo.findByKeyPrefix(prefix);

        return candidates.stream()
            .filter(k -> BCrypt.checkpw(providedKey, k.getHashedKey()))
            .findFirst()
            .map(k -> customerRepo.findById(k.getCustomerId()));
    }
}

Interview Questions & Answers

Q1. What is an API Gateway and what problems does it solve? Easy

An API Gateway is a single entry point for all client requests to backend microservices. It solves several cross-cutting concerns:

  • Authentication/Authorization: Validates JWTs/API keys once, instead of in every service
  • Rate limiting: Prevents API abuse centrally
  • SSL termination: Handles HTTPS, services use HTTP internally
  • Routing: Maps external URL paths to internal service URLs
  • Observability: Central logging and tracing of all API traffic
  • Request aggregation: Combines multiple service calls into one client response
  • Protocol translation: REST → gRPC, HTTP → WebSocket

Without a gateway: Every service must implement its own auth, rate limiting, logging — massive duplication. Client must know about all service URLs and versions.

Q2. What is the difference between an API Gateway and a Load Balancer? Easy

Load Balancer: Distributes traffic across multiple instances of the SAME service. Works at L4 (TCP) or L7 (HTTP). Concerned with availability and capacity, not API management. Minimal intelligence — round-robin, least-connections, etc.

API Gateway: Routes traffic to DIFFERENT services based on path, headers, methods. Application-aware — understands APIs. Handles cross-cutting concerns (auth, rate limiting, transformation). Sits in front of multiple services.

Typical setup: API Gateway (routes to services) → Service Load Balancer (distributes across service instances) → Service instances. Both exist in the same architecture for different purposes.

Q3. Explain REST vs GraphQL — when would you choose each? Intermediate

Choose REST when:

  • Public API for external developers — familiar, well-documented, easy tooling
  • Simple CRUD operations
  • HTTP caching is important (GET requests are cacheable)
  • Team prefers convention over configuration
  • Existing infrastructure doesn't support GraphQL

Choose GraphQL when:

  • Multiple client types (mobile, web, third-party) with different data needs
  • Over-fetching is a real problem (mobile data costs)
  • Complex, deeply nested data that requires multiple REST calls
  • Frontend teams want autonomy to fetch exactly what they need
  • Rapidly evolving API where REST versioning would be cumbersome

Common hybrid: REST for public API, GraphQL for internal BFF that aggregates data for your own frontends.

Q4. What is the N+1 problem in GraphQL and how do you solve it? Intermediate

When resolving a list of items, each item's sub-resolver fires individually, causing N+1 DB queries (1 for the list, N for sub-fields).

Example: Query for 20 orders with customer names → 1 query for orders + 20 queries for each customer = 21 queries.

Solution: DataLoader

  1. DataLoader collects all .load(customerId) calls made during a single execution tick
  2. At the end of the tick, batches all IDs into a single DB query: WHERE id IN (1,2,...,20)
  3. Also caches: if the same ID is requested multiple times, only fetched once

Result: 21 individual resolver calls → 2 DB queries (orders + customers batch).

Tip: Create a DataLoader per request (not global) to avoid cross-request cache contamination.

Q5. How do you design for API versioning? What's the best strategy? Intermediate

No universally "best" strategy — depends on context:

URI versioning (/v1/, /v2/) is the most practical for public APIs:

  • Explicit and visible in browsers, logs, documentation
  • Easy to route in API gateways
  • Simple for clients to understand and switch

Versioning principles:

  • Never break backward compatibility within a version
  • Additive changes (new optional fields, new endpoints) don't need a new version
  • Breaking changes (rename/remove fields, change semantics): new version
  • Maintain old versions for a reasonable deprecation period (e.g., 6-12 months for external APIs)
  • Communicate deprecation via Deprecation and Sunset HTTP headers

Protobuf/gRPC: Use field numbers, mark deprecated fields with [deprecated=true]. Field numbers are the contract, not names — never reuse a field number.

Q6. Explain the OAuth 2.0 Authorization Code Flow with PKCE. Intermediate

PKCE (Proof Key for Code Exchange) makes the Authorization Code flow safe for public clients (SPAs, mobile apps) where a client secret can't be kept confidential.

PKCE prevents authorization code interception: Without PKCE, a malicious app could intercept the authorization code (via a custom URL scheme) and exchange it for tokens. With PKCE, the code is useless without the original code_verifier.

Flow:

  1. Client generates random code_verifier (43-128 chars)
  2. Client computes code_challenge = BASE64URL(SHA256(code_verifier))
  3. Auth request includes code_challenge (sent over HTTPS to auth server)
  4. After login, auth server returns authorization code
  5. Token request includes both the code AND code_verifier
  6. Auth server recomputes SHA256(code_verifier) and verifies it matches stored code_challenge
  7. Only the original client has the code_verifier → tokens issued

Best practices: Store access token in memory (not localStorage), refresh token in HttpOnly cookie. Short access token TTL (5-15 min), longer refresh token TTL (7-30 days). Rotate refresh tokens on use.

Q7. How do you validate and secure JWTs? What are common JWT vulnerabilities? Intermediate

Validation checklist:

  1. Verify signature (RS256 preferred over HS256 for microservices — uses public key, no shared secret)
  2. Verify iss (issuer) matches expected auth server
  3. Verify aud (audience) includes your service
  4. Verify exp is in the future (not expired)
  5. Verify iat is not in the future (clock skew tolerance: 60 seconds)
  6. Verify nbf (not before) if present

Common vulnerabilities:

  • alg:none attack: Attacker sets alg: "none" to bypass signature verification. Fix: reject tokens with alg: none, whitelist allowed algorithms explicitly.
  • RS256 → HS256 confusion: If server uses public key as HMAC secret, attacker can forge tokens signed with the public key. Fix: don't auto-detect algorithm from token header.
  • Missing audience validation: Token for Service A accepted by Service B. Fix: always validate aud claim.
  • Weak secrets (HS256): Short or dictionary-based secrets can be brute-forced. Fix: use RS256 or ES256 (asymmetric), or 256-bit random HS256 secrets.
  • Token theft (XSS): Token in localStorage readable by injected JavaScript. Fix: store in HttpOnly cookies or memory.
Q8. How do you implement rate limiting at scale across multiple gateway instances? Advanced

Single-instance rate limiting uses in-memory counters. With multiple gateway instances, each has its own counter — clients can bypass limits by routing through different instances.

Distributed rate limiting with Redis:

  • All gateway instances read/write counters from a central Redis cluster
  • Atomic operations via Lua scripts (Redis single-threaded, Lua runs atomically)
  • Redis replication for availability

Sliding window in Redis:

-- Sorted set: member=request_id, score=timestamp
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])  -- e.g., 60000ms
local limit = tonumber(ARGV[3])

-- Remove expired entries
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- Count current window
local count = redis.call('ZCARD', key)

if count < limit then
    redis.call('ZADD', key, now, now .. math.random())
    redis.call('EXPIRE', key, window / 1000 + 1)
    return 1
end
return 0

Alternative: Redis INCR + EXPIRE (fixed window, simpler). Kong, AWS API GW, and most enterprise gateways support Redis-backed distributed rate limiting out of the box.

Q9. When would you use cursor-based pagination over offset pagination? Intermediate

Always use cursor-based pagination for:

  • Real-time feeds (Twitter timeline, social feeds) where new items are added constantly
  • Large datasets (millions of rows) — offset pagination is O(n) at the DB level
  • Any scenario where consistency matters (no duplicate/skipped items due to concurrent writes)

Cursor design: The cursor encodes the sort key(s) of the last item seen. For ORDER BY created_at DESC, id DESC, the cursor is Base64({createdAt, id}). Next page query: WHERE (created_at, id) < (cursor.createdAt, cursor.id).

Offset pagination is fine when:

  • Data is static/append-only and doesn't change between pages
  • Users need random access ("go to page 50")
  • Admin UIs with small datasets
  • Total count is needed (cursor-based makes counting hard)

Q11. How does gRPC handle backward compatibility as protobuf schemas evolve? Intermediate

Protobuf is designed for backward compatibility via field numbers:

  • Field numbers are the wire contract — names can change, but field numbers cannot be reused
  • Adding new fields: Always backward compatible if the field is optional/has a default. Old clients ignore unknown fields. New clients use defaults for missing fields.
  • Removing fields: Mark as reserved to prevent future reuse of that field number
  • Changing types: Dangerous — only compatible if wire types match (e.g., int32 and int64 are compatible; string and int are not)
  • Renaming fields: Safe (wire uses field number, not name)
  • Renaming RPC methods: Breaking change — clients use method names for routing
message PaymentRequest {
  string order_id = 1;
  double amount = 2;
  reserved 3, 4;           // Field 3 was "old_currency", 4 was "deprecated_field"
  reserved "old_currency", "deprecated_field"; // Prevent name reuse too
  string currency = 5;     // New field — backward compatible
  PaymentMethod method = 6;
}
Q12. How do you design an idempotent REST API? Advanced

HTTP methods have defined idempotency characteristics:

  • GET, HEAD, PUT, DELETE: Inherently idempotent (calling N times = calling once)
  • POST: Not idempotent by default — creates a new resource each time

Making POST idempotent with Idempotency-Key:

  1. Client generates a unique key (UUID) and sends it in the Idempotency-Key header
  2. Server checks if a response for this key is cached
  3. If yes: return cached response (don't re-execute)
  4. If no: process, store result with the key, return result

Key storage: Redis with TTL (24h typical). Key: idempotency:{client_id}:{idempotency_key}. Value: serialized response.

Stripe's implementation: Idempotency-Key is scoped per client (API key). Same key for different clients is treated independently. Conflicting requests (same key, different parameters) return 422.

Q13. What are the security risks of API Gateway and how do you mitigate them? Advanced

OWASP API Security Top 10 — Gateway-level mitigations:

  • Broken Object Level Authorization (BOLA/IDOR): Can't be fixed at gateway; must validate in each service. Gateway can enforce user ID in token matches request context.
  • Broken Authentication: Gateway validates JWT signature, expiry, issuer, audience. Block invalid tokens before reaching services.
  • Excessive Data Exposure: Response transformation — strip sensitive fields at gateway level.
  • Lack of Rate Limiting: Implement per-client rate limits at gateway.
  • Injection attacks: WAF (Web Application Firewall) at gateway detects SQLi, XSS, XXE, command injection patterns.
  • Improper Assets Management: API gateway enforces routing — only registered routes are accessible. Unknown paths return 404.
  • Security Misconfiguration: Disable debug endpoints in production, enforce HTTPS only.

Additional gateway security: mTLS for internal service communication, IP allowlisting for admin APIs, request size limits, SSL/TLS version enforcement (TLS 1.2+).

Q14. How do you implement GraphQL authorization? Advanced

GraphQL authorization is more complex than REST because a single query can fetch data from multiple types/resolvers.

Levels of authorization:

  • Operation-level: Is this user allowed to run this query/mutation at all? (Middleware/plugin before execution)
  • Field-level: Is this user allowed to see this specific field? (Per-resolver auth check)
  • Object-level: Is this user allowed to see this specific record? (After fetching, check ownership)
// Using graphql-shield for declarative authorization
const permissions = shield({
  Query: {
    users: isAdmin,              // Only admins can list all users
    user: isAuthenticated,       // Any authenticated user
  },
  Mutation: {
    deleteUser: isAdmin,
    updateUser: rule()(async (parent, { id }, ctx) => {
      // Can only update own profile unless admin
      return ctx.user.id === id || ctx.user.roles.includes('admin');
    }),
  },
  User: {
    email: rule()(async (parent, args, ctx) => {
      // Only see your own email or if admin
      return parent.id === ctx.user.id || ctx.user.roles.includes('admin');
    }),
    salary: isAdmin,  // Field-level: only admins see salary
  }
});

const server = new ApolloServer({
  schema: applyMiddleware(schema, permissions),
});
Q15. What is the difference between REST HATEOAS and regular REST? Is it practical? Advanced

HATEOAS (Hypermedia As The Engine Of Application State) is the highest level of REST maturity (Richardson Maturity Model Level 3). Responses include hypermedia links showing what actions are available.

// HATEOAS response
{
  "id": "order-123",
  "status": "CONFIRMED",
  "total": 99.99,
  "_links": {
    "self": { "href": "/orders/123" },
    "cancel": { "href": "/orders/123/cancel", "method": "POST" },
    "track": { "href": "/shipments/ship-456", "method": "GET" },
    "invoice": { "href": "/invoices/inv-789", "method": "GET" }
  }
}
// Client doesn't need to know business rules — server tells it what's possible
// If order is CANCELLED, cancel link disappears from response

Practical reality: HATEOAS is rarely implemented in practice:

  • Clients (especially mobile) typically ignore links and hardcode URLs
  • API versioning breaks link semantics
  • Significant server-side complexity to generate accurate links per state

Verdict: Understand it conceptually for interviews. In practice, most "REST APIs" are Level 2 (resource-oriented with HTTP verbs). HATEOAS adds value in very dynamic workflow-driven APIs where the set of available actions genuinely varies per state.

Q16. How would you design an API rate limiter for a multi-tenant SaaS product? Very Advanced

Requirements: Different limits per plan tier, per endpoint, per tenant, per user within tenant.

Design:

  1. Rate limit keys: Hierarchical — rl:tenant:{tenantId}:endpoint:{path}, rl:user:{userId}:endpoint:{path}
  2. Configuration store: Per-tenant limits in DB/cache: tenant_id → {plan: "enterprise", limits: {"/api/orders": 1000/min, "*": 5000/min}}
  3. Algorithm: Token bucket (allows bursts) stored in Redis, separate bucket per key
  4. Response headers: 
    X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1756000060
Retry-After: 30   # only when 429
  5. Tenant-level vs user-level: Tenant bucket (shared across all users in org) AND per-user bucket. Both must have tokens for request to pass.
  6. Soft vs hard limits: At 80% of limit, add warning header. At 100%, return 429. Enterprise tenants may get "overflow" to burst queue instead of hard reject.
  7. Observability: Track rate limit hits per tenant in InfluxDB/Prometheus for capacity planning and billing.
Q17. What are the trade-offs of spec-first vs code-first API development? Intermediate

Spec-First (Design-First):

  • Write OpenAPI/GraphQL SDL/Protobuf before any code
  • Frontend and backend agree on contract; can develop in parallel
  • Auto-generate server stubs, client SDKs, mocks, documentation
  • API design reviewed before implementation (cheaper to change a spec than code)
  • Challenge: Discipline to keep spec and implementation in sync; spec can drift

Code-First:

  • Write code with annotations (@GetMapping, @ApiOperation); generate spec from code
  • Spec always reflects implementation (can't drift)
  • Familiar workflow for backend developers
  • Challenge: API design is an afterthought; harder for contract-first development; frontend blocked until API is coded

Recommendation: Spec-first for any API with external consumers or multiple team collaboration. Code-first for internal APIs where teams are co-located and move fast. Use tools like Prism (spec-first mock server) to enable parallel development.

Q18. How do you handle API breaking changes for mobile apps that can't be forced to update? Very Advanced

Mobile apps are the hardest versioning challenge: old app versions remain in the wild for months/years (users who don't update), and you can't force them to upgrade.

Strategies:

  • Never make breaking changes within a version: Only additive changes (new optional fields). Clients ignore unknown fields (both REST and Protobuf).
  • Version your API and maintain old versions: /v1/ supported alongside /v2/. Use analytics to track which client versions still call /v1/. Sunset only when usage drops to near zero.
  • Feature flags with version detection: Gateway extracts app version from User-Agent or custom header; routes to version-specific logic or response transformer.
  • Transformation layer: API Gateway transforms /v2/ responses to /v1/ format for old clients — translation layer instead of maintaining full separate service.
  • Force update mechanism: For truly critical breaking changes, return 410 Gone with {"error": "CLIENT_UPDATE_REQUIRED", "updateUrl": "https://..."}. App detects and shows update prompt.

Proactive approach: Semantic versioning with a sunset policy (e.g., "v1 supported for 18 months after v2 GA"). Notify through in-app messages, developer portal, email.

Q19. What is the difference between synchronous and asynchronous API patterns? When to use which? Intermediate

Synchronous: Client waits for response. Simple request-response. Client thread/connection held open during processing.

Asynchronous: Client submits request, gets acknowledgment (202 Accepted), polls for result or receives callback (webhook).

Use Async API when:

  • Operation takes more than a few seconds (video processing, ML inference, report generation)
  • Operation involves multiple steps or approval workflows
  • You want to throttle work (accept requests faster than you can process them)
  • High reliability needed (queue survives downstream failures)

Q20. How do you design a zero-downtime API migration from REST to GraphQL? Very Advanced

A complete overnight migration is too risky. Use an incremental strategy:

  1. Run both in parallel: Deploy GraphQL endpoint alongside existing REST. Don't remove REST. Some clients can start using GraphQL immediately.
  2. GraphQL as a BFF layer: Initially, GraphQL resolvers call existing REST services internally. No new backend logic — GraphQL is a thin wrapper.
  3. Schema design: Design the GraphQL schema based on what clients need, NOT based on existing REST endpoints. Don't just map REST to GraphQL 1:1.
  4. Migrate clients incrementally: New features built in GraphQL. Existing REST features migrated one by one with client teams.
  5. Track REST usage: Monitor /v1/users call volume. When it approaches zero, deprecate with Sunset header, then remove.
  6. Feature flags: Toggle per-client between REST and GraphQL during rollout.

Timeline: Full migration for a large app typically takes 6-18 months. Don't force all teams to migrate at the same time — let them move at their own pace as long as REST endpoints are maintained.

Q21. What is the GraphQL vs REST vs gRPC decision framework for a new project? Advanced

Decision tree:

  1. Is this an internal service-to-service API in a polyglot microservices architecture? → gRPC (strong typing, performance, auto-generated clients)
  2. Is this a public API consumed by external developers you don't control? → REST (universally understood, excellent tooling)
  3. Are there multiple diverse clients (mobile, web, desktop, TV) with very different data needs? → GraphQL (client-defined queries, BFF elimination)
  4. Do you need real-time bidirectional streaming? → gRPC (4 streaming types) or WebSocket
  5. Is caching via HTTP infrastructure critical? → REST (GET requests are natively cacheable)
  6. Do you control all clients and need to optimize payload size? → gRPC (binary Protobuf, ~7x smaller than JSON)
  7. Default for most web APIs: → REST with OpenAPI spec

Real-world combination: REST for public API + GraphQL for internal BFF consumed by own frontends + gRPC for high-performance internal microservice communication. All three can coexist, each where it provides the most value.

Q22. How does an API Gateway handle circuit breaking differently from a service mesh? Very Advanced

API Gateway circuit breaking:

  • Handles north-south traffic (external clients → gateway → services)
  • Configured per route/service in gateway
  • When upstream service is unhealthy, gateway fails fast to external clients
  • Can serve cached responses or custom error pages during circuit open state
  • Kong: circuit-breaker plugin; AWS API GW: no native CB, use Lambda with Resilience4j

Service mesh circuit breaking (Istio DestinationRule):

  • Handles east-west traffic (service ↔ service)
  • Configured as infrastructure policy (DestinationRule), transparent to app code
  • More granular: can circuit-break per pod, not just per service
  • Combines with outlier detection (automatic ejection of unhealthy instances)
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: payment-circuit-breaker
spec:
  host: payment-service
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 50
        maxRequestsPerConnection: 1
    outlierDetection:
      consecutive5xxErrors: 5       # Eject after 5 consecutive errors
      interval: 30s
      baseEjectionTime: 30s         # Eject for 30s
      maxEjectionPercent: 50        # Eject max 50% of instances

Both are complementary and needed for a robust system.
