1. What is Temporal?

Temporal is an open-source durable execution platform. It ensures that your application code runs to completion even in the face of hardware failures, network outages, process crashes, or long periods of waiting. Rather than coordinating state through external databases or message queues, Temporal is the state machine — the entire execution history is stored in the Temporal Server and replayed on-demand.

Core promise: Write code as if failures do not exist. Temporal handles retries, timeouts, and state persistence transparently. A workflow function that sleeps for 30 days is just await workflow.sleep('30 days').

Key Properties

  • Durable: Workflow state survives process crashes; execution resumes from where it stopped.
  • Reliable: Activities are retried automatically with configurable back-off.
  • Scalable: Millions of concurrent workflows per namespace.
  • Observable: Full execution history — every event logged and queryable.
  • Developer-centric: Workflow logic is plain TypeScript/Go/Java/Python.

How Durable Execution Works

Every state transition in a workflow is persisted to an immutable event history in the Temporal server. When a worker crashes mid-workflow, a new worker picks up the task queue entry, downloads the history, and replays the workflow code deterministically to reconstruct in-memory state — then continues from the last durable checkpoint.

3. Core Concepts

Workflow

A durable function that orchestrates activities. It is deterministic — given the same event history it always produces the same result. The workflow function itself never performs I/O directly.

Activity

A function that performs side effects: HTTP calls, DB writes, file I/O, sending emails. Activities can fail and are retried by Temporal automatically. They run in a regular environment with no determinism constraints.

Worker

A process you run that polls a Task Queue, executes workflow and activity code, and reports completions back to the Temporal server. You control scaling workers independently.

Task Queue

A logical channel between the Temporal server and your workers. Workflows are started on a specific task queue; workers poll that queue. One queue can have many workers for horizontal scaling.

Namespace

An isolation boundary within a Temporal cluster. Workflows in different namespaces cannot directly communicate. Used for environment separation (dev/staging/prod) or multi-tenancy.

Workflow Execution

A single running instance of a workflow function, identified by workflowId (user-defined) and runId (system-assigned). The workflowId can be reused after completion.

Service Responsibilities

  • Frontend Service: Single entry point for all client API calls (gRPC + HTTP). Routes requests to appropriate internal services.
  • History Service: Owns the workflow execution state machine and event history. Sharded by workflowId. Durably persists every state change.
  • Matching Service: Manages task queues. Matches workflow/activity tasks to polling workers. Handles sticky execution for performance.
  • Worker Service: Internal Temporal workers that handle background tasks (archival, replication).

5. Determinism Rules

Critical: Workflow code MUST be deterministic. Temporal replays your workflow history to restore state — any non-deterministic operation will produce different results on replay, causing a non-determinism error and failing the workflow.

Date.now() / new Date()Different timestamp on replayworkflow.now()
setTimeout / setIntervalNot tracked in event historyworkflow.sleep(duration)
Direct HTTP/DB callsSide effects not persistedWrap in an Activity
Global mutable stateNot part of event historyUse workflow variables
process.env readsEnvironment may differ on replayPass as workflow input or activity param
External library with side effectsMay behave differentlyMove to Activity
Non-deterministic iteration (Map/Set without sort)Order may changeSort before iterating

Safe Workflow APIs (TypeScript)

import { workflow } from '@temporalio/workflow';

// Safe: deterministic time
const now: Date = workflow.now();

// Safe: deterministic sleep (persisted, survives restarts)
await workflow.sleep('30 days');
await workflow.sleep(1000 * 60 * 60 * 24); // ms also accepted

// Safe: deterministic UUID
const id: string = workflow.uuid4();

// Safe: wait for condition
await workflow.condition(() => someFlag === true, '1 hour'); // optional timeout

// Cancellation scope
const { CancellationScope } = workflow;
await CancellationScope.cancellable(async () => {
  await someActivity();
});

6. Sleep, Signals, Queries & Updates

Workflow Sleep

workflow.sleep() persists a timer in the Temporal server. The worker is free; no process needs to stay running. When the timer fires, any available worker picks up the task.

// Free billing reminder workflow
export async function billingReminderWorkflow(userId: string): Promise {
  await workflow.sleep('7 days');         // server-side timer, no process held
  await sendReminderActivity({ userId }); // resumes on any worker
  await workflow.sleep('30 days');
  await chargeCreditCardActivity({ userId });
}

Signals — Sending Data In

Signals are fire-and-forget messages sent to a running workflow. They are buffered until the workflow handles them. Defined with defineSignal, handled with workflow.setHandler.

// workflow.ts
import { defineSignal, setHandler, condition } from '@temporalio/workflow';

export const approveSignal = defineSignal<[{ approvedBy: string }]>('approve');
export const rejectSignal  = defineSignal<[{ reason: string }]>('reject');

export async function approvalWorkflow(requestId: string): Promise {
  let decision: 'approved' | 'rejected' | null = null;
  let meta: any = {};

  setHandler(approveSignal, ({ approvedBy }) => {
    decision = 'approved';
    meta = { approvedBy };
  });
  setHandler(rejectSignal, ({ reason }) => {
    decision = 'rejected';
    meta = { reason };
  });

  // Block until signal received OR 72-hour timeout
  const gotDecision = await condition(() => decision !== null, '72 hours');
  if (!gotDecision) return 'timeout';
  return `${decision} by ${meta.approvedBy ?? 'N/A'}`;
}

// client.ts
await client.workflow.getHandle(workflowId).signal(approveSignal, { approvedBy: 'manager1' });

Queries — Reading State

Queries are synchronous reads of workflow state. They do NOT advance the workflow and have no side effects. The response is returned directly from the worker holding the sticky execution cache.

// workflow.ts
import { defineQuery, setHandler } from '@temporalio/workflow';

export const getStatusQuery = defineQuery('getStatus');

export async function orderWorkflow(): Promise {
  let status = 'created';
  setHandler(getStatusQuery, () => status);

  status = 'processing';
  await processOrderActivity();
  status = 'shipped';
  await shipOrderActivity();
  status = 'delivered';
}

// client.ts
const status = await client.workflow.getHandle(workflowId).query(getStatusQuery);
console.log(status); // 'processing' | 'shipped' | 'delivered' ...

Updates (Temporal 1.21+)

Updates combine Signal (mutate) and Query (return value) — they modify workflow state and synchronously return a result to the caller. Updates can also be validated (rejected before applying).

import { defineUpdate, setHandler } from '@temporalio/workflow';

export const addItemUpdate = defineUpdate('addItem');

export async function cartWorkflow(): Promise {
  const items: string[] = [];
  setHandler(
    addItemUpdate,
    (item: string) => {
      items.push(item);
      return `Added: ${item}, total: ${items.length}`;
    },
    {
      validator: (item: string) => {
        if (!item || item.trim() === '') throw new Error('Item cannot be empty');
      }
    }
  );
  await workflow.condition(() => false); // run forever until cancelled
}

// client — returns the update result synchronously
const result = await handle.executeUpdate(addItemUpdate, { args: ['widget'] });
// result === 'Added: widget, total: 1'

7. Workflow Versioning with workflow.patched()

When you change workflow logic while executions are still running, replaying old history against new code causes non-determinism errors. workflow.patched() (formerly getVersion in other SDKs) provides a safe path.

import { patched, deprecatePatch } from '@temporalio/workflow';

// STEP 1: Introduce the patch — old workers take the else branch, new workers take the if branch
export async function myWorkflow(): Promise {
  if (patched('my-new-behaviour-v2')) {
    // New code path
    await newActivityV2();
  } else {
    // Old code path — kept for replay compatibility with running instances
    await oldActivityV1();
  }
  await finishActivity();
}

// STEP 2: Once all pre-patch executions have completed, mark patch as deprecated
// Old code path is removed; deprecatePatch() is a no-op that keeps the marker in history
export async function myWorkflowV3(): Promise {
  deprecatePatch('my-new-behaviour-v2'); // marker only, no branching
  await newActivityV2();
  await finishActivity();
}

// STEP 3: Eventually remove deprecatePatch() once all v2-patched executions are done
Best practice: Treat versioning as a 3-stage migration: (1) add patched(), (2) promote to deprecatePatch() after old runs drain, (3) remove entirely. Never delete workflow code while instances are still running.

8. Continue-As-New

Temporal stores the complete event history for a workflow execution. Very long-running or high-throughput workflows can accumulate hundreds of thousands of events, causing slow replay and large memory usage. continueAsNew starts a fresh execution with a clean history, passing current state as input.

import { continueAsNew, isCancellation } from '@temporalio/workflow';

interface PollerState { itemsProcessed: number; cursor: string }

export async function longPollerWorkflow(state: PollerState): Promise {
  for (let i = 0; i < 1000; i++) {
    const result = await pollForItemsActivity({ cursor: state.cursor });
    state.cursor = result.nextCursor;
    state.itemsProcessed += result.items.length;
  }

  // After 1000 iterations, reset history by continuing as new
  // Passes current state so no data is lost
  await continueAsNew(state);
}
When to use continueAsNew: If your workflow runs for months/years, or processes in a loop, call continueAsNew every ~1000–10000 iterations or when history size approaches 50k events.

Long-Running Activities & Heartbeat

Long-running activities (file uploads, ML model training, video encoding) must call activity.heartbeat() periodically. If the heartbeat isn't received within heartbeatTimeout, Temporal marks the activity as failed and schedules a retry — the new attempt can even pick up from the last checkpoint via activity.getHeartbeatDetails().

// activities.ts
import { Context } from '@temporalio/activity';

export async function uploadLargeFileActivity(params: {
  fileUrl: string;
  destination: string;
}): Promise {
  const ctx = Context.current();
  const chunks = await getFileChunks(params.fileUrl);

  // Retrieve last successful chunk from previous attempt (if any)
  const lastChunk: number = ctx.info.heartbeatDetails ?? 0;

  for (let i = lastChunk; i < chunks.length; i++) {
    // Check if workflow wants to cancel this activity
    ctx.cancellationSignal.throwIfAborted();

    await uploadChunk(chunks[i], params.destination);

    // Heartbeat with progress — saved in server for retry pickup
    ctx.heartbeat(i + 1); // last completed chunk index
  }
}

// In workflow, use heartbeatTimeout:
const { uploadLargeFileActivity } = proxyActivities({
  startToCloseTimeout: '2 hours',
  heartbeatTimeout: '30 seconds', // must heartbeat every 30s
});

Define Workflow

// src/workflows.ts
import { proxyActivities, defineSignal, setHandler,
         condition, sleep, defineQuery } from '@temporalio/workflow';
import type * as activities from './activities';

const { sendEmailActivity, getUserProfile } = proxyActivities({
  startToCloseTimeout: '30 seconds',
  retry: { maximumAttempts: 5, initialInterval: '2 seconds', backoffCoefficient: 2 },
});

export const pauseSignal   = defineSignal('pause');
export const resumeSignal  = defineSignal('resume');
export const statusQuery   = defineQuery('status');

export async function onboardingWorkflow(userId: string): Promise {
  let paused = false;
  let status = 'started';

  setHandler(pauseSignal,  () => { paused = true;  status = 'paused'; });
  setHandler(resumeSignal, () => { paused = false; status = 'running'; });
  setHandler(statusQuery,  () => status);

  // Step 1: Get user profile
  status = 'fetching-profile';
  const user = await getUserProfile(userId);

  // Step 2: Wait for pause/resume, proceed when unpaused
  await condition(() => !paused);

  // Step 3: Send welcome email
  status = 'sending-welcome';
  await sendEmailActivity({
    to: user.email,
    subject: 'Welcome!',
    body: `Hello ${user.name}, welcome aboard!`,
  });

  // Step 4: Wait 7 days and send follow-up
  status = 'waiting-7-days';
  await sleep('7 days');

  status = 'sending-followup';
  await sendEmailActivity({
    to: user.email,
    subject: 'How are you settling in?',
    body: `Hi ${user.name}, checking in after your first week!`,
  });

  status = 'completed';
}

Start Workflow from Client

// src/client.ts
import { Client, Connection } from '@temporalio/client';
import { onboardingWorkflow, pauseSignal, resumeSignal, statusQuery } from './workflows';

async function main() {
  const connection = await Connection.connect({ address: 'localhost:7233' });
  const client = new Client({ connection, namespace: 'default' });

  // Start a new workflow execution
  const handle = await client.workflow.start(onboardingWorkflow, {
    taskQueue: 'onboarding-queue',
    workflowId: `onboarding-${userId}`,  // idempotent — safe to call again
    args: [userId],
    // Optional workflow-level timeout
    workflowExecutionTimeout: '30 days',
  });

  console.log(`Started workflow: ${handle.workflowId}`);

  // Send signal
  await handle.signal(pauseSignal);
  await new Promise(r => setTimeout(r, 5000));
  await handle.signal(resumeSignal);

  // Query current status
  const status = await handle.query(statusQuery);
  console.log('Status:', status);

  // Wait for result (blocks until workflow completes)
  const result = await handle.result();
  console.log('Workflow finished:', result);
}

15. Q&A — 15 Questions

Q1. What is durable execution and why does Temporal achieve it? Easy

Durable execution means application code that runs to successful completion regardless of hardware or software failures. Temporal achieves this by persisting every state transition — workflow task completions, activity scheduling, timers, signals — as immutable events in its History Service backed by a database (Cassandra/Postgres). When a worker crashes, a new worker downloads the event history and replays the deterministic workflow code to reconstruct in-memory state exactly, then resumes from the last recorded checkpoint. The developer writes code as if failures don't exist; Temporal's infrastructure handles the durability.

Q2. Why must workflow code be deterministic, and what happens if it is not? Easy

Temporal reconstructs workflow state by replaying event history. Replaying means re-executing the workflow function from the top and comparing what the code "wants to do" with what the history says "already happened." If the code is non-deterministic (e.g., calls Math.random()), it may take a different branch on replay than the original execution, causing the commands it emits to mismatch the history. Temporal detects this as a non-determinism error and fails the workflow task with a DeterminsticError. The workflow is stuck and requires investigation. Always use Temporal's safe APIs: workflow.now(), workflow.sleep(), workflow.uuid4().

Q3. What is the difference between a Signal and a Query? Easy

Signal: Asynchronous, one-way message sent to a running workflow. It can modify workflow state (set flags, add items to a queue). The caller does not wait for a return value. Signals are buffered and processed in order.

Query: Synchronous read of current workflow state. Queries do NOT modify state, do NOT add events to history, and return data directly to the caller. They are served by the worker currently holding the workflow in its sticky cache. Used for dashboards, progress reporting, or reading derived state.

Update (Temporal 1.21+): Combines both — modifies state AND returns a value synchronously to the caller. Can also be validated and rejected before applying.

Q4. How does workflow.sleep() differ from a plain setTimeout? Easy

setTimeout is an in-memory OS timer — it is lost the moment the process restarts. It also creates a non-deterministic event from Temporal's perspective (not tracked in history).

workflow.sleep(duration) creates a durable timer event in the Temporal server. The worker is free to handle other work. If the worker restarts, the sleep simply continues counting down on the server. If the sleep has already elapsed when the worker resumes, the workflow immediately continues. A sleep of 30 days works exactly as expected even if your workers restart dozens of times during that period.

Q5. Describe the four activity timeout types and when to use each. Intermediate

scheduleToStart: Time from when Temporal enqueues the activity to when a worker picks it up. Detects overloaded or offline worker pools. Set this short (30s–2min) to fail fast when the task queue is backed up.

startToClose: Time a single execution attempt may take. Most commonly configured. Must be set; Temporal defaults to scheduleToClose if not explicitly set.

scheduleToClose: Overall budget for ALL attempts including retries. If retries keep failing beyond this duration, the activity fails permanently regardless of maximumAttempts.

heartbeatTimeout: For long-running activities. The activity must call Context.current().heartbeat() at least this frequently. Detects silent crashes mid-execution (e.g., hung HTTP calls, stuck upload loops). New attempts can pick up from last heartbeat details.

Q6. How do you safely update workflow code that has running executions? Intermediate

Use workflow.patched('patch-id') (TypeScript) / workflow.getVersion() (Go/Java). This is a 3-step migration:

  1. Deploy with patch: Wrap new code in if (patched('v2')) { newCode } else { oldCode }. Running old executions replay through the else branch; new executions use the if branch and write a marker event to history.
  2. Drain old executions: Wait until all pre-patch workflow runs have completed.
  3. Deprecate: Replace patched() with deprecatePatch('v2') and remove the old code. This records a deprecation marker for any still-running v2 executions. Eventually, remove deprecatePatch too once all executions have finished.

Never delete workflow code that may still be needed for replay — this will cause non-determinism errors on running instances.

Q7. What is Continue-As-New and when is it needed? Intermediate

Temporal stores every event in workflow history. Workflows running for months or looping thousands of times accumulate large histories, causing slow replay, high memory usage, and eventually hitting the hard server-side limit (~50k events default). continueAsNew atomically completes the current execution and starts a brand-new execution with a fresh (empty) history, passing the current state as input arguments. From the outside, it looks like one continuous workflow; internally it is a chain of executions. Best practice: call continueAsNew every ~1000–10000 iterations in polling loops, or proactively for any workflow intended to run indefinitely.

Q8. Compare Local Activities with regular Activities. Intermediate

Regular Activities are scheduled via the Temporal server — the server maintains a task queue, dispatches to any available worker, and tracks the full lifecycle in history. Each execution round-trips through the server, adding latency (~5–20ms) but providing strong durability and the ability to retry on a different worker.

Local Activities run in-process within the workflow worker itself. They bypass the server task queue, producing only a compressed marker event in history. Latency is sub-millisecond. Best for fast, CPU-bound operations (input validation, small transforms) that should complete in under a second. Drawbacks: no cross-worker retry, longer retries block the workflow task, and they don't support heartbeating — keep them short.

Q9. How would you implement a long-running ETL pipeline with Temporal that can resume mid-stream after a crash? Advanced

Design approach:

  1. Activity for each chunk: Process data in batches. Each batch is a separate activity — on crash, only the current batch retries.
  2. Heartbeat with progress cursor: Within the batch activity, call ctx.heartbeat(cursor) periodically. On retry, read ctx.info.heartbeatDetails to resume from the last committed cursor.
  3. Continue-As-New after N batches: To avoid history bloat, call continueAsNew({ offset: currentOffset }) after processing every 1000 batches, passing the current offset as workflow input.
  4. Signal for pause/resume: Use a signal handler with workflow.condition() to allow operators to pause the pipeline during business hours.
  5. Non-retryable errors: Schema validation errors should be in nonRetryableErrorTypes — no point retrying a malformed record; route to a dead-letter queue activity instead.

This design gives at-least-once delivery for each batch with the ability to resume from the last heartbeat checkpoint within a batch.

Q10. How does Temporal handle the Saga pattern for distributed transactions? Advanced

Temporal is an excellent fit for Sagas. You implement the saga orchestrator directly as a workflow:

  1. Call each microservice as an activity in sequence.
  2. Wrap the sequence in a try/catch. On failure, execute compensating activities (rollback) in reverse order.
  3. Use CancellationScope.nonCancellable() for compensating transactions so they are not cancelled even if the workflow is cancelled.
export async function orderSagaWorkflow(order: Order): Promise {
  let paymentId: string | null = null;
  let inventoryReserved = false;
  try {
    paymentId = await chargePaymentActivity(order);
    inventoryReserved = await reserveInventoryActivity(order);
    await shipOrderActivity(order);
  } catch (err) {
    await CancellationScope.nonCancellable(async () => {
      if (inventoryReserved) await releaseInventoryActivity(order);
      if (paymentId)         await refundPaymentActivity(paymentId);
    });
    throw err;
  }
}

Temporal handles retries on each activity automatically, and the compensations are themselves durable activities — no saga state machine in an external DB needed.

Q11. What strategies exist for scaling Temporal workers under high load? Advanced

Horizontal scaling: Run multiple worker process replicas — they all poll the same task queue. Temporal's Matching service distributes tasks across pollers. Add replicas via Kubernetes HPA or container orchestration.

Dedicated task queues: Separate activity workers from workflow workers. Separate high-priority tasks (payments) from low-priority (reports) onto different task queues with different worker pools.

Worker concurrency tuning: Increase maxConcurrentActivityTaskExecutions (default 100) and maxConcurrentWorkflowTaskExecutions (default 40) on each worker instance.

Sticky execution: Temporal keeps workflows on the same worker (sticky cache) to avoid re-downloading history on every task. Increase stickyScheduleToStartTimeout to reduce replay frequency when workers are stable.

Rate limiting: Use maxTaskQueueActivitiesPerSecond on the worker or Temporal Cloud namespace limits to prevent downstream overload during traffic spikes.

Q12. How do workflow IDs and run IDs interact, and what is the workflow ID conflict policy? Advanced

workflowId: User-defined, business-meaningful identifier (e.g., order-12345). Reusable across executions. At any point, at most one open (running) execution per workflowId exists within a namespace.

runId: System-assigned UUID for each individual execution run. A workflowId can have multiple runIds over time (each new execution gets a new runId).

ID Conflict Policies (on start):

  • ALLOW_DUPLICATE: Start a new run even if one completed before.
  • ALLOW_DUPLICATE_FAILED_ONLY: Only start new run if the last run failed.
  • REJECT_DUPLICATE: Fail the start request if any execution with this ID exists.
  • TERMINATE_IF_RUNNING: Terminate any running execution and start a new one.

Setting a meaningful workflowId with ALLOW_DUPLICATE_FAILED_ONLY is a common pattern to make workflow starts idempotent — safe to call from an at-least-once message consumer.

Q13. Explain how Temporal achieves exactly-once semantics for activities. Advanced

Temporal provides at-least-once execution semantics for activities by default (retries on failure). Achieving idempotence / effectively-once requires application-level design:

  1. Idempotency keys: Pass a stable idempotency key (e.g., workflowId + activityId + attempt) to downstream APIs that support it (Stripe, Braintree). The same charge call with the same key is a no-op.
  2. Database upserts: Use INSERT ... ON CONFLICT DO NOTHING or upsert semantics keyed on the operation ID.
  3. Check-then-act: In the activity, first check if the side effect already occurred; skip if yes. This is safe because activities are retried from scratch, not from mid-execution.

Note: Temporal guarantees that a successfully completed activity result is durably persisted and will NOT be re-executed on workflow replay. Retries only happen when an activity fails (throws an exception or times out).

Q14. How would you model a human-in-the-loop approval process with SLA enforcement? Very Advanced

Approach: Model the approval wait as a workflow.condition() with a timeout, combined with Signals for approve/reject.

export async function approvalWorkflow(request: ApprovalRequest): Promise {
  let decision: 'approved' | 'rejected' | null = null;
  let reviewer = '';

  setHandler(approveSignal, ({ by }) => { decision = 'approved'; reviewer = by; });
  setHandler(rejectSignal,  ({ by, reason }) => { decision = 'rejected'; reviewer = by; });

  // Send notification to approvers
  await notifyApproversActivity(request);

  const slaMs = request.slaHours * 60 * 60 * 1000;
  const approved = await condition(() => decision !== null, slaMs);

  if (!approved) {
    // SLA breached — escalate or auto-approve based on policy
    await escalateActivity(request);
    decision = request.defaultOnTimeout;
  }

  await auditLogActivity({ request, decision, reviewer, timestamp: workflow.now() });
  return { decision, reviewer };
}

SLA monitoring: Run a side workflow (or use a separate timer signal) that pings an escalation channel at 50%/80%/100% of SLA. Use Temporal's visibility API to query all open approval workflows approaching their SLA via ExecutionStatus='Running' AND StartTime < '...'.

Audit: The immutable event history is itself a full audit trail — every signal received, every state change timestamped. Export to your audit system via the archival feature.

Q15. How does Temporal's event sourcing model compare to traditional event sourcing (EventStoreDB) architectures? Very Advanced

Both use an immutable, append-only event log as the source of truth. Key similarities and differences:

Similarities: Immutable history, state reconstructed by replaying events, full audit log, temporal queries (point-in-time state).

Differences:

  • Purpose: Traditional event sourcing stores domain events for the entire application's aggregate state, often feeding multiple read models/projections. Temporal's event log is per-workflow-execution and private to Temporal — it stores workflow task commands and results, not necessarily your domain events.
  • Visibility: Traditional ES exposes events to consumers (event bus, subscriptions). Temporal's history is internal — you get it via query/describe, not as a consumer stream.
  • Projections: ES practitioners build read models by projecting the event stream. With Temporal you use Queries and the Visibility API (ElasticSearch) for read models.
  • Complementary use: You can use Temporal to orchestrate workflows that emit domain events to an event bus (Kafka, SNS) as activities. Temporal handles the orchestration durability; the bus handles the projection fan-out.

In practice, Temporal reduces the need for full event sourcing in the orchestration layer — its implicit event log provides the durability guarantees that event sourcing was often adopted for, without the CQRS complexity.
