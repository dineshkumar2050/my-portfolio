1. HTML Fundamentals

Document Structure

Every HTML document begins with a DOCTYPE declaration, followed by a root <html> element containing <head> (metadata) and <body> (content).

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Page Title</title>
  </head>
  <body>
    <h1>Hello, World</h1>
  </body>
</html>

Semantic — communicates meaning to browsers, assistive tech, and search engines.

  • Decorative image: alt="" (empty string, NOT omitted)
  • Linked image: describe the destination, not the image

Lazy Loading

<img src="hero.jpg"    alt="Hero"    loading="eager" />

Q & A

Easy

Q1: What is a DOCTYPE declaration and why is it needed?

<!DOCTYPE html> is an instruction to the browser telling it which version of HTML the document uses. It must appear as the very first line, before the <html> tag.

Why it matters: Without a DOCTYPE, browsers enter quirks mode — they emulate bugs from old browsers (Netscape 4, IE 5) to avoid breaking legacy pages. With <!DOCTYPE html>, the browser enters standards mode, rendering the page according to current specifications.

  • HTML5 DOCTYPE is deliberately simple — it's not a reference to a DTD file, just a mode switch.
  • HTML 4.01 required a full URL referencing the W3C DTD: <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://...">
  • There is also a near-standards mode ("almost standards") triggered by certain older doctypes.
Always use <!DOCTYPE html>. It is valid for both HTML5 and future HTML Living Standard documents.
Q2: What is the difference between semantic elements and generic div/span?

Semantic elements carry meaning about the role of their content. div and span are purely structural — they exist to group elements for styling or scripting without conveying any meaning.

AspectSemantic (nav, article…)Generic (div, span)
MeaningDescribes content purposeNo inherent meaning
AccessibilityProvides implicit ARIA landmark rolesRequires explicit ARIA to be useful to AT
SEOHelps crawlers understand page structureNo structural signal
ReadabilitySelf-documenting HTMLRequires class names to convey intent

Use div when no semantic element applies — for pure layout grouping or JS hooks. Use span for inline styling when no semantic inline element (em, strong, code) fits.

Q3: What is the purpose of the alt attribute on images?

The alt attribute provides a text alternative for an image. It serves multiple audiences:

  • Screen readers announce the alt text to visually impaired users
  • Search engine crawlers use it to understand image content
  • Broken image fallback — displayed when the image fails to load
  • Low-bandwidth / text-only browsers can display the text alternative

Rules for writing good alt text:

  • Describe what the image communicates, not its visual appearance literally
  • Decorative images: use alt="" — screen readers skip the element entirely
  • Omitting alt entirely is different: some ATs will announce the filename
  • For complex images (charts, diagrams): supplement with an extended description
<!-- Informative -->
<img src="graph.png" alt="Bar chart: revenue grew 40% in Q3" />

<!-- Decorative -->
<img src="divider.svg" alt="" role="presentation" />
Q4: What is the difference between defer and async on script tags?

Both attributes make the browser download the script in parallel with HTML parsing, but they differ in when the script executes:

deferasync
DownloadParallel to parsingParallel to parsing
ExecutionAfter full HTML is parsed, just before DOMContentLoadedAs soon as downloaded — may pause parser
OrderIn document order, alwaysWhichever downloads first
DOM accessSafe — DOM is completeRisky — DOM may be incomplete
Best forApp bundles, UI scripts that need the DOMCompletely independent scripts (analytics)
Placing scripts at the end of <body> is the old workaround. Using defer in <head> is modern best practice — it keeps metadata and resource hints together.

Intermediate

Q5: What are the key accessibility best practices when building a web page?

Accessibility (a11y) ensures everyone, including people using assistive technologies, can use your page. Key practices:

Structure

  • Use one <main> per page with a skip-nav link (<a href="#main">Skip to content</a>)
  • Use proper heading hierarchy — one h1, logical nesting of h2→h3
  • Use semantic HTML so landmarks are available for free

Keyboard

  • All interactive elements must be reachable by Tab and activatable by Enter/Space
  • Visible focus indicators — never outline: none without a replacement
  • Logical tab order following visual reading flow

Color & Contrast

  • WCAG AA: 4.5:1 for normal text, 3:1 for large text and UI components
  • Never convey information by color alone — use icons, text labels, patterns

ARIA

  • First rule of ARIA: don't use ARIA if a native element exists
  • Use aria-live="polite" for dynamic notifications (toast messages, form errors)
  • Manage focus when dialogs open/close
Q6: What does the meta viewport tag do and why is it essential?

<meta name="viewport" content="width=device-width, initial-scale=1.0">

Without it: Mobile browsers (iOS Safari, Chrome Android) render pages at a virtual width of ~980px to avoid breaking desktop-only sites, then scale the result down. Everything looks tiny and users must pinch-zoom.

With it: The browser sets the viewport width to match the physical CSS pixel width of the device. Combined with responsive CSS (media queries, flexible layouts), the page fills the screen correctly at 1:1 scale.

Common values explained:

  • width=device-width — viewport equals device CSS pixel width
  • initial-scale=1.0 — no zoom on load
  • maximum-scale=1 — prevents user zoom (avoid: accessibility violation)
  • user-scalable=no — disables pinch-zoom (avoid: violates WCAG 1.4.4)
Never set user-scalable=no — it breaks accessibility for low-vision users and violates WCAG 2.1 Success Criterion 1.4.4.
Q7: What is the difference between preload, prefetch, and preconnect?

All three are resource hints that improve performance by changing when the browser fetches resources, but they serve different purposes:

HintWhen to fetchUse casePriority
preconnectImmediatelyWarm up a third-party origin (DNS + TCP + TLS) without fetching yetHighest — free TCP handshake
preloadImmediatelyFetch a critical resource for the current page (fonts, hero image, critical CSS)High — required, will warn if unused
prefetchIdle timeFetch a resource likely needed on the next navigationLow — best-effort, browser may ignore

Key rules:

  • preload with as attribute is mandatory — tells browser correct priority and CORS mode
  • Cross-origin fonts need crossorigin attribute even if same CDN
  • Over-preloading hurts performance — each preload competes for bandwidth
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link rel="preload" href="/hero.jpg" as="image" fetchpriority="high" />
<link rel="prefetch" href="/next-page.js" as="script" />
Q8: How does HTML5 native form validation work and what are its limitations?

HTML5 form validation runs in the browser before submission, using constraint attributes on input elements. The browser shows native error popups styled to the OS.

How it works:

  • Browser validates on submit (and progressively on blur/input depending on browser)
  • First invalid field receives focus; form submission is blocked
  • CSS pseudo-classes :valid, :invalid, :required reflect constraint state

Constraint API in JS:

const input = document.querySelector('#email');
input.setCustomValidity('Email already registered');
input.reportValidity(); // Shows browser tooltip

// Clear custom message
input.setCustomValidity('');

Limitations:

  • Native error UI is not styleable beyond CSS (tooltip position, colors vary by OS)
  • No cross-field validation (e.g., "password confirm must match")
  • No async validation (e.g., check username availability via API)
  • Error messages not always ARIA-announced; custom UI needed for a11y compliance
Use novalidate on the form when building custom validation UI, then use the Constraint Validation API to check validity programmatically.

Advanced

Q9: What is the Critical Rendering Path and how does HTML affect it?

The Critical Rendering Path (CRP) is the sequence of steps the browser performs to convert HTML, CSS, and JS into rendered pixels on screen:

flowchart LR A[HTML bytes] --> B[DOM] C[CSS bytes] --> D[CSSOM] B & D --> E[Render Tree] E --> F[Layout] F --> G[Paint] G --> H[Composite]

HTML decisions that impact CRP:

  • Parser-blocking scripts: <script src="..."> without defer/async stops DOM construction entirely until the script downloads and executes
  • Render-blocking CSS: All <link rel="stylesheet"> block rendering until CSSOM is built — minimize render-blocking CSS by inlining critical CSS
  • Resource hints: preload moves resource fetches earlier in the waterfall, shortening CRP
  • DOM size: Large DOMs (>1500 nodes) slow layout recalculation and paint
  • Image dimensions: Setting explicit width/height attributes prevents Cumulative Layout Shift (CLS) by reserving space before image loads

Key metrics (Core Web Vitals):

  • LCP — Largest Contentful Paint: time to render largest above-fold element. Optimize with fetchpriority="high" on hero image.
  • CLS — Cumulative Layout Shift: prevent with explicit image dimensions and font-display.
  • INP — Interaction to Next Paint: minimize main-thread blocking.
Q10: When should you use ARIA roles vs native HTML elements?

The five rules of ARIA (W3C):

  1. Don't use ARIA if a native HTML element can do the job
  2. Don't change native semantics unless you absolutely have to
  3. All interactive ARIA controls must be keyboard operable
  4. Don't use role="presentation" or aria-hidden="true" on focusable elements
  5. All interactive elements must have an accessible name
Use ARIA when…Prefer native HTML when…
No native element exists for the widget (e.g., role="tree", role="combobox")The element exists: <button>, <input>, <select>, <details>
You must use a <div> for layout reasons but need semanticsYou can reach for <nav>, <main>, <aside>
Communicating dynamic state changes (aria-live)Static, non-interactive content
Using ARIA incorrectly is worse than using no ARIA at all. A <div role="button"> without tabindex="0" and keyboard event handlers creates an inaccessible control.
<!-- Bad: ARIA-only with missing keyboard support -->
<div role="button" onclick="submit()">Submit</div>

<!-- Good: Native element, all behavior built-in -->
<button type="submit">Submit</button>
Q11: How do custom data attributes (data-*) work and what are good patterns?

data-* attributes let you embed custom data in HTML elements without non-standard attributes. They create a private data namespace that doesn't affect browser rendering or semantics.

<button
  data-action="delete"
  data-item-id="42"
  data-confirm="true"
  data-analytics-event="cta_click">
  Delete
</button>
const btn = document.querySelector('[data-action="delete"]');
// Access via dataset (camelCased)
const id = btn.dataset.itemId;       // "42"
const confirm = btn.dataset.confirm; // "true" (string, not boolean)

// Set
btn.dataset.status = 'loading';
// Remove
delete btn.dataset.confirm;

Good patterns:

  • Event delegation: one listener on a container reads data-action to dispatch behavior
  • JS/CSS communication: CSS [data-state="open"] selectors driven by JS dataset.state = 'open'
  • Analytics hooks: data-analytics-* for tracking without polluting class names
  • Server-side templating: embed IDs or config from the server for JS to consume

Anti-patterns:

  • Storing sensitive data (tokens, PII) — all HTML is visible to the user
  • Using as a CSS-only styling hook when a class is cleaner
  • Replacing proper state management in large applications
Q12: What are Web Components and Custom Elements in HTML?

Web Components is a suite of browser standards for creating reusable, encapsulated custom HTML elements without a framework.

Four technologies:

  • Custom Elements API — define new HTML tags (<my-tooltip>)
  • Shadow DOM — scoped DOM subtree with encapsulated styles
  • HTML Templates — <template> and <slot> for inert, reusable markup
  • ES Modules — import component definitions as JS modules
class MyTooltip extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: 'open' });
    shadow.innerHTML = `
      <style>:host { display: inline-block; }</style>
      <slot></slot>
      <span class="tip">${this.getAttribute('text')}</span>`;
  }
}
customElements.define('my-tooltip', MyTooltip);
<my-tooltip text="Helpful info">Hover me</my-tooltip>

Browser support: All modern browsers. IE11 is unsupported without polyfills. Declarative Shadow DOM (HTML-only, no JS) landed in Chrome 90+ and Firefox 123+.

Custom elements work alongside frameworks — React, Angular, and Vue all support web components as leaf-level elements, making them ideal for design system tokens shared across stacks.

Very Advanced

Q13: What is Progressive Enhancement and how does it differ from Graceful Degradation?

Both strategies address how to handle environments where features are unsupported, but they take opposite starting points.

Progressive EnhancementGraceful Degradation
Start withMinimal working HTML baselineFull-featured modern version
DirectionLayer up: CSS → JS → advanced featuresFall back: strip features for old browsers
BaselineSemantic HTML works everywhere alwaysModern version is canonical
MindsetInclusion-first; every user gets something usefulExceptions-first; patch edge cases

Practical Progressive Enhancement strategy:

  1. Layer 1 — HTML: All content and core functionality accessible via plain HTML (forms POST to server, links navigate)
  2. Layer 2 — CSS: Visual presentation and layout. Page is usable even with CSS disabled.
  3. Layer 3 — JavaScript: Enhanced interactivity, SPA routing, real-time updates. Use feature detection, not browser detection.
// Feature detection pattern
if ('IntersectionObserver' in window) {
  // Enhanced lazy-loading with IntersectionObserver
} else {
  // Baseline: load all images immediately
}

Why it matters today: Progressive enhancement isn't just about old browsers. It addresses flaky networks (JS fails to load), corporate proxies stripping scripts, crawlers and bots, assistive technology, and search engine indexing.

HTML forms that POST to a server URL and refresh the page are the ultimate progressive enhancement baseline — they work without CSS, JS, or even a graphical browser.

  • loading="lazy" reduces initial page weight (but not on LCP image)

Incomplete OG tags cause social unfurls to fall back to unoptimized data. Always provide: og:title, og:description, og:image (1200×630), og:url, og:type.

Heading hierarchy

One h1 per page matching the title tag. Don't skip levels. Headings are the document outline crawlers use to understand topic hierarchy.

Semantic landmarks

Google's crawlers understand <article>, <main>, <nav> for content boundaries — they help identify the primary content versus navigation/ads.

Q15: Explain the browser rendering pipeline in detail — from bytes to pixels.

The browser rendering pipeline converts raw bytes into the pixels you see. Understanding it helps you make targeted performance optimizations.

flowchart TD A["1. Bytes → Characters\n(HTTP response decoded)"] --> B["2. Tokenization\n(chars → HTML tokens)"] B --> C["3. Tree Construction\n(tokens → DOM nodes)"] D["CSS bytes → CSSOM"] --> E["4. Render Tree\n(DOM + CSSOM, visible nodes only)"] C --> E E --> F["5. Layout / Reflow\n(geometry: position, size)"] F --> G["6. Paint\n(fill pixels per layer)"] G --> H["7. Compositing\n(GPU: layer order, transforms)"]

Step-by-step breakdown:

  1. Bytes → Tokens: The HTML parser tokenizes the byte stream. It handles invalid HTML gracefully via error-correction algorithms (unlike XHTML).
  2. DOM construction: Tokens become DOM nodes in a tree. Parser encounters <script> without defer/async — pauses, downloads, executes, then resumes.
  3. CSSOM construction: CSS bytes parse into a separate CSSOM tree. CSS is render-blocking — the browser won't build the render tree until all stylesheets are processed.
  4. Render tree: DOM + CSSOM are merged. Nodes with display: none are excluded. Each visible node gets its computed styles.
  5. Layout (Reflow): Browser calculates exact position and size of every element in device pixels. Expensive — triggered by reading layout properties (offsetWidth, getBoundingClientRect) after DOM changes.
  6. Paint: The browser fills in pixels for each layer — backgrounds, borders, text, shadows. Some properties (color, background) only trigger paint, not layout.
  7. Compositing: The GPU assembles painted layers in the correct order. CSS transforms, opacity, and will-change: transform promote elements to their own compositor layer, skipping layout and paint on animation.

Performance implications:

  • Avoid forced synchronous layouts: reading then writing layout properties in a loop triggers reflow each iteration
  • Prefer transforms and opacity for animations — they only trigger compositing (cheapest)
  • Use will-change: transform to promote stable animated elements, but sparingly — each compositor layer uses GPU memory
  • contain: layout paint scopes reflow/repaint to the element's subtree
The fastest rendering optimization is reducing DOM size. Every extra DOM node adds to layout complexity. Keep the DOM under 1500 total nodes for best performance.
