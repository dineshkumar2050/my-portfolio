Access Control Priority

Bucket Policy (resource-based) > IAM Policy (identity-based) > ACLs (legacy). Explicit DENY in any policy wins.

Bucket policies vs IAM policies: Bucket policies can grant access to other AWS accounts and anonymous principals. IAM policies only control what the identity can do. For cross-account access, you need BOTH an IAM policy on the caller AND a bucket policy allowing the caller.

Aurora Key Features

  • Aurora Cluster: 1 primary + up to 15 read replicas sharing same distributed storage (6-way replication across 3 AZs)

  • Aurora Serverless v2: Instantly scales capacity in fine-grained increments (0.5 ACU steps); great for variable workloads

RDS Proxy

Fully managed database proxy that pools and shares connections. Critical for Lambda (prevents connection exhaustion). Supports IAM authentication, secrets rotation, auto-reconnect on failover.

Cold Start Mitigation

  • Provisioned Concurrency — Pre-initialized environments; always warm; cost extra
  • SnapStart — For Java 11/17/21; takes snapshot of initialized execution env; faster resume
  • Minimize package size — Smaller deployment package = faster init
  • Use ARM/Graviton2 — 19% cheaper, often faster cold starts
  • Avoid VPC if possible — VPC Lambda attaches ENI (extra latency, though improved in 2020)

Concurrency

Account concurrency limit: 1000 per region (soft limit, increase via support)

Reserved Concurrency: Guarantee X concurrency for a function (throttles others)
  Use: Ensure critical function always has capacity
  Risk: Others can't use that concurrency

Provisioned Concurrency: Pre-warm X executions (charged even when idle)
  Use: Latency-sensitive APIs that can't tolerate cold starts

6. IAM

Policy Types

TypeAttached toExamples

Permission BoundaryIAM entities (users/roles)Limits maximum permissions; doesn't grant

Policy Evaluation Logic

  1. Explicit DENY — immediately deny (always wins)
  2. Check SCPs — if denied, stop
  3. Check resource-based policy — if allow, check identity has allow too (cross-account)
  4. Check permission boundary — if set, must be in boundary
  5. Check identity-based policy — if allow, grant access
  6. Default DENY — if no explicit allow found

import * as cdk from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';

      versioned: true,
      removalPolicy: cdk.RemovalPolicy.DESTROY,
      encryption: s3.BucketEncryption.S3_MANAGED,

    const fn = new lambda.Function(this, 'MyFunction', {

      handler: 'index.handler',
      code: lambda.Code.fromAsset('lambda'),
      environment: { BUCKET_NAME: bucket.bucketName },
      architecture: lambda.Architecture.ARM_64,
    });

    bucket.grantRead(fn);
  }
}

10. DynamoDB

Data Modeling

Single-table design: Store multiple entity types in one table

Partition Key (PK) design — CRITICAL for avoiding hot partitions:
  - High cardinality keys (userId, orderId, UUID)
  - For time-series: shard with suffix (userId#0, userId#1)

Composite sort key patterns:
  PK: USER#123      SK: PROFILE
  PK: USER#123      SK: ORDER#2024-01-15#ORD-456
  PK: USER#123      SK: ORDER#2024-02-01#ORD-789
  → Get all orders for user: PK=USER#123, SK begins_with ORDER#

GSI vs LSI

FeatureGSI (Global Secondary Index)LSI (Local Secondary Index)
Create whenAnytimeOnly at table creation
PK scopeDifferent PK from base tableSame PK as base table, different SK
ConsistencyEventually consistent onlyStrongly consistent available
StorageSeparate, own RCU/WCUShared with base table (10 GB limit)
Use caseQuery by any attributeAlternate sort key on same partition

DynamoDB Streams & DAX

Streams:
  - Ordered record of all item changes (24h retention)
  - View types: KEYS_ONLY | NEW_IMAGE | OLD_IMAGE | NEW_AND_OLD_IMAGES
  - Use cases: replication, event-driven triggers, search sync (OpenSearch), audit

DAX (DynamoDB Accelerator):
  - In-memory cache cluster (microsecond reads vs millisecond)
  - Write-through: writes go to DynamoDB and cache
  - When NOT to use: strongly consistent reads, write-heavy workloads,
    infrequent access (cache cold), financial transactions

Capacity Modes

  • On-Demand — Pay per request; scales instantly; good for unknown/spiky traffic
  • Provisioned — Set RCU/WCU; cheaper at steady load; auto-scaling available
  • RCU: 1 RCU = 1 strongly consistent read/s (or 2 eventually consistent) for items ≤4KB
  • WCU: 1 WCU = 1 write/s for items ≤1KB

Redis Cluster (Sharding)

Redis Cluster shards keyspace into 16,384 hash slots
  HASH_SLOT = CRC16(key) mod 16384

Each shard handles a range of slots:
  Shard 1: slots 0-5460
  Shard 2: slots 5461-10922
  Shard 3: slots 10923-16383

Keys in {} use only the bracketed part for slot calculation:
  {user}.profile and {user}.sessions → same shard

Key Types:
  AWS Managed Keys (aws/s3, aws/rds) — Free; auto-rotated; limited control
  Customer Managed Keys (CMK) — $1/month; custom policy; manual/auto rotation

  2. DEK encrypts your data (done in your application)
  3. KMS CMK encrypts the DEK (encrypted DEK stored with data)

Interview Q&A

Q1: What is the difference between EC2 security groups and NACLs? Easy

Security Group: Virtual firewall at the instance/ENI level. Stateful — if you allow inbound traffic, the response is automatically allowed. Only allow rules (no deny). All rules evaluated.

NACL: Optional firewall at the subnet level. Stateless — you must explicitly allow both inbound AND outbound traffic. Supports both allow and deny rules. Rules processed in order (lowest number first), first match wins.

Key gotcha: If you block an IP in a NACL, you must add a deny rule for both inbound AND outbound. With SG stateful behavior, blocking inbound is sufficient.

Q2: What is the difference between Multi-AZ and Read Replicas in RDS? Easy

Multi-AZ:

  • Purpose: High Availability
  • Synchronous replication to standby in another AZ
  • Automatic failover on primary failure (~60-120s)
  • Standby is NOT readable — purely passive

Read Replicas:

  • Purpose: Read Scalability
  • Asynchronous replication (slight lag possible)
  • Readable — offload read queries from primary
  • Must be manually promoted to standalone instance if primary fails
  • Can be in different regions (cross-region read replicas)

You can combine both — Multi-AZ for HA + Read Replicas for read scaling.

Q3: What is S3 Presigned URL and when would you use it? Easy

A presigned URL grants temporary access to a private S3 object without requiring AWS credentials. The URL includes the signer's credentials embedded in the signature and an expiration time.

Use cases:

  • GET presigned URL: Allow users to download private files (profile photos, reports) without making the bucket public
  • PUT presigned URL: Allow clients to upload directly to S3 without routing through your server (avoids bandwidth cost and bottleneck)

Security note: If generated with an IAM Role, the URL is invalid once the role's session expires (even if URL TTL hasn't expired). Use IAM Users for long-lived presigned URLs.

Q4: Explain Lambda cold starts and how to mitigate them Intermediate

A cold start occurs when Lambda needs to create a new execution environment: download code, start runtime, run initialization code (outside handler).

Typical cold start times: Python/Node.js ~100-500ms; Java 5-15s; .NET ~2-5s.

Mitigation strategies:

  1. Provisioned Concurrency — Pre-initialize environments; guaranteed warm; costs extra even when idle
  2. SnapStart (Java) — Snapshot initialized execution environment; restore from snapshot instead of full init
  3. Minimize deployment package — Smaller package = faster download + init
  4. Use lightweight runtimes — Python/Node.js > Java/.NET for cold start performance
  5. ARM/Graviton2 — Often faster cold starts + 19% cheaper
  6. Avoid VPC unless necessary (additional ENI attachment latency, though improved)
  7. Move initialization outside handler — DB connections, SDK clients init once and reused across warm invocations
Q5: What is VPC peering vs Transit Gateway? Intermediate

VPC Peering:

  • Direct 1-to-1 connection between two VPCs
  • Non-transitive: A↔B, B↔C does NOT mean A↔C
  • Works across accounts and regions
  • No bandwidth limit, no single point of failure
  • Simple but scales poorly (N VPCs = N*(N-1)/2 peering connections)

Transit Gateway:

  • Hub-and-spoke model; connects many VPCs and on-prem
  • Transitive routing (all connected VPCs can talk to each other)
  • Centralized routing tables and security policies
  • Supports VPN, Direct Connect attachments
  • Additional cost ($0.05/hr/attachment + $0.02/GB)

Choose peering for: Few VPCs, low cost. Choose TGW for: many VPCs, complex routing, centralized policy.

Q6: How does IAM policy evaluation work? Advanced

AWS evaluates policies in order:

  1. Explicit DENY — If any policy has Deny, access is denied immediately (no exceptions)
  2. SCPs (Org-level) — If account is in an Org and SCP denies, access denied
  3. Resource-based policy — If cross-account, need both resource policy allow AND identity policy allow. Same account: either is sufficient.
  4. IAM Permission Boundaries — If set, effective permissions = intersection of boundaries + identity policies
  5. Identity-based policy — If any allows, access granted
  6. Default DENY — No explicit allow found → denied

Key rule: Explicit DENY always wins over any Allow. Default state is DENY (implicit).

Q7: What is DynamoDB single-table design? When would you use it? Advanced

Single-table design stores multiple entity types in one DynamoDB table, using generic PK/SK patterns (e.g., USER#123, ORDER#456) rather than separate tables per entity.

Benefits:

  • All related data fetched in single operation (no JOINs)
  • Reduces number of DynamoDB tables to manage
  • Better performance for hierarchical data access patterns

When to use:

  • Clear access patterns known upfront
  • Data has parent-child or one-to-many relationships
  • Need to fetch related items together efficiently

When to use multiple tables:

  • Different access patterns for different entities
  • Team prefers simplicity over performance optimization
  • Table TTL or stream processing differs per entity
Q8: What is the difference between SQS Standard and FIFO queues? Intermediate

Standard Queue:

  • Nearly unlimited throughput (TPS)
  • Best-effort ordering (not guaranteed)
  • At-least-once delivery (duplicates possible)
  • Use when ordering doesn't matter and duplicates are tolerable

FIFO Queue:

  • 300 TPS (3,000 with batching)
  • Exact ordering within a MessageGroupId
  • Exactly-once processing (deduplication via MessageDeduplicationId or content-based)
  • Use for financial transactions, order processing, event sequencing

Key FIFO concepts:

  • MessageGroupId — ordering group (separate FIFO per group)
  • MessageDeduplicationId — 5-minute deduplication window
Q9: What is CloudFormation drift detection? Intermediate

Drift detection compares the actual configuration of stack resources against the expected configuration defined in the CloudFormation template.

Drift occurs when: Someone manually changes a resource outside CloudFormation (e.g., manually changes a security group rule).

Detection: aws cloudformation detect-stack-drift — asynchronous operation. Check status: describe-stack-drift-detection-status. View drifted resources: describe-stack-resource-drifts.

Resolution: Either update the template to match current state (import), or fix the manual changes (re-apply stack).

Prevention: Use SCPs or SGs that prevent manual changes; use AWS Config rules to alert on drift.

Q10: What is Route 53 ALIAS record and why is it preferred over CNAME at zone apex? Intermediate

An ALIAS record is a Route 53 extension that maps a domain name to AWS resources (ALB, CloudFront, S3 website, etc.).

Why preferred at zone apex (naked domain like example.com):

  • DNS spec prohibits CNAME at zone apex (can't have example.com CNAME to something — would break SOA and NS records)
  • ALIAS works at zone apex: example.com → ALB DNS name

Other ALIAS benefits:

  • No extra DNS query charge for ALIAS queries
  • Automatically follows target's IP changes (ALBs change IPs)
  • Health check integration
Q11: Explain the fan-out pattern with SNS and SQS Intermediate

Fan-out delivers one message to multiple consumers simultaneously by combining SNS (pub/sub) with multiple SQS queues.

Pattern:

  1. Producer publishes to SNS topic
  2. SNS delivers to all subscribed SQS queues in parallel
  3. Each service consumes from its own queue independently

Benefits:

  • Decoupling: producer doesn't know about consumers
  • Parallel processing: all consumers process simultaneously
  • Reliability: SQS provides buffering; consumers process at their own pace
  • Fan-out: easily add new consumers by adding new SQS subscriptions

Example: Order placed → SNS → SQS (Inventory service), SQS (Email service), SQS (Analytics)

Q12: What are ECS task roles vs execution roles? Intermediate

Task Execution Role: Used by ECS agent to pull images from ECR, write logs to CloudWatch, retrieve secrets from SSM/Secrets Manager. This is the "ECS infrastructure" role.

Task Role: Used by your container code to call AWS services (S3, DynamoDB, SQS). This is the "application" role. Credentials available via instance metadata endpoint to containers.

Analogy: Execution role is like the warehouse manager getting the box (pulling image). Task role is like the employee inside doing their job (app calling AWS APIs).

Keep them separate and minimal (principle of least privilege). Never give task role permission to pull images — that's execution role's job.

Q13: How does DynamoDB handle hot partitions and how do you avoid them? Advanced

DynamoDB distributes data across partitions based on partition key hash. A hot partition occurs when too many requests go to the same partition key, exceeding its 3,000 RCU or 1,000 WCU throughput limit.

Common causes:

  • Low-cardinality PK (e.g., only a few possible values)
  • Popular item that everyone reads (celebrity problem)
  • Time-series data with date as PK (all writes to today)

Solutions:

  1. Write sharding — Add random suffix: PRODUCT#123_1 through PRODUCT#123_10. Read all shards and merge.
  2. High-cardinality PK — Use UUID, user-specific IDs instead of category names
  3. Cache popular items — Use DAX to absorb reads on hot items
  4. Burst capacity — DynamoDB retains up to 5 minutes of unused capacity for bursts
  5. On-Demand mode — AWS auto-scales; avoids hot partition throttling
Q14: What is KMS envelope encryption and why is it used? Advanced

Envelope encryption is a two-layer encryption pattern:

  1. KMS generates a Data Encryption Key (DEK)
  2. DEK encrypts your actual data (locally in your application)
  3. KMS CMK encrypts the DEK (stored alongside the data)
  4. To decrypt: call KMS.Decrypt(encrypted_DEK) → get plaintext DEK → decrypt data

Why used:

  • KMS imposes a 4KB limit on data it can encrypt directly
  • Performance: Only small DEK (32 bytes) goes to KMS, not large data payloads
  • Reduced KMS API calls: encrypt once to get DEK, encrypt many items locally
  • Data key caching: reuse plaintext DEK for multiple operations before refreshing
Q15: What is IRSA in EKS and why is it better than node-level IAM roles? Advanced

IRSA (IAM Roles for Service Accounts) allows K8s pods to assume specific AWS IAM roles using OIDC federation, rather than relying on the node's instance profile.

How it works:

  1. EKS cluster has an OIDC provider URL
  2. Create IAM role with trust policy allowing the K8s ServiceAccount via OIDC
  3. Annotate K8s ServiceAccount with the IAM role ARN
  4. Pod using that SA gets temporary credentials via token volume mount

Why better than node-level roles:

  • Least privilege: Each pod gets only the permissions it needs, not everything the node has
  • No privilege escalation: One compromised pod can't use other pods' permissions
  • Audit trail: CloudTrail shows which pod/SA made which API call
  • No credential rotation: Temporary credentials auto-rotate via SDK
Q16: What is Aurora Serverless v2 and when should you use it? Advanced

Aurora Serverless v2 automatically scales database capacity from 0.5 to 128 Aurora Capacity Units (ACUs) in fine-grained increments (~seconds), based on actual workload.

Key differences from v1:

  • Near-instant scaling (seconds vs minutes in v1)
  • Can scale while serving traffic (no pauses)
  • Supports Multi-AZ, read replicas, and all Aurora features
  • Minimum 0.5 ACU (not truly 0 unless paused)

Use cases:

  • Variable/unpredictable traffic (dev, staging, SaaS apps)
  • Bursty workloads with quiet periods
  • Mixed load (OLTP spikes during business hours)

When NOT to use: Steady high-throughput workloads (provisioned Aurora is cheaper); pure OLAP (use Redshift).

Q17: How does CloudWatch differ from X-Ray and CloudTrail? Intermediate

CloudWatch: Monitoring and observability. Metrics (infrastructure + custom), logs, alarms, dashboards. Answers: "Is my system healthy? What's my CPU? Are there errors?"

X-Ray: Distributed tracing. Traces requests as they flow through microservices. Identifies bottlenecks and root cause of errors. Answers: "Why is this request slow? Which service is failing?"

CloudTrail: Audit log of all AWS API calls. Who did what, when, from where. Answers: "Who created this S3 bucket? Who changed this security group?" Security and compliance.

Use all three: CloudWatch for operational monitoring, X-Ray for application debugging, CloudTrail for security auditing.

Q18: What is the difference between S3 bucket policies and IAM policies? Intermediate

IAM Policies (identity-based): Attached to IAM users/groups/roles. Controls what the identity can do. Only affects AWS principals within your account (or assumed roles).

S3 Bucket Policies (resource-based): Attached to the bucket. Controls who can access the bucket. Can grant access to other AWS accounts, AWS services, or anonymous principals.

When to use what:

  • Cross-account access: Need BOTH — bucket policy allows the other account, AND the other account's IAM policy allows S3 access
  • Grant anonymous/public access: Only bucket policy (IAM has no anonymous users)
  • Control within your account: Either works; IAM is often simpler
  • IP restriction on bucket: Bucket policy with aws:SourceIp condition
Q19: What is an API Gateway Lambda proxy integration? Intermediate

Lambda proxy integration passes the entire HTTP request to Lambda as a structured event (method, path, headers, query params, body) and returns the Lambda response directly to the client.

Event structure:

{
  "httpMethod": "POST",
  "path": "/users/123",
  "pathParameters": {"userId": "123"},
  "queryStringParameters": {"page": "1"},
  "headers": {"Authorization": "Bearer ..."},
  "body": "{\"name\": \"John\"}",
  "isBase64Encoded": false
}

Response structure: Lambda must return {"statusCode": 200, "headers": {...}, "body": "..."}

vs non-proxy: Non-proxy uses mapping templates (Velocity) to transform request/response. More control but more complex.

Q20: How does EventBridge differ from SQS and SNS? Advanced

SNS: Simple pub/sub. Publish message to topic → push to subscribers (SQS, Lambda, HTTP, email). Message filtering available. For notifications and fan-out.

SQS: Queue. Decouple producers from consumers. Consumers poll. Handles backpressure. For async task processing.

EventBridge: Serverless event bus. Routes events based on content patterns. Native integration with 90+ AWS services + 3rd-party SaaS (Datadog, Auth0, etc.). Schema registry. Cross-account/cross-region event routing. For event-driven architectures, automation, SaaS integration.

Choose based on: SNS for simple fan-out; SQS for reliable async processing; EventBridge for complex event routing, AWS service events, and SaaS integrations.

Q21: How do you design for high availability in AWS? Very Advanced

Multi-AZ deployments:

  • EC2 + ASG across 3 AZs with ALB
  • RDS Multi-AZ for database HA
  • ElastiCache with Multi-AZ and automatic failover

Multi-Region (highest HA):

  • Route 53 Failover/Latency routing
  • Aurora Global Database (RPO~0, RTO~1min)

  • DynamoDB Global Tables

  • Circuit breakers (AppMesh, custom)

Q22: What is VPC PrivateLink and when should you use it? Advanced

PrivateLink allows exposing a service to other VPCs/accounts privately, without VPC peering, internet gateway, or NAT. Traffic stays on the AWS network.

Components:

  • Service provider — Puts service behind an NLB and creates an Endpoint Service
  • Consumer — Creates an Interface VPC Endpoint (ENI in their VPC)
  • Traffic from consumer ENI → PrivateLink → NLB → your service

When to use:

  • Expose SaaS/shared services to customers without exposing your full VPC
  • Access AWS services (API Gateway, ECR, SSM) privately without IGW
  • Overlapping IP CIDRs (VPC peering doesn't work with overlapping CIDRs)
  • Service marketplace: AWS Marketplace services use PrivateLink
Q23: How do you secure an S3 bucket with sensitive data? Advanced
  1. Block all public access — Enable "Block Public Access" settings at account and bucket level
  2. Bucket policy — Deny HTTP (require HTTPS): "aws:SecureTransport": "false"
  3. Encryption at rest — SSE-S3 (free), SSE-KMS (audit trail, key control), SSE-C (customer keys)
  4. Versioning — Protect against accidental deletion
  5. MFA Delete — Require MFA to permanently delete objects
  6. VPC Endpoint — Restrict access to only requests from within VPC
  7. Access logging — Log all S3 API calls to another bucket
  8. S3 Object Lock — WORM (Write Once Read Many) for compliance (Governance/Compliance mode)
  9. Macie — Discover and protect sensitive data (PII detection)
  10. IAM policies — Least privilege; use SCPs to prevent turning off protections
Q24: What is the difference between Secrets Manager and SSM Parameter Store? When would you use each? Intermediate

Use Secrets Manager when:

  • You need automatic secret rotation (especially RDS, Redshift, DocumentDB)
  • Secrets need to be replicated across regions
  • Cross-account access is needed
  • Budget allows $0.40/secret/month

Use SSM Parameter Store when:

  • Storing non-sensitive configuration (feature flags, API endpoints)
  • Small secrets where cost matters (free Standard tier)
  • Hierarchical parameter organization (/app/prod/db-url)
  • Integration with AWS Systems Manager workflows

Both support: KMS encryption (SecureString), version history, IAM-based access control, CloudTrail auditing.
