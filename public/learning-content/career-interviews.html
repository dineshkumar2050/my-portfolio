Career Roadmap & Interview Prep

Junior FDE (0–2 Years)

Goal: Build strong foundations, ship real features, learn from senior engineers, establish healthy engineering habits.

Core Technical Skills

  • HTML/CSS: Semantic HTML, Flexbox/Grid, responsive design, accessibility basics (ARIA, keyboard nav)
  • JavaScript: ES6+, DOM manipulation, event handling, async/await, Fetch API, error handling
  • One framework (React / Vue / Angular): Component lifecycle, state management basics, routing
  • Git: Branching strategies, pull requests, resolving merge conflicts, meaningful commit messages
  • Agile basics: Daily standup, sprint ceremonies, writing user stories, acceptance criteria
  • Debugging: Chrome DevTools, network tab, console profiling, reading stack traces
  • REST APIs: CRUD operations, HTTP methods, status codes, headers, authentication patterns
  • Testing: Unit test basics (Jest), what to test and what not to test

Soft Skills at Junior Level

  • Ask for help effectively (provide context, show what you tried, be specific)
  • Communicate blockers early, not after days of being stuck
  • Accept feedback gracefully — code review is about the code, not you
  • Over-document your code as you learn (will help you and future you)
  • Write good PR descriptions — make reviewers' lives easy

Key Learning Resources

  • MDN Web Docs (the authoritative browser API reference)
  • JavaScript.info (comprehensive modern JS course)
  • React docs (react.dev) — official, now uses hooks throughout
  • CS50 (Harvard) for CS fundamentals if needed
  • The Odin Project (free, project-based curriculum)

Mid-Level FDE (2–4 Years)

Goal: Own features end-to-end, contribute to architecture decisions, mentor juniors, improve team processes.

Core Technical Skills

  • TypeScript: Generics, utility types (Partial, Pick, Omit, Record), discriminated unions, type guards, strict mode
  • Advanced React/framework: Custom hooks, Context, performance optimization (memo, useMemo, useCallback, lazy/Suspense), advanced patterns
  • Testing: TDD, integration testing, React Testing Library, Playwright/Cypress for E2E, testing async behavior
  • Performance optimization: Core Web Vitals, Lighthouse, bundle analysis, code splitting, lazy loading, caching strategies
  • System design basics: Client-server architecture, REST vs GraphQL, CDN usage, database basics, caching
  • Tooling: Webpack/Vite config, build optimization, CI/CD pipeline understanding, Docker basics
  • Accessibility (a11y): WCAG 2.1 AA, screen reader testing, focus management, color contrast
  • Security basics: XSS, CSRF, Content Security Policy, HTTPS, secure cookies, input sanitization

Leadership at Mid-Level

  • Start mentoring junior engineers — code reviews, pairing sessions, answering questions
  • Lead smaller initiatives (new library adoption, test coverage improvement)
  • Write technical documentation and ADRs for decisions you make
  • Participate in on-call rotation, learn incident response
  • Contribute to hiring: participate in interviews, improve interview process

Senior FDE (4–7 Years)

Goal: Set technical direction, unblock the team, make trade-offs explicitly, amplify the team (your impact through others > your individual output).

Core Technical Skills

  • Architecture decisions: Micro-frontends, monorepo vs polyrepo, state management at scale, design system architecture
  • Cross-team collaboration: API contract design, backend coordination, design system contribution, platform team engagement
  • Deep expertise in 2-3 areas: e.g., React performance + TypeScript + accessibility; or Node.js + React + testing
  • Technical leadership: RFC/design doc writing, running design reviews, driving technical decisions by consensus
  • Estimation & planning: Breaking down large projects, identifying risks, creating roadmaps, managing technical dependencies
  • Production operations: Incident response, runbooks, observability setup (dashboards, alerts), performance analysis

Senior Engineer Multiplier Behaviors

  • Write clear technical docs that unblock multiple people (not just answer one person)
  • Proactively identify systemic problems before they become incidents
  • Mentor mid-level engineers toward senior-level thinking, not just senior-level skills
  • Build consensus and align on technical direction before committing to build
  • Push back on scope when scope will compromise quality — know when to say "we can do this, but here's what we trade off"
  • Represent your team's work and capabilities to leadership

Staff / Principal FDE (7+ Years)

Goal: Org-wide technical impact. Define engineering standards, shape technical strategy, affect hiring and culture, influence product direction.

Responsibilities

  • Org-wide standards: Define coding standards, testing requirements, deployment practices that all teams adopt
  • Technical strategy: Multi-year technology roadmap, platform investment decisions, build-vs-buy analysis
  • Hiring bar: Define what "good engineering" looks like for the org, run calibration sessions, improve hiring processes
  • External presence: Conference talks, blog posts, open source contributions that attract talent and build brand
  • Executive communication: Translate technical complexity to business outcomes, present technology risk to the board
  • Cross-org influence: Drive adoption without authority — through persuasion, working prototypes, and demonstrated results

Getting to Staff Level

  • Staff is about scope, not seniority — solve problems that span multiple teams
  • Find your "Staff project" — a high-visibility initiative with org-wide impact
  • Build alliances: staff engineers succeed through relationships and trust, not just technical ability
  • Develop a "technical vision" narrative — what should engineering look like in 3 years and why
  • Read: "The Staff Engineer's Path" (Tanya Reilly), "Staff Engineer" (Will Larson)

GitHub Portfolio Tips

Profile Setup

  • Profile README: Create a <username>/<username> repo with a README — it appears on your profile page. Include: brief bio, current tech stack, what you're learning, how to reach you
  • Pinned repos: Pin 4-6 of your best projects. Mix of: production-quality projects, learning projects, open-source contributions
  • Contribution graph: Consistency matters — aim for regular green activity. Even small contributions (docs, issues, small PRs) count
  • Professional photo + bio: Use a professional headshot, fill in website, Twitter/LinkedIn links

Project Quality Checklist

  • Clear README: what it does, tech stack, how to run it, screenshots/demo link
  • Working live demo (Vercel, Netlify, Railway — free tiers are sufficient)
  • Test coverage (even basic tests show you care about quality)
  • Clean commit history — meaningful commit messages, no "fix stuff" commits
  • Issue tracker used (even for your own projects — shows project management thinking)
  • No hardcoded secrets, proper .gitignore
  • Latest dependency versions, no security vulnerabilities

Open Source Contributions

  • Start with "good first issue" labels on repos you already use
  • Documentation improvements are underrated — they're real contributions
  • Bug reports with minimal reproductions are valued contributions
  • Don't target popular repos initially — smaller projects are more welcoming
  • Follow contribution guides strictly before submitting PRs

Resume Tips

Format

  • ATS-friendly: Single column, standard section headings (Experience, Skills, Education), no tables/columns/headers/footers that confuse ATS parsers
  • Length: 1 page for <5 years experience; 2 pages for senior/staff; never more than 2 pages
  • Font: Calibri, Garamond, Arial — readable at 11pt, avoid fancy fonts
  • File format: PDF (preserves formatting), name it FirstName-LastName-Resume.pdf

STAR Bullet Points

Each resume bullet should quantify impact. Bad: "Built a payment API." Good: "Built a payment processing API using Node.js and Stripe, handling $2M+ monthly transactions with 99.98% uptime across 50k+ users."

Formula: [Action verb] + [what you did] + [technology/method used] + [measurable impact]

Skills Section

  • List technologies you can discuss fluently in an interview — don't pad with things you've barely used
  • Group by category: Languages, Frameworks, Cloud/Infrastructure, Tools, Databases
  • Match keywords in the job description (ATS parsing)

What to Include / Exclude

IncludeExclude
Quantified impact (revenue, users, performance %, time saved)Personal info (age, marital status, photo — unless local norms require)
Technologies you'd be happy being tested onTechnologies listed just to fill space / game ATS
Open source contributions / side projects (if impressive)References section ("available on request" is implied)
Awards, promotions, scope increasesObjective statement (outdated — use a professional summary instead)
Education (degree, institution, GPA if >3.5)Every job if irrelevant — trim to last 10 years / relevant roles

LinkedIn Optimization

Headline Formula

Don't just write your current title. Use the formula: [Role] | [Specialty/Impact] | [Industry/Company Type]

Examples:
Senior Full Stack Engineer | React + Node.js | Fintech @ CBA
Frontend Lead | Design Systems & Performance | Banking Technology
Software Engineer | Building scalable payment platforms | Open to Opportunities

About Section Structure

  1. Hook (2 sentences): What do you do and what's your superpower?
  2. Experience highlights (3 bullets): Most impressive achievements with numbers
  3. Technologies: Brief list of your key stack
  4. Current focus / what excites you: Shows passion and growth mindset
  5. CTA: "Open to [opportunities/speaking/collaborations]. Connect via DM or [email]."

Featured Section

Use this prime real estate for: blog posts you've written, conference talks, side project links (live demo), GitHub profile, podcast appearances.

Activity & Network

  • Post 1-2x/week: technical learnings, project updates, opinions on industry trends
  • Comment meaningfully on others' posts — adds visibility
  • Connect with people after conferences, meetups, interviews — personalize the connection request
  • Endorsements: endorse colleagues genuinely (they often reciprocate)
  • Recommendations: give 2-3 genuine recommendations — many will write one back
  • Creator mode: enable for greater distribution of your posts

System Design Interview Prep Roadmap

Month 1: Fundamentals

  • How the internet works: DNS, HTTP/HTTPS, TCP/IP, TLS
  • Client-server architecture, load balancing concepts
  • Database fundamentals: RDBMS vs NoSQL, ACID vs BASE, indexing
  • Caching basics: cache-aside, write-through, eviction policies (LRU, LFU)
  • CAP theorem: consistency vs availability vs partition tolerance
  • Read: "Designing Data-Intensive Applications" (Kleppmann) — chapters 1-3

Month 2: Common Patterns

  • Microservices vs monolith: when to use each, trade-offs
  • Message queues and event-driven architecture (Kafka, RabbitMQ)
  • CDN usage, static asset serving
  • SQL vs NoSQL selection criteria
  • Rate limiting, circuit breakers, bulkheads
  • API gateway patterns, service mesh
  • Read: system design primer (GitHub), ByteByteGo newsletter

Month 3: Practice

  • Practice designing 2 systems per week, time-boxed to 45 minutes
  • Classic systems to design: URL shortener, Twitter/X feed, Netflix, Uber, WhatsApp, Google Search, YouTube, Stripe
  • Use the RESHADED framework: Requirements → Estimation → Storage → High-level design → API design → Detailed design → Evaluation → Distinctive components
  • Mock interviews (Pramp, interviewing.io, with friends)

System Design Interview Framework (RESHADED)

Time Management in Coding Interviews

  • First 5 min: Clarify inputs, outputs, constraints, edge cases. Verbalize your understanding
  • Next 5 min: Discuss approach before coding. State time/space complexity upfront
  • Coding (20 min): Talk while coding. Name variables clearly. Structure code well
  • Last 10 min: Test with examples (including edge cases), trace through code, optimize if time
  • If stuck: talk about a simpler version (brute force first), then optimize

Communicating While Coding

  • "I'm going to start with a brute force O(n²) approach and optimize from there"
  • "I'm using a HashMap here to trade space for O(1) lookup time"
  • "Let me verify with this edge case: empty array should return..."
  • "I see a potential off-by-one error here, let me check my boundary condition"
  • If you need to think silently: "Give me 30 seconds to think through this"

Behavioral Interview STAR Method

STAR: Situation (context) → Task (your responsibility) → Action (what YOU specifically did) → Result (measurable outcome)

STAR Method Tips

  • Situation: Brief context — 2-3 sentences. Don't over-explain the background
  • Task: Your specific role — "as the tech lead, I was responsible for..."
  • Action: This is the most important part — be specific about YOUR actions, not "we did..."
  • Result: Quantify — "reduced latency by 40%," "increased test coverage from 30% to 85%," "shipped 2 weeks ahead of schedule"
  • Prepare 8-10 stories that can flex to answer different question types
  • Each story should demonstrate: technical skill, leadership, communication, handling adversity

10 STAR Stories Library

Story 1: Technical Decision Under Uncertainty Advanced
Situation

Our team needed to choose a state management solution for a new React application that would serve 500K+ daily users. Redux, Zustand, Jotai, and React Query were all viable options. There was no clear org standard and team members had strong opinions.

Task

As the senior engineer, I was responsible for making a recommendation and getting team alignment before we started building.

Action

I ran a structured evaluation over 3 days. I wrote a 1-pager comparing each option across: learning curve, bundle size, DevTools support, server state vs client state needs, community longevity. I built a small proof-of-concept with React Query (for server state) + Zustand (for client UI state), presented it in a design review with working code. I explicitly listed what I was trading off (more moving parts than pure Redux) and addressed each team member's concern individually. I called for a time-boxed decision — "we decide in this meeting or defer to me."

Result

Team aligned on React Query + Zustand. Bundle size was 8KB vs 21KB for Redux Toolkit equivalent. Developer productivity improved — survey after 1 sprint showed 8/10 engineers preferred the pattern. The architecture became the template for 2 other teams in our org.

Story 2: Rescuing a Behind-Schedule Project Intermediate
Situation

6 weeks into an 8-week project, we had delivered only 40% of the committed features for a high-visibility product launch at CBA. The PM was escalating to leadership, team morale was low, and there was pressure to work overtime.

Task

I was the tech lead. My job was to either deliver on time or clearly communicate what we could deliver and what we couldn't.

Action

I ran an emergency triage session. First, I mapped every remaining feature to business impact and implementation complexity — identified that 3 low-impact features were consuming 30% of remaining effort. I proposed to the PM: descope 3 features (defer to phase 2), reduce scope of 2 others to MVP version. I then re-estimated the remaining work with the team — they'd been over-estimating to "feel safe." I removed blockers: I personally pair-programmed on the two most complex stories, unblocking two engineers in 2 days each. I gave the team permission to skip perfection and ship production-ready (not perfect) code.

Result

Shipped the descoped version on time. Post-launch metrics showed the 3 deferred features were actually the right call — they were low-usage. The PM thanked the team publicly. I also ran a retrospective on why we were so wrong in initial estimates — led to better estimation practices using reference class forecasting.

Story 3: Improving Engineering Quality Culture Advanced
Situation

Our team's bug rate in production was high — roughly 30% of sprints had production hotfixes. Code reviews were perfunctory (approved within minutes without meaningful feedback). There was no shared definition of "done" and testing was an afterthought.

Task

I was a senior engineer, no formal leadership authority, but recognized this as systemic and decided to address it.

Action

I data-gathered first: tracked bug sources over 4 sprints — 70% came from missing edge case handling and lack of integration tests. I presented this data at a retrospective, framing it as "here's what the data says" not "here's what you're doing wrong." I proposed 3 changes: (1) a code review checklist (security, error handling, test coverage, performance implications); (2) a team-agreed Definition of Done including integration tests; (3) 20% sprint capacity reserved for tests. I modeled the behavior — submitted very detailed code review comments on every PR I reviewed for 2 sprints.

Result

Production hotfix rate dropped from 30% to 8% over 3 months. Code review turnaround improved from avg 4 days to 1 day because reviews became more focused. Two team members told me this was the most improvement they'd seen in a team's quality culture in their careers.

Story 4: Handling a Disagreement With a Colleague Intermediate
Situation

A senior colleague and I disagreed strongly on whether to introduce a GraphQL API or extend the existing REST API for a new set of mobile features. Both approaches were technically defensible. The discussion in PR comments was becoming heated.

Task

Resolve the disagreement in a way that produced the best technical decision and preserved the working relationship.

Action

I moved the conversation from async (PR comments — easy to misread tone) to synchronous (30-min video call). I came in with genuine curiosity: "Help me understand your concern about GraphQL" — I learned his real objection was operational complexity and our team's lack of GraphQL expertise, not the technology itself. I acknowledged this was a legitimate risk I hadn't weighted sufficiently. I proposed a smaller scope: use GraphQL only for the read-heavy mobile feed endpoint (the hardest REST problem), REST for everything else — letting us learn GraphQL in a bounded way. We wrote up the decision as an ADR together.

Result

The hybrid approach worked well. The GraphQL endpoint reduced mobile data over-fetching by 60%. 6 months later, my colleague became the team's GraphQL advocate after seeing the results. The ADR we wrote together became the template the org adopted for documenting tech decisions.

Story 5: Performance Optimization Under Pressure Advanced
Situation

Two days before a product launch, performance testing revealed our payment summary page had a 4.2-second initial load time — the business requirement was <2 seconds. Cancelling the launch was not on the table.

Task

As the frontend tech lead, I needed to identify the bottlenecks and fix them within 36 hours.

Action

I used Chrome DevTools waterfall + Webpack Bundle Analyzer. Identified: (1) 900KB JavaScript bundle from unused icon library imports — tree-shaking wasn't working due to a Babel config issue; (2) 3 sequential API calls that could be parallelized; (3) no code splitting on chart library (only used on one page). Fixed the Babel config (bundle dropped 280KB), converted sequential API calls to Promise.all() (saved 1.8s), lazy-loaded the chart library. Added a Lighthouse CI gate so this couldn't regress.

Result

Load time dropped from 4.2s to 1.6s — under the 2-second requirement. Launched on schedule. The Lighthouse CI gate caught 2 future regressions before they reached staging. The Webpack analysis technique became a standard step in our release checklist.

Story 6: Mentoring a Struggling Junior Engineer Intermediate
Situation

A junior engineer on my team was struggling — PRs were frequently sent back with the same type of feedback (missing error handling, over-complicated solutions), they were missing sprint commitments, and seemed demoralized.

Task

As their assigned mentor, I needed to diagnose why they were struggling and create a path to improvement.

Action

I had a direct (but kind) 1:1 — "I've noticed X patterns in your PRs. I want to understand what's happening from your perspective before assuming anything." Turns out they were overwhelmed by not knowing what "good code" looked like — they didn't have a mental model of error handling patterns. I shifted from code review comments (prescriptive) to pair programming twice a week for a month — I showed my thought process out loud. I created a personal learning plan: 2 specific patterns per sprint to focus on (error handling + extracting helper functions). I celebrated small wins explicitly in team Slack.

Result

Within 2 months, their PR approval time went from average 5 iterations to 2. They successfully led their first small feature (auth flow refactor) 3 months later. At the retro they said: "This is the first team where I feel like I'm actually learning, not just being told I'm wrong." They were promoted to mid-level 9 months later.

Story 7: Managing a Production Incident Advanced
Situation

At 2pm on a Thursday, our payment processing service began throwing 500 errors. Error rate jumped from 0.1% to 23% in 5 minutes. Approximately 15,000 customers were affected.

Task

As on-call senior engineer, I needed to restore service and coordinate the incident response.

Action

Immediately opened a war room Slack channel, pinged the team. Checked CloudWatch: no recent deploys. Checked AppDynamics: DB connection pool at 100% utilization — but traffic was normal. Checked recent changes: a new database query added to the checkout flow was not using the connection pool correctly (creating a new connection per request). Confirmed by checking connection count in RDS. Immediate mitigation: rolled back the last merge (10 minutes). Then proper fix: patched the query to use the connection pool, tested in staging, deployed via emergency change process. Total impact: 22 minutes of degraded service. Wrote a full incident report with 5-why root cause analysis.

Result

Service restored in 22 minutes, under our 30-minute SLA. Post-incident: added a connection pool monitoring dashboard and alert (threshold: >80% utilization). Added a code review checklist item for database query patterns. 0 recurrences in the following 18 months. The incident report format I used was adopted as the team standard.

Story 8: Introducing a New Technology Intermediate
Situation

Our team was writing complex long-running background jobs in a basic queue system. Jobs would fail silently, had no visibility, and retry logic was hand-rolled differently by each developer.

Task

I identified Temporal as a potential solution and wanted to propose adopting it — but the team had no experience with it and there was natural skepticism about introducing new dependencies.

Action

I ran a "spike" (time-boxed investigation) over 3 days. I rebuilt one of our most complex jobs (payment reconciliation, with 5 retry conditions) in Temporal, measuring: code reduction, visibility, error handling completeness. I presented the spike at a design review with working code and a live demo showing Temporal's Web UI (a major wow factor — our current system had zero visibility). I explicitly addressed the "new dependency risk" with: vendor support evidence, open-source fallback, adoption at similar fintechs (Stripe, DoorDash). I proposed a 6-week pilot with one non-critical job before committing.

Result

Pilot approved. The pilot job's code was 60% shorter, had zero silent failures over 6 weeks. The team voted unanimously to adopt Temporal for all new long-running workflows. I later presented this adoption story at an internal CBA tech talk, leading to 2 other teams adopting Temporal.

Story 9: Cross-Functional Collaboration on a Tight Deadline Intermediate
Situation

We were building a new onboarding flow with 3 weeks to launch. Frontend (my team), backend, mobile, and design were all involved. Design was changing requirements 3 days before the deadline, and mobile team said they couldn't implement the new design in time.

Task

As the frontend lead, I needed to facilitate a resolution that let us ship without sacrificing quality or burning out any team.

Action

I called a multi-team sync immediately. First, I got everyone to acknowledge the constraint (fixed deadline). Then I got design to explain WHY the change — turned out it was based on last-minute user research showing the original CTA placement had 30% lower conversion in testing. Armed with the "why," I negotiated: implement the CTA change only (high impact), defer the 3 other design tweaks to 2 weeks post-launch. Mobile agreed to the CTA-only change (2 hours of work). I coordinated the API contract changes between frontend and backend live in the meeting to avoid async back-and-forth.

Result

Shipped on deadline. The CTA placement change increased conversion by 28% post-launch (validating the design research). The deferred changes were shipped 10 days later. The PM noted this was the smoothest cross-team launch in the organization's memory — specifically calling out the collaborative decision-making approach.

Story 10: Failure and What You Learned Advanced
Situation

Early in my career as a mid-level engineer, I was leading the migration of a critical authentication service. I was confident in my technical approach and under-communicated the risk to stakeholders. The migration caused 2 hours of login failures for 20,000 users during peak hours.

Task

Execute the migration and restore service. Then deal with the aftermath honestly.

Action

In the moment: I immediately rolled back, restored service in 45 minutes, communicated status updates every 10 minutes to the business. I wrote a thorough incident report accepting full ownership: the root cause was my decision to perform a hot migration without a dark launch phase, and I'd ignored a colleague's suggestion to test with 5% of traffic first. At the post-incident review, I didn't make excuses — I presented what I'd learned and proposed concrete changes: dark launch pattern as standard for auth changes, a migration runbook template, and a stakeholder sign-off requirement for changes affecting core auth flows.

Result

Short-term: reputational hit was real but manageable because I owned it. The runbook template I created was adopted org-wide. Long-term: this incident became foundational to how I now approach production changes — my default question before any migration is "what's the blast radius, and do we have a rollback?" Ironically, this incident led to me being trusted with larger projects because leadership saw how I handled adversity.

Negotiation Tips

Research Market Rate

  • Sources: Levels.fyi (tech companies with detailed TC breakdowns), Glassdoor, LinkedIn Salary, Seek Salary Insights (Australia), SEEK Technology Salary Report
  • Adjust for: company size/stage, location (Sydney vs Melbourne premium), industry (fintech premiums in AU)
  • Ask your network — many engineers are surprisingly open about comp when asked directly
  • Aim for the 75th percentile as your target (not the median)

Total Compensation Breakdown

ComponentNotes
Base salaryYour guaranteed income. Most important for Australian market (less equity-heavy than US)
Annual bonusAt large companies (CBA, Atlassian) typically 10-20% of base. Note: usually variable/discretionary
Equity (RSUs / options)RSUs are more valuable than options. Vesting schedule matters (4-year cliff vs monthly). Public co RSUs = real value; startup options = uncertain
SuperannuationAustralian employers required to pay 11% super (2024). Some companies pay 12-15%
BenefitsHealth insurance, professional development budget ($2k-5k/yr is good), home office allowance, parental leave policy
FlexibilityWFH days, flexible hours — has real monetary value (commute costs, childcare timing)

Negotiation Strategy

  1. Never reveal your current salary if you can help it — in some AU states, asking current salary is restricted. Deflect: "I'd rather focus on the value I bring and your budget for the role."
  2. Get the offer in writing before negotiating — gives you something concrete to work with
  3. Competing offers are powerful — even one alternative offer dramatically improves leverage. Time your job search so offers arrive simultaneously
  4. Counter-offer formula: Ask for 10-20% above offer. Anchor high — you can come down, you can't go up
  5. If they say "this is our best offer": Ask for a non-monetary improvement (extra annual leave, $5k signing bonus, earlier performance review, remote work flexibility)
  6. Get everything agreed in writing before giving notice at current role
Scripts: "Based on my research and the market for someone with my experience in [specialty], I was expecting something in the range of $X-$Y. Is there flexibility?" / "I'm very excited about this role. To make this decision easier, could you get to $X base? I have another offer at $Z but I'd prefer to join here."
