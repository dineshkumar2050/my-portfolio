Node.js — Comprehensive Learning Reference

What is Node.js

Node.js is a runtime environment that executes JavaScript outside the browser. It is built on two core components:

  • V8 — Google's open-source JavaScript engine (also used in Chrome). Compiles JS to machine code using JIT compilation.
  • libuv — A multi-platform C library that provides the event loop, async I/O, thread pool, timers, and OS-level abstractions (file system, DNS, networking).
Key design principle: Node.js is single-threaded on the JavaScript side but uses a thread pool (default 4 threads) internally via libuv for I/O operations that cannot be made asynchronous at the OS level (file I/O on some platforms, DNS, crypto). 
// Node.js internals
// V8 handles: JS parsing, compilation, garbage collection
// libuv handles: event loop, I/O, timers, thread pool
// Node bindings: C++ glue connecting V8 + libuv + Node APIs

// Thread pool size (default 4)
process.env.UV_THREADPOOL_SIZE = '8';  // must be set before any I/O

Event Loop — Phase by Phase

The event loop is libuv's mechanism for handling asynchronous callbacks. It runs in a single thread and processes tasks in distinct phases.

graph LR A[Start] --> B[timers\nsetTimeout\nsetInterval] B --> C[pending callbacks\nI/O errors from prev iter] C --> D[idle / prepare\ninternal use] D --> E[poll\nretrieve new I/O events\nexecute I/O callbacks] E --> F[check\nsetImmediate callbacks] F --> G[close callbacks\nsocket.on close] G -->|next iteration| B M[microtasks\nrun between every phase] M -.->|process.nextTick| B M -.->|Promise .then| B style B fill:#1a4731,color:#3fb950 style E fill:#1f3358,color:#58a6ff style F fill:#2d2b00,color:#e3b341 style M fill:#3d1f00,color:#f0883e

Phase Descriptions

PhaseWhat runs hereNotes
timerssetTimeout, setInterval callbacksMinimum delay, not exact — depends on poll phase duration
pending callbacksI/O callbacks deferred from previous iteratione.g., TCP errors (ECONNREFUSED)
idle / prepareInternal Node.js useNot accessible by userland code
pollRetrieve new I/O events; execute I/O callbacksWill block here if no timers pending and callback queue empty
checksetImmediate callbacksAlways runs after poll, before timers of next iteration
close callbacks'close' events (socket, file handle)e.g., socket.on('close', ...)

Microtasks

Microtasks run between every event loop phase (and between each callback in a phase in Node 11+). They are processed in order:

  1. process.nextTick queue (all of them, before Promises)
  2. Promise.then / queueMicrotask queue
// Event loop ordering demo
console.log('1 - sync');

setTimeout(() => console.log('5 - setTimeout'), 0);
setImmediate(() => console.log('4 - setImmediate'));

Promise.resolve().then(() => console.log('3 - Promise'));
process.nextTick(() => console.log('2 - nextTick'));

console.log('1b - sync');
// Output: 1, 1b, 2, 3, 4, 5  (setImmediate before setTimeout when no I/O)

// Inside I/O callback: setImmediate ALWAYS before setTimeout
fs.readFile('file.txt', () => {
  setTimeout(() => console.log('timer'), 0);
  setImmediate(() => console.log('immediate'));
  // "immediate" always prints first here
});

Event Emitter Pattern

const { EventEmitter } = require('events');

class OrderService extends EventEmitter {
  placeOrder(order) {
    // process...
    this.emit('order:placed', order);
    this.emit('order:placed', { ...order, quantity: -1 });  // emitting errors
  }
}

const service = new OrderService();
service.setMaxListeners(20);  // default 10, increase to avoid warning

// on — persistent listener
service.on('order:placed', (order) => console.log('New order:', order.id));

// once — fires once then removes itself
service.once('order:placed', (order) => sendWelcomeEmail(order));

// off — remove specific listener
const handler = (order) => console.log(order);
service.on('order:placed', handler);
service.off('order:placed', handler);

// Error events are special — unhandled throws
service.on('error', (err) => console.error('OrderService error:', err));

// EventEmitter.listenerCount
EventEmitter.listenerCount(service, 'order:placed');

// Promisify events
const { once } = require('events');
const [data] = await once(emitter, 'data');

Streams

Streams are Node's abstraction for processing data piece by piece without loading it all into memory. There are four types:

TypeDescriptionExample
ReadableSource of datafs.createReadStream, HTTP request body
WritableDestination for datafs.createWriteStream, HTTP response
TransformRead + write, transforms datazlib.createGzip, crypto cipher
DuplexRead + write, independent channelsTCP socket, net.Socket

pipe vs pipeline

const { pipeline } = require('stream/promises');
const { createReadStream, createWriteStream } = require('fs');
const { createGzip } = require('zlib');

// PREFER pipeline over pipe — handles errors and cleanup automatically
await pipeline(
  createReadStream('input.txt'),
  createGzip(),
  createWriteStream('output.txt.gz')
);

// Old pipe — does NOT handle errors on intermediate streams!
// If gzip fails, input stream may leak
readable.pipe(transform).pipe(writable);  // avoid in production

Backpressure

// Backpressure — writable signals it can't keep up
const writable = fs.createWriteStream('large.txt');

readable.on('data', (chunk) => {
  const canContinue = writable.write(chunk);
  if (!canContinue) {
    readable.pause();  // stop reading until writable drains
    writable.once('drain', () => readable.resume());
  }
});

// pipeline() handles backpressure automatically!

// In worker.js
process.on('message', ({ task, data }) => {
  const result = data.reduce((a, b) => a + b, 0);
  process.send({ result });
});

Worker Threads

Worker Threads enable true parallel JavaScript execution. Each worker has its own V8 instance and event loop. Unlike child processes, workers share memory via SharedArrayBuffer.

// main.js
const { Worker, isMainThread, parentPort, workerData, MessageChannel } = require('worker_threads');

if (isMainThread) {
  const worker = new Worker(__filename, {
    workerData: { numbers: [1, 2, 3, 4, 5, 6, 7, 8] }
  });

  worker.on('message', (result) => console.log('Sum:', result));
  worker.on('error', console.error);
  worker.on('exit', (code) => { if (code !== 0) throw new Error(`Worker exited ${code}`); });
} else {
  // Worker thread code
  const sum = workerData.numbers.reduce((a, b) => a + b, 0);
  parentPort.postMessage(sum);
}

// SharedArrayBuffer + Atomics — shared memory between threads
const sharedBuffer = new SharedArrayBuffer(Int32Array.BYTES_PER_ELEMENT * 4);
const sharedArray = new Int32Array(sharedBuffer);

// In worker — atomic operations prevent race conditions
Atomics.add(sharedArray, 0, 1);       // atomic increment
Atomics.load(sharedArray, 0);          // atomic read
Atomics.store(sharedArray, 0, 42);     // atomic write
Atomics.compareExchange(sharedArray, 0, 42, 0);  // CAS operation

// Atomics.wait / Atomics.notify — mutex pattern
Atomics.wait(sharedArray, 0, 0);       // block thread until value changes
Atomics.notify(sharedArray, 0, 1);    // wake 1 waiting thread

// MessageChannel — direct worker-to-worker communication
const { port1, port2 } = new MessageChannel();
worker1.postMessage({ port: port1 }, [port1]);
worker2.postMessage({ port: port2 }, [port2]);

Cluster Module

const cluster = require('cluster');
const os = require('os');

if (cluster.isPrimary) {
  const numCPUs = os.availableParallelism();  // Node 18+ (os.cpus().length before)
  console.log(`Primary ${process.pid} forking ${numCPUs} workers`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died — respawning`);
    cluster.fork();  // auto-restart
  });

  // Zero-downtime reload
  cluster.on('listening', (worker) => {
    console.log(`Worker ${worker.id} listening`);
  });
} else {
  // Worker process — each has its own event loop
  const http = require('http');
  http.createServer((req, res) => {
    res.end(`Worker ${process.pid}`);
  }).listen(3000);
}

// Cluster vs Worker Threads:
// Cluster: separate processes, separate memory, OS load-balancing of TCP connections
// Worker Threads: same process, shared memory option, manual work distribution

Fastify

  return (req, res, next) => {
    const result = schema.safeParse(req.body);

Error Handling Patterns

// Custom error classes
class AppError extends Error {
  constructor(message, statusCode = 500, code = 'INTERNAL_ERROR') {
    super(message);
    this.name = this.constructor.name;
    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = true;
    Error.captureStackTrace(this, this.constructor);
  }
}

class NotFoundError extends AppError {
  constructor(resource) {
    super(`${resource} not found`, 404, 'NOT_FOUND');
  }
}

class ValidationError extends AppError {
  constructor(details) {
    super('Validation failed', 422, 'VALIDATION_ERROR');
    this.details = details;
  }
}

// Async error wrapper (avoid try/catch in every route)
const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

app.get('/users/:id', asyncHandler(async (req, res) => {
  const user = await User.findById(req.params.id);
  if (!user) throw new NotFoundError('User');
  res.json(user);
}));

// Result pattern (functional error handling)
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

async function safeFind(id: string): Promise<Result<User>> {
  try {
    const user = await User.findById(id);
    return user ? { ok: true, value: user } : { ok: false, error: new NotFoundError('User') };
  } catch (e) {
    return { ok: false, error: e as Error };
  }
}

Interview Q&A

Q1: What is the Node.js event loop and why is Node single-threaded? Easy

Node.js uses a single-threaded event loop to handle all JavaScript execution. However, it is not truly single-threaded at the system level — libuv uses a thread pool (default 4 threads) for blocking I/O operations (file system, DNS, crypto) that cannot be made async by the OS.

The event loop continuously checks queues of callbacks to execute. When your JS code makes an async call (e.g., fs.readFile), it registers a callback and returns immediately. The I/O happens on a thread pool thread. When done, the callback is enqueued on the event loop and executed when the JS thread is free.

This model is efficient for I/O-bound workloads (many concurrent connections with little CPU work per request) but poor for CPU-bound workloads (heavy computation blocks the single JS thread).

Q2: What is the difference between process.nextTick and Promise.then? Intermediate

Both schedule microtasks, but process.nextTick has higher priority — its queue is drained completely before any Promise microtasks run.

Promise.resolve().then(() => console.log('Promise'));
process.nextTick(() => console.log('nextTick'));
// Output: nextTick, Promise

Overuse of nextTick can starve I/O — if you keep queuing nextTick callbacks, the event loop never advances to the poll phase. Use nextTick for: ensuring callbacks are called asynchronously (after current operation), or for emitting events before the end of the current tick.

Use setImmediate or queueMicrotask/Promise for most scheduling needs.

Q3: What is backpressure in streams and how do you handle it? Intermediate

Backpressure occurs when a writable stream's internal buffer is full and cannot accept more data. writable.write(chunk) returns false when the buffer is full. If you ignore this and keep writing, the buffer grows unboundedly — causing memory leaks.

The correct pattern: pause the readable when writable returns false, and resume on the 'drain' event. stream.pipeline() handles this automatically — it is the recommended approach for production use.

highWaterMark controls buffer size: default 16KB for byte streams, 16 objects for object mode streams.

Q4: What is the difference between spawn, exec, execFile, and fork? Intermediate
  • spawn: Launches a process. Returns a ChildProcess with streaming stdin/stdout/stderr. No shell by default. Best for long-running processes or when you need streaming output.
  • exec: Runs command in a shell. Buffers all output into memory. Callback with (error, stdout, stderr). Dangerous with unsanitized user input (shell injection).
  • execFile: Like exec but no shell — executes the file directly. Safer, no shell injection risk. Still buffers.
  • fork: Spawns a new Node.js process. Automatically sets up an IPC channel for process.send()/process.on('message'). Used for parallelizing Node.js work.
Q5: What is the difference between Worker Threads and the Cluster module? Intermediate

Cluster: Creates child processes. Each worker is a separate OS process with its own memory space. The OS load-balances incoming TCP connections across workers. Good for scaling HTTP servers across CPU cores. Uses more memory (separate V8 heaps).

Worker Threads: Creates threads within the same process. Threads share memory via SharedArrayBuffer. Good for CPU-intensive tasks (image processing, crypto, data transformation) without spawning a full process. The thread pool can be managed manually. Not suitable for distributing HTTP traffic — use Cluster for that.

In practice: Cluster for HTTP scaling, Worker Threads for CPU-bound parallelism within a single Node instance.

Q6: What is the CommonJS vs ESM module difference and how does interop work? Intermediate

CJS uses require() (synchronous) and module.exports. ESM uses import/export (parsed statically, loaded asynchronously).

Interop rules:

  • ESM can import CJS modules — they get the module.exports value as the default import
  • CJS cannot require() ESM modules directly (except Node 22+ synchronous ESM)
  • Use import() (dynamic, async) in CJS to load ESM packages
  • "type": "module" in package.json makes all .js files ESM; use .cjs for CommonJS
Q7: How does Node.js handle CPU-intensive tasks without blocking the event loop? Intermediate

Options from simplest to most capable:

  1. Break work into chunks: Use setImmediate to yield between iterations, giving the event loop a chance to process other callbacks between chunks.
  2. Worker Threads: Offload the computation to a worker thread. Communicate results via postMessage. The main event loop remains responsive.
  3. Child Process: child_process.fork a separate Node process for isolation.
  4. Native addons (N-API): Write the hot path in C++ with async NAN/N-API calls.
// Chunk approach with setImmediate
async function processLargeArray(arr) {
  const CHUNK = 1000;
  for (let i = 0; i < arr.length; i += CHUNK) {
    processChunk(arr.slice(i, i + CHUNK));
    await new Promise(resolve => setImmediate(resolve));  // yield
  }
}
Q8: What causes "MaxListenersExceededWarning" and how do you fix it? Easy

EventEmitter emits a warning when more than 10 listeners are registered for the same event on the same emitter (default limit). This is a memory leak detector — it usually means you're adding listeners in a loop or inside a function that runs many times without removing old listeners.

Fixes:

  • Remove listeners when done: emitter.off('event', handler)
  • Use emitter.once() for one-time listeners
  • Increase limit if legitimate: emitter.setMaxListeners(20)
  • Set globally: EventEmitter.defaultMaxListeners = 20
Q9: How does the Node.js permission model work in Node 20+? Advanced

The Permission Model (experimental in Node 20, stabilizing in later versions) restricts what a Node process can access. Launched with --experimental-permission or --permission flags:

node --permission --allow-fs-read=/tmp --allow-fs-write=/tmp --allow-net app.js

Without flags, all access is denied. Permissions can be checked at runtime:

process.permission.has('fs.read', '/tmp/file.txt')
process.permission.has('net')
process.permission.has('child_process')

Categories: fs.read, fs.write, net, child_process, worker, inspect. Useful for defense-in-depth with untrusted plugin code.

Q10: What is prototype pollution and how do you prevent it in Node.js? Advanced

Prototype pollution occurs when an attacker can set properties on Object.prototype (or other base prototypes) via user-supplied data, affecting all objects in the process. Classic vector: deep merge with unsanitized input containing __proto__ key.

// VULNERABLE
function merge(target, src) {
  for (const key in src) target[key] = src[key];  // __proto__ is enumerable
}
merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
({}).isAdmin;  // true — ALL objects now have isAdmin!

Prevention:

  • Use Object.create(null) for dictionaries (no prototype)
  • Validate/sanitize keys: if (key === '__proto__' || key === 'constructor') continue
  • Use safe merge: structuredClone, JSON.parse(JSON.stringify(x)), or lodash's mergeWith with sanitization
  • Use Object.hasOwn(obj, key) instead of hasOwnProperty
  • Freeze the prototype: Object.freeze(Object.prototype)
Q11: Explain the difference between setImmediate and setTimeout(fn, 0) Intermediate

setTimeout(fn, 0) schedules in the timers phase of the next event loop iteration. setImmediate schedules in the check phase of the current iteration (after poll).

When called outside I/O callbacks: order is non-deterministic (depends on OS timer resolution).

When called inside an I/O callback: setImmediate always fires before setTimeout(fn, 0) — because check phase comes before timers in the loop ordering from poll's perspective.

Use setImmediate when you want to run after the current I/O phase, use process.nextTick when you want to run before any I/O (within same iteration).

Q12: What is a Transform stream and when would you use one? Intermediate

A Transform stream is both Readable and Writable — it receives data, transforms it, and outputs transformed data. It sits in the middle of a pipeline.

Use cases: compression/decompression (zlib), encryption/decryption, CSV parsing, JSON line parsing, text encoding, data aggregation.

// CSV line counter Transform
class LineCounter extends Transform {
  constructor() { super({ objectMode: true }); this.count = 0; }
  _transform(chunk, _, cb) {
    this.count += chunk.toString().split('\n').length - 1;
    this.push(chunk);  // pass through unchanged
    cb();
  }
  _flush(cb) {
    console.log(`Lines: ${this.count}`);
    cb();
  }
}
Q13: How does pnpm's symlink-based node_modules work? Advanced

npm/yarn use a flat node_modules — all packages hoisted to the top level. This enables "phantom dependencies" (packages you can require but didn't declare).

pnpm uses a two-level structure:

  1. A global content-addressable store (~/.pnpm-store) with hard-linked files
  2. node_modules/.pnpm contains the full dependency graph with each package's own node_modules containing only its declared dependencies
  3. Top-level node_modules has only symlinks to packages declared in your package.json

Benefits: disk efficient (hard links share inodes), strict (cannot use undeclared deps), faster installs (copy-on-write via hard links).

Q14: What is graceful shutdown and how do you implement it? Advanced 
async function gracefulShutdown(signal) {
  console.log(`${signal} received — graceful shutdown`);

  // 1. Stop accepting new connections
  await new Promise((resolve, reject) =>
    server.close((err) => err ? reject(err) : resolve())
  );

  // 2. Wait for existing requests to complete (with timeout)
  const timeout = setTimeout(() => {
    console.error('Forced shutdown after 30s');
    process.exit(1);
  }, 30_000);

  // 3. Close DB connections, flush caches, etc.
  await db.destroy();
  await redis.quit();
  await messageQueue.close();

  clearTimeout(timeout);
  console.log('Graceful shutdown complete');
  process.exit(0);
}

process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));

In Kubernetes: the pod receives SIGTERM → waits up to terminationGracePeriodSeconds → sends SIGKILL. Your handler must finish within that window.

Q15: What is libuv's thread pool and what operations use it? Advanced

libuv's thread pool (default size 4, max 1024 via UV_THREADPOOL_SIZE) handles operations that cannot be done asynchronously by the OS:

  • File system operations (on all platforms — even Linux's io_uring is a layer above)
  • DNS resolution (dns.lookup — dns.resolve uses the OS async resolver)
  • Crypto operations (via Node's crypto module — AES, hashing)
  • Zlib compression
  • User native addons that use uv_queue_work

TCP/UDP networking does NOT use the thread pool — it uses OS-level async I/O (epoll/kqueue/IOCP).

Thread pool exhaustion shows up as: all file I/O operations queuing up, DNS lookups stalling. Increase UV_THREADPOOL_SIZE if needed (but each thread costs ~1MB stack).

Q16: How do you prevent event loop starvation from process.nextTick? Advanced

If a nextTick callback schedules another nextTick, and that one schedules another, the event loop never moves forward — all I/O, timers, and promises starve. This is called nextTick recursion.

Node will execute all nextTick callbacks before moving to the next phase, even newly enqueued ones. A recursive nextTick loop will DoS the server.

// DANGEROUS — infinite loop on the nextTick queue
function bad() { process.nextTick(bad); }

// SAFE alternative — use setImmediate (yields to the event loop between calls)
function good() { setImmediate(good); }
// Or async iteration with await:

Recommendation: Use process.nextTick only once per call, never recursively. Use setImmediate or yielding async patterns for iterative work.

Q17: What does --watch do in Node 19+ and how does it compare to nodemon? Easy

node --watch server.js is a built-in file watcher that restarts the process when any file loaded by the module system changes. Added in Node 19 (unstable), stabilized in Node 22.

vs nodemon:

  • No installation required
  • Watches only files actually imported (not the whole directory)
  • Supports --watch-path to add specific directories
  • Less configurable than nodemon (no delay, no exec, no ignore globs until newer versions)

Sufficient for simple development servers; use nodemon for advanced patterns (TypeScript exec, custom ignore rules).

Q18: How does Node.js native fetch differ from node-fetch? Intermediate

Node 18 added native fetch (stable in Node 21). Based on the WHATWG Fetch spec, implemented via undici under the hood.

Key differences from node-fetch v2:

  • Native fetch follows the browser spec more closely (proper Headers, Request, Response)
  • Supports streaming response bodies natively
  • No need for extra package installation
  • Does not follow http_proxy env var by default (use undici.ProxyAgent or global-agent)
  • Cookies not persisted by default (no jar); use undici.CookieAgent

Q20: How do SharedArrayBuffer and Atomics enable lock-free data structures? Very Advanced

SharedArrayBuffer allocates memory accessible from multiple Worker Threads simultaneously. Without synchronization, concurrent reads/writes cause data races.

Atomics provides CPU-level atomic operations:

  • Atomics.add/sub/and/or/xor — read-modify-write atomically
  • Atomics.compareExchange — CAS (Compare-And-Swap) for lock-free algorithms
  • Atomics.wait — block thread until value changes (mutex sleep)
  • Atomics.notify — wake waiting threads (mutex wakeup)
  • Atomics.load/store — with memory ordering guarantees

Use case: a work-stealing queue where multiple workers atomically claim items from a shared index without a mutex, or a ring buffer for producer-consumer patterns between workers.

Q21: What is the difference between dns.lookup and dns.resolve? Advanced

dns.lookup: Uses the OS resolver (getaddrinfo) — reads /etc/hosts, respects system DNS config, local mDNS. Runs on the libuv thread pool. Can cause thread pool contention in high-DNS-volume apps.

dns.resolve (and dns.resolve4, dns.resolveCname, etc.): Queries DNS directly using Node's async DNS client (c-ares). Bypasses /etc/hosts. Non-blocking (no thread pool). Supports all DNS record types.

HTTP clients like axios and Node's http.request use dns.lookup by default. To avoid thread pool saturation, use a custom lookup with caching, or configure HTTP agents with c-ares-based lookup.
