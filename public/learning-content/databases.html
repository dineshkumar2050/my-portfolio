ACID Properties

ACID guarantees that database transactions are processed reliably. Every relational database engine (MySQL InnoDB, PostgreSQL, Oracle) enforces ACID at its core.

PropertyDefinitionExample
AtomicityA transaction is an all-or-nothing unit. Either all operations succeed or none take effect. The undo log is used to roll back partial work.Bank transfer: debit + credit must both succeed or both fail.
ConsistencyA transaction brings the database from one valid state to another. All integrity constraints, triggers, and cascades are satisfied.A transfer cannot leave a negative balance if a CHECK constraint prevents it.
IsolationConcurrent transactions execute as if they were serial. Intermediate state is invisible to other transactions.Two users booking the last seat simultaneously — only one succeeds.
DurabilityOnce committed, a transaction's changes survive crashes. Achieved via the write-ahead log (WAL / redo log) flushed to disk before ACK.After COMMIT, a server crash cannot undo the transfer.

Transactions

-- Basic transaction
START TRANSACTION;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;

-- With rollback on error
START TRANSACTION;
  INSERT INTO orders (customer_id, total) VALUES (42, 299.99);
  -- If inventory update fails:
  UPDATE inventory SET qty = qty - 1 WHERE product_id = 7;
  -- Check affected rows; if 0 → not enough stock
  -- Application calls ROLLBACK
ROLLBACK;

-- Savepoints
START TRANSACTION;
  INSERT INTO logs VALUES ('step1');
  SAVEPOINT sp1;
  INSERT INTO logs VALUES ('step2');
  ROLLBACK TO SAVEPOINT sp1;  -- undo step2 only
  INSERT INTO logs VALUES ('step2-corrected');
COMMIT;
InnoDB internals: Every DML statement is wrapped in an implicit transaction. The undo log stores before-images for rollback; the redo log (iblogfile) ensures durability. Transactions are identified by a transaction ID (TID) used for MVCC visibility checks.

Anomaly Definitions

  • Dirty Read: Transaction A reads data written but not yet committed by Transaction B. If B rolls back, A has read invalid data.
  • Non-Repeatable Read: Transaction A reads the same row twice; between the reads, Transaction B commits an UPDATE. A sees different values.
  • Phantom Read: Transaction A executes the same range query twice; between the reads, Transaction B inserts/deletes rows that match. A sees different row counts.
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Check current isolation level
SELECT @@transaction_isolation;

Deadlocks

A deadlock occurs when two transactions each hold a lock the other needs. InnoDB detects cycles in the waits-for graph and rolls back the transaction with fewer undo log records (cheapest victim).

-- Transaction 1                   -- Transaction 2
START TRANSACTION;                 START TRANSACTION;
UPDATE t SET v=1 WHERE id=1;      UPDATE t SET v=2 WHERE id=2;
-- waits for T2's lock on id=2    -- waits for T1's lock on id=1
UPDATE t SET v=3 WHERE id=2;      UPDATE t SET v=4 WHERE id=1;
-- DEADLOCK DETECTED → T1 or T2 rolled back by InnoDB

Deadlock Prevention Strategies

  • Always acquire locks in the same order across transactions.
  • Keep transactions short; commit quickly.
  • Use SELECT ... FOR UPDATE SKIP LOCKED for queue-style processing.
  • Use optimistic locking (version column) for low-contention scenarios.
  • Use innodb_deadlock_detect=ON (default) and monitor SHOW ENGINE INNODB STATUS.

Left-Prefix Rule for Composite Indexes

-- Index: (last_name, first_name, dob)
-- Uses index:
SELECT * FROM employees WHERE last_name = 'Smith';
SELECT * FROM employees WHERE last_name = 'Smith' AND first_name = 'John';
SELECT * FROM employees WHERE last_name = 'Smith' AND first_name = 'John' AND dob = '1990-01-01';

-- Does NOT use index (skips leading column):
SELECT * FROM employees WHERE first_name = 'John';
SELECT * FROM employees WHERE dob = '1990-01-01';

-- Partial use (stops at range):
SELECT * FROM employees WHERE last_name = 'Smith' AND first_name LIKE 'J%';
-- Uses last_name equality + first_name range scan; dob column not used

Index Selectivity & Cardinality

Selectivity = unique values / total rows. High selectivity (close to 1) → index is efficient. Low-cardinality columns (gender: M/F) rarely benefit from a standalone index. Check with:

SELECT COUNT(DISTINCT column) / COUNT(*) AS selectivity FROM table;
SHOW INDEX FROM table;  -- shows Cardinality column

Query Optimization

Key Rules

  • Avoid SELECT * — fetch only needed columns, enables covering indexes.
  • Avoid functions on indexed columns in WHERE: WHERE YEAR(created_at) = 2024 disables the index; rewrite as WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'.
  • Avoid implicit type conversions: WHERE id = '42' on an INT column causes full scan.
  • Use LIMIT with ORDER BY on indexed columns.
  • Prefer EXISTS over IN for correlated subqueries against large sets.
  • Use covering indexes to eliminate bookmark lookups.
  • Enable slow query log: slow_query_log=1, long_query_time=1.
-- Bad: function on indexed column
SELECT * FROM orders WHERE DATE(created_at) = '2024-06-01';

-- Good: range scan on index
SELECT id, total FROM orders
WHERE created_at >= '2024-06-01' AND created_at < '2024-06-02';

-- Bad: wildcard prefix kills index
SELECT * FROM products WHERE name LIKE '%phone%';

-- Good: full-text search
SELECT * FROM products WHERE MATCH(name) AGAINST('phone' IN BOOLEAN MODE);

-- Covering index example
CREATE INDEX idx_orders_cover ON orders(customer_id, status, created_at, total);
SELECT status, created_at, total FROM orders WHERE customer_id = 42;
-- Extra: Using index (no table row lookup needed)

Normalization

Normal Forms

First Normal Form (1NF)

Each column must contain atomic (indivisible) values. No repeating groups. Each row must be uniquely identifiable.

Before (Violation)After (1NF)
Orders: id=1, items="book,pen,ruler"order_items: order_id=1, item="book"; order_id=1, item="pen"

Second Normal Form (2NF)

Must be 1NF. Every non-key attribute must depend on the whole composite primary key (no partial dependency).

-- Violation: StudentID+CourseID composite PK
-- CourseName depends only on CourseID (partial dependency)
StudentCourse(StudentID, CourseID, Grade, CourseName)

-- Fixed: split into two tables
StudentCourse(StudentID, CourseID, Grade)  -- Grade depends on full PK
Course(CourseID, CourseName)               -- CourseName depends only on CourseID

Third Normal Form (3NF)

Must be 2NF. No transitive dependencies — non-key columns must not depend on other non-key columns.

-- Violation: ZipCode → City (transitive dependency through non-key)
Employee(EmpID, Name, ZipCode, City)

-- Fixed:
Employee(EmpID, Name, ZipCode)
ZipCodes(ZipCode, City)

Boyce-Codd Normal Form (BCNF)

Stricter than 3NF. For every functional dependency X → Y, X must be a superkey. Handles anomalies 3NF misses when there are overlapping candidate keys.

Denormalization

Intentionally introducing redundancy for performance. Common when joins become too expensive at scale.

  • Pre-joining: store user_name in orders table to avoid JOIN at read time.
  • Aggregates: store order_count in customers table; update via trigger.
  • Trade-off: faster reads, slower/complex writes, potential data inconsistency.

Subqueries vs CTEs

-- Subquery (inline)
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- CTE (WITH clause) — same result, more readable
WITH avg_salary AS (
  SELECT AVG(salary) AS avg_sal FROM employees
)
SELECT e.name, e.salary
FROM employees e
CROSS JOIN avg_salary a
WHERE e.salary > a.avg_sal;

-- Recursive CTE — organizational hierarchy
WITH RECURSIVE hierarchy AS (
  SELECT id, name, manager_id, 1 AS level
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, h.level + 1
  FROM employees e
  JOIN hierarchy h ON e.manager_id = h.id
)
SELECT * FROM hierarchy ORDER BY level;

-- CTE advantages: reusable in same query, can be recursive,
-- easier to read complex multi-step transformations

Window Functions

-- ROW_NUMBER — unique sequential number
SELECT name, salary, department,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
FROM employees;

-- RANK — same rank for ties, gaps after ties (1,2,2,4)
-- DENSE_RANK — same rank for ties, no gaps (1,2,2,3)
SELECT name, salary,
  RANK()       OVER (ORDER BY salary DESC) AS rank_with_gaps,
  DENSE_RANK() OVER (ORDER BY salary DESC) AS rank_no_gaps
FROM employees;

-- NTILE — divide into N buckets
SELECT name, salary,
  NTILE(4) OVER (ORDER BY salary DESC) AS quartile
FROM employees;

-- LAG/LEAD — access previous/next rows
SELECT name, salary, hire_date,
  LAG(salary,  1, 0) OVER (ORDER BY hire_date) AS prev_salary,
  LEAD(salary, 1, 0) OVER (ORDER BY hire_date) AS next_salary
FROM employees;

-- SUM OVER PARTITION — running total per department
SELECT name, department, salary,
  SUM(salary) OVER (
    PARTITION BY department
    ORDER BY hire_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total
FROM employees;

-- FIRST_VALUE / LAST_VALUE
SELECT name, department, salary,
  FIRST_VALUE(name) OVER (
    PARTITION BY department ORDER BY salary DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS top_earner
FROM employees;

Stored Procedures, Triggers & Views

-- Stored Procedure
DELIMITER $$
CREATE PROCEDURE transfer_funds(
  IN from_id INT, IN to_id INT, IN amount DECIMAL(10,2)
)
BEGIN
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN ROLLBACK; END;
  START TRANSACTION;
    UPDATE accounts SET balance = balance - amount WHERE id = from_id;
    UPDATE accounts SET balance = balance + amount WHERE id = to_id;
  COMMIT;
END$$
DELIMITER ;
CALL transfer_funds(1, 2, 500.00);

-- Trigger (audit log)
CREATE TRIGGER after_salary_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
  IF OLD.salary != NEW.salary THEN
    INSERT INTO salary_audit(emp_id, old_sal, new_sal, changed_at)
    VALUES (OLD.id, OLD.salary, NEW.salary, NOW());
  END IF;
END;

-- View
CREATE OR REPLACE VIEW active_orders AS
SELECT o.id, o.total, c.name AS customer
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status != 'cancelled';
-- Updatable views: no GROUP BY, DISTINCT, aggregate functions, subqueries
-- Materialized views: not native in MySQL (use scheduled table refresh)

Consistent Hashing is used by DynamoDB, Cassandra, and distributed caches. It arranges shards on a virtual ring; adding/removing a node only remaps 1/N of the keys rather than rehashing everything.

Replication

MySQL Replication

  • Async Master-Slave: Binary log events sent to replica asynchronously. Replica lag possible. Read scaling. Failover requires manual promotion.
  • Semi-sync: Master waits for at least one replica to acknowledge before returning to client. Reduces data loss risk.
  • GTID-based: Global Transaction Identifiers enable automatic failover. Each transaction gets a unique ID; replicas track which GTIDs they have applied.
  • Group Replication / InnoDB Cluster: Multi-master with distributed consensus (Paxos). Used in MySQL InnoDB Cluster / MySQL Shell.
-- Check replica lag
SHOW SLAVE STATUS\G
-- Look at: Seconds_Behind_Master, Relay_Log_Pos, Exec_Master_Log_Pos

-- GTID setup
SET GLOBAL gtid_mode = ON;
SET GLOBAL enforce_gtid_consistency = ON;
CHANGE MASTER TO MASTER_HOST='primary', MASTER_AUTO_POSITION=1;

Connection Pooling — HikariCP

// HikariCP — fastest Java connection pool
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/mydb");
config.setUsername("user");
config.setPassword("secret");
config.setMaximumPoolSize(20);          // max connections
config.setMinimumIdle(5);              // min idle connections
config.setIdleTimeout(600000);         // 10 min idle before eviction
config.setMaxLifetime(1800000);        // 30 min max connection lifetime

config.setLeakDetectionThreshold(2000); // warn if connection held > 2s

Pool sizing rule (Little's Law): pool_size = (core_count * 2) + effective_spindle_count. For I/O-bound workloads on SSDs, start with core_count * 2. Too large a pool wastes memory and causes context switching. Netflix and others find 10-20 connections often outperforms 100.

MongoDB — Data Model

MongoDB stores data as BSON (Binary JSON) documents inside collections inside databases. Documents are schema-flexible (each document can have different fields). A document's maximum size is 16 MB.

BSON Types

  • String, Integer (32/64-bit), Double, Boolean, Date, Null, Regex, Array, Object, ObjectId (12-byte unique ID), Binary, Timestamp, Decimal128, MinKey/MaxKey

CRUD Operations & Query Operators

// Insert
db.users.insertOne({ name: "Alice", age: 30, tags: ["admin", "user"] });
db.users.insertMany([{ name: "Bob" }, { name: "Carol" }]);

// Read
db.users.find({ age: { $gt: 25, $lte: 40 } });           // $gt, $gte, $lt, $lte
db.users.find({ tags: { $in: ["admin", "moderator"] } }); // $in
db.users.find({ email: { $exists: true } });              // $exists
db.users.find({ name: { $regex: /^Al/i } });              // $regex
db.users.find({ $and: [{ age: { $gt: 20 } }, { active: true }] }); // $and
db.users.find({ $or: [{ role: "admin" }, { role: "superuser" }] }); // $or
db.users.find({ age: { $not: { $lt: 18 } } });            // $not
db.users.find({}, { name: 1, age: 1, _id: 0 });           // projection

// Update
db.users.updateOne({ name: "Alice" }, { $set: { age: 31 }, $push: { tags: "verified" } });
db.users.updateMany({ active: false }, { $set: { deleted: true } });
db.users.findOneAndUpdate({ name: "Bob" }, { $inc: { loginCount: 1 } }, { returnDocument: "after" });

// Delete
db.users.deleteOne({ name: "Bob" });
db.users.deleteMany({ deleted: true });

Aggregation Pipeline

// Full pipeline example: revenue by category for active orders
db.orders.aggregate([
  { $match: { status: "completed", createdAt: { $gte: new Date("2024-01-01") } } },
  { $unwind: "$items" },
  { $lookup: {
      from: "products",
      localField: "items.productId",
      foreignField: "_id",
      as: "product"
  }},
  { $unwind: "$product" },
  { $group: {
      _id: "$product.category",
      totalRevenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } },
      orderCount: { $sum: 1 },
      avgOrderValue: { $avg: "$items.price" }
  }},
  { $addFields: { category: "$_id" } },
  { $project: { _id: 0, category: 1, totalRevenue: 1, orderCount: 1, avgOrderValue: 1 } },
  { $sort: { totalRevenue: -1 } },
  { $limit: 10 }
]);

$groupGroup by _id, apply accumulators: $sum, $avg, $min, $max, $push, $addToSet
$projectReshape documents: include/exclude fields, compute expressions

  await db.accounts.updateOne({ _id: from }, { $inc: { balance: -amount } }, { session });

  await session.commitTransaction();
} catch (err) {

} finally {
  session.endSession();
}

Sharding Architecture

  • mongos: Router — receives client queries, routes to correct shards
  • Config servers: Store cluster metadata (chunk ranges → shard mapping)
  • Shards: Each shard is itself a replica set
  • Shard key selection: High cardinality + low frequency + not monotonically increasing. Hashed shard key distributes writes evenly; ranged shard key enables range queries on one shard.

Cassandra — Data Model

Cassandra is a wide-column store designed for massive write throughput and linear horizontal scalability. Data is modeled around query patterns, not entity relationships.

ConceptDescription
KeyspaceTop-level namespace; defines replication strategy and factor
TableCollection of rows; each row identified by primary key
Partition KeyDetermines which node stores the data (via consistent hashing of token ring). Rows with same PK are on same node — design for even distribution.
Clustering ColumnsSort order within a partition. Enables efficient range scans inside a partition.
Static ColumnsShared across all rows in a partition; stored once per partition

CREATE KEYSPACE ecommerce WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc1': 3
};

-- User messages table: query by user_id, sorted by time
CREATE TABLE messages_by_user (
  user_id   UUID,
  sent_at   TIMESTAMP,
  message   TEXT,
  sender    TEXT,
  thread_id UUID STATIC,           -- same for all rows in partition
  PRIMARY KEY (user_id, sent_at)

Cassandra Read & Write Path

Write Path

  1. Write to CommitLog (sequential disk append — crash recovery)
  2. Write to MemTable (in-memory, per table)
  3. Return ACK to client
  4. When MemTable reaches threshold → flush to SSTable (immutable, sorted on disk)

Read Path

  1. Check Bloom Filter — probabilistic check: "Does this SSTable potentially contain this key?" Skip if definitely not.
  2. Check Key Cache (partition key → offset in SSTable)
  3. Check Row Cache if enabled
  4. Read SSTable Partition Summary → locate partition index range
  5. Read SSTable Partition Index → exact offset
  6. Seek to offset and read from SSTable(s)
  7. Merge results from MemTable + all SSTables using timestamps (most recent wins)

Gossip Protocol

Each node exchanges state with 1-3 other nodes every second. Within ~log(N) rounds, all nodes know the state of every other node (membership, load, schema version). No single point of failure for cluster membership.

Tombstones

Deletes in Cassandra write a tombstone marker (not physical delete). Tombstones are removed during compaction after gc_grace_seconds (default: 10 days). Too many tombstones cause GC pressure and slow reads. Monitor with nodetool tablehistograms.

Vector Databases — Embeddings

An embedding is a dense numerical vector (e.g., 1536 floats) produced by a neural network that captures semantic meaning. Similar concepts end up geometrically close in vector space. Models like OpenAI text-embedding-3-small, BERT, or Sentence Transformers produce these vectors.

Approximate Nearest Neighbor (ANN) Algorithms

HNSW — Hierarchical Navigable Small World

Builds a multi-layer graph. Top layers are sparse (long-range connections for fast navigation); bottom layer is dense (all nodes connected to neighbors). Search starts at top, greedily moves toward query, descends to next layer when local minimum found. Used by Weaviate, Qdrant, Milvus, pgvector.

  • M: max connections per node per layer — higher = better recall, more memory
  • ef_construction: search width during indexing — higher = better quality index, slower build
  • ef: search width at query time — tunable recall/latency trade-off

IVF — Inverted File Index

Divides vector space into nlist clusters (k-means). At query time, search only the nprobe closest clusters. Faster than brute-force but approximate. Used by Faiss, Milvus.

Product Quantization (PQ)

Compresses vectors by splitting into sub-vectors and quantizing each independently. Reduces memory 4-32x at cost of accuracy. Often combined with IVF (IVF-PQ) for large datasets.

Interview Q&As — 20+ Questions

Q1. What is the difference between Atomicity and Consistency in ACID? Easy

Atomicity ensures all operations in a transaction succeed or none do — it's an all-or-nothing guarantee enforced by the undo log. Consistency ensures the database transitions from one valid state to another, honoring all integrity constraints (foreign keys, CHECK constraints, triggers). Atomicity is about execution; consistency is about state validity. A transaction can be atomic (fully committed) yet still violate consistency if the application logic is wrong — that's why consistency is partly the application's responsibility.

Q2. Explain the difference between Dirty Read, Non-Repeatable Read, and Phantom Read. Easy
  • Dirty Read: Tx A reads uncommitted changes from Tx B. If B rolls back, A read data that never existed. Prevented by Read Committed+.
  • Non-Repeatable Read: Tx A reads a row twice; between reads, Tx B commits an UPDATE. A gets different values. Prevented by Repeatable Read+.
  • Phantom Read: Tx A executes a range query twice; between reads, Tx B inserts a row that matches the range. A sees a different number of rows. Prevented by Serializable (and by InnoDB's gap locks in Repeatable Read for locking reads).
Q3. How does InnoDB implement MVCC? Intermediate

InnoDB adds two hidden columns to every row: DB_TRX_ID (ID of the last transaction that inserted/updated) and DB_ROLL_PTR (pointer to the undo log record for the previous version). When a transaction reads, it uses its snapshot timestamp to follow the undo log chain until it finds a version created before its own start. This means readers never block writers and writers never block readers — crucial for high concurrency. The snapshot is taken at the first read in the transaction (RR) or at each statement (RC).

Q4. What is a covering index and when should you use one? Intermediate

A covering index contains all columns referenced in a query (SELECT, WHERE, JOIN, ORDER BY) so the query can be satisfied entirely from the index without fetching the actual row (no "bookmark lookup"). In EXPLAIN, you see "Using index" in the Extra column. Use it for high-frequency, performance-critical queries with a predictable shape. Example: SELECT status, total FROM orders WHERE customer_id = ? ORDER BY created_at → create index (customer_id, created_at, status, total). Downsides: larger index, slower writes.

Q5. What does the type column in EXPLAIN mean? What types indicate problems? Intermediate

The type column shows how MySQL joins/accesses the table:

  • system/const: At most 1 row — best. Constant lookup (equality on PK).
  • eq_ref: One row per row from previous table. JOIN on PK or unique index.
  • ref: Multiple rows per join; non-unique index or leftmost prefix.
  • range: Index range scan (BETWEEN, >, <, IN). OK for selective ranges.
  • index: Full index scan — reads all index entries. Faster than ALL but still O(N).
  • ALL: Full table scan. Usually a problem on large tables — add an index.

"Using filesort" and "Using temporary" in Extra also indicate expensive operations that may need index or query redesign.

Q6. Explain 3NF vs BCNF with an example. Intermediate

Table: CourseSchedule(student, course, teacher) where each course has exactly one teacher, and each teacher teaches only one course. Candidate keys: {student, course} and {student, teacher}. FDs: course → teacher, teacher → course.

This is in 3NF (no transitive dependencies via non-key attributes) because teacher is part of a candidate key. But it violates BCNF because the FD course → teacher has a left side (course) that is not a superkey. BCNF requires decomposing into CourseTeacher(course, teacher) + StudentCourse(student, course). BCNF may lose FD preservation (teacher→course can't be enforced without JOIN) — sometimes 3NF is preferred for that reason.

Q7. How would you design a schema for a messaging app in Cassandra? Advanced

Key query: "Get last N messages in a conversation, sorted by time." Design around the read pattern:

CREATE TABLE messages (
  conversation_id UUID,
  sent_at         TIMEUUID,    -- TIMEUUID = timestamp + UUID, monotonically unique
  sender_id       UUID,
  content         TEXT,
  PRIMARY KEY (conversation_id, sent_at)
) WITH CLUSTERING ORDER BY (sent_at DESC)
  AND default_time_to_live = 7776000;  -- 90 days TTL

Partition key = conversation_id → all messages for one conversation on same node (efficient). Clustering by sent_at DESC → range scan without sort. For "get conversations for a user," maintain a separate table conversations_by_user(user_id, last_message_at, conversation_id). Avoid wide partitions: enforce a time-bucketing strategy (conversation_id + bucket_date) to cap partition size for high-traffic conversations.

Q8. What is a ghost record in InnoDB and how does it relate to gap locks? Advanced

When InnoDB uses Repeatable Read, range queries use next-key locks (row lock + gap lock on the preceding gap). The gap lock prevents other transactions from inserting into the range between existing index entries, preventing phantom reads for locking reads (SELECT ... FOR UPDATE / LOCK IN SHARE MODE). However, gap locks can increase deadlock probability — two transactions both holding gap locks and then trying to insert into the same gap will deadlock. For workloads needing maximum concurrency, Read Committed (which doesn't use gap locks) + application-level conflict handling is sometimes preferable.

Q9. Explain MongoDB's aggregation $lookup and its limitations. Intermediate

$lookup performs a LEFT OUTER JOIN from the current collection to another. It adds matched documents as an array field. Limitations: (1) The "from" collection must be in the same database. (2) The pipeline variant ($lookup with pipeline) allows filtering but is more expensive. (3) For sharded collections, $lookup on the shard key works; otherwise it may require scatter-gather. (4) Results can hit the 16 MB document size limit. For high-throughput use cases, consider denormalizing (embedding related data) rather than using $lookup at read time.

Q10. How does Cassandra handle writes and what is the write path? Intermediate

1. Write arrives at coordinator node (any node can be coordinator). 2. Coordinator routes to replica nodes based on partition key hash + consistent hashing ring. 3. Each replica: (a) appends to CommitLog sequentially (crash recovery); (b) updates in-memory MemTable. 4. Coordinator waits for responses based on write consistency level (ONE, QUORUM, ALL). 5. When MemTable hits threshold → flushed to immutable SSTable on disk. 6. Compaction periodically merges SSTables, removes tombstones, reclaims space. This design makes writes extremely fast (sequential disk writes to CommitLog, no lock contention) at the cost of read amplification (must merge multiple SSTables).

Q11. What is sharding and how is consistent hashing used? Advanced

Sharding distributes data across multiple database servers (shards) to scale writes beyond a single machine. Consistent hashing arranges virtual nodes (vnodes) on a hash ring (0 to 2^128-1). Each physical server owns several vnodes. A key is hashed to a position on the ring; it belongs to the first vnode clockwise from that position. Adding a server: only 1/N of keys move (those between the new server and its predecessor). Without consistent hashing, a modulo-based approach requires remapping almost all keys when N changes. Cassandra uses 256 vnodes per node by default, giving even distribution and fine-grained rebalancing.

Q12. Explain the CAP theorem and give examples of where different databases sit. Intermediate

CAP: a distributed system can guarantee at most two of: Consistency (every read gets the latest write), Availability (every request gets a response), Partition Tolerance (system works despite network partitions). Since partitions happen in real networks, you effectively choose CP or AP:

  • CP: HBase, Zookeeper, etcd — sacrifice availability (refuse requests) during partition to stay consistent.
  • AP: Cassandra (tunable), DynamoDB, CouchDB — remain available but may serve stale data.
  • CA: Traditional single-node RDBMS (MySQL, Postgres) — not partition tolerant by design; not a distributed system.

PACELC extends CAP: even when no partition, there's a latency vs consistency trade-off (L vs C).

Q13. What is a B-tree vs B+ tree and why do databases use B+ trees? Advanced

In a B-tree, data is stored in all nodes (internal + leaf). In a B+ tree, data is stored only in leaf nodes; internal nodes contain only keys for navigation. Leaf nodes are linked in a doubly linked list. Databases use B+ trees because: (1) Range scans are O(log N + K) — navigate to start, then scan the leaf chain; (2) Internal nodes hold more keys (no data pointers) → shorter tree height → fewer I/O reads; (3) Sequential reads of leaves exploit disk prefetching; (4) All queries go to leaves, giving predictable performance.

Q14. How do you handle pagination efficiently in MySQL for millions of rows? Advanced

Offset-based pagination (LIMIT 20 OFFSET 10000) requires scanning and discarding the first 10,000 rows — O(offset) performance. Solutions:

  • Keyset/Cursor pagination: WHERE id > last_seen_id ORDER BY id LIMIT 20 — O(log N), uses index, no degradation at deep pages. Works for monotonic ordering.
  • Deferred join: SELECT * FROM t JOIN (SELECT id FROM t ORDER BY created_at LIMIT 20 OFFSET 10000) x ON t.id = x.id — covering index scan for IDs, then row lookup for only 20 rows. Better than naive OFFSET but still O(offset).
  • For random-access pagination, consider Elasticsearch for search-as-you-scroll or Cassandra's token-based pagination.
Q15. What is a vector database and how does HNSW work? Intermediate

A vector database indexes high-dimensional embedding vectors for fast approximate nearest neighbor (ANN) search. HNSW (Hierarchical Navigable Small World) builds a multi-layer graph: each node represents a vector; edges connect it to its M nearest neighbors. Upper layers are sparse (coarse navigation); the bottom layer is dense (all nodes). Searching: start at the entry point of the top layer, greedily move to the neighbor closest to the query vector, descend to the next layer when stuck at a local minimum, repeat until layer 0. Index construction: each new vector is inserted at a random maximum layer; connections are made to ef_construction nearest neighbors at each layer it participates in. HNSW achieves sub-millisecond query times on millions of vectors with 95-99% recall.

Q16. Explain window functions vs GROUP BY — when does each apply? Intermediate

GROUP BY collapses multiple rows into one (aggregation) — you lose individual row data. Window functions (OVER()) perform calculations across rows related to the current row without collapsing them — each row retains its identity plus the computed value. Use GROUP BY for: "total revenue by category." Use window functions for: "rank each employee by salary within their department while keeping all employee rows," "running totals," "compare a row to the previous row (LAG/LEAD)." Window functions are processed after WHERE/GROUP BY/HAVING but before ORDER BY and LIMIT.

Q17. What is connection pooling and why does pool size matter? Easy

Connection pooling maintains a cache of pre-established database connections that can be reused, avoiding the expensive overhead (TCP handshake + auth) of opening a new connection per request. Pool size matters because: (1) too few → requests queue and timeout under load; (2) too many → each connection consumes memory on the DB server (~1-8 MB/connection in MySQL), and context switching overhead increases. The sweet spot (per Little's Law) is often core_count × 2 for CPU-bound queries. HikariCP metrics to monitor: active connections, idle connections, connection acquisition time, pool wait count.

Q18. How do you prevent and resolve deadlocks in MySQL? Intermediate

Prevention: (1) Always access tables and rows in the same order across transactions. (2) Keep transactions small and short-lived. (3) Use optimistic locking (version column + CAS) for read-heavy patterns. (4) Use SELECT ... FOR UPDATE SKIP LOCKED for work queues. (5) Avoid user input inside transactions.

Detection/Recovery: InnoDB detects deadlocks automatically via the waits-for graph; it rolls back the transaction with fewer undo records. The application must catch ER_LOCK_DEADLOCK (1213) and retry. Enable innodb_print_all_deadlocks=1 and analyze SHOW ENGINE INNODB STATUS for the deadlock section.

Q19. Compare MongoDB vs Cassandra for a write-heavy IoT use case. Advanced

Cassandra wins for: Linear write scalability (no master), predictable low latency for high-frequency writes, built-in TTL for data expiry, TWCS compaction ideal for time-series, tunable consistency allows sacrifice of strong consistency for throughput, multi-DC replication. MongoDB wins for: Rich query capabilities, aggregation pipeline for ad-hoc analytics, flexible schema (varying sensor types), change streams for real-time apps. Recommendation: Cassandra for pure ingestion + time-range reads with known access patterns; MongoDB if you need ad-hoc queries, richer data models, or multi-document transactions alongside IoT data.

Q20. What is the difference between horizontal and vertical scaling? When does each break down? Easy

Vertical scaling (scale up): add more CPU/RAM/faster disk to existing server. Simple, no application changes, but has hardware limits, single point of failure, and diminishing returns (doubling cores doesn't double throughput due to lock contention). Horizontal scaling (scale out): add more servers. Linear scalability in theory, fault tolerant, but requires application changes (sharding logic, eventual consistency handling, distributed transactions become hard). Relational databases traditionally scale vertically; NoSQL databases (Cassandra, MongoDB with sharding, DynamoDB) are designed for horizontal scaling. Read-heavy SQL workloads can scale horizontally with read replicas.

Q21. What is index cardinality and how does it affect query performance? Intermediate

Cardinality is the number of distinct values in a column. High cardinality (e.g., user_id, email) → highly selective index → optimizer chooses it for most queries. Low cardinality (e.g., gender, boolean flag) → not selective → index scan reads almost all rows, so optimizer may prefer a full table scan. The MySQL optimizer uses index statistics (stored in information_schema.STATISTICS, updated by ANALYZE TABLE) to estimate selectivity. For a low-cardinality column used with a high-cardinality column, a composite index (low_card_col, high_card_col) can still be useful if queries filter on both, though the order in the index should match the query's equality conditions before range conditions.

Q22. What are the trade-offs between embedding vs referencing in MongoDB? Intermediate

Embedding (nested document): denormalized; single-document read — no $lookup; great for one-to-few relationships with data that is frequently read together; update propagation is simple (one document to update). Downsides: document grows large (16 MB limit); updating a single embedded field requires locking the parent document; data duplication when same sub-entity appears in many documents. Referencing (foreign key as ObjectId): normalized; requires $lookup (extra I/O, cannot use efficiently across shards in all cases); better for large sub-documents or one-to-many/many-to-many. Rule of thumb: embed for "owns" relationships (order → line items); reference for "refers to" (order → customer).

Q23. Explain the Cassandra "denormalize by query" principle. Advanced

In Cassandra, you cannot do arbitrary JOINs or secondary index scans efficiently. Instead, you create a table for every distinct query pattern you need, duplicating data across tables. Example: for a ride-sharing app you might have: rides_by_driver(driver_id, started_at, ...) for driver history queries and rides_by_rider(rider_id, started_at, ...) for rider history — same ride data stored twice. The application writes to both tables (ideally in a batch using LOGGED BATCH for atomicity across tables in the same partition, or with idempotent retries). This trades storage for query performance and eliminates the need for expensive scatter-gather reads.

Q24. What is the "N+1 query problem" and how do you solve it? Easy

N+1 occurs when code fetches a list of N records (1 query) then executes an additional query for each record to fetch related data (N queries) — total N+1 queries. Example: fetch 100 orders (1 query), then for each order fetch the customer (100 queries) = 101 queries. Solutions: (1) JOIN / eager loading: fetch orders + customers in one query; (2) IN clause batch: collect all customer IDs from orders, execute one WHERE id IN (...) query; (3) DataLoader pattern: batch + cache loads within a request (used in GraphQL). ORM solutions: Hibernate's JOIN FETCH, Sequelize's include, Prisma's nested include.

Q25. How does pgvector compare to dedicated vector databases? Advanced

pgvector advantages: Lives inside PostgreSQL — combine vector similarity search with full SQL (JOINs, transactions, RBAC, existing tooling). No additional infrastructure. Use HNSW or IVFFlat index. Good for <10M vectors with moderate QPS. pgvector limitations: Not optimized for pure vector workloads; HNSW index build is single-threaded (slow for large datasets); memory-bound (index must fit in shared_buffers/RAM for good performance); limited to cosine, L2, and inner product. Dedicated DBs (Pinecone, Qdrant, Weaviate) advantages: Purpose-built for billion-scale ANN search, distributed, serve 1000s of QPS, richer filtering (pre-filter vs post-filter strategies), metadata storage optimized alongside vectors. Choose pgvector for pragmatism and small-medium scale; choose dedicated for high QPS or billion-scale.
