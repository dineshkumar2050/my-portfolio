1What is GraphQL?

GraphQL is a query language for APIs and a runtime for fulfilling those queries, developed at Facebook (Meta) in 2012 and open-sourced in 2015. Clients define the exact shape of data they need; the server returns exactly that — no more, no less.

REST vs GraphQL Comparison

ConcernRESTGraphQL
Over-fetchingCommon — endpoint returns fixed shape, client may only need 2 of 20 fieldsEliminated — client selects exact fields needed
Under-fetching (N+1)Common — fetch user, then fetch their posts separately (multiple round trips)Single request can fetch user + posts + comments in one query
EndpointsMultiple endpoints: GET /users, POST /posts, GET /users/:id/postsSingle endpoint: POST /graphql (or GET for persisted queries)

2Core Concepts — SDL & Type System

The Schema Definition Language (SDL) is the human-readable syntax for defining a GraphQL schema. The schema is the contract between client and server.

Scalar Types

String

UTF-8 character sequence

Int

Signed 32-bit integer

Float

Signed double-precision float

Boolean

true or false

ID

Unique identifier (serialized as String but semantically distinct)

Custom Scalars

Date, DateTime, JSON, URL, UUID — defined with scalar keyword + custom serializer

Type Definitions

# Object Type — main building block
type User {
  id: ID!              # ! = non-null (required)
  name: String!
  email: String!
  age: Int             # nullable — may be null
  posts: [Post!]!      # non-null list of non-null Post objects
  role: UserRole!      # enum
}

# Enum
enum UserRole {
  ADMIN
  EDITOR
  VIEWER
}

# Interface — shared fields across types
interface Node {
  id: ID!
}

type Post implements Node {
  id: ID!
  title: String!
  author: User!
  tags: [String!]!
}

# Union — one of several types (no shared fields required)
union SearchResult = User | Post | Comment

# Input Type — used for mutation arguments (cannot use object types as args)
input CreatePostInput {
  title: String!
  content: String!
  authorId: ID!
  tags: [String!]
}

# The root operation types
type Query {
  user(id: ID!): User
  users(filter: UserFilter): [User!]!
  search(term: String!): [SearchResult!]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): Boolean!
}

type Subscription {
  postCreated: Post!
  commentAdded(postId: ID!): Comment!
}
Non-null (!) semantics String! means the field will never be null (server guarantees it). [Post!]! means the list itself is non-null AND each item in the list is non-null. A field without ! is nullable and may return null. Over-using ! makes schemas brittle — nullable fields allow graceful degradation when partial data is available.

3Queries

Basic Query, Fields, and Nested Fields

# Named query with variable
query GetUser($id: ID!) {
  user(id: $id) {
    id
    name
    email           # only the fields you need
    posts {
      id
      title
      # deeply nested
      author {
        name
      }
    }
  }
}

# Variables (sent as JSON alongside the query)
{ "id": "user-123" }

Aliases — Fetch Same Field Twice

query ComparePosts {
  firstPost: post(id: "1") {    # alias: firstPost
    title
    likes
  }
  secondPost: post(id: "2") {   # alias: secondPost
    title
    likes
  }
}

Fragments — Reusable Field Sets

fragment UserFields on User {
  id
  name
  email
  avatar
}

query GetUsers {
  admin: user(id: "1") { ...UserFields }   # spread fragment
  editor: user(id: "2") { ...UserFields }
}

Inline Fragments — Polymorphic Queries on Unions/Interfaces

query Search($term: String!) {
  search(term: $term) {
    ... on User {        # inline fragment — only if result is User
      name
      email
    }
    ... on Post {
      title
      createdAt
    }
    ... on Comment {
      body
      author { name }
    }
  }
}

Directives — @include and @skip

query GetUser($id: ID!, $withPosts: Boolean!, $skipEmail: Boolean!) {
  user(id: $id) {
    name
    email @skip(if: $skipEmail)        # omit field if variable is true
    posts @include(if: $withPosts) {   # include field only if variable is true
      title
    }
  }
}
# Variables: { "id": "1", "withPosts": true, "skipEmail": false }

4Mutations

Mutations modify server-side data. By convention, mutation names use verbs: createPost, updateUser, deleteComment. Mutations always return data — typically the affected object so the client can update its cache.

# Mutation definition using Input Types
mutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {   # return the created post for cache update
    id
    title
    createdAt
    author {
      id
      name
    }
  }
}

# Variables
{
  "input": {
    "title": "Hello GraphQL",
    "content": "My first post",
    "authorId": "user-1",
    "tags": ["graphql", "tutorial"]
  }
}

Mutation Naming Conventions

PatternExampleUse Case
Verb + NouncreateUser, deletePostStandard CRUD
Nested InputupdateUser(input: UpdateUserInput!)Complex updates with multiple fields
Payload type returncreatePost: CreatePostPayload!Return both data and errors/metadata
 
# Payload pattern — separate success data from errors
type CreatePostPayload {
  post: Post            # null if failed
  errors: [UserError!]! # empty if succeeded
}

type UserError {
  message: String!
  field: String         # which field caused the error
}

type Mutation {
  createPost(input: CreatePostInput!): CreatePostPayload!
}
Multiple mutations in one request Unlike queries (which execute in parallel), mutations in a single request execute serially in order. This allows you to safely chain dependent mutations: mutation { createUser(...) { id } updateProfile(...) { ... } }.

5Subscriptions

GraphQL subscriptions provide real-time updates via long-lived connections (typically WebSocket). They are defined in the schema's Subscription type and use the same field selection syntax as queries.

Schema Definition

type Subscription {
  commentAdded(postId: ID!): Comment!       # scoped to a specific post
  userTyping(roomId: ID!): TypingEvent!     # real-time typing indicator
  orderStatusUpdated(orderId: ID!): Order!  # order tracking
}

type TypingEvent {
  user: User!
  isTyping: Boolean!
}

Client Subscription (Apollo Client)

import { useSubscription, gql } from '@apollo/client'

const COMMENT_ADDED = gql`
  subscription OnCommentAdded($postId: ID!) {
    commentAdded(postId: $postId) {
      id
      body
      author { name avatar }
      createdAt
    }
  }
`

function Comments({ postId }) {
  const { data, loading } = useSubscription(COMMENT_ADDED, {
    variables: { postId },
    onData: ({ client, data }) => {
      // Can update the cache manually here
      client.cache.modify({
        id: client.cache.identify({ __typename: 'Post', id: postId }),
        fields: {
          comments: (existing, { toReference }) =>
            [...existing, toReference(data.data.commentAdded)],
        },
      })
    },
  })
}

GraphQL over WebSocket Protocol

The modern standard is the graphql-ws protocol (successor to the older subscriptions-transport-ws). Transport sequence:

sequenceDiagram participant Client participant Server Client->>Server: WebSocket connection (ws://) Client->>Server: connection_init message Server-->>Client: connection_ack Client->>Server: subscribe {id, payload: {query, variables}} loop Real-time events Server-->>Client: next {id, payload: {data}} end Client->>Server: complete {id} OR Server sends complete

Use Cases

Real-time Chat

New messages pushed to all subscribers in a chat room as they are posted.

Live Dashboard

Metrics, analytics, or monitoring data updated in real-time as server-side values change.

Collaborative Editing

Cursor positions, document changes, and presence indicators in collaborative tools.

Order/Job Tracking

Status updates pushed to the client when an order or background job changes state.

6Resolvers

Resolvers are functions that fulfill each field in a GraphQL schema. The resolver tree mirrors the schema structure — every field can have a resolver.

Resolver Function Signature

// Every resolver receives these 4 arguments
function fieldResolver(
  parent: ParentType,  // result of the parent resolver (or root value for root fields)
  args: ArgsType,      // arguments passed to this field in the query
  context: Context,    // shared object: { db, user, dataloaders, request, ... }
  info: GraphQLResolveInfo  // AST info: field name, schema, path, etc.
): FieldType | Promise<FieldType>

Resolver Map Example (Apollo Server)

const resolvers = {
  // Root resolvers
  Query: {
    user: async (_, { id }, { db }) =>
      db.users.findById(id),

    users: async (_, { filter }, { db }) =>
      db.users.findAll(filter),
  },

  Mutation: {
    createPost: async (_, { input }, { db, user }) => {
      if (!user) throw new GraphQLError('Not authenticated', {
        extensions: { code: 'UNAUTHENTICATED' },
      })
      return db.posts.create({ ...input, authorId: user.id })
    },
  },

  // Object type resolvers — field-level
  User: {
    posts: async (parent, _, { db }) =>
      // parent is the User object returned by the Query.user resolver
      db.posts.findByAuthorId(parent.id),

    // Default resolver behavior — if no resolver defined:
    // returns parent[fieldName] — works automatically for scalar fields
    name: (parent) => parent.name,  // this resolver is redundant (default)
  },

  // Union/Interface resolver
  SearchResult: {
    __resolveType: (obj) => {
      if (obj.email) return 'User'
      if (obj.title) return 'Post'
      return null
    },
  },
}

// Context factory — runs on every request
const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: async ({ req }) => ({
    db: database,
    user: await authenticateToken(req.headers.authorization),
    dataloaders: createDataLoaders(database),
  }),
})
Default resolvers For scalar and enum fields, if no resolver is defined, GraphQL uses a default resolver that returns parent[fieldName]. You only need explicit resolvers for computed fields, fields with different names between DB and schema, or fields requiring data from another source.

7N+1 Problem & DataLoader

The N+1 Problem

When querying a list of items where each item has a related object resolved by a separate database call, you get 1 query for the list + N queries for the related objects — the "N+1 problem".

# This query triggers the N+1 problem
query {
  posts {          # 1 query: SELECT * FROM posts  → returns 100 posts
    title
    author {       # 100 queries: SELECT * FROM users WHERE id = ?
      name         # ...for each of the 100 posts
    }
  }
}
// Root resolver fires 1 query
Query: {
  posts: () => db.query('SELECT * FROM posts'),  // returns 100 rows
}
// Post.author resolver fires 1 query PER post
Post: {
  author: (post) => db.query('SELECT * FROM users WHERE id = ?', post.authorId),
  // Called 100 times = 100 DB queries!
}

DataLoader Solution

DataLoader batches multiple individual loads that happen within a single JavaScript event loop tick into a single call. It also caches results within a request lifecycle.

import DataLoader from 'dataloader'

// batchFn receives an ARRAY of keys collected within one event loop tick
const userLoader = new DataLoader(async (userIds: readonly string[]) => {
  // ONE batch query for all collected IDs
  const users = await db.query(
    'SELECT * FROM users WHERE id IN (?)',
    [userIds]
  )
  // CRITICAL: return results in the SAME ORDER as the input IDs
  const userMap = new Map(users.map(u => [u.id, u]))
  return userIds.map(id => userMap.get(id) ?? new Error(`User ${id} not found`))
})

// Use in resolver context — create per-request to prevent cross-request caching
const resolvers = {
  Post: {
    // Now all 100 author lookups within the same tick are batched into 1 DB query
    author: (post, _, { dataloaders }) =>
      dataloaders.users.load(post.authorId),
  },
}

// Context factory — create fresh loaders per request
const context = ({ req }) => ({
  db,
  dataloaders: {
    users: new DataLoader(batchUsers),
    posts: new DataLoader(batchPosts),
  },
})
graph TD A[GraphQL Request: 100 posts] --> B[Post.author called 100 times] B --> C[DataLoader collects IDs in event loop tick] C --> D[Single batch: SELECT WHERE id IN 100 IDs] D --> E[Return ordered results] E --> F[Each load promise resolves]
DataLoader caching DataLoader caches by key within a request lifecycle — if the same user is an author of multiple posts, it only fetches that user once. Create new DataLoader instances per request (not global singleton) to avoid serving stale data across requests.

loadMany

// Load multiple IDs at once from a single resolver
const users = await dataloaders.users.loadMany(['id-1', 'id-2', 'id-3'])
// Returns array: each element is either the value or an Error instance

8Schema Design

Connections Pattern (Relay Spec)

The Relay specification defines a standard for cursor-based pagination using connections. This pattern is widely adopted even outside of Relay because it's comprehensive and forward-compatible.

type UserConnection {
  edges: [UserEdge!]!
  pageInfo: PageInfo!
  totalCount: Int!
}

type UserEdge {
  node: User!           # the actual data object
  cursor: String!       # opaque pagination cursor
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

type Query {
  users(
    first: Int          # forward pagination: take N items
    after: String       # forward pagination: cursor to start after
    last: Int           # backward pagination
    before: String      # backward pagination
    filter: UserFilter
  ): UserConnection!
}

Nullable vs Non-Null Design

Make fields nullable when...

  • The data is optional by nature
  • A partial failure shouldn't null out the entire object
  • The relationship may not always be populated
  • You're exposing a field whose existence is uncertain

Use non-null (!) when...

  • The field is always present when the object exists
  • The ID of an entity
  • Required system fields (createdAt, updatedAt)
  • List containers (the list itself, not necessarily items)

9Apollo Federation

Apollo Federation allows you to build a distributed GraphQL schema where each microservice owns a piece of the schema (a "subgraph") and a central Router/Gateway composes them into a unified API.

graph TD Client --> Router[Apollo Router/Gateway] Router --> UsersService[Users Subgraph] Router --> PostsService[Posts Subgraph] Router --> ReviewsService[Reviews Subgraph] UsersService -.-> SharedEntity[User Entity key: id] PostsService -.-> SharedEntity ReviewsService -.-> SharedEntity

Subgraph — Defining an Entity

# users-service/schema.graphql
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.0", import: ["@key"])

type User @key(fields: "id") {    # @key marks this as a Federation entity
  id: ID!
  name: String!
  email: String!
}

type Query {
  user(id: ID!): User
  me: User
}

Subgraph — Extending an Entity from Another Service

# posts-service/schema.graphql
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.0",
        import: ["@key", "@external"])

# Reference the User entity defined in users-service
type User @key(fields: "id") {
  id: ID! @external   # field lives in users-service, referenced here
  posts: [Post!]!     # extension field owned by posts-service
}

type Post {
  id: ID!
  title: String!
  author: User!
}

type Query {
  post(id: ID!): Post
  posts: [Post!]!
}

Entity Resolver — __resolveReference

// posts-service resolvers
const resolvers = {
  User: {
    // Called by the Router when it needs to resolve User fields
    // from the posts-service — receives the key fields { id }
    __resolveReference: async (reference, { db }) => {
      // reference = { __typename: 'User', id: '123' }
      return db.users.findById(reference.id)
    },
    posts: (user, _, { db }) =>
      db.posts.findByAuthorId(user.id),
  },
}
Federation Router The Apollo Router (Rust-based, replaces the JS Gateway) composes the subgraphs' schemas, generates a query plan, and routes fields to the appropriate subservice — transparently to clients who see a single unified schema.

useQuery, useMutation, useSubscription Hooks

import { useQuery, useMutation, gql } from '@apollo/client'

const GET_USERS = gql`
  query GetUsers($role: UserRole) {
    users(filter: { role: $role }) {
      id
      name
      email
    }
  }
`

function UserList() {
  const { loading, error, data, refetch } = useQuery(GET_USERS, {
    variables: { role: 'ADMIN' },
    fetchPolicy: 'cache-first',      // cache policy (see below)
    pollInterval: 0,                 // 0 = no polling; set ms for polling
    skip: false,                     // skip query entirely
  })

  if (loading) return <Spinner />
  if (error) return <Error error={error} />
  return <ul>{data.users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
}

InMemoryCache — Normalization

Apollo Client normalizes cached data by __typename + id. Every object with an id (or custom key fields) is stored as a flat reference, so the same entity referenced in multiple queries is stored once and updates propagate everywhere.

const cache = new InMemoryCache({
  typePolicies: {
    Query: {
      fields: {
        users: {
          // Merge paginated results instead of replacing them
          keyArgs: ['filter'],  // cache by filter arg, not pagination args
          merge(existing = [], incoming) {
            return [...existing, ...incoming]
          },
        },
      },
    },
    User: {
      // Custom key fields if not using 'id'
      keyFields: ['email'],  // normalize by email instead of id
    },
  },
})

11Client-Side Alternatives

urql — Lightweight & Flexible

Exchange-based architecture — each capability (caching, auth, subscriptions, offline) is a composable exchange. Smaller bundle (~7KB gz). Built-in document caching and normalized caching (via @urql/exchange-graphcache).

import { createClient, Provider } from 'urql'
const client = createClient({ url: '/graphql' })
// <Provider value={client}>
// useQuery, useMutation, useSubscription hooks same API pattern

TanStack Query + graphql-request

For teams already using TanStack Query for REST APIs — add graphql-request as the fetch layer and use useQuery/useMutation normally. No normalized caching but full TanStack Query features (staleTime, refetching, devtools).

import { request } from 'graphql-request'
useQuery({
  queryKey: ['users'],
  queryFn: () => request('/graphql', GET_USERS),
})

12Error Handling

GraphQL Errors vs Network Errors

// GraphQL response with PARTIAL data + errors
{
  "data": {
    "user": { "id": "1", "name": "Alice" },
    "posts": null    // this field failed
  },
  "errors": [
    {
      "message": "Cannot fetch posts: DB timeout",
      "locations": [{ "line": 3, "column": 3 }],
      "path": ["posts"],
      "extensions": {
        "code": "INTERNAL_SERVER_ERROR",
        "timestamp": "2024-01-15T10:30:00Z"
      }
    }
  ]
}

A GraphQL response can have BOTH data AND errors — this is called a "partial success." The client can still render the user data even though posts failed to load.

Apollo Client Error Policies

errorPolicyBehaviour
none (default)Any error causes the entire data to be set to undefined. error is populated. No partial data.
ignoreErrors are silently discarded. Only the partial data is returned. error is undefined.
allBoth data (partial) AND error are populated. Allows rendering partial results while showing error state for failed fields.
 
const { data, error } = useQuery(QUERY, { errorPolicy: 'all' })

// With errorPolicy: 'all', both can be present simultaneously
if (error) console.warn('Partial error:', error.graphQLErrors)
if (data) renderPartialUI(data)  // render what succeeded

Query Complexity Limiting

import costAnalysis from 'graphql-cost-analysis'

const server = new ApolloServer({
  plugins: [
    costAnalysis({
      maximumCost: 1000,       // reject queries above this cost
      defaultCost: 1,

    }),
  ],

Depth Limiting

import depthLimit from 'graphql-depth-limit'

const server = new ApolloServer({
  validationRules: [depthLimit(7)],  // reject queries deeper than 7 levels
})

Persisted Queries

Instead of sending full query strings on every request (expensive to parse), store queries server-side by their hash. Clients send only the hash — the server looks up the query string.

// Automatic Persisted Queries (APQ) — Apollo built-in
import { createPersistedQueryLink } from '@apollo/client/link/persisted-queries'
import { sha256 } from 'crypto-hash'

const link = createPersistedQueryLink({ sha256 }).concat(httpLink)
// First request: sends hash + full query; server caches it
// Subsequent requests: sends only hash — smaller payload, CDN cacheable

Field-Level Caching with @cacheControl

type Post @cacheControl(maxAge: 60) {  # cache responses for 60s
  id: ID!
  title: String!
  author: User @cacheControl(maxAge: 300)  # author data cached 5min
  content: String! @cacheControl(maxAge: 0)  # never cache
}

14Security

Disable Introspection in Production

const server = new ApolloServer({
  introspection: process.env.NODE_ENV !== 'production',
  // Introspection exposes your entire schema to attackers — disable in prod
})

Rate Limiting

import rateLimit from 'express-rate-limit'

// Limit to 100 requests per 15 minutes per IP
app.use('/graphql', rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
  message: { errors: [{ message: 'Too many requests' }] },

Authentication in Context

const server = new ApolloServer({
  context: async ({ req }) => {
    const token = req.headers.authorization?.replace('Bearer ', '')
    let user = null
    if (token) {
      try {
        user = await verifyJWT(token)  // throws if invalid
      } catch (e) {
        // Invalid token — user stays null; resolvers handle authorization
      }
    }
    return { user, db, dataloaders: createLoaders(db) }
  },
})

Authorization Patterns

Resolver-Level Authorization

Mutation: {
  deletePost: (_, { id }, { user }) => {
    if (!user) throw new GraphQLError(
      'Not authenticated',
      { extensions: { code: 'UNAUTHENTICATED' } }
    )
    if (user.role !== 'ADMIN') throw new GraphQLError(
      'Not authorized',
      { extensions: { code: 'FORBIDDEN' } }
    )
    return db.posts.delete(id)
  }
}

Schema-Level with @auth Directive

directive @auth(
  requires: UserRole = USER
) on OBJECT | FIELD_DEFINITION

type Mutation {
  deletePost(id: ID!): Boolean!
    @auth(requires: ADMIN)
  updatePost(id: ID!, input: UpdatePostInput!): Post!
    @auth(requires: EDITOR)
}

17Q&A — 20 Questions

Easy What is over-fetching and how does GraphQL solve it?

Over-fetching occurs in REST APIs when an endpoint returns more data than the client needs. For example, a GET /users/:id endpoint might return 20 fields (name, email, phone, address, bio, avatar, createdAt, etc.) but the client only needs name and email for a list view — wasting bandwidth and parsing time.

GraphQL solves this because the client explicitly lists every field it wants in the query. The server returns exactly those fields and nothing else. A GraphQL client fetching a user list only for display purposes writes: { users { id name } } — and receives only id and name for each user, regardless of how many fields the User type has in the schema.

Easy What is the difference between type and input in GraphQL SDL?

Object types (defined with type) describe data that the server returns. They can have resolvers, and their fields can resolve to other object types, forming a graph.

Input types (defined with input) describe arguments passed to the server in mutations and queries. Input types can only contain scalar types, enum types, and other input types — they cannot reference object types (no circular dependencies back into the query graph). This separation exists because output types may have resolver logic, but input arguments are simple data structures.

type User { id: ID!, name: String! }    # output — what server returns
input CreateUserInput { name: String! } # input — what client sends
Easy What is GraphQL introspection and when should it be disabled?

Introspection is a built-in GraphQL feature that allows clients to query the schema itself — what types exist, what fields they have, what queries/mutations/subscriptions are available. Tools like GraphiQL, Apollo Studio, and code generators rely on introspection to understand the API.

In production, introspection should be disabled because it exposes your entire API surface area to potential attackers, giving them a roadmap for crafting targeted queries, finding deprecated fields, or discovering sensitive operations. Disable it with introspection: process.env.NODE_ENV !== 'production' in Apollo Server, or via the equivalent setting in your server library.

Easy What is a fragment in GraphQL and why would you use one?

A fragment is a reusable set of fields that can be spread into multiple queries, mutations, or subscriptions using the ... spread syntax. Fragments serve two purposes:

1. DRY (Don't Repeat Yourself): If multiple queries need the same set of user fields, define them once as a fragment fragment UserFields on User { id name email avatar } and spread them in each query.

2. Component colocation: In the "fragment colocation" pattern, each component defines a fragment declaring its own data needs. The parent query composes all fragments. This makes data dependencies explicit and local to each component — changing a component's data needs only requires updating its fragment.

Easy What are the four arguments to a resolver function?

(parent, args, context, info) — conventionally shortened to (root, args, ctx, info) or (_, args, { db, user }):

  • parent — the result returned by the parent field's resolver. For root-level Query/Mutation fields, this is the root value (often undefined or an empty object). For nested fields like User.posts, it's the User object returned by Query.user.
  • args — arguments passed to this specific field in the query (e.g., user(id: "123") gives args = { id: "123" }).
  • context — shared request-scoped object: typically contains authenticated user, database connections, DataLoaders, and request metadata.
  • info — AST information about the field: schema, path, return type, field name, selected sub-fields. Rarely needed in application code.
Intermediate Explain the N+1 problem with a concrete example and how DataLoader solves it.

Given a query that fetches 100 posts with their authors, the naive resolver approach fires 1 DB query to fetch all posts, then 1 DB query per post to fetch each author — 101 total queries. This is "N+1" (1 for the list + N for the related objects).

DataLoader works by exploiting the JavaScript event loop. When all 100 Post.author resolvers call userLoader.load(post.authorId), DataLoader does NOT immediately execute 100 DB calls. Instead, it collects all IDs within the same event loop tick, then fires a single batch function at the end of the tick: SELECT * FROM users WHERE id IN (id1, id2, ..., id100) — 1 DB query total for all 100 authors.

The batch function must return an array of results in the same order as the input IDs — this is critical and a common bug source. DataLoader also caches results by key within a request, so if the same user authored 5 posts, they are only fetched once.

Intermediate What is the Relay Connection spec and why is it the recommended pagination pattern?

The Relay Connection spec defines a standard structure for paginated lists: each paginated field returns a connection object containing edges (array of { node, cursor } objects) and pageInfo ({ hasNextPage, hasPreviousPage, startCursor, endCursor }).

Benefits of this pattern:

  • Cursor-based pagination is stable even when items are inserted or deleted (unlike offset pagination where inserting row 3 shifts all subsequent offsets).
  • Bidirectional navigation — the spec supports forward (first/after) and backward (last/before) traversal.
  • Metadata extensibility — adding totalCount or other metadata to the connection object is straightforward without breaking the shape.
  • Tooling support — Relay's built-in pagination hooks, Apollo's relayStylePagination() cache policy, and various code generators understand this pattern natively.
Intermediate How does Apollo Client's InMemoryCache normalize data?

Apollo Client's InMemoryCache normalizes objects by their __typename + id (or custom key fields). When data is stored in the cache, each object with an id is stored as a flat reference (like User:123) rather than nested under the query that fetched it.

When two different queries both return the same user (e.g., a user list and a user detail query), Apollo Client recognizes they have the same __typename and id, and stores only one copy. Any mutation that updates User:123 via cache.writeFragment or cache.modify automatically updates all components that display data from that user — regardless of which query fetched it.

The cache is essentially a normalized relational store keyed by __typename:id. This is why Apollo automatically includes __typename in all queries — without it, normalization cannot work.

Intermediate What are GraphQL subscriptions and how do they differ from queries and mutations?

Subscriptions are long-lived connections that push data from server to client whenever a specified event occurs. Unlike queries (request-response, client asks once) and mutations (trigger a change), subscriptions maintain an open channel (typically WebSocket) and the server pushes updates proactively.

Key differences:

  • Protocol: queries/mutations use HTTP; subscriptions use WebSocket (graphql-ws protocol)
  • Direction: queries/mutations are client-initiated pull; subscriptions are server-initiated push
  • Lifecycle: queries are one-shot; subscriptions remain active until client unsubscribes
  • Execution: each subscription type requires a resolver with both a subscribe function (returns AsyncIterable) and a resolve function (formats the pushed event)

Use subscriptions only when real-time push is genuinely needed — for data that changes at unpredictable intervals, client-side polling (pollInterval) is often simpler and more scalable.

Intermediate Explain the Apollo Client fetch policies and when to use each.

cache-first (default): Check cache first; only hit network on a cache miss. Best for data that doesn't change often and where slight staleness is acceptable (e.g., user profile, category lists). Best performance.

cache-and-network: Return cached data immediately (fast render) while simultaneously fetching fresh data from the network to update the cache. Best UX for data that changes but immediate display is important. Slightly higher network usage.

network-only: Always fetch from network; ignore and overwrite cache. Use for critical data that must always be current (e.g., current balance, security-sensitive information).

cache-only: Only read from cache; throw error if cache miss. Used in offline-first apps or when you're certain the data is already cached.

no-cache: Always fetch from network and do NOT write the result to the cache. For sensitive data (medical records, financial transactions) that should not persist in browser memory.

Advanced Walk through how Apollo Federation composes a distributed schema and resolves a cross-service query.

Schema composition: At startup (or CI time), the Router fetches SDL from each registered subgraph. It validates that entities are consistent (same @key fields, no conflicting types) and composes them into a single "supergraph SDL" that represents the unified API clients see.

Query planning: When a client sends a query, the Router analyzes which subgraphs own which fields, generates a query plan (a tree of "fetch" operations), and executes them — potentially in parallel for independent fields.

Cross-service entity resolution: When query field B in Service B requires a User entity that was returned by Service A, the Router takes the id (the @key field) from Service A's response and sends a "representations" query to Service B: _entities(representations: [{__typename: "User", id: "123"}]). Service B's __resolveReference resolver fetches the full user data and returns the extended fields.

This process is transparent to the client — they just write a normal GraphQL query spanning multiple services and receive a unified response.

Advanced What are the differences between GraphQL errors in errors array vs throwing exceptions in resolvers?

When a resolver throws an error, GraphQL catches it and adds it to the response errors array. The affected field is set to null in data. If the field is non-null (!`), the null propagates up to the nearest nullable parent. Apollo Server sanitizes error messages in production — only errors with known codes (or set exposeErrors: true) show their message; others become "Internal server error."

Expected errors (validation failures, auth errors, not found) should use GraphQLError with meaningful extensions.code values — these are user-facing and Apollo Server exposes their message.

Unexpected errors (DB timeouts, null pointer exceptions) are sanitized and logged server-side — clients receive a generic message. The errors array can coexist with partial data when using errorPolicy: 'all' on the client.

The payload pattern is an alternative — return errors as part of the data type (not in the GraphQL errors array), enabling typed error handling without relying on the errors mechanism. This keeps the response structure consistent and plays better with code generation.

Advanced How does GraphQL Code Generator improve type safety end-to-end?

GraphQL Code Generator reads your schema SDL and your operation documents (queries, mutations, fragments in .graphql files or gql tagged templates) and generates TypeScript types that exactly match both.

Without codegen: You cast API responses to manually defined types, which drift from the schema over time. A server-side type change won't automatically surface as a TypeScript error in the client.

With codegen: Every operation gets a generated variables type and result type derived directly from the schema. If the schema changes (e.g., a field is renamed), codegen regenerates the types and TypeScript compilation fails at the exact component that uses the renamed field — instant catch before deployment.

Codegen also generates typed hooks (useGetUsersQuery) that eliminate the need for generic type parameters on Apollo's useQuery<GetUsersQuery, GetUsersQueryVariables>. In watch mode (codegen --watch), types regenerate on every schema or operation file change during development.

Advanced Explain the difference between schema-stitching and Apollo Federation. When would you choose one over the other?

Schema Stitching (via @graphql-tools/stitch) merges multiple GraphQL schemas in a gateway layer. The gateway has full knowledge of all schemas and handles type merging manually. The subgraphs don't need to know about each other.

Apollo Federation is a first-class distributed schema protocol. Each subgraph declares its piece of the schema using @key, @external, and other federation directives. Subgraphs are independently deployable and each one knows its own domain. The Router composes subgraphs automatically based on these declarations.

Choose Stitching when: You have existing GraphQL services not built with Federation in mind, you need to wrap third-party schemas, or you have a small number of services with a single gateway team. Stitching gives more flexibility in how you compose schemas.

Choose Federation when: You have multiple teams owning different domain services and need clear ownership boundaries, you need the Router's advanced features (traffic shaping, observability, schema checks), and you can adopt the Federation spec from the start. Federation is the better long-term choice for large microservice architectures.

Very Advanced What are the trade-offs of nullability in GraphQL schema design and how does it affect error propagation?

GraphQL's null propagation rule states: if a non-null field returns null (due to a resolver error or explicit null), the null propagates up to the nearest nullable ancestor field. If that ancestor is also non-null, it continues propagating up.

Over-using non-null (!) creates brittle schemas. If Post.author: User! is non-null and the author lookup fails (e.g., DB timeout), the entire post becomes null. If Query.posts: [Post!]! is also non-null, the entire response data becomes null — despite many posts loading successfully.

Schema design principle: Use nullable fields at "natural failure boundaries" — fields that cross service boundaries, involve optional relationships, or could partially fail. Make leaf scalar fields (id, name, createdAt) non-null when they're guaranteed. The more nullable your schema, the better partial data resilience you get.

The semantic nullable debate: Some argue all fields should be nullable by default to enable graceful degradation. Others argue that excessive nullability forces clients to handle null everywhere, polluting code. The GraphQL Working Group continues to discuss "semantic non-null" (field won't be null unless an error occurs) as a potential solution for a future spec version.

Very Advanced Describe how Automatic Persisted Queries (APQ) work and the security/performance trade-offs.

APQ replaces full query strings with SHA-256 hashes. The flow:

First request (cache miss): Client sends only the hash. Server doesn't recognize it, returns a PERSISTED_QUERY_NOT_FOUND error. Client resends with both the hash and the full query string. Server stores the query string keyed by hash (in Redis or in-memory), then executes it.

Subsequent requests: Client sends only the hash. Server finds the query in its store and executes it — no query string transfer overhead.

Performance benefits: Query strings can be kilobytes for complex queries. APQ reduces payload to ~32 bytes (the hash). Combined with GET requests for queries (query in URL parameters), responses become CDN-cacheable — a major win for public APIs.

Security consideration: APQ alone does not prevent unauthorized queries — any client can still send new queries by including the full text. For tighter security, use "trusted document" mode: pre-register only your application's queries server-side (at build/deploy time), reject any query not in the registry. This prevents clients from executing arbitrary GraphQL queries against your API.

Trade-off: Trusted documents require rebuilding and redeploying both client and server when query changes are needed — introduces deployment coupling. APQ without the trusted-document restriction is a pure performance win with no security trade-offs.

Very Advanced How do you implement real-time subscriptions at scale, and what are the infrastructure challenges?

Scaling WebSocket subscriptions requires solving the fan-out problem: when a server receives an event (e.g., a new message in room "X"), it must notify all clients subscribed to that room — potentially connected to different server instances.

Pub/Sub with Redis: Each server instance subscribes to a Redis channel. When any server receives an event (mutation), it publishes to Redis. All server instances receive the publication via Redis and push to their locally-connected clients subscribed to that event. Apollo Server uses graphql-redis-subscriptions for this pattern.

import { RedisPubSub } from 'graphql-redis-subscriptions'
const pubsub = new RedisPubSub({ connection: redisClient })

// In mutation resolver
await pubsub.publish('POST_CREATED', { postCreated: newPost })

// In subscription resolver
Subscription: {
  postCreated: {
    subscribe: () => pubsub.asyncIterator(['POST_CREATED']),
  },
}

Infrastructure challenges:

  • Sticky sessions: Load balancers must route reconnecting clients to the same server instance (or use a stateless architecture where any instance can serve any subscription via shared pub/sub).
  • Connection limits: Each WebSocket is a persistent connection consuming memory. A single Node.js server can handle ~10K-100K concurrent WebSocket connections; plan capacity accordingly.
  • Authorization on reconnect: JWT tokens expire; subscriptions must handle token refresh and re-authenticate without losing the connection.
  • Filtering: Redis fan-out pushes to all instances; subscription resolvers must filter events per-subscriber efficiently.
Very Advanced Compare urql's exchange architecture with Apollo Client's link chain and explain the design philosophy difference.

Both are middleware pipelines for processing GraphQL operations, but they differ in philosophy and composability.

Apollo Client Links form a directional chain where each link can forward to the next or short-circuit. Links are composed with .concat() or from([]): authLink.concat(retryLink).concat(httpLink). Links are typically stateful (e.g., InMemoryCache link has embedded state). The chain is set up once and each operation passes through it linearly.

urql Exchanges are bidirectional — they see both the operation going down (from client to network) and the result coming back up (from network to component). Each exchange wraps the next exchange's forward function: [dedupExchange, cacheExchange, fetchExchange]. This bidirectional visibility makes features like logging, error handling, and offline queuing more natural — the exchange sees both sides of each operation without needing separate request/response links.

Key philosophical difference: Apollo's links encourage composing specialized single-purpose layers. urql's exchanges encourage writing stateful middleware that can intercept operations going either direction. urql's design is arguably more Haskell-inspired (similar to Conduit/pipes), while Apollo's is more Express middleware-inspired.

For most applications, either achieves the same outcomes; the choice often comes down to bundle size requirements (urql is significantly smaller) and ecosystem preference.
