CI vs CD vs CD

graph LR DEV[Developer
Code Commit] CI[Continuous Integration
Build + Unit Test + Lint] CDE[Continuous Delivery
Integration Test + UAT
Staging Deploy] CDP[Continuous Deployment
Auto Deploy to Production] DEV --> CI --> CDE --> CDP
PracticeDefinitionHuman Approval?
Continuous Integration (CI)Automatically build and test code on every commit. Catch integration bugs early.No
Continuous Delivery (CD)CI + automatically deploy to staging/test environments. Production deploy is MANUAL approval.Yes — for production
Continuous Deployment (CDP)CI + automatically deploy to production on every commit that passes all tests. No human gate.No
Key distinction: Continuous Delivery = ability to deploy anytime (human decides when). Continuous Deployment = every passing commit automatically goes to production.

CI/CD Principles & Benefits

Core Principles

  • Everything as Code — Pipeline definitions, infrastructure, configuration all in version control
  • Fast feedback — Build/test failures detected within minutes, not days
  • Small batches — Commit and deploy frequently (reduce risk per change)
  • Fail fast — Run fastest checks first (lint → unit tests → integration tests)
  • Idempotent deployments — Same artifact deployed the same way every time
  • Single source of truth — Git is the source of truth for code AND infrastructure
  • Immutable artifacts — Build once, deploy the same artifact through all environments

Benefits

  • Reduced time to market (release faster)
  • Higher quality (bugs caught earlier when cost to fix is lower)
  • Reduced risk (smaller changes = easier rollback)
  • Developer productivity (no manual deployments)
  • Consistent environments (infra as code)

Pros and Cons of GitFlow

  • Pro: Clear structure, works well for scheduled releases, parallel development
  • Con: Complex, hard to maintain for CI/CD, long-lived branches cause merge conflicts

Trunk-Based Development

All developers integrate to a single branch (trunk/main) at least daily. Feature branches are short-lived (hours to 1-2 days max).

Feature Flags

Allow merging incomplete features to trunk without exposing them to users. Flags enable/disable features at runtime.

  • Release flags — Enable for testing, disable for users until ready
  • Experiment flags — A/B testing
  • Ops flags — Kill switches for failing features
  • Permission flags — Enable for specific user groups
// Feature flag check
if (featureFlags.isEnabled('new-checkout-flow', userId)) {
  return newCheckoutFlow();
} else {
  return legacyCheckoutFlow();
}

SonarQube — Code Quality

Key Concepts

  • Quality Gate — Pass/fail criteria for the build (e.g., coverage > 80%, no new critical bugs). If quality gate fails, pipeline stops.
  • Quality Profile — Set of active rules for a language
  • Code Smells — Maintainability issues (long methods, duplicated code, complex logic)
  • Bugs — Code issues likely to cause runtime errors
  • Vulnerabilities — Security hotspots (XSS, SQL injection patterns)
  • Technical Debt — Estimated time to fix all code smells
  • Coverage — % of code exercised by unit tests
  • Duplications — % of duplicated code blocks

Deployment Strategies

Blue/Green Deployment

graph LR LB[Load Balancer] BLUE[Blue Environment
v1 - Current Production] GREEN[Green Environment
v2 - New Version] LB -->|100% traffic| BLUE LB -.->|switch to green| GREEN
  • Run two identical production environments (blue = current, green = new)
  • Deploy to green, run smoke tests, then switch LB to green
  • Blue remains as instant rollback target
  • Pros: Zero downtime, instant rollback
  • Cons: 2x infrastructure cost during deployment

Canary Deployment

graph LR LB[Load Balancer] V1[v1 Pods
95% traffic] V2[v2 Pods - Canary
5% traffic] LB --> V1 LB --> V2
  • Deploy new version to a small subset of users/pods (5-10%)
  • Monitor metrics (errors, latency) then gradually increase traffic
  • Pros: Low risk, real user testing, easy rollback
  • Cons: Complex routing, monitoring critical, multiple versions running

Rolling Deployment

graph LR P1[Pod v1] P2[Pod v1 - Updating...] P3[Pod v2] P4[Pod v2] P1 --> P2 --> P3 --> P4
  • Replace pods/instances one by one (or in batches)
  • Old and new versions run simultaneously during rollout
  • Pros: No extra infrastructure, simple, Kubernetes default
  • Cons: Slow rollback, mixed versions during rollout

Recreate

  • Stop all old instances, then start all new instances
  • Pros: Simple, no version mixing
  • Cons: Downtime during deployment

A/B Testing

  • Route specific users (based on header/cookie/region) to different versions
  • Statistical comparison of user behavior/conversion rates
  • Not for deployment but for experimentation

GitHub Actions

name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]
  workflow_dispatch:          # Manual trigger
    inputs:
      environment:
        description: "Deploy environment"
        required: true
        default: "staging"
        type: choice
        options: [staging, production]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ── Test Job ────────────────────────────────────────────────
  test:
    runs-on: ubuntu-latest
    services:                 # Sidecar services
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: testdb
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
    strategy:
      matrix:                 # Matrix strategy — multiple variations
        node-version: [18, 20]
        os: [ubuntu-latest, windows-latest]
      fail-fast: false        # Don't cancel other jobs on failure
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: npm
      - run: npm ci
      - run: npm test
        env:
          DATABASE_URL: postgres://test:test@localhost:5432/testdb
      - name: Upload coverage
        uses: codecov/codecov-action@v4

  # ── Build & Push Image ──────────────────────────────────────
  build:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha
            type=semver,pattern={{version}}
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ── Deploy to Staging ───────────────────────────────────────
  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment:              # GitHub Environment with protection rules
      name: staging
      url: https://staging.example.com
    steps:
      - uses: actions/checkout@v4
      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/GitHubActionsRole
          aws-region: us-east-1
      - name: Deploy to EKS
        run: |
          aws eks update-kubeconfig --name my-cluster
          kubectl set image deployment/myapp \
            app=${{ needs.build.outputs.image-tag }}
          kubectl rollout status deployment/myapp

  # ── Deploy to Production ────────────────────────────────────
  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production          # Requires approval from CODEOWNERS
      url: https://example.com
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to production
        run: echo "Deploying ${{ needs.build.outputs.image-tag }}"

Jenkins Architecture

graph TB subgraph JC["Jenkins Controller"] UI[Web UI / REST API] JQ[Job Queue] SCH[Scheduler] PLG[Plugins 1800+] end subgraph A1["Agent 1 - Linux"] E1[Executor 1] E2[Executor 2] end subgraph A2["Agent 2 - Windows"] E3[Executor 1] end subgraph A3["Kubernetes Agent"] POD[Dynamic Pod
Spun on demand] end JC --> A1 & A2 & A3 JQ --> SCH --> E1 & E2 & E3 & POD

Key Concepts

  • Controller — Central server managing configuration, jobs, scheduling
  • Agent/Node — Machine that executes build steps; connected via JNLP or SSH
  • Executor — A slot on an agent for running builds (concurrency = executor count)
  • Labels — Tag agents with capabilities (linux, docker, gpu); jobs run on matching agents
  • Workspace — Working directory on the agent where job runs
  • Credentials — Secrets stored encrypted in Jenkins; accessed by ID

Jenkinsfile — Declarative Pipeline

// Declarative Pipeline (recommended)
pipeline {
  agent {
    kubernetes {                         // Run on K8s pod
      yaml """
        apiVersion: v1
        kind: Pod
        spec:
          containers:
            - name: maven
              image: maven:3.9-eclipse-temurin-17
              command: ['sleep', 'infinity']
            - name: docker
              image: docker:24-dind
              securityContext:
                privileged: true
      """
      defaultContainer 'maven'
    }
  }

  options {
    timeout(time: 1, unit: 'HOURS')
    buildDiscarder(logRotator(numToKeepStr: '10'))
    skipDefaultCheckout()                // Manual checkout below
    disableConcurrentBuilds()
    timestamps()
  }

  environment {
    DOCKER_REGISTRY = 'registry.company.com'
    APP_NAME         = 'myapp'
    // withCredentials pattern
    SONAR_TOKEN = credentials('sonar-token')
  }

  parameters {
    choice(name: 'DEPLOY_ENV', choices: ['dev','staging','prod'], description: 'Deploy to?')
    booleanParam(name: 'SKIP_TESTS', defaultValue: false)
    string(name: 'IMAGE_TAG', defaultValue: '', description: 'Override image tag')
  }

  stages {
    stage('Checkout') {
      steps {
        checkout scm
        sh "git log -1 --format='%H %s'"
      }
    }

    stage('Build & Test') {
      parallel {                         // Parallel stages
        stage('Unit Tests') {
          when {
            not { expression { params.SKIP_TESTS } }
          }
          steps {
            sh 'mvn test'
            junit 'target/surefire-reports/*.xml'
            jacoco()
          }
          post {
            always {
              publishHTML([
                reportDir: 'target/site/jacoco',
                reportFiles: 'index.html',
                reportName: 'Code Coverage'
              ])
            }
          }
        }
        stage('Code Analysis') {
          steps {
            withSonarQubeEnv('SonarQube') {
              sh 'mvn sonar:sonar'
            }
          }
        }
      }
    }

    stage('Quality Gate') {
      steps {
        timeout(time: 5, unit: 'MINUTES') {
          waitForQualityGate abortPipeline: true
        }
      }
    }

    stage('Package') {
      steps {
        sh 'mvn package -DskipTests'
        archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
      }
    }

    stage('Docker Build & Push') {
      steps {
        container('docker') {
          withCredentials([usernamePassword(
            credentialsId: 'registry-creds',
            usernameVariable: 'USER',
            passwordVariable: 'PASS'
          )]) {
            sh """
              docker login ${DOCKER_REGISTRY} -u ${USER} -p ${PASS}
              docker build -t ${DOCKER_REGISTRY}/${APP_NAME}:${BUILD_NUMBER} .
              docker push ${DOCKER_REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
            """
          }
        }
      }
    }

    stage('Deploy') {
      matrix {                           // Matrix: deploy to multiple envs
        axes {
          axis {
            name 'REGION'
            values 'us-east-1', 'eu-west-1'
          }
        }
        stages {
          stage('Deploy to Region') {
            steps {
              sh "deploy.sh ${REGION} ${BUILD_NUMBER}"
            }
          }
        }
      }
    }

    stage('Approval') {
      when {
        branch 'main'
      }
      steps {
        input(
          message: 'Deploy to Production?',
          ok: 'Deploy',
          submitter: 'release-managers',
          parameters: [
            string(name: 'RELEASE_NOTES', description: 'Release notes')
          ]
        )
      }
    }
  }

  post {
    always {
      cleanWs()                          // Clean workspace
    }
    success {
      slackSend(
        channel: '#deployments',
        color: 'good',
        message: "Build ${BUILD_NUMBER} deployed successfully"
      )
    }
    failure {
      emailext(
        to: 'team@example.com',
        subject: "Build FAILED: ${JOB_NAME} #${BUILD_NUMBER}",
        body: "${BUILD_URL}"
      )
    }
  }
}

ArgoCD — GitOps

GitOps Principles

  1. Declarative — Entire system state described declaratively
  2. Versioned — Git is the single source of truth
  3. Automatic — Approved changes are applied automatically
  4. Self-healing — Software agents reconcile actual vs desired state
# ArgoCD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/myapp-gitops.git
    targetRevision: HEAD
    path: k8s/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:                  # Auto-sync when git changes
      prune: true               # Remove resources not in git
      selfHeal: true            # Fix drift (manual changes)
    syncOptions:
      - CreateNamespace=true
      - PruneLast=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        maxDuration: 3m
        factor: 2

Interview Q&A

Q1: What is the difference between Continuous Delivery and Continuous Deployment? Easy

Continuous Delivery: Every code change that passes all automated tests is automatically released to a staging/pre-production environment and is ready to be deployed to production. The actual production deployment requires a human approval/trigger.

Continuous Deployment: Every code change that passes all automated tests is automatically deployed to production without any human intervention.

Both require robust automated testing. Continuous Delivery is common in enterprises where regulatory approval is needed. Continuous Deployment is used by high-velocity teams (Netflix, Amazon).

Q2: What is GitFlow and when would you choose trunk-based development instead? Intermediate

GitFlow: Uses multiple long-lived branches (main, develop, feature, release, hotfix). Good for versioned releases, multiple parallel versions.

Trunk-based development: All developers commit to main daily; feature branches live <2 days; feature flags hide incomplete work. Better for CI/CD.

Choose trunk-based when:

  • Practicing true CI/CD (frequent, small releases)
  • You want to avoid long-lived branch merge conflicts
  • Team is mature with strong automated testing

Stick with GitFlow when:

  • Multiple release versions in production simultaneously
  • Regulatory release freeze periods
  • Large teams with less CI/CD maturity
Q3: What is a Jenkinsfile and what are the two types of Jenkins pipelines? Easy

A Jenkinsfile is a text file stored in source control that defines the Jenkins pipeline as code.

Declarative Pipeline: Structured, opinionated syntax using pipeline { } block. Easier to read, validates syntax, supports Blue Ocean visualization. Recommended for most use cases.

Scripted Pipeline: Full Groovy code using node { }. More powerful/flexible but complex. Legacy option.

Benefits of Pipeline as Code: Version controlled, code reviewed, reusable (shared libraries), auditable, reproducible.

Q4: Explain blue/green vs canary deployment strategies Intermediate

Blue/Green:

  • Run two full environments (blue = live, green = new)
  • Deploy to green, test, then switch LB instantly
  • Blue kept for instant rollback
  • Zero downtime, instant rollback, but 2x infrastructure cost
  • Good for: major version changes, database schema changes

Canary:

  • Deploy to small % (5-10%) of production traffic first
  • Monitor error rates, latency, conversions
  • Gradually increase if healthy
  • Low risk, real production testing, no extra infra cost
  • Complex: version mismatch, monitoring-heavy
  • Good for: feature rollouts, A/B experiments
Q5: What is SonarQube and what is a Quality Gate? Intermediate

SonarQube is a code quality and security platform that performs static analysis on source code to detect bugs, code smells, and vulnerabilities.

Quality Gate: A set of conditions the code must meet before it can proceed in the pipeline. Example: coverage >= 80%, no new critical bugs, no new high vulnerabilities, duplications < 3%.

If the quality gate fails, the build fails — preventing poor quality code from progressing to deployment.

Key metrics: Code coverage, duplications, code smells (maintainability), bugs (reliability), vulnerabilities (security), technical debt estimate.

Q6: What security scanning tools would you include in a CI/CD pipeline? Intermediate

A comprehensive DevSecOps pipeline includes:

  1. Secret scanning (pre-commit/CI): GitLeaks, TruffleHog — prevent API keys in code
  2. SAST (static analysis): SonarQube, Semgrep, CodeQL — analyze source code
  3. SCA (dependency scanning): Snyk, Dependabot, OWASP DC — check CVEs in deps
  4. Container scanning: Trivy, Grype — scan Docker image layers
  5. IaC scanning: Checkov, tfsec — check Terraform/K8s manifests for misconfigs
  6. DAST (dynamic): OWASP ZAP against deployed application

Fail early: Run fast checks (secret scanning, SAST) early in pipeline. Save slow checks (DAST) for after deployment to staging.

Q7: What is GitOps and how does ArgoCD implement it? Advanced

GitOps is an operational framework where Git is the single source of truth for infrastructure and application configuration. Changes are made via Git (PR/merge), and an operator automatically applies them.

ArgoCD implementation:

  1. Developer merges PR to GitOps repo (manifests/Helm charts)
  2. ArgoCD polls/webhooks detects change
  3. ArgoCD compares desired state (Git) vs actual state (cluster)
  4. With automated sync: applies diff automatically
  5. With selfHeal: reverts any manual kubectl changes
  6. With prune: removes resources deleted from Git

Benefits: Audit trail (git history), rollback = git revert, declarative, self-healing, works with any Kubernetes cluster.

Q8: How do Jenkins shared libraries work? Advanced

Shared libraries allow reusable pipeline code (functions, classes) stored in a separate Git repository, shared across all Jenkinsfiles.

Structure:

  • vars/ — Global variables (functions callable as steps)
  • src/ — Groovy classes (imported with import)
  • resources/ — Non-Groovy files (JSON, YAML configs)

Configuration: Defined in Jenkins → Manage Jenkins → Configure System → Global Pipeline Libraries. Can be loaded implicitly or explicitly with @Library('name') _.

Benefits: DRY principle, consistent pipelines across teams, centrally maintained, tested separately.

Q9: What is the test pyramid and why does it matter for CI/CD? Intermediate

The test pyramid (coined by Mike Cohn) recommends having many unit tests, fewer integration tests, and even fewer E2E tests.

Rationale:

  • Unit tests: milliseconds, cheap to write, pinpoint failures
  • Integration tests: seconds, test component interactions
  • E2E tests: minutes, test full flows, brittle, expensive

Anti-pattern (ice cream cone): Many E2E tests, few unit tests → slow CI, flaky tests, difficult to debug failures.

For CI/CD: Unit tests run on every commit (fast gate). Integration tests on PR. E2E tests after staging deploy. This provides fast feedback without blocking deployments.

Q10: Explain Terraform state and why it's important Intermediate

Terraform state (terraform.tfstate) is a JSON file mapping Terraform resources to real infrastructure. It tracks what Terraform manages.

Why critical:

  • Terraform uses state to know what exists and needs changing
  • Without state, Terraform can't track drift
  • State contains sensitive data (resource IDs, some outputs)

Remote state best practices:

  • Store in S3/GCS/Azure Blob + DynamoDB for locking
  • Never commit state to Git
  • Enable encryption
  • Use workspaces or separate state per environment
  • State locking prevents concurrent modifications

Q12: What are DORA metrics and why are they important? Advanced

DORA (DevOps Research & Assessment) metrics are 4 key measures of software delivery performance:

  1. Deployment Frequency — How often code is deployed to production. Elite: multiple/day.
  2. Lead Time for Changes — Time from commit to production. Elite: <1 hour.
  3. Change Failure Rate — % of deployments causing production failure. Elite: 0-15%.
  4. Time to Restore — Time to recover from failures. Elite: <1 hour.

These metrics predict organizational performance and are backed by extensive research. High performers in DORA metrics deliver more value with less burnout.

How to improve: CI/CD automation, smaller batch sizes, feature flags, observability, incident management processes.

Q13: How would you implement a zero-downtime deployment pipeline? Advanced
  1. Containerize the app with proper health checks
  2. Use rolling update or blue/green deployment strategy
  3. Database migrations must be backward-compatible (additive only, never remove columns immediately)
  4. Feature flags to decouple deploy from release
  5. Readiness probes ensure traffic only routes to healthy pods
  6. Graceful shutdown — handle SIGTERM, complete in-flight requests, drain connections
  7. PodDisruptionBudget — maintain minimum availability during rolling updates
  8. Circuit breakers — prevent cascading failures
  9. Automated rollback — on error rate spike, trigger rollback (ArgoCD rollback or helm rollback)
Q14: What is GitHub Actions OIDC and why is it preferred over long-lived secrets? Advanced

OIDC (OpenID Connect) allows GitHub Actions workflows to authenticate directly to cloud providers (AWS, GCP, Azure) without storing long-lived credentials as secrets.

How it works:

  1. GitHub generates a short-lived JWT token for each workflow run
  2. Workflow exchanges JWT for cloud provider credentials via AssumeRoleWithWebIdentity (AWS)
  3. Credentials are temporary (1 hour) and scoped to the workflow

Why preferred:

  • No long-lived secrets to rotate or leak
  • Automatic expiry — credentials valid only during run
  • Auditable — cloud logs show exactly which workflow ran
  • Conditional access — restrict by repo/branch/environment
Q15: How do you handle secrets in CI/CD pipelines? Advanced

Never:

  • Hardcode secrets in Jenkinsfile/workflow files
  • Store secrets in environment variables in plaintext CI config
  • Log secrets in build output

Best practices:

  • GitHub Secrets / GitLab CI Variables — Encrypted at rest, masked in logs
  • HashiCorp Vault — Dynamic secrets, short-lived, audit trail
  • AWS Secrets Manager / Parameter Store — IAM-controlled access
  • OIDC for cloud auth — No stored cloud credentials
  • Jenkins Credentials — Encrypted store, accessed by ID
  • Secret scanning in CI — Detect leaked secrets in code

Rotation: Automate secret rotation; use short-lived secrets where possible.

Q16: What is artifact management and why is it important? Intermediate

Artifact management is the storage and distribution of build outputs (JARs, Docker images, npm packages) in a centralized repository.

Why important:

  • Immutability — Build once, promote the same artifact (no rebuilds per env)
  • Reproducibility — Exact binary deployed to prod can be traced back to source commit
  • Dependency proxying — Cache external deps (Maven Central, npm), prevent internet dependency
  • Security scanning — Scan before publishing/pulling
  • Access control — Who can publish to release vs snapshot repos

Tools: JFrog Artifactory (enterprise, supports all formats), Nexus Repository, AWS ECR (Docker), GitHub Packages.

Q17: How would you structure a CI/CD pipeline for a microservices application? Very Advanced

Mono-repo approach:

  • Detect which services changed (path-based filtering)
  • Run CI only for changed services + dependent services
  • Build/test/push image per service independently

Per-service pipeline stages:

  1. Lint + unit tests (fast gate)
  2. Build Docker image
  3. Security scan (Trivy + Snyk)
  4. Integration tests (Testcontainers)
  5. Push to registry with git SHA tag
  6. Update GitOps repo with new image tag (ArgoCD sync)

Cross-service concerns:

  • Contract tests (Pact) to verify API compatibility
  • E2E tests after all services deployed to staging
  • Centralized observability for tracking deployment health
Q18: What is trunk-based development and how do feature flags enable it? Advanced

Trunk-based development: all developers integrate code to the main branch (trunk) at least once daily. Feature branches are short-lived (<2 days).

The problem: How do you merge incomplete features?

Feature flags solve this:

  • Merge code to main with feature disabled by default
  • Enable flag for internal testers first
  • Gradual rollout: 1% → 10% → 50% → 100%
  • Kill switch: disable if issues found in production

Tools: LaunchDarkly, Unleash, AWS AppConfig, Split.io, custom Redis-backed flags.

Benefits for CI/CD: True CI (everyone integrates daily), no merge conflicts, decouple deploy from release, instant rollback via flag disable.

Q20: What is the Definition of Done and why is it important in Agile? Easy

The Definition of Done (DoD) is a shared agreement among the team on what criteria must be met before a User Story or feature can be considered "done." It prevents different interpretations of completion.

Why important:

  • Ensures consistent quality — all work meets the same standard
  • Prevents "almost done" — no partially done items count as complete
  • Enables accurate velocity — only truly done work counts
  • Reduces technical debt — testing and documentation are non-negotiable
  • Builds trust — product owners know exactly what delivered means

DoD is different from Acceptance Criteria — DoD applies to ALL stories; AC is specific to one story.
