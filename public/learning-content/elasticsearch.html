Shards & Replicas

An index is divided into primary shards (horizontal scaling unit). Each primary can have N replica shards (exact copies). A replica is never allocated to the same node as its primary.

Shard sizing rule: Target 10–50 GB per shard. Too small: overhead of many small shards. Too large: slow search and recovery. For time-series data (logs): use daily/weekly rollover indices with ILM. 
// Create index with explicit shard count
PUT /orders
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1,
    "refresh_interval": "1s"
  }
}

// Check cluster health
GET /_cluster/health?level=indices
// status: green (all shards allocated), yellow (replicas unallocated), red (primary unallocated)

// Shard allocation explain
GET /_cluster/allocation/explain
{
  "index": "orders",
  "shard": 0,
  "primary": false
}

replicas=0replicas=1replicas=2+

Dynamic Mapping

When you index a document without pre-defining the mapping, Elasticsearch auto-detects field types — called dynamic mapping.

JSON ValueDetected Mapping TypeNote
true / falseboolean
123longAll integers mapped to long by default
1.5floatFloats mapped to float
"2024-01-15"dateOnly if matches date format
"hello world"text + keywordDual mapping: text (analyzed for full-text) + keyword (raw, for sorting/aggregation)
{"k":"v"}objectFields mapped individually
[1,2,3]longArrays always take type of first element
// Dynamic mapping configuration
PUT /orders
{
  "mappings": {
    "dynamic": "strict",   // strict=error on unknown fields; true=auto-map; false=ignore
    "date_detection": true,
    "numeric_detection": true,
    "dynamic_date_formats": ["yyyy-MM-dd", "yyyy/MM/dd"]
  }
}

// Dynamic templates: auto-map strings matching pattern as keyword
PUT /logs
{
  "mappings": {
    "dynamic_templates": [
      {
        "strings_as_keyword": {
          "match_mapping_type": "string",
          "match": "*_id",
          "mapping": { "type": "keyword" }
        }
      },
      {
        "strings_as_text": {
          "match_mapping_type": "string",
          "mapping": {
            "type": "text",
            "fields": { "raw": { "type": "keyword" } }
          }
        }
      }
    ]
  }
}

Full-Text Search Queries

// match — basic full-text search (tokenizes query before matching)
GET /products/_search
{
  "query": {
    "match": {
      "description": {
        "query": "wireless noise cancelling headphones",
        "operator": "and",      // all terms must match (default: or)
        "minimum_should_match": "75%",  // or: require 75% of terms
        "fuzziness": "AUTO"     // allow typos (AUTO: 0 for 1-2 chars, 1 for 3-5, 2 for 6+)
      }
    }
  }
}

// match_phrase — exact phrase with word-order preserved
GET /articles/_search
{
  "query": {
    "match_phrase": {
      "body": "climate change is real"
    }
  }
}

// match_phrase_prefix — autocomplete (last word prefix match)
GET /products/_search
{
  "query": {
    "match_phrase_prefix": {
      "name": "wire",
      "max_expansions": 10
    }
  }
}

// multi_match — search across multiple fields
GET /products/_search
{
  "query": {
    "multi_match": {
      "query": "iphone charger",
      "type": "best_fields",     // best_fields, most_fields, cross_fields, phrase, phrase_prefix
      "fields": ["name^3", "description", "tags^2"],  // ^N = boost
      "tie_breaker": 0.3
    }
  }
}

// intervals — complex proximity queries
GET /articles/_search
{
  "query": {
    "intervals": {
      "body": {
        "all_of": {
          "intervals": [
            { "match": { "query": "climate" } },
            { "match": { "query": "change" } }
          ],
          "max_gaps": 5,    // max 5 words between "climate" and "change"
          "ordered": true
        }
      }
    }
  }
}

Term-Level Queries

// term — exact match (keyword fields, not analyzed)
{ "query": { "term": { "status": { "value": "published" } } } }

// terms — match any in list
{ "query": { "terms": { "tags": ["redis", "kafka", "elasticsearch"] } } }

// range — numeric/date ranges
{
  "query": {
    "range": {
      "created_at": {
        "gte": "2024-01-01",
        "lt": "2025-01-01",
        "format": "yyyy-MM-dd"
      }
    }
  }
}

// exists — field is present and not null
{ "query": { "exists": { "field": "email" } } }

// prefix — starts with (on keyword fields)
{ "query": { "prefix": { "username": { "value": "john" } } } }

// wildcard — pattern matching (* and ?)
{ "query": { "wildcard": { "email": { "value": "*@gmail.com" } } } }

// regexp
{ "query": { "regexp": { "postcode": { "value": "[0-9]{5}" } } } }

// fuzzy — typo-tolerant exact matching
{ "query": { "fuzzy": { "name": { "value": "elasticserach", "fuzziness": 2 } } } }

// ids — lookup by document IDs
{ "query": { "ids": { "values": ["1", "2", "3"] } } }

Boolean Queries & Scoring

// bool query — combine multiple queries
GET /products/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "wireless headphones" } }
      ],
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price": { "lte": 200 } } }
      ],
      "should": [
        { "term": { "brand": "sony" } },
        { "term": { "brand": "bose" } }
      ],
      "must_not": [
        { "term": { "status": "discontinued" } }
      ],
      "minimum_should_match": 1
    }
  }
}
// must: must match; contributes to _score
// filter: must match; does NOT affect _score (cached! use for yes/no conditions)
// should: optional; matching clauses BOOST _score; minimum_should_match controls minimum
// must_not: must NOT match; cached, no scoring
Performance tip: Use filter context (not must) for conditions that don't need scoring (date ranges, status checks, boolean flags). Filter results are cached in the filter cache by Elasticsearch for repeated use.

Relevance Scoring — BM25 & Function Score

TF-IDF vs BM25

AspectTF-IDF (legacy)BM25 (default since ES 5.0)
Term FrequencyIncreases linearlySaturates (diminishing returns for repeated terms)
IDFlog(N/df)log(1 + (N-df+0.5)/(df+0.5)) — smoother
Document LengthNorm factork1 (term saturation) + b (length normalization) parameters
ResultLonger docs over-scoredBetter handling of varying document lengths
// Explain scoring for a document
GET /products/_explain/1
{
  "query": { "match": { "description": "wireless headphones" } }
}

// function_score — custom scoring
GET /products/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "description": "headphones" } },
      "functions": [
        {
          "filter": { "term": { "featured": true } },
          "weight": 3
        },
        {
          "field_value_factor": {
            "field": "sales_count",
            "factor": 0.001,
            "modifier": "log1p",   // log(1 + sales_count * factor)
            "missing": 1
          }
        },
        {
          "gauss": {
            "created_at": {
              "origin": "now",
              "scale": "30d",   // half score at 30 days old
              "decay": 0.5
            }
          }
        }
      ],
      "score_mode": "sum",    // how to combine function scores
      "boost_mode": "multiply" // how to combine function score with query score
    }
  }
}

// script_score — arbitrary scoring function
{
  "query": {
    "script_score": {
      "query": { "match_all": {} },
      "script": {
        "source": "_score * Math.log(1 + doc['popularity'].value)"
      }
    }
  }
}

Nested Documents vs Parent-Child Joins

The Problem with Object Arrays

// Flattened object (problem): can match across unrelated objects
{
  "variants": [
    { "size": "L", "color": "red",  "price": 29.99 },
    { "size": "S", "color": "blue", "price": 19.99 }
  ]
}
// A query for "size=L AND color=blue" would INCORRECTLY match this document
// because ES flattens: variants.size=[L,S], variants.color=[red,blue]

Nested Type (Separate Hidden Documents)

// Nested stores each array element as a hidden sub-document
// Queries must use "nested" query wrapper
GET /products/_search
{
  "query": {
    "nested": {
      "path": "variants",
      "query": {
        "bool": {
          "must": [
            { "term": { "variants.size": "L" } },
            { "term": { "variants.color": "red" } }
          ]
        }
      },
      "inner_hits": {}  // return the matching nested documents
    }
  }
}
// Pros: correct query semantics; can use inner_hits
// Cons: more storage (hidden docs); slower updates (full document re-index)

Parent-Child Join

// Parent-child: separate top-level documents linked by join field
// Useful for very frequent updates to "child" without re-indexing "parent"
PUT /shop
{
  "mappings": {
    "properties": {
      "join_field": {
        "type": "join",
        "relations": { "product": "review" }
      }
    }
  }
}
// Index parent
PUT /shop/_doc/product-1
{ "name": "Headphones", "join_field": "product" }

// Index child (must go to same shard as parent → routing=parent_id)
PUT /shop/_doc/review-1?routing=product-1
{ "stars": 5, "text": "Great!", "join_field": { "name": "review", "parent": "product-1" } }

// has_child query
{ "query": { "has_child": { "type": "review", "query": { "term": { "stars": 5 } } } } }
// has_parent query
{ "query": { "has_parent": { "parent_type": "product", "query": { "term": { "name": "headphones" } } } } }
AspectNestedParent-Child
Update costFull parent document re-indexOnly child document re-indexed
Query performanceFaster (all in same document block)Slower (join across documents in memory)
Use caseSub-objects read together, infrequent updatesMany independent child objects, frequent child updates

Pagination Strategies

from + size (Simple Pagination)

GET /products/_search
{
  "from": 0, "size": 20,  // page 1
  "query": { "match_all": {} },
  "sort": [{ "created_at": "desc" }]
}
// Deep pagination problem: from=10000&size=20 requires ES to fetch+sort 10,020 documents
// on every shard, then merge. Max default: index.max_result_window=10000

search_after (Cursor-Based — Recommended)

// First page
GET /products/_search
{
  "size": 20,
  "sort": [{ "created_at": "desc" }, { "_id": "asc" }],  // tie-breaker on _id
  "query": { "match_all": {} }
}
// Returns last sort values: ["2024-06-01T10:00:00", "prod-123"]

// Next page using search_after
{
  "size": 20,
  "sort": [{ "created_at": "desc" }, { "_id": "asc" }],
  "search_after": ["2024-06-01T10:00:00", "prod-123"],
  "query": { "match_all": {} }
}
// O(log N) for each page; stateless cursor; consistent across index changes

Scroll API (Large Data Export)

// Initial scroll request
POST /logs/_search?scroll=2m   // keep scroll context alive for 2 minutes
{
  "size": 1000,
  "query": { "range": { "timestamp": { "gte": "2024-01-01" } } }
}
// Returns: "_scroll_id": "FGluY2x1ZGVfY29udGVy..."

// Subsequent scroll pages
POST /_search/scroll
{
  "scroll": "2m",
  "scroll_id": "FGluY2x1ZGVfY29udGVy..."
}
// Empty hits = done. Delete scroll context when finished:
DELETE /_search/scroll { "scroll_id": "..." }
// Note: scroll is for bulk export, not real-time pagination. Use search_after for live pagination.

Performance Tuning

Shard Sizing

  • Target 10–50 GB per shard (search performance degrades with very large shards; very small shards waste resources).
  • Shards per node: aim for <20 shards per GB of heap. With 30 GB heap → max ~600 shards.
  • For time-series: use ILM rollover (max_size=50gb, max_age=7d) to auto-create right-sized indices.

Bulk Indexing Optimization

// Step 1: Disable refresh and replicas for bulk load
PUT /my-index/_settings
{
  "index": {
    "refresh_interval": "-1",  // disable refresh
    "number_of_replicas": 0    // temporarily remove replicas
  }
}

// Step 2: Bulk index (use _bulk API — never index one document at a time)
POST /_bulk
{ "index": { "_index": "my-index", "_id": "1" } }
{ "field1": "value1", "field2": "value2" }
{ "index": { "_index": "my-index", "_id": "2" } }
{ "field1": "value3" }

// Step 3: Force merge (reduces segment count for read performance)
POST /my-index/_forcemerge?max_num_segments=1

// Step 4: Restore refresh and replicas
PUT /my-index/_settings
{
  "index": { "refresh_interval": "1s", "number_of_replicas": 1 }
}

Query Optimization

  • Use filter context (not must) for non-scoring conditions — filters are cached.
  • Avoid wildcard and prefix queries on analyzed text fields — use keyword fields or edge_ngram for autocomplete.
  • Avoid script queries in the hot path — pre-compute values at index time instead.
  • Use _source filtering or stored fields to reduce network payload.
  • Set track_total_hits: false if exact count beyond 10K is not needed (saves sort + count work).
  • Profile slow queries with the Search Profiler in Kibana or "profile": true in the query.
// Query with source filtering and profiling
GET /products/_search
{
  "profile": true,
  "track_total_hits": false,
  "_source": ["id", "name", "price"],
  "query": {
    "bool": {
      "must": [
        { "match": { "description": "headphones" } }
      ],
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price": { "lte": 500 } } }
      ]
    }
  }
}

JVM & OS Tuning

  • Heap: set to 50% of RAM (max 30-31 GB — stay below 32 GB to keep compressed oops). Example: 16 GB RAM → -Xms8g -Xmx8g.
  • Use G1GC (default) or ZGC for large heaps.
  • Disable swap: bootstrap.memory_lock: true or swapoff -a.
  • Set vm.max_map_count=262144 for Lucene mmap.
  • Use multiple data paths (path.data: [/data1, /data2]) to stripe across disks.

Interview Q&As — 20+ Questions

Q1. What is the difference between an index, a shard, and a replica in Elasticsearch? Easy

An index is a logical namespace containing documents with similar structure (like a database table). It is divided into primary shards (1 by default, configurable at creation time) which provide horizontal scaling — each shard is a self-contained Lucene index stored on a data node. A replica is an exact copy of a primary shard, allocated on a different node. Replicas provide: (1) fault tolerance — if the primary fails, the replica is promoted; (2) read scaling — search requests can be served by any replica. Replica count can be changed at runtime; primary shard count cannot (requires reindex).

Q2. What is the difference between filter context and query context in Elasticsearch? Easy

Query context: Used in must / should / the top-level query. Answers "how well does this document match?" — produces a _score. Used for relevance ranking. Filter context: Used in filter / must_not. Answers "does this document match or not?" — binary yes/no, does NOT compute _score. Filter results are cached in the filter cache (bitset per segment, very fast). Use filter for: status fields, date ranges, boolean flags, any condition where relevance doesn't matter. Use query for: full-text search, fuzzy matching, anything where ranking matters. Mixing both: put scoring queries in must, non-scoring conditions in filter.

Q3. Why would a cluster be in yellow status vs red status? Easy

Green: All primary and replica shards are allocated and active.

Yellow: All primary shards are active, but one or more replica shards are not allocated. Data is safe (primaries are fine) but there is no redundancy — if a node hosting a primary fails while yellow, data loss is possible. Common cause: not enough nodes (1 node can't host primary + replica of same shard). Fix: add more nodes, or reduce number_of_replicas.

Red: One or more primary shards are unallocated. Some data is unavailable. Queries on affected indices may return partial or no results. Requires immediate investigation: disk full, node down, corrupt shard.

Q4. Explain the text vs keyword field type difference. When would you use each? Easy

text: Analyzed during indexing — runs through character filters, tokenizer, and token filters to produce tokens stored in the inverted index. "Hello World" becomes tokens ["hello", "world"]. Supports full-text match queries (match, match_phrase). Cannot be used for sorting, aggregations, or exact-match term queries (because it's tokenized). keyword: Not analyzed — stored as-is. "Hello World" is stored as "Hello World". Supports exact-match (term), sorting, aggregation. Common dual-field pattern: map a string as both text (for full-text search) and keyword (for sort/agg): "fields": { "raw": { "type": "keyword" } }. Then query with name for search, name.raw for sort/aggregation.

Q5. What is the deep pagination problem in Elasticsearch and how do you solve it? Intermediate

With from + size pagination, requesting page 500 (from=10000, size=20) requires each shard to return the top 10,020 documents, the coordinating node sorts all of them (potentially thousands from multiple shards), and discards 10,000 to return 20. This is O(from + size) work per shard — very expensive for deep pages. ES limits this to 10,000 results by default (index.max_result_window). Solutions: (1) search_after: stateless cursor using the sort values of the last seen document — O(log N) per page, works for any depth. Requires a consistent sort order with a tie-breaker. (2) Scroll API: for bulk export only — creates a snapshot of the search context (kept alive for a configurable period). Memory intensive; not for live pagination. (3) Point in Time (PIT) + search_after: ES 7.10+: create a PIT, use it with search_after for consistent pagination across index changes.

Q6. How does BM25 scoring work and how can you customize it? Intermediate

BM25 (Best Match 25) is the default similarity algorithm in ES (since 5.0). Key parameters: k1 (1.2 by default) controls term frequency saturation — higher k1 = term frequency matters more (no saturation); b (0.75) controls length normalization — b=1 = full normalization; b=0 = no length penalty. Score ≈ IDF × (TF × (k1+1)) / (TF + k1 × (1 - b + b × docLen/avgDocLen)). Customize: (1) Change k1/b at index level: "similarity": { "my_bm25": { "type": "BM25", "k1": 1.5, "b": 0.8 } }; apply to field mapping. (2) Use function_score to add custom signals (popularity, recency, business rules). (3) Use boost on query clauses to upweight certain fields.

Q7. What is the difference between nested documents and parent-child relationships? Intermediate

Nested documents: Array of sub-objects stored as hidden Lucene documents within the same Lucene block as the parent. Querying requires a nested query wrapper. Updating one sub-object re-indexes the entire parent document. Faster query performance (co-located on disk). Parent-child join: Completely separate top-level documents linked by a join field. Child documents can be updated independently without re-indexing the parent. Use has_child/has_parent queries. Slower (joins performed in memory at query time). Parent and child documents must be on the same shard (use routing). Choose nested for "owned" sub-objects that change together; choose parent-child for high-frequency independent updates of many children.

Q8. Explain ILM phases and when to move data from hot to warm to cold. Intermediate

ILM (Index Lifecycle Management) automates management of time-series indices. Hot phase: Active indexing and frequent searching. Store on fast NVMe. Use rollover to create a new index when the current one reaches a size/age threshold. Warm phase: No new writes; still frequently queried. Shrink to 1 shard (reduce overhead), force merge to 1 segment (faster reads), reduce replicas to 1. Move to slower SSD/HDD. Cold phase: Infrequently queried. Can make searchable snapshot (serve from S3 with small local cache). Frozen phase: very large old datasets — blocks are loaded from S3 on demand. Delete: Finally remove old data. Transitions based on min_age (since rollover), size, or doc count. Configure once, applies to all matching indices automatically.

Q9. How does Elasticsearch handle full-text search with analyzers? Walk through an example. Intermediate

At index time: "The Quick Brown Fox!" → standard analyzer → character filter (no-op for standard) → tokenizer (split on whitespace/punctuation) → ["The", "Quick", "Brown", "Fox"] → lowercase token filter → ["the", "quick", "brown", "fox"] → stored in inverted index. At search time: the query string goes through the same analyzer (by default). "Quick Brown" → ["quick", "brown"]. ES looks up both tokens in the inverted index, scores documents by how many terms match and how rare those terms are (TF-IDF/BM25). Mismatch between index-time and query-time analyzer causes failed searches (e.g., indexing with English stemmer but querying with standard analyzer). Use the same analyzer for both, or explicitly set search_analyzer separately from analyzer.

Q10. What is a coordinating node and when would you dedicate nodes to this role? Intermediate

Any ES node can act as a coordinating node for a request — it routes the request to shards, collects and merges partial results, and returns the final response. The merge step (sorting, aggregating, de-duplicating) is CPU and memory intensive for large result sets or complex aggregations. Dedicated coordinating-only nodes (no data, no master roles) make sense when: (1) you have large Kibana dashboards with heavy aggregations; (2) many concurrent search requests overload data nodes; (3) clients connect to a load-balanced coordinating tier (data nodes are not exposed directly). These nodes handle the "gather" phase while data nodes focus on the "scatter" phase. They require less disk but more RAM and CPU.

Q11. Explain the difference between match_phrase and match_phrase_prefix queries. Easy

match_phrase: Requires all query tokens to appear in the exact specified order with no other tokens in between (configurable with slop parameter for allowed gap). "Quick brown fox" → document must contain "quick brown fox" as a phrase. Uses positional information from the inverted index. match_phrase_prefix: Like match_phrase but the last token is treated as a prefix — used for as-you-type autocomplete. "quick br" → matches "quick brown fox", "quick bridge design", etc. The last term is expanded into all terms in the index starting with that prefix (limited by max_expansions). Better alternative for autocomplete: use a dedicated edge_ngram token filter at index time — stores "b", "br", "bro", "brow" etc. in the inverted index, enabling a simple term query without runtime prefix expansion.

Q12. How would you design an autocomplete search in Elasticsearch? Advanced

Three approaches: (1) edge_ngram analyzer: Index-time tokenization produces prefix tokens. "iPhone" → ["i", "ip", "iph", "ipho", "iPhon", "iPhone"]. Use a standard analyzer at search time (exact token lookup, not re-tokenizing). Very fast, no query-time overhead. Increases index size. Best for product/user search. (2) completion suggester: Dedicated FST (finite state transducer) data structure, fastest possible prefix lookup (microseconds). But limited: no full-text scoring, no filtering after suggestion retrieval, separate field. Best for pure "search as you type" suggestion dropdowns. (3) search_as_you_type field type: Creates subfields for edge ngrams and prefix at different positions. Supports phrase queries. Most flexible for mixed autocomplete + full-text. Recommendation: edge_ngram for most use cases; completion for dedicated suggest dropdowns; search_as_you_type for rich search bars.

Q13. What causes split-brain in Elasticsearch and how does it prevent it? Advanced

Split-brain: network partition causes two subsets of nodes to each elect their own master and make conflicting cluster state changes. Old prevention: discovery.zen.minimum_master_nodes = (N/2)+1. ES 7+ replaced this with a Raft-based consensus algorithm: each cluster change (shard assignment, index creation) requires a majority quorum of master-eligible nodes to acknowledge. With 3 master-eligible nodes: quorum = 2. A partition creating two groups of 1 cannot form a majority — the minority side refuses to elect a new master or accept cluster state changes. Best practice: always use an odd number of master-eligible nodes (3 or 5); never 2. Use dedicated master nodes in large production clusters (separate from data nodes).

Q14. What is the difference between fielddata and doc_values for aggregations? Advanced

doc_values: Column-oriented data structure built at index time for all field types except text. Stored on disk in a compressed, sorted format. Lives outside the JVM heap (memory-mapped files). Enables sorts, aggregations, scripting with no heap memory overhead. Default for keyword, numeric, date, boolean, geo fields. fielddata: In-memory, heap-based data structure built lazily (on first aggregation) for text fields. Must load entire field's terms for all documents into JVM heap — causes GC pressure and potential OOM for large datasets. Very expensive. Recommendation: Never enable fielddata on text fields in production. Instead: use a keyword sibling field (.raw) for aggregations; or use a separate keyword field. Control with indices.fielddata.cache.size (circuit breaker).

Q15. Explain Elasticsearch snapshots and SLM (Snapshot Lifecycle Management). Intermediate

Snapshots are incremental backups of indices stored in a remote repository (S3, GCS, Azure Blob, HDFS, shared filesystem). First snapshot is a full backup; subsequent snapshots only copy changed segments. Snapshots are at the Lucene segment level — they capture committed segments, so in-memory but not flushed data may not be included (force a flush before snapshotting if needed). SLM automates snapshot creation with a cron-like schedule, retention policies (min_count, max_count, expire_after), and automatic deletion of expired snapshots. SLM also tracks snapshot status and exposes metrics. Use SLM for: disaster recovery, cross-cluster restore, data migration. Searchable snapshots (Frozen tier) mount snapshots directly as read-only indices without full restore — data stays in S3, cached on local disk on-demand.

Q16. When would you use terms aggregation vs date_histogram aggregation? Easy

terms aggregation: Groups documents by unique values of a field. Output: {key: "electronics", doc_count: 1234}. Use for categorical dimensions: product categories, user countries, status values, top N items. Has a size parameter (default 10) — returns only the top N terms by count (approximate for distributed indices; use shard_size to improve accuracy). date_histogram aggregation: Groups documents by time buckets (hour, day, week, month). Output: {key_as_string: "2024-06-01", doc_count: 500}. Use for time-series visualization: events per day, revenue over time, error rate trends. Supports fixed_interval (7d) or calendar_interval (1M, 1y) — use calendar for month/year to handle varying month lengths. Combine both: nested date_histogram inside terms to get "orders per category per day."

Q17. How would you implement semantic search in Elasticsearch? Advanced

Three approaches: (1) dense_vector + kNN search (ES 8.0+): Generate embeddings externally (OpenAI, Cohere, sentence-transformers), store as dense_vector field. At query time, embed the query and search using knn parameter (HNSW index). Supports hybrid search (BM25 + kNN) with reciprocal rank fusion. (2) ELSER (Elastic Learned Sparse EncodeR, ES 8.8+): Elastic's own ML model that generates sparse vectors (term weights, like BM25 but ML-generated). Deployed as an ML model in ES. Use sparse_vector field + text_expansion query. No external service needed. Better than BM25 for semantic nuance. (3) Inference API (ES 8.12+): Integrate third-party embedding models (OpenAI, Cohere, Azure) natively — embeddings generated at index and query time by ES via the inference service. Simplifies the architecture. For production: use hybrid search combining BM25 (lexical) + ELSER/kNN (semantic) + reciprocal rank fusion for the best of both worlds.

Q18. What is the refresh interval and how does it affect near-real-time search? Intermediate

Elasticsearch writes new documents to an in-memory buffer and periodically flushes them to a new Lucene segment. The refresh_interval (default: 1s) controls how often this happens. After a refresh, new documents become searchable (near-real-time, not real-time). Setting refresh_interval: -1 disables automatic refresh — useful during bulk indexing (significantly increases indexing throughput). Setting to 30s or 60s for write-heavy indices where staleness is acceptable reduces I/O overhead. You can manually trigger a refresh: POST /my-index/_refresh. ES 7.6+: dynamic refresh — if an index has no searches in the last 30 seconds (configurable with index.search.idle.after), refresh is automatically suspended until next search, improving write performance for rarely-searched indices.

Q19. How does Logstash differ from Filebeat? When would you use each? Intermediate

Filebeat: Written in Go; extremely lightweight (~20-50 MB RAM); designed for single task — reliably shipping log files to a destination (Logstash, Kafka, Elasticsearch). Has basic filter capability via processors. Backpressure handling: slows reading if output is overwhelmed; doesn't lose events. Runs on every server as a log forwarder. Logstash: Written in Java; heavier (500 MB+ RAM); runs a JVM; powerful filtering pipeline with 200+ plugins (grok, mutate, jdbc, aggregate). Can read from many sources (Kafka, S3, JDBC, Syslog) and write to many outputs. Complex transformation logic. Central aggregation point. Architecture: use Filebeat on every server to collect and forward logs with minimal resources → Logstash for centralized complex parsing/enrichment → Elasticsearch. Or ship directly from Filebeat to Elasticsearch using ingest pipelines (Logstash-like transformation built into ES) — simpler but less flexible.

Q20. What are the trade-offs of more shards vs fewer shards for an index? Intermediate

More shards: Higher parallelism for indexing (more shards = more nodes can write simultaneously); higher search parallelism within a single query (all shards searched in parallel). Downsides: each shard has overhead (file handles, memory, Lucene segment management); scatter-gather overhead increases with shard count (coordinating node must merge results from N shards); small shards are inefficient (lots of overhead for little data); recovery time after failure proportional to shard count. Fewer shards: Less overhead, faster recovery, less merge overhead. Downside: search cannot be parallelized beyond shard count; large shards are slow to search and slow to recover. Rule: 10-50 GB per shard is the sweet spot. Use ILM rollover for time-series to auto-size. For static indices: number_of_shards = (expected_data_size_gb / 30) rounded up, minimum 1.

Q21. How would you troubleshoot a slow Elasticsearch search query? Advanced

Step 1: Add "profile": true to the query — the profile API shows how long each query clause took on each shard. Identifies the slow clause. Step 2: Check if the slow clause can be moved to filter context (saves scoring work + enables caching). Step 3: Identify if fielddata is being used on text fields (appears in profile as "load_stored_fields") — switch to keyword field. Step 4: Check if the query forces a full-scan (wildcard with leading *, regexp, script query) — rewrite or pre-compute at index time. Step 5: Use GET /_cat/shards?v and GET /_nodes/stats to check if specific shards/nodes are slow (hardware issues, GC pauses). Step 6: Check if the index has too many small segments (force merge helps). Step 7: Check for heavy aggregations — add execution_hint: "map" or increase shard_size. Step 8: Enable Slow Log: index.search.slowlog.threshold.query.warn: 2s.

Q22. What is ES|QL and how does it differ from the Query DSL? Advanced

ES|QL (Elasticsearch Query Language, introduced in ES 8.10) is a pipe-based query language designed for analytics and data exploration. Syntax: FROM logs | WHERE level == "ERROR" | STATS count = COUNT(*) BY service | SORT count DESC | LIMIT 10. Advantages over Query DSL: (1) More readable and writable for analysts familiar with SQL-like syntax; (2) Pipe operators (WHERE, STATS, EVAL, SORT, LIMIT, ENRICH, DISSECT, GROK, RENAME) are composable; (3) Can perform in-query computations (EVAL new_field = field1 * 2); (4) Unified query + aggregation in one statement; (5) Better for ad-hoc analysis in Kibana Discover. Limitations vs DSL: (1) Less mature — not all DSL features available yet; (2) Full-text relevance scoring not the focus; (3) Does not support all aggregation types yet.
