Pods

A Pod is the smallest deployable unit in Kubernetes — one or more containers sharing the same network namespace and storage.

apiVersion: v1
kind: Pod
metadata:
  name: myapp
  namespace: default
  labels:
    app: myapp
    version: v1
  annotations:
    prometheus.io/scrape: "true"
spec:
  restartPolicy: Always  # Always | OnFailure | Never
  serviceAccountName: myapp-sa
  securityContext:          # Pod-level security
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault

  initContainers:           # Run to completion before main containers
    - name: db-migrator
      image: myapp:migrate
      command: ["python", "manage.py", "migrate"]
      env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-secrets
              key: url

  containers:
    - name: app
      image: myapp:v1.2
      ports:
        - containerPort: 8080
      resources:
        requests:           # Scheduler uses this for placement
          cpu: "100m"       # 100 millicores = 0.1 CPU
          memory: "128Mi"
        limits:             # Container is OOM-killed if exceeded
          cpu: "500m"
          memory: "512Mi"
      env:
        - name: NODE_ENV
          value: production
        - name: SECRET_KEY
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: secret-key
        - name: POD_NAME
          valueFrom:
            fieldRef:
              fieldPath: metadata.name  # Downward API
      volumeMounts:
        - name: config
          mountPath: /etc/config
          readOnly: true
        - name: data
          mountPath: /var/data
      securityContext:      # Container-level security
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      livenessProbe:
        httpGet:
          path: /healthz
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet:
          path: /ready
          port: 8080
        initialDelaySeconds: 5
        periodSeconds: 5

    # Sidecar container (K8s 1.28: native sidecar containers)
    - name: log-shipper
      image: fluent/fluent-bit
      volumeMounts:
        - name: logs
          mountPath: /var/log/app

  # Ephemeral containers (debugging - kubectl debug)
  # Added via kubectl debug -it pod/myapp --image=busybox

  volumes:
    - name: config
      configMap:
        name: app-config
    - name: data
      persistentVolumeClaim:
        claimName: app-pvc
    - name: logs
      emptyDir: {}          # Shared between containers in same pod

ReplicaSets

Ensures a specified number of Pod replicas are running at any time. Usually managed by a Deployment, not directly.

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp       # Must match pod template labels
  template:            # Pod template
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: myapp:v1

Deployments

Deployments manage ReplicaSets and provide declarative updates with rollout strategies.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 5
  selector:
    matchLabels:
      app: myapp
  strategy:
    type: RollingUpdate    # or Recreate
    rollingUpdate:
      maxSurge: 2          # Extra pods during rollout (absolute or %)
      maxUnavailable: 1    # Pods that can be unavailable (absolute or %)
  revisionHistoryLimit: 10  # Number of old ReplicaSets to keep
  minReadySeconds: 10       # Wait before considering pod available
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: myapp:v2

Deployment Commands

kubectl rollout status deployment/myapp
kubectl rollout history deployment/myapp
kubectl rollout history deployment/myapp --revision=3
kubectl rollout undo deployment/myapp              # Rollback to previous
kubectl rollout undo deployment/myapp --to-revision=2
kubectl rollout pause deployment/myapp             # Pause rollout (canary)
kubectl rollout resume deployment/myapp            # Resume paused rollout
kubectl set image deployment/myapp app=myapp:v3   # Trigger rollout
kubectl scale deployment myapp --replicas=10

Rolling Update vs Recreate

StrategyBehaviorDowntimeUse Case
RollingUpdateIncrementally replaces podsNoneDefault; most production cases
RecreateKills all old pods, then creates newYesDB schema changes that are incompatible

StatefulSets

For stateful applications requiring stable network IDs, ordered deployment/scaling, and persistent storage.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless   # Headless service for DNS
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0               # Only update pods >= partition index
  podManagementPolicy: OrderedReady  # or Parallel
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:15
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:          # Each pod gets its own PVC
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: fast
        resources:
          requests:
            storage: 10Gi
StatefulSet guarantees:
  • Stable pod names: postgres-0, postgres-1, postgres-2
  • Stable DNS: postgres-0.postgres-headless.default.svc.cluster.local
  • Ordered scaling: pods are created/deleted in order (0,1,2... forward; 2,1,0 reverse)
  • Persistent storage per pod (PVC not deleted on pod deletion)

DaemonSets

Ensures one Pod runs on every (or selected) nodes. Used for cluster-wide services.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      tolerations:              # Run on control-plane nodes too
        - key: node-role.kubernetes.io/control-plane
          effect: NoSchedule
      hostNetwork: true         # Use host network
      hostPID: true
      containers:
        - name: node-exporter
          image: prom/node-exporter
          ports:
            - containerPort: 9100
              hostPort: 9100

Use cases: Log collectors (Fluentd/Filebeat), monitoring agents (Prometheus node exporter), CNI plugins, storage drivers, network overlays.

Jobs & CronJobs

apiVersion: batch/v1
kind: Job
metadata:
  name: db-backup
spec:
  completions: 5          # Total successful completions needed
  parallelism: 2          # Max pods running simultaneously
  backoffLimit: 4         # Max retries before marking failed
  activeDeadlineSeconds: 600  # Job timeout
  ttlSecondsAfterFinished: 100  # Auto-cleanup after finish
  template:
    spec:
      restartPolicy: OnFailure   # Never | OnFailure (not Always!)
      containers:
        - name: backup
          image: backup-tool
          command: ["backup.sh"]
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
spec:
  schedule: "0 2 * * *"         # Cron: 2am daily
  concurrencyPolicy: Forbid     # Allow | Forbid | Replace
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  startingDeadlineSeconds: 200  # Deadline to start missed job
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool

kind: Service
metadata:
  name: myapp-svc
spec:
  type: ClusterIP              # ClusterIP | NodePort | LoadBalancer | ExternalName
  selector:
    app: myapp                 # Routes to pods with this label
  ports:
    - name: http
      port: 80                 # Service port
      targetPort: 8080         # Pod port
      protocol: TCP

---

metadata:
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
spec:
  type: LoadBalancer
  externalTrafficPolicy: Local  # Preserve client IP; Local | Cluster

Ingress

Manages external HTTP/HTTPS access to services with path-based and host-based routing, TLS termination, and more.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/rate-limit: "100"
    nginx.ingress.kubernetes.io/proxy-body-size: "100m"
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.example.com
        - www.example.com
      secretName: example-tls-secret     # TLS cert stored as Secret
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /v1/users
            pathType: Prefix             # Prefix | Exact | ImplementationSpecific
            backend:
              service:
                name: user-service
                port:
                  number: 80
          - path: /v1/orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
    - host: www.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80

ConfigMaps & Secrets

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  config.yaml: |
    server:
      port: 8080
      timeout: 30s
---
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque                      # Opaque | kubernetes.io/tls | kubernetes.io/dockerconfigjson
data:
  db-password: cGFzc3dvcmQ=      # base64 encoded
  api-key: c2VjcmV0a2V5          # echo -n "secretkey" | base64
stringData:                       # Auto-encoded (takes plain text)
  new-secret: "plaintext-value"
# Using ConfigMap and Secret in a Pod
spec:
  containers:
    - name: app
      # Method 1: As environment variables (individual keys)
      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_ENV
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: db-password
      # Method 2: All keys as env vars
      envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: app-secret
      volumeMounts:
        - name: config-vol
          mountPath: /etc/config
          readOnly: true
  volumes:
    # Method 3: Volume mount (updates when ConfigMap changes)
    - name: config-vol
      configMap:
        name: app-config
        items:
          - key: config.yaml
            path: config.yaml
Secrets are NOT encrypted by default! They are only base64-encoded. For real security:
  • Enable Encryption at Rest for etcd (EncryptionConfiguration)
  • Use Sealed Secrets (Bitnami) — encrypt with cluster public key
  • Use External Secrets Operator — sync from AWS Secrets Manager / HashiCorp Vault
  • Use CSI Secret Store Driver — mount secrets from external store

PersistentVolumes & PVCs

apiVersion: v1
kind: PersistentVolume
metadata:
  name: my-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteOnce        # RWO: single node RW
    # - ReadOnlyMany       # ROX: multiple nodes RO
    # - ReadWriteMany      # RWX: multiple nodes RW (NFS, EFS)
    # - ReadWriteOncePod   # K8s 1.22: single pod RW (strict)
  persistentVolumeReclaimPolicy: Retain   # Retain | Recycle (deprecated) | Delete
  storageClassName: fast
  volumeMode: Filesystem   # Filesystem | Block
  csi:
    driver: ebs.csi.aws.com
    volumeHandle: vol-0abcd1234efgh5678
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast   # Must match PV or StorageClass
  resources:
    requests:
      storage: 50Gi
---
# StorageClass for dynamic provisioning
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iopsPerGB: "10"
  fsType: ext4
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer   # Topology-aware provisioning

# Role — namespace-scoped
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]                # "" = core API group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
# ClusterRole — cluster-scoped (or referenced from any namespace)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: secret-reader
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list"]
---

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default

    name: jane

    name: dev-team
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: myapp-sa
    namespace: default
roleRef:
  kind: Role           # Role | ClusterRole
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Taints, Tolerations, Affinity & Priority

# Taints — added to nodes (repel pods)
# kubectl taint nodes node1 key=value:NoSchedule
# kubectl taint nodes node1 key=value:NoExecute
# kubectl taint nodes node1 key=value:PreferNoSchedule

spec:
  # Tolerations — allow pod to be scheduled on tainted nodes
  tolerations:
    - key: "dedicated"
      operator: "Equal"     # Equal | Exists
      value: "gpu"
      effect: "NoSchedule"  # NoSchedule | NoExecute | PreferNoSchedule

  # Node Affinity — schedule pods on specific nodes
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:  # Hard
        nodeSelectorTerms:
          - matchExpressions:
              - key: node.kubernetes.io/instance-type
                operator: In
                values: ["m5.xlarge", "m5.2xlarge"]
      preferredDuringSchedulingIgnoredDuringExecution: # Soft
        - weight: 1
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values: ["us-east-1a"]

    # Pod Affinity — co-locate pods
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: cache
          topologyKey: kubernetes.io/hostname  # Same node

    # Pod Anti-Affinity — spread pods across nodes
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: myapp
            topologyKey: kubernetes.io/hostname  # Different nodes
---
# Priority Class
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "High priority workloads"
preemptionPolicy: PreemptLowerPriority

Liveness, Readiness & Startup Probes

ProbePurposeAction on Failure
LivenessIs the container running? Detect deadlocksRestart container
ReadinessIs the container ready to serve traffic?Remove from Service endpoints (no restart)
StartupHas the application started? (slow starters)Restart container; disables liveness during startup
livenessProbe:
  httpGet:              # HTTP GET — 2xx/3xx = success
    path: /healthz
    port: 8080
    httpHeaders:
      - name: X-Health-Check
        value: "true"
  initialDelaySeconds: 30   # Wait before first probe
  periodSeconds: 10          # How often to probe
  timeoutSeconds: 5          # Probe timeout
  successThreshold: 1        # Consecutive successes to mark healthy
  failureThreshold: 3        # Consecutive failures to take action

readinessProbe:
  tcpSocket:            # TCP check — connection established = success
    port: 5432
  periodSeconds: 10
  failureThreshold: 3

startupProbe:
  exec:                 # Execute command — exit 0 = success
    command:
      - /bin/sh
      - -c
      - "cat /tmp/ready"
  failureThreshold: 30  # 30 * 10s = 300s for slow starts
  periodSeconds: 10

# gRPC probe (K8s 1.24+)
livenessProbe:
  grpc:
    port: 50051
    service: "grpc.health.v1.Health"

Pod-to-Pod Communication

  • Each Pod gets a unique cluster-wide IP (from Pod CIDR)
  • Pods on the same node communicate via a virtual ethernet pair (veth)
  • Pods on different nodes communicate via CNI plugin (overlay or BGP routing)

Interview Q&A

Q1: What is Kubernetes and why is it needed? Easy

Kubernetes is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications. Originally from Google (Borg/Omega internally), donated to CNCF.

Why needed: Containers alone don't provide HA, auto-scaling, self-healing, service discovery, rolling updates, or secret management. Kubernetes provides all of these.

Key capabilities: Auto-scaling (HPA/VPA), self-healing (restarts failed containers), service discovery (DNS), rolling updates with zero downtime, bin packing (efficient resource use), declarative config (desired state).

Q2: What is the difference between a Pod, Deployment, and StatefulSet? Easy

Pod: Smallest deployable unit. One or more containers sharing network/storage. Ephemeral — if a pod dies, it's gone.

Deployment: Manages ReplicaSets to maintain desired number of Pod replicas. Supports rolling updates and rollbacks. Use for stateless apps.

StatefulSet: Like Deployment but for stateful apps. Provides stable network identifiers (pod-0, pod-1), stable persistent storage per pod, ordered deployment/scaling. Use for databases, Kafka, ZooKeeper.

Q3: What is the difference between liveness and readiness probes? Easy

Liveness: Checks if the container is alive (no deadlock/crash). Failure → container is restarted. Use for detecting hangs.

Readiness: Checks if the container is ready to serve traffic. Failure → pod is removed from Service endpoints (NOT restarted). Use for startup delays, temporary unavailability.

Startup: Checks if app has started (for slow starters). Disables liveness/readiness during startup period. Failure → container restarted.

Critical difference: Failing liveness restarts the container. Failing readiness only removes it from load balancing.

Q4: How does Service discovery work in Kubernetes? Easy

Kubernetes uses CoreDNS for service discovery.

When a Service is created, CoreDNS creates a DNS record: <service-name>.<namespace>.svc.cluster.local

Services also get a ClusterIP (virtual IP). kube-proxy maintains iptables/ipvs rules to route traffic to actual pod IPs.

Pods can reach services by short name (within same namespace) or FQDN.

Headless services (clusterIP: None) return pod IPs directly instead of a virtual IP, useful for StatefulSets.

Q5: What is a Namespace and what are its use cases? Easy

Namespaces provide virtual cluster isolation within a physical cluster. Resources in different namespaces are isolated but can communicate if allowed.

Use cases:

  • Environment separation (dev/staging/prod in same cluster)
  • Team isolation (team-a/team-b)
  • Resource quotas per team/environment
  • RBAC scoping

Not isolated: Nodes, PersistentVolumes, StorageClasses, ClusterRoles are cluster-scoped.

Default namespaces: default, kube-system, kube-public, kube-node-lease

Q6: Explain the difference between ClusterIP, NodePort, and LoadBalancer services Intermediate

ClusterIP: Reachable only inside cluster via virtual IP. Default type. Used for inter-service communication.

NodePort: Exposes service on a static port (30000-32767) on every node's IP. Any NodeIP:NodePort reaches the service. Not suitable for production external access.

LoadBalancer: Provisions a cloud load balancer (AWS ELB, GCP LB). Gets an external IP. Built on top of NodePort + ClusterIP. Most production external traffic.

ExternalName: CNAME alias to external service. No proxying.

Ingress: Not a service type but routes HTTP/HTTPS traffic to multiple services via single LB. Much more cost-effective than one LB per service.

Q7: What is RBAC and how does it work in Kubernetes? Intermediate

Role-Based Access Control controls who can do what to which resources.

Components:

  • Role — Namespace-scoped permissions (verbs on resources)
  • ClusterRole — Cluster-scoped permissions (also used across namespaces)
  • RoleBinding — Assigns Role/ClusterRole to subjects in a namespace
  • ClusterRoleBinding — Assigns ClusterRole cluster-wide
  • Subjects: Users, Groups, ServiceAccounts

Principle of least privilege: Always grant minimum permissions needed. Use ServiceAccounts per workload, not shared accounts.

Q8: How does Kubernetes handle rolling updates and how would you rollback? Intermediate

Rolling updates replace pods incrementally based on maxSurge and maxUnavailable:

  1. Kubernetes creates new ReplicaSet with new image
  2. Scales up new RS by maxSurge pods
  3. Waits for new pods to be ready (readiness probe)
  4. Scales down old RS by maxUnavailable pods
  5. Repeats until all pods are new

Rollback:

kubectl rollout undo deployment/myapp
kubectl rollout undo deployment/myapp --to-revision=3
kubectl rollout history deployment/myapp

Old ReplicaSets are retained (controlled by revisionHistoryLimit) to enable rollback.

Q9: What is a ConfigMap vs Secret and what are the security concerns? Intermediate

ConfigMap: Non-sensitive configuration data. Stored in plain text in etcd.

Secret: Sensitive data. Stored as base64-encoded in etcd (NOT encrypted by default!).

Security concerns with Secrets:

  • base64 is NOT encryption — anyone with etcd access can read secrets
  • Secrets are visible in pod specs and environment variables

Best practices:

  • Enable etcd encryption at rest (EncryptionConfiguration)
  • Use Sealed Secrets or External Secrets Operator
  • Mount as volumes (not env vars) — less risk of accidental logging
  • Use RBAC to restrict Secret access
  • Rotate secrets regularly
Q10: What is the difference between DaemonSet and Deployment? Intermediate

Deployment: Runs a specified number of pod replicas distributed across nodes. Pods can be on any node. Scale by changing replica count. For application workloads.

DaemonSet: Ensures exactly one pod runs on every (or filtered) node. When nodes are added, pods are automatically added. Used for cluster-wide infrastructure: log collectors, monitoring agents, network plugins, storage drivers.

DaemonSet pods bypass the normal scheduler for node assignment.

Q11: How does HPA work? What metrics does it use? Intermediate

HPA (Horizontal Pod Autoscaler) automatically scales pod replicas based on observed metrics.

Control loop (every 15s by default):

  1. HPA controller queries metrics server (or custom metrics API)
  2. Calculates desired replicas: ceil(current * current_metric / desired_metric)
  3. Updates Deployment/ReplicaSet replica count

Metric types:

  • Resource: CPU/memory utilization (from metrics-server)
  • Pods: custom per-pod metrics (Prometheus Adapter)
  • Object: metrics from specific K8s objects
  • External: metrics from outside K8s (SQS queue depth via KEDA)

Gotcha: HPA requires metrics-server installed. Won't work without it.

Q12: What is etcd and why is it critical to Kubernetes? Advanced

etcd is a distributed, consistent key-value store using the Raft consensus algorithm. It stores ALL cluster state: pod specs, deployments, secrets, configmaps, service endpoints, RBAC rules.

Critical because: All kube-apiserver state is stored here. If etcd is corrupted, the cluster is broken. etcd is the single source of truth.

Best practices:

  • Run etcd on dedicated nodes (separate from control plane)
  • Use 3 or 5 members (always odd for quorum)
  • Regular backups: etcdctl snapshot save
  • Enable TLS encryption
  • SSD storage (latency-sensitive)
Q13: Explain Kubernetes networking — how do pods on different nodes communicate? Advanced

Kubernetes requires every pod to have a routable IP in the cluster network. Pods on different nodes communicate without NAT.

Implementation (depends on CNI):

Overlay (Flannel VXLAN):

  1. Pod A (node1, 10.244.1.5) sends packet to Pod B (node2, 10.244.2.8)
  2. Flannel encapsulates packet in VXLAN (UDP port 8472)
  3. Outer packet: node1 IP → node2 IP
  4. node2 decapsulates and delivers to Pod B

No-overlay (Calico BGP):

  1. Each node advertises its pod CIDR via BGP
  2. Packets routed directly at L3 — no encapsulation overhead

AWS VPC CNI: Each pod gets a real VPC IP (from ENI secondary IPs). No overlay needed — native VPC routing.

Q14: What is Helm and what problem does it solve? Intermediate

Helm is the package manager for Kubernetes. It solves the problem of managing complex K8s applications that span many YAML files.

Problems solved:

  • Templating — parameterize manifests for different environments
  • Versioning — chart versions track application packaging changes
  • Dependency management — include dependencies (subcharts)
  • Release management — upgrade/rollback with history tracking
  • Packaging — distribute applications as charts

Helm v3 vs v2: v3 removed Tiller (server-side component). Security and simplification improvement.

Q15: What are Init Containers and when would you use them? Intermediate

Init containers run to completion before any app containers start. Multiple init containers run sequentially.

Use cases:

  • Wait for dependencies: wait-for-database, wait-for-kafka
  • DB migrations before app starts
  • Clone git repo, fetch configuration
  • Register with service mesh, generate TLS certs
  • Permissions setup: chmod, chown

Key properties: Must complete successfully for app container to start. If init container fails, pod restarts (per restartPolicy). They have different resource limits from app containers.

Q16: What is a NetworkPolicy and how does it differ from a firewall? Advanced

NetworkPolicy is a Kubernetes resource that controls ingress/egress traffic between pods using label selectors. Implemented by the CNI plugin.

Key differences from traditional firewall:

  • Identity-based (pod labels, namespace labels) not just IP-based
  • Dynamic — automatically updates as pods scale
  • Declarative K8s resource, version-controlled
  • Applied by CNI plugin (Calico, Cilium, Weave)

Important: NetworkPolicies are additive. If no NetworkPolicy selects a pod, all traffic is allowed. Once any NetworkPolicy selects a pod, traffic not explicitly allowed is denied.

Default deny all:

spec:
  podSelector: {}        # All pods
  policyTypes: [Ingress, Egress]  # No rules = deny all
Q17: What is the Operator pattern? Advanced

The Operator pattern extends Kubernetes to manage stateful/complex applications using custom controllers. It encodes operational knowledge (how to deploy, scale, backup, upgrade a complex system) in code.

Components:

  • CRD — Defines the custom resource schema (e.g., PostgresCluster)
  • Custom Controller — Watches CRD instances, reconciles desired vs actual state

Examples: Prometheus Operator (manages Prometheus + Alertmanager), Strimzi (Kafka), CloudNativePG (PostgreSQL), Argo CD.

Operator maturity model: Basic install → Seamless upgrades → Full lifecycle → Deep insights → Auto-pilot

Q18: What is Pod Disruption Budget (PDB)? Advanced

PDB limits the number of pods of a replicated application that can be down simultaneously due to voluntary disruptions (node drain, rolling updates, cluster upgrades).

Not applies to: Involuntary disruptions (node failure, OOM kill, hardware failure).

minAvailable: 2 — at least 2 pods must be available
maxUnavailable: 1 — at most 1 pod can be unavailable

Critical for maintaining availability during cluster maintenance. kubectl drain will respect PDBs.

Q19: How does Kubernetes scheduler work? Advanced

The scheduler assigns pods to nodes in two phases:

Filtering: Eliminates nodes that don't satisfy requirements:

  • Resource availability (CPU/memory requests)
  • Node selectors and affinity
  • Taints and tolerations
  • Volume topology constraints
  • Pod affinity/anti-affinity

Scoring: Ranks remaining nodes (0-100):

  • LeastRequestedPriority — prefer least loaded node
  • BalancedResourceAllocation — balance CPU/memory
  • NodeAffinityPriority — preferred affinity

Pod is assigned to highest-scoring node. Multiple schedulers can co-exist; custom schedulers possible.

Q20: What is a Service Mesh and when should you use one? Very Advanced

A service mesh adds a dedicated infrastructure layer for service-to-service communication, typically via sidecar proxies (Envoy in Istio/Linkerd).

Capabilities:

  • mTLS — automatic mutual TLS between all services
  • Traffic management — canary releases, circuit breaking, retries
  • Observability — distributed tracing, metrics, access logs without code changes
  • Policy enforcement — rate limiting, authorization policies

When to use:

  • Security: Zero-trust networking, encrypt all traffic
  • Advanced traffic management (A/B, canary)
  • Observability needed across many services

When NOT to use: Small deployments (operational complexity), when performance overhead is unacceptable, when a simpler solution suffices.

Q21: What happens when you run kubectl apply? Advanced
  1. kubectl reads the YAML and sends HTTP PATCH/POST to kube-apiserver
  2. apiserver authenticates (client cert, bearer token, OIDC)
  3. apiserver authorizes (RBAC)
  4. Admission controllers run (mutating first, then validating — e.g., add labels, security policies)
  5. apiserver persists to etcd
  6. Relevant controllers detect the change via watch
  7. e.g., Deployment controller creates/updates ReplicaSet
  8. ReplicaSet controller creates Pods (adds to pending queue)
  9. Scheduler assigns pods to nodes (adds nodeName to pod spec)
  10. kubelet on target node detects new pod assignment
  11. kubelet calls containerd (CRI) to pull image and start container
  12. kube-proxy updates iptables rules if services changed
Q22: What is Resource Quota and LimitRange? Intermediate

ResourceQuota: Namespace-level limit on total resource consumption. Constrains total CPU, memory, pod count, service count, PVC count in a namespace.

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 4Gi
    limits.cpu: "8"
    limits.memory: 8Gi
    count/pods: "20"

LimitRange: Sets default/min/max resource limits for pods/containers in a namespace. Ensures every container has limits.

spec:
  limits:
    - type: Container
      default:
        cpu: 200m
        memory: 256Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      max:
        cpu: "2"
        memory: 2Gi
Q23: Explain Istio's traffic management capabilities Very Advanced

VirtualService: Routes traffic based on headers, weight, source. Defines retry, timeout, fault injection.

DestinationRule: Defines load balancing policy, circuit breaking, connection pool settings, and subsets (versions).

Gateway: Manages ingress/egress for the mesh (separate from K8s Ingress).

Traffic splitting (canary): Route 10% to v2, 90% to v1 by weight in VirtualService.

Circuit breaking (outlierDetection in DestinationRule): Eject unhealthy endpoints after consecutive errors.

Fault injection (for chaos testing): Inject HTTP delays or errors in VirtualService.

mTLS: PeerAuthentication resource enables STRICT or PERMISSIVE mTLS mode.

Q24: What is the difference between VPA and HPA? Advanced

HPA (Horizontal Pod Autoscaler): Adds/removes pod replicas based on metrics. Scale out/in. Works well for stateless applications. Does NOT change resource requests/limits.

VPA (Vertical Pod Autoscaler): Adjusts CPU/memory requests and limits for existing pods. Scale up/down. Must restart pods to apply (in-place resize alpha in K8s 1.27). Better for stateful apps or apps that don't scale horizontally.

Can you use both? Not recommended to use both on CPU/memory simultaneously — they conflict. You can use VPA for memory and HPA for CPU (advanced config), or use KEDA for custom metrics with HPA.

Q25: How do you secure a Kubernetes cluster? Very Advanced

4 C's of Cloud Native Security: Cloud, Cluster, Container, Code

Cluster level:

  • Enable RBAC (always on in modern K8s)
  • Enable etcd encryption at rest
  • Use Pod Security Admission (enforce restricted profile)
  • Network policies — default deny, whitelist needed traffic
  • Keep K8s updated (patch CVEs)
  • Audit logging enabled

Workload level:

  • Non-root containers, read-only filesystem
  • Drop all capabilities
  • No privileged containers
  • Use ServiceAccounts with minimal permissions
  • Secrets encrypted / External Secrets
  • Image scanning in CI/CD (Trivy, Grype)

Supply chain:

  • Admission controllers: OPA Gatekeeper, Kyverno
  • Image signing: Cosign + policy enforcement
  • SBOM generation
