Caching: Patterns, Eviction, Redis, CDN & Browser Caching

Why Cache?

Caching is the practice of storing computed or fetched results closer to the consumer so future requests can be served faster without repeating expensive work.

BenefitDetail
Latency ReductionMemory access: ~100 ns. SSD read: ~100 µs. Network DB query: ~1-10 ms. Caching eliminates the expensive path.
Throughput IncreaseOne DB server can serve 1K TPS; a Redis cluster can serve 1M+ ops/sec. Cache absorbs the read amplification.
DB Load ReductionPopular queries (hot keys) hitting cache instead of DB allows DB to handle complex writes and analytics.
ResilienceCache can serve stale data during DB downtime if configured with stale-while-revalidate.

Cache Hit Ratio

Hit Ratio = Cache Hits / (Cache Hits + Cache Misses)

A hit ratio of 80% means 80% of requests are served from cache. Aim for >90% for effective caching. Monitor with Redis INFO stats: keyspace_hits / (keyspace_hits + keyspace_misses).

Cache-Aside (Lazy Loading)

Application code manages the cache explicitly. Cache is populated on a miss. Most widely used pattern.

sequenceDiagram participant App participant Cache as Cache (Redis) participant DB App->>Cache: GET user:42 alt Cache Hit Cache-->>App: return user data else Cache Miss Cache-->>App: nil App->>DB: SELECT * FROM users WHERE id=42 DB-->>App: user data App->>Cache: SET user:42 {data} EX 300 App-->>App: return user data end 
async function getUser(userId) {
  const cacheKey = `user:${userId}`;
  // Try cache first
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  // Cache miss: fetch from DB
  const user = await db.query('SELECT * FROM users WHERE id = ?', [userId]);
  if (user) {
    await redis.setex(cacheKey, 300, JSON.stringify(user)); // 5 min TTL
  }
  return user;
}

// Invalidation: delete on update
async function updateUser(userId, data) {
  await db.query('UPDATE users SET ? WHERE id = ?', [data, userId]);
  await redis.del(`user:${userId}`); // invalidate
}
Cache-Aside
ProsCache only what's requested; resilient to cache failure (app reads DB); flexible TTL per object; works with any cache store
ConsInitial cache miss overhead; stale data possible if invalidation is missed; cache stampede risk on cold start

Write-Through

Every write goes through the cache — data is written to cache and database synchronously before returning to the client.

sequenceDiagram participant App participant Cache participant DB App->>Cache: WRITE user:42 data Cache->>DB: INSERT/UPDATE user (synchronous) DB-->>Cache: OK Cache-->>App: OK Note over Cache,DB: Cache and DB always in sync
Write-Through
ProsCache and DB always consistent; no stale reads after writes; no invalidation logic needed
ConsWrite latency = cache + DB latency; cache may fill with infrequently-read data (write-heavy workloads waste cache space); cache failure on write = write failure
Best ForRead-heavy data that is always written then read shortly after (user sessions, product details post-update)

Write-Behind (Write-Back)

Write goes to cache immediately; cache asynchronously flushes to the database later (after a delay or in batches).

sequenceDiagram participant App participant Cache participant Queue as Async Queue participant DB App->>Cache: WRITE user:42 data Cache-->>App: OK (instant) Cache->>Queue: queue DB write Queue->>DB: batch INSERT/UPDATE (delayed) DB-->>Queue: OK
Write-Behind
ProsLowest write latency; DB writes can be batched (reduces I/O); absorbs write spikes
ConsData loss risk if cache fails before flush; complex to implement correctly; eventual consistency between cache and DB; dirty tracking required
Best ForHigh-frequency writes where some data loss is tolerable (view counts, analytics counters, gaming scores)

Write-Around

Writes bypass the cache and go directly to the database. Cache is only populated on reads (cache-aside on read).

Write-Around
ProsCache not polluted with write-once / rarely-read data; prevents cache churn
ConsFirst read after a write always misses cache; higher read latency for recently-written data
Best ForWrite-once read-never or read-rarely data (logs, audit records, large files)

Read-Through

Cache sits in front of DB. Application always reads from cache. On a miss, the cache itself (not the application) fetches from DB, populates itself, and returns. Application code is simpler.

sequenceDiagram participant App participant Cache as Cache Layer (provider) participant DB App->>Cache: GET user:42 alt Hit Cache-->>App: data else Miss Cache->>DB: SELECT ... DB-->>Cache: data Cache->>Cache: store in cache Cache-->>App: data end
Read-Through
ProsApplication code simplified (no cache population logic); works well with write-through (cache always warm)
ConsFirst request always slow (cold cache); tightly couples cache to data model; harder to customize per-entity TTL
Best ForManaged caches (AWS ElastiCache DAX for DynamoDB, NCache, Ehcache with CacheLoader)

Eviction Policies — LRU

LRU (Least Recently Used) evicts the item that has not been accessed for the longest time. Implementation: doubly linked list (order of use) + hashmap (O(1) lookup).

// LRU Cache implementation from scratch in JavaScript
// O(1) get and put using Map (insertion-ordered) as LRU queue
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.cache = new Map(); // key → value, maintains insertion order
  }

  get(key) {
    if (!this.cache.has(key)) return -1;
    // Move to end (most recently used)
    const value = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, value);
    return value;
  }

  put(key, value) {
    if (this.cache.has(key)) {
      this.cache.delete(key); // remove to re-insert at end
    } else if (this.cache.size >= this.capacity) {
      // Evict LRU: first key in Map (least recently used)
      const lruKey = this.cache.keys().next().value;
      this.cache.delete(lruKey);
    }
    this.cache.set(key, value);
  }
}

// Usage
const cache = new LRUCache(3);
cache.put(1, 'a'); // {1:'a'}
cache.put(2, 'b'); // {1:'a', 2:'b'}
cache.put(3, 'c'); // {1:'a', 2:'b', 3:'c'}
cache.get(1);      // returns 'a', moves 1 to end: {2:'b', 3:'c', 1:'a'}
cache.put(4, 'd'); // evicts 2 (LRU): {3:'c', 1:'a', 4:'d'}

Doubly Linked List + HashMap (Classic Implementation)

class Node {
  constructor(key, val) { this.key = key; this.val = val; this.prev = this.next = null; }
}

class LRUCacheLinked {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();
    // Sentinel head (LRU end) and tail (MRU end)
    this.head = new Node(0, 0);
    this.tail = new Node(0, 0);
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  _addToTail(node) {
    node.prev = this.tail.prev;
    node.next = this.tail;
    this.tail.prev.next = node;
    this.tail.prev = node;
  }

  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key);
    this._remove(node);
    this._addToTail(node);
    return node.val;
  }

  put(key, val) {
    if (this.map.has(key)) this._remove(this.map.get(key));
    else if (this.map.size >= this.capacity) {
      const lru = this.head.next;
      this._remove(lru);
      this.map.delete(lru.key);
    }
    const node = new Node(key, val);
    this._addToTail(node);
    this.map.set(key, node);
  }
}

Eviction Policies — LFU

LFU (Least Frequently Used) evicts the item with the lowest access frequency. Ties broken by LRU among same frequency. Requires tracking a frequency counter per key.

class LFUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.minFreq = 0;
    this.keyMap = new Map();   // key → {value, freq}
    this.freqMap = new Map();  // freq → LinkedSet of keys (insertion order = LRU within freq)
  }

  _updateFreq(key) {
    const { value, freq } = this.keyMap.get(key);
    this.keyMap.set(key, { value, freq: freq + 1 });
    this.freqMap.get(freq).delete(key);
    if (this.freqMap.get(freq).size === 0) {
      this.freqMap.delete(freq);
      if (this.minFreq === freq) this.minFreq++;
    }
    if (!this.freqMap.has(freq + 1)) this.freqMap.set(freq + 1, new Set());
    this.freqMap.get(freq + 1).add(key);
  }

  get(key) {
    if (!this.keyMap.has(key)) return -1;
    this._updateFreq(key);
    return this.keyMap.get(key).value;
  }

  put(key, value) {
    if (this.capacity === 0) return;
    if (this.keyMap.has(key)) {
      this.keyMap.get(key).value = value;
      this._updateFreq(key);
      return;
    }
    if (this.keyMap.size >= this.capacity) {
      // Evict LFU (and LRU among same frequency)
      const minFreqKeys = this.freqMap.get(this.minFreq);
      const evictKey = minFreqKeys.values().next().value;
      minFreqKeys.delete(evictKey);
      if (minFreqKeys.size === 0) this.freqMap.delete(this.minFreq);
      this.keyMap.delete(evictKey);
    }
    this.keyMap.set(key, { value, freq: 1 });
    if (!this.freqMap.has(1)) this.freqMap.set(1, new Set());
    this.freqMap.get(1).add(key);
    this.minFreq = 1;
  }
}

FIFOOldest entry (by insertion time)Simple queue-like access patternsNo recency/frequency tracking; misses recently used but old items
LIFOMost recently insertedStack-like, rarely used for cachesCounter-intuitive for caching; rarely used
MRU (Most Recently Used)Most recently accessed itemCyclic access patterns where last-used is least likely to be needed againGood for scan resistance (e.g., DB buffer pool when doing full table scans)
ARC (Adaptive Replacement Cache)Dynamically balances between LRU and LFU ghostsGeneral-purpose high-performance cachingMaintains 4 lists: T1 (recent once), T2 (recent twice+), B1 (ghost of T1), B2 (ghost of T2). Adapts to workload. Used in ZFS, Solaris.

Cache Stampede (Thundering Herd)

Occurs when a popular cached item expires and many concurrent requests all miss cache simultaneously, all hitting the database at once, potentially overwhelming it.

Solutions

1. Mutex / Locking

// Only one request refreshes cache; others wait
async function getWithMutex(key) {
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const lockKey = `lock:${key}`;
  const locked = await redis.set(lockKey, '1', 'NX', 'EX', 5); // 5s lock
  if (locked) {
    try {
      const data = await db.fetchData(key);
      await redis.setex(key, 300, JSON.stringify(data));
      return data;
    } finally {
      await redis.del(lockKey);
    }
  } else {
    // Wait and retry (another process is refreshing)
    await sleep(100);
    return getWithMutex(key);
  }
}

2. Probabilistic Early Expiration (XFetch)

// Probabilistically refresh BEFORE expiry to avoid simultaneous expiry
async function getWithEarlyExpiry(key, beta = 1) {
  const data = await redis.get(key);
  if (!data) return refreshCache(key);

  const { value, delta, expiry } = JSON.parse(data);
  const now = Date.now() / 1000;
  // Recompute if random threshold crossed before TTL expires
  if (now - delta * beta * Math.log(Math.random()) >= expiry) {
    refreshCacheAsync(key); // background refresh
  }
  return value;
}

3. Background Refresh (Stale-While-Revalidate)

Return stale value immediately; asynchronously kick off a background job to refresh the cache. Client gets fast response; cache freshness converges.

Cache Penetration

Requests for keys that never exist in cache or DB (e.g., querying non-existent user IDs) bypass cache entirely and hammer the database on every request.

Solutions

1. Cache Null Values

const result = await db.findById(id);
if (result === null) {
  // Cache the absence with short TTL
  await redis.setex(`user:${id}`, 60, '__NULL__');
  return null;
}
await redis.setex(`user:${id}`, 300, JSON.stringify(result));

2. Bloom Filter

// Add all valid IDs to bloom filter on startup
// Before any DB query, check bloom filter
import { BloomFilter } from 'bloom-filters';
const bloomFilter = BloomFilter.create(1000000, 0.01); // 1M items, 1% false positive

function getUser(id) {
  if (!bloomFilter.has(String(id))) {
    return null; // Definitely doesn't exist — skip DB entirely
  }
  return db.findById(id); // May exist (bloom filter says yes, 1% may be false positive)
}

// Rebuild bloom filter periodically from DB

Cache Avalanche

Large numbers of cache keys expire simultaneously, causing a sudden surge of database load — the "avalanche" of cache misses all hitting the DB at the same time.

Solutions

  • TTL Jitter: Add random spread to TTLs: TTL = baseTTL + random(0, baseTTL * 0.1). Keys expire gradually over a time window.
  • Circuit Breaker: Monitor DB error rate; if threshold exceeded, fail fast and return cached/default data rather than amplifying DB load.
  • Cache Warm-up: Pre-populate cache before traffic hits (e.g., after deployment, after Redis restart). Load data from DB in background before going live.
  • Multi-level Caching: L1 (local in-memory Caffeine) + L2 (Redis). Even if Redis has a gap, L1 absorbs some traffic.
  • Distributed Lock on Repopulation: For each key, only one node refreshes it (mutex pattern).
// TTL Jitter
function setWithJitter(key, value, baseTtl) {
  const jitter = Math.floor(Math.random() * baseTtl * 0.1);
  return redis.setex(key, baseTtl + jitter, value);
}

Cache Pollution

Cache is filled with items that are accessed once (or rarely) and never evicted quickly enough, crowding out frequently-accessed items. Common with LRU when scan operations (full table reads, batch jobs) evict hot data.

Solutions

  • Use MRU eviction for sequential scan access patterns (evicts the last-scanned item).
  • Use TinyLFU/W-TinyLFU — frequency tracking prevents single-access items from displacing frequently-used ones.
  • Use segmented caches (protected + probationary segments like SLRU) — new items start in probationary; only promoted to protected after second access.
  • Use explicit bypass hints: database buffer pool has SQL_NO_CACHE; application can skip caching for known bulk operations.

Redis Clustering & Sentinel

Redis Cluster (Horizontal Sharding)

Automatically shards data across multiple master nodes. Uses 16,384 hash slots. Key's slot = CRC16(key) % 16384. Each master owns a range of slots (e.g., 0-5460, 5461-10922, 10923-16383 for 3 masters). Each master has replica nodes.

Redis Sentinel (HA for Standalone Redis)

Sentinel monitors Redis master and replicas. On master failure: Sentinel cluster elects a new master via majority vote and promotes a replica. Requires 3+ Sentinel processes for fault tolerance.

# sentinel.conf
sentinel monitor mymaster 127.0.0.1 6379 2  # 2 sentinels must agree for failover
sentinel down-after-milliseconds mymaster 30000
sentinel failover-timeout mymaster 180000
sentinel parallel-syncs mymaster 1  # replicas syncing in parallel during failover

Complete LRU Cache Implementation (JavaScript)

// Production-ready LRU with TTL support
class LRUCacheWithTTL {
  constructor(capacity) {
    this.capacity = capacity;
    this.cache = new Map(); // key → {value, expiry}
  }

  _isExpired(entry) {
    return entry.expiry !== null && Date.now() > entry.expiry;
  }

  get(key) {
    if (!this.cache.has(key)) return undefined;
    const entry = this.cache.get(key);
    if (this._isExpired(entry)) {
      this.cache.delete(key);
      return undefined;
    }
    // Move to end (MRU position)
    this.cache.delete(key);
    this.cache.set(key, entry);
    return entry.value;
  }

  set(key, value, ttlMs = null) {
    if (this.cache.has(key)) this.cache.delete(key);
    else if (this.cache.size >= this.capacity) {
      // Evict: find first non-expired LRU item
      for (const [k, v] of this.cache) {
        if (this._isExpired(v)) {
          this.cache.delete(k);
          break;
        }
      }
      // If no expired items found, evict true LRU
      if (this.cache.size >= this.capacity) {
        this.cache.delete(this.cache.keys().next().value);
      }
    }
    this.cache.set(key, {
      value,
      expiry: ttlMs ? Date.now() + ttlMs : null
    });
  }

  delete(key) { return this.cache.delete(key); }
  clear()     { this.cache.clear(); }
  get size()  { return this.cache.size; }
  get stats() {
    let expired = 0;
    for (const v of this.cache.values()) {
      if (this._isExpired(v)) expired++;
    }
    return { size: this.cache.size, expired };
  }
}

// Usage
const cache = new LRUCacheWithTTL(1000);
cache.set('user:1', { name: 'Alice' }, 5 * 60 * 1000); // 5 min TTL
const user = cache.get('user:1');  // { name: 'Alice' }

Interview Q&As — 20+ Questions

Q1. What is the difference between cache-aside and read-through patterns? Easy

In cache-aside (lazy loading), the application code is responsible for managing the cache: check cache first, on miss fetch from DB and populate cache. The application controls what gets cached and when. In read-through, the cache layer itself is responsible: on a miss, the cache fetches from the DB automatically and returns the data. Application code always talks only to the cache. Cache-aside is more flexible and explicit; read-through is simpler for the application but requires a caching middleware that understands the data model. Cache-aside fails gracefully if cache goes down (app falls back to DB); read-through may fail if the cache layer is unavailable.

Q2. What is a cache stampede and how do you prevent it? Intermediate

A cache stampede (thundering herd) occurs when a hot cache key expires and many concurrent requests simultaneously miss cache and all query the database simultaneously, potentially overloading it. Prevention strategies: (1) Mutex/Distributed lock: Only one process refreshes; others wait. Use Redis SET with NX+EX for an atomic distributed lock. (2) Probabilistic early expiration (XFetch): Probabilistically refresh the key before it expires, with probability increasing as TTL decreases. (3) Background refresh: Serve stale value instantly while an async job refreshes the cache. (4) Double-checked locking: After acquiring lock, re-check cache in case another process already refreshed it.

Q3. Explain the difference between cache penetration, avalanche, and stampede. Intermediate
  • Cache Penetration: Requests for keys that don't exist in cache OR database (invalid IDs). Cache is bypassed every time → DB hammered. Fix: Bloom filter to reject impossible keys; cache null values with short TTL.
  • Cache Avalanche: Many keys expire at the same time → sudden surge of DB load. Fix: TTL jitter (random spread), cache warm-up, circuit breaker.
  • Cache Stampede: One popular key expires → many concurrent requests all miss and hit DB simultaneously. Fix: mutex/lock, probabilistic early refresh, stale-while-revalidate.
Q4. What Redis data structure would you use for a leaderboard? Why? Easy

Redis Sorted Set (ZSET) is perfect for leaderboards. It stores member-score pairs and keeps members sorted by score. Operations: ZADD leaderboard 1500 "player1" to update a score; ZREVRANGE leaderboard 0 9 WITHSCORES for the top 10; ZREVRANK leaderboard "player1" for a player's rank — all O(log N). The score can be a float, and ZINCRBY atomically increments scores. For global leaderboards with millions of players, combine with periodic snapshots or use approximate ranking.

Q5. How does Redis achieve atomic operations if it's single-threaded? Intermediate

Redis processes commands in a single-threaded event loop. Since commands execute serially, every individual command is atomic by design — no two commands interleave. For multi-command atomicity, use: (1) MULTI/EXEC: queue commands, execute them all as a batch without interleaving (no rollback on individual command failure though). (2) Lua scripts (EVAL): script runs atomically — Redis blocks other commands while Lua executes; scripts are the preferred way for complex atomic operations. (3) Atomic single commands: INCR, GETSET, SETNX — inherently atomic since single command. Note: Redis 6+ added I/O threads for network, but command processing remains single-threaded.

Q6. When would you choose LFU over LRU eviction in Redis? Intermediate

LFU (allkeys-lfu) is better when your access pattern has a stable set of "hot" keys that are accessed very frequently and you need them to survive even brief periods of inactivity. For example: configuration data, permission tables, category trees — accessed thousands of times per second, but perhaps not in the last 10 seconds. LRU would evict a hot key if it happens to not be touched recently due to a traffic lull. LFU tracks long-term frequency and resists eviction of genuinely hot keys. Redis implements LFU with an 8-bit logarithmic counter per key and halves all counts every lfu-decay-time minutes to account for frequency changes over time.

Q7. Explain the difference between RDB and AOF persistence. Which would you choose? Intermediate

RDB creates point-in-time snapshots of the dataset (dump.rdb). Fast restart, compact file, minimal I/O during operation. Downside: data since last snapshot is lost on crash. AOF appends every write command to a log file; with appendfsync=everysec, you lose at most 1 second of data. Slower restart (must replay all commands); larger file. Hybrid (RDB+AOF): AOF file begins with an RDB snapshot, then appends incremental commands. Best of both worlds — recommended for production. Recommendation: use hybrid for most production use cases. Use RDB-only if a few minutes of data loss is acceptable and fast restart is critical. Use AOF-only if you need minute-level durability guarantees without the hybrid overhead.

Q8. What is a Bloom filter and how does it solve cache penetration? Intermediate

A Bloom filter is a space-efficient probabilistic data structure that answers "is this element definitely NOT in the set, or possibly in the set?" There are no false negatives — if the filter says "not present," it's definitely not present. There can be false positives (says "present" when it's not). For cache penetration: load all valid IDs into the Bloom filter at startup. Before hitting cache or DB for any ID, check the Bloom filter — if "not present," return null immediately (no DB hit). Only proceed to cache/DB if the filter says "possibly present." A 1% false positive rate requires ~10 bits per element. Redis has the RedisBloom module; in application code, use libraries like bloom-filters (JS) or Guava BloomFilter (Java).

Q9. How does Redis Cluster handle a key that belongs to a different node? Advanced

When a client sends a command for a key to the wrong node, that node calculates the key's hash slot and, if it doesn't own that slot, returns a MOVED error: MOVED 7638 127.0.0.1:7002. The client redirects the request to the correct node. Smart Redis clients (JedisCluster, StackExchange.Redis) maintain a slot-to-node mapping and route directly, only redirecting on MOVED (which means the cluster topology changed). During a slot migration (resharding), the source node returns ASK (temporary redirect) instead of MOVED — client sends ASKING + the command to the destination node for that single request only (doesn't update its routing table).

Q10. What is the write-behind pattern and what are its risks? Advanced

Write-behind (write-back) writes data to cache immediately and flushes to DB asynchronously. Risk: if the cache node crashes before the flush, the unflushed data is permanently lost — the DB has stale/missing data. Other risks: (1) ordering violations — if key A is written then deleted, async processing out of order could resurrect A in DB; requires careful sequencing. (2) DB schema changes between cache write and flush. (3) Dirty tracking overhead. Mitigation: use an async queue with retry/dead-letter; use write-ahead log semantics on the cache; consider Redis Streams as the async buffer. Best for counters, view counts, game scores — where some loss is acceptable and performance is critical.

Q11. Explain the Cache-Control: no-cache header. Does it mean "don't cache"? Easy

Counterintuitively, no-cache does NOT mean "never cache." It means "cache it, but always revalidate with the server before using the cached version." The browser stores the response but on every request sends a conditional request (If-None-Match/If-Modified-Since) to the server. If unchanged, server returns 304 Not Modified (no body) and the browser uses its cached copy. This saves bandwidth but not round-trips. If you truly want "never store this," use no-store. Use no-cache for dynamic pages that must always be fresh but where the content often hasn't changed (saves bandwidth on 304 responses).

Q12. How would you implement a rate limiter using Redis? Intermediate 
-- Sliding window rate limiter using sorted set
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])  -- in milliseconds
local now = tonumber(ARGV[3])     -- current timestamp in ms

-- Remove entries outside the window
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- Count requests in window
local count = redis.call('ZCARD', key)
if count >= limit then
  return 0  -- rate limited
end
-- Add current request
redis.call('ZADD', key, now, now .. math.random())
redis.call('PEXPIRE', key, window)
return 1  -- allowed

Fixed window: simpler — INCR key (key = "ratelimit:userId:minuteTimestamp"), EXPIRE key 60. Problem: burst at window boundary (2x limit in 2 seconds). Sliding window (sorted set above): more accurate but uses more memory. Token bucket: complex but smoothest. For distributed environments, use Lua script for atomicity.

Q13. What is the difference between WATCH/MULTI/EXEC and Lua scripting in Redis? Advanced

WATCH/MULTI/EXEC (Optimistic Locking): Watch a key; if it changes before EXEC, the transaction aborts (EXEC returns nil). Application must retry. Good for low-contention scenarios. Works across multiple client connections. Cannot have conditional logic inside the transaction body.

Lua scripts: Execute atomically on the server (no interleaving). Can have conditional logic (if/else inside script). No optimistic retry needed. Scripts are cached by SHA hash (EVALSHA). Better for complex atomic operations. Cannot block on slow DB lookups inside Lua. Time-limited to prevent blocking Redis indefinitely.

Choose WATCH+MULTI for simple CAS (compare-and-swap); choose Lua for complex atomic server-side logic.

Q14. How does CDN cache invalidation work? Intermediate

CDN cache invalidation removes or updates stale content from edge nodes. Methods: (1) TTL expiry: Wait for Cache-Control max-age/s-maxage to expire — simplest but slow to propagate. (2) Cache purge API: Most CDNs (Cloudflare, Fastly, AWS CloudFront) offer an API to instantly purge by URL, path pattern, or cache tags. (3) Versioned URLs: Change the URL when content changes (append content hash to filename: app.abc123.js) — browser/CDN treat it as a new resource; no purge needed. (4) Surrogate keys/Cache tags: Tag responses with logical keys (e.g., product-id-42); purge all cached responses for that tag with one API call. Best practice: use versioned URLs for static assets (immutable) + purge API for dynamic content changes.

Q15. What is TinyLFU and why is it better than traditional LRU for application caches? Advanced

TinyLFU (used by Caffeine in Java) uses a Count-Min Sketch (a probabilistic frequency counter using 4-bit counters + multiple hash functions) to estimate access frequency with minimal memory overhead. W-TinyLFU adds a Window Cache: 1% of capacity is a small window LRU that acts as a probationary area for recently new items (recency buffer). Remaining 99% is a main SLRU (Segmented LRU with protected + probationary segments). When the window is full, the window's LRU candidate is compared against the main cache's LRU victim via frequency. The item with higher frequency wins a spot in main cache. This combines recency (new items get a chance via the window) with frequency (main cache keeps genuinely hot items). Result: 5-35% better hit rate than pure LRU in real-world access traces (Zipf/power-law distributions).

Q16. How would you design a session store for 10 million concurrent users? Advanced

Use Redis Cluster for horizontal scaling. Key design: session:{sessionId} → Hash with user_id, roles, preferences, expiry. TTL: 24h or sliding (EXPIRE reset on access). Cluster: 3+ masters with replicas, each owning ~5461 hash slots — auto-shards sessions by sessionId hash. Capacity math: 10M sessions × ~500 bytes/session = 5 GB data; with 3 replicas = 15 GB total. Use volatile-lru eviction; active sessions will be accessed and refreshed regularly. For session affinity (if needed), use sticky routing based on user_id. Consider Redis 7+ with ACL security and TLS. Also: SCAN with pattern for admin operations (never KEYS * in production). For cross-region: Redis Enterprise Active-Active geo-distribution.

Q17. Explain the ARC (Adaptive Replacement Cache) algorithm. Very Advanced

ARC maintains four lists: T1 (pages seen once recently), T2 (pages seen at least twice recently), B1 (ghost entries: pages evicted from T1 — just keys, no data), B2 (ghost entries: pages evicted from T2). Total T1+T2 = cache capacity. When a page is requested: hit in T1 → move to T2 (promote to frequent); hit in T2 → keep at head; hit in B1 (ghost) → increase c1 target (favor recency more); hit in B2 (ghost) → increase c2 target (favor frequency more); miss → evict from T1 or T2 based on current balance. ARC adapts its balance between recency and frequency based on observed workload patterns — no manual tuning needed. Used in ZFS filesystem cache (ARC was patented by IBM; Solaris/ZFS licensed it).

Q18. When would you use Redis Streams instead of Pub/Sub? Intermediate

Use Streams when: (1) consumers can go offline and must not miss messages (pub/sub drops messages for disconnected subscribers); (2) you need exactly-once processing guarantees (XACK + PEL — pending entries list); (3) you need message history/replay (debug, new consumer catching up); (4) you have multiple competing consumers that should each process a distinct subset (consumer groups); (5) you need backpressure monitoring (check stream length). Use Pub/Sub when: (1) fire-and-forget is acceptable; (2) you need true fan-out (all subscribers get every message, not just one consumer group member); (3) extremely low latency matters (pub/sub has lower overhead); (4) messages are ephemeral notifications (WebSocket push, chat rooms).

Q19. What is cache pollution and how do you detect it? Intermediate

Cache pollution occurs when cache fills with low-value items (accessed once or rarely) that displace frequently-accessed hot items, lowering the hit rate. Common causes: (1) Full table scans / batch jobs evicting hot keys via LRU; (2) Long-tail requests (rarely repeated unique queries); (3) Speculative pre-loading of data that's never accessed. Detection: monitor hit rate over time — sudden drop indicates pollution. Check Redis with redis-cli --hotkeys and redis-cli --bigkeys. Use OBJECT FREQ keyname with LFU policy to see access frequency. Remedies: switch to LFU/TinyLFU policy; use cache bypass for bulk operations; implement separate cache tiers (hot vs warm); use SCAN + TTL inspection to find orphaned keys.

Q20. What is the Vary header and why is it critical for shared caches? Intermediate

The Vary header tells CDNs and proxies that the response content varies based on specified request headers. Example: Vary: Accept-Encoding means the server may return different content for gzip vs brotli vs uncompressed requests — CDN must cache a separate copy per encoding variant. Vary: Accept-Language caches separate copies per locale. Vary: Authorization effectively disables CDN caching (each user has different auth header). Pitfall: Vary: User-Agent creates thousands of cache variants (one per browser string) — cache efficiency collapses. Solution: normalize at origin (detect mobile/desktop and use a single clean variant header instead) or use Vary: Sec-CH-UA-Mobile (client hints) which has fewer variants.

Q21. Describe how you would implement a distributed cache invalidation system. Very Advanced

Challenge: when data changes in DB, invalidate cached copies across all nodes consistently. Approaches: (1) Event-driven invalidation: On DB write, publish an invalidation event to Redis Pub/Sub or Kafka; all cache nodes subscribe and delete their local copies. Risk: events may be lost. (2) Cache tags: Tag cached items with logical identifiers (product:42); on update, send a purge for that tag to all cache layers. (3) CDC (Change Data Capture) with Debezium: Capture DB changelog (MySQL binlog / Postgres WAL) and stream invalidation events to Kafka → cache invalidation consumers. Guarantees no events are missed. (4) Version-based invalidation: Store version number in DB; cache key includes version; on update, increment version → old keys become unreachable and expire via TTL. Avoid distributed cache invalidation entirely by using immutable versioned cache keys for static content.

Q22. How does ETag caching work and when does a 304 response save bandwidth? Easy

ETags (Entity Tags) are opaque identifiers (usually hash of content) that the server attaches to responses. The browser stores the ETag alongside the cached response. On the next request (after TTL expires), the browser sends If-None-Match: "abc123". The server checks if the current content hash matches — if yes, returns 304 Not Modified with no body (~200 bytes) instead of the full response. This saves bandwidth for the body but not the round-trip. A 304 is useful when: response body is large and content changes rarely; network bandwidth is constrained. It's NOT useful if the content always changes (generates new ETag every time) — you pay for a round-trip plus get the full body anyway. Combine with proper max-age: browser only revalidates after TTL expires, so most requests don't even need the 304 round-trip.
