Creational Patterns

Creational

1. Singleton

Ensures a class has only one instance and provides a global access point to it.

When to use: Configuration managers, connection pools, logging services — anything where exactly one object must coordinate actions across the system.
TypeScript Example 
class DatabaseConnection {
  private static instance: DatabaseConnection;
  private constructor(private url: string) {}

  static getInstance(): DatabaseConnection {
    if (!DatabaseConnection.instance) {
      DatabaseConnection.instance = new DatabaseConnection('postgres://localhost/db');
    }
    return DatabaseConnection.instance;
  }

  query(sql: string): string {
    return `[${this.url}] Running: ${sql}`;
  }
}

const db1 = DatabaseConnection.getInstance();
const db2 = DatabaseConnection.getInstance();
console.log(db1 === db2); // true

2. Factory Method

Defines an interface for creating an object but lets subclasses decide which class to instantiate.

When to use: When the exact type of object to create is determined at runtime or when subclasses should control instantiation logic.
TypeScript Example 
interface Button { render(): void; }

class WindowsButton implements Button {
  render() { console.log('Render Windows button'); }
}
class MacButton implements Button {
  render() { console.log('Render Mac button'); }
}

abstract class Dialog {
  abstract createButton(): Button;
  open() { this.createButton().render(); }
}

class WindowsDialog extends Dialog {
  createButton(): Button { return new WindowsButton(); }
}
class MacDialog extends Dialog {
  createButton(): Button { return new MacButton(); }
}

const dialog: Dialog = new MacDialog();
dialog.open(); // Render Mac button

3. Abstract Factory

Provides an interface for creating families of related objects without specifying concrete classes.

When to use: When the system must be independent of how its products are created and when you need to enforce product family consistency (e.g. UI themes).
TypeScript Example 
interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}
interface Checkbox { check(): void; }

class DarkFactory implements UIFactory {
  createButton(): Button { return { render: () => console.log('Dark Button') }; }
  createCheckbox(): Checkbox { return { check: () => console.log('Dark Checkbox') }; }
}
class LightFactory implements UIFactory {
  createButton(): Button { return { render: () => console.log('Light Button') }; }
  createCheckbox(): Checkbox { return { check: () => console.log('Light Checkbox') }; }
}

function buildUI(factory: UIFactory) {
  factory.createButton().render();
  factory.createCheckbox().check();
}
buildUI(new DarkFactory());

4. Builder

Separates the construction of a complex object from its representation so the same process can create different representations.

When to use: When constructing complex objects step-by-step, especially when many optional parameters would lead to a telescoping constructor.
TypeScript Example 
class QueryBuilder {
  private table = '';
  private conditions: string[] = [];
  private limitVal = 100;

  from(table: string) { this.table = table; return this; }
  where(cond: string) { this.conditions.push(cond); return this; }
  limit(n: number) { this.limitVal = n; return this; }

  build(): string {
    const where = this.conditions.length
      ? ` WHERE ${this.conditions.join(' AND ')}` : '';
    return `SELECT * FROM ${this.table}${where} LIMIT ${this.limitVal}`;
  }
}

const sql = new QueryBuilder()
  .from('users')
  .where('age > 18')
  .where('active = true')
  .limit(50)
  .build();
console.log(sql);

5. Prototype

Creates new objects by copying an existing object (the prototype), avoiding the cost of re-initialization.

When to use: When object creation is expensive and a similar object already exists, or when the class to instantiate is specified at run-time.
TypeScript Example 
interface Cloneable { clone(): T; }

class Shape implements Cloneable {
  constructor(
    public type: string,
    public color: string,
    public x: number,
    public y: number
  ) {}
  clone(): Shape {
    return new Shape(this.type, this.color, this.x, this.y);
  }
}

const original = new Shape('circle', 'red', 0, 0);
const copy = original.clone();
copy.color = 'blue';
console.log(original.color); // red
console.log(copy.color);     // blue

Structural Patterns

Structural

6. Adapter

Converts the interface of a class into another interface clients expect, enabling incompatible interfaces to work together.

When to use: Integrating a third-party library whose interface doesn't match yours, or when reusing existing code with an incompatible interface.
TypeScript Example 
// Legacy logger with old interface
class LegacyLogger {
  logMessage(severity: string, msg: string) {
    console.log(`[${severity.toUpperCase()}] ${msg}`);
  }
}

// New interface our code expects
interface Logger {
  info(msg: string): void;
  error(msg: string): void;
}

class LoggerAdapter implements Logger {
  constructor(private legacy: LegacyLogger) {}
  info(msg: string) { this.legacy.logMessage('info', msg); }
  error(msg: string) { this.legacy.logMessage('error', msg); }
}

const logger: Logger = new LoggerAdapter(new LegacyLogger());
logger.info('Service started');
logger.error('Connection refused');

7. Bridge

Decouples an abstraction from its implementation so the two can vary independently.

When to use: When you want to avoid a permanent binding between abstraction and implementation, or when both should be extensible via subclassing.
TypeScript Example 
interface Renderer { renderShape(shape: string): void; }

class SVGRenderer implements Renderer {
  renderShape(s: string) { console.log(`SVG: <${s} />`); }
}
class CanvasRenderer implements Renderer {
  renderShape(s: string) { console.log(`Canvas: draw(${s})`); }
}

abstract class Shape2 {
  constructor(protected renderer: Renderer) {}
  abstract draw(): void;
}
class Circle2 extends Shape2 {
  draw() { this.renderer.renderShape('circle'); }
}
class Square extends Shape2 {
  draw() { this.renderer.renderShape('rect'); }
}

new Circle2(new SVGRenderer()).draw();   // SVG: 
new Square(new CanvasRenderer()).draw(); // Canvas: draw(rect)

8. Composite

Composes objects into tree structures to represent part-whole hierarchies, letting clients treat individual objects and compositions uniformly.

When to use: File systems, UI component trees, org charts — any scenario with nested structures that must be treated uniformly.
TypeScript Example 
interface FileSystemNode {
  name: string;
  size(): number;
}

class File implements FileSystemNode {
  constructor(public name: string, private bytes: number) {}
  size() { return this.bytes; }
}

class Directory implements FileSystemNode {
  private children: FileSystemNode[] = [];
  constructor(public name: string) {}
  add(node: FileSystemNode) { this.children.push(node); }
  size() { return this.children.reduce((s, c) => s + c.size(), 0); }
}

const root = new Directory('root');
root.add(new File('readme.txt', 1024));
const src = new Directory('src');
src.add(new File('index.ts', 4096));
root.add(src);
console.log(root.size()); // 5120

9. Decorator

Attaches additional responsibilities to an object dynamically, providing a flexible alternative to subclassing for extending functionality.

When to use: Adding features like logging, caching, encryption, or compression to objects without modifying their class.
TypeScript Example 
interface TextProcessor { process(text: string): string; }

class PlainText implements TextProcessor {
  process(text: string) { return text; }
}

class UpperCaseDecorator implements TextProcessor {
  constructor(private wrapped: TextProcessor) {}
  process(text: string) { return this.wrapped.process(text).toUpperCase(); }
}
class TrimDecorator implements TextProcessor {
  constructor(private wrapped: TextProcessor) {}
  process(text: string) { return this.wrapped.process(text).trim(); }
}

const processor = new UpperCaseDecorator(new TrimDecorator(new PlainText()));
console.log(processor.process('  hello world  ')); // HELLO WORLD

10. Facade

Provides a simplified interface to a complex subsystem, hiding its complexity from clients.

When to use: When you want to provide a simple interface to a complex body of code, e.g. wrapping a complex library or a set of subsystems.
TypeScript Example 
class AudioDecoder { decode(file: string) { return `decoded(${file})`; } }
class VideoDecoder { decode(file: string) { return `video(${file})`; } }
class Renderer3D { render(v: string, a: string) { console.log(`Rendering ${v} + ${a}`); } }

class MediaPlayerFacade {
  private audio = new AudioDecoder();
  private video = new VideoDecoder();
  private renderer = new Renderer3D();

  play(file: string) {
    const audio = this.audio.decode(file);
    const video = this.video.decode(file);
    this.renderer.render(video, audio);
  }
}

const player = new MediaPlayerFacade();
player.play('movie.mp4'); // Rendering video(movie.mp4) + decoded(movie.mp4)

11. Flyweight

Uses sharing to support large numbers of fine-grained objects efficiently by separating intrinsic (shared) state from extrinsic (unique) state.

When to use: Rendering large numbers of similar objects (particles, characters in a text editor, map tiles) where memory is a concern.
TypeScript Example 
class TreeType {
  constructor(public name: string, public texture: string) {}
  draw(x: number, y: number) {
    console.log(`Draw ${this.name} at (${x},${y}) texture:${this.texture}`);
  }
}

class TreeFactory {
  private static types = new Map();
  static getType(name: string, texture: string): TreeType {
    const key = `${name}_${texture}`;
    if (!this.types.has(key)) this.types.set(key, new TreeType(name, texture));
    return this.types.get(key)!;
  }
  static count() { return this.types.size; }
}

for (let i = 0; i < 1000; i++) {
  TreeFactory.getType('oak', 'oak.png').draw(i, i * 2);
}
console.log(TreeFactory.count()); // 1 — only one TreeType created

12. Proxy

Provides a surrogate or placeholder for another object to control access, add lazy initialization, logging, or caching.

When to use: Lazy loading expensive resources, access control, logging requests, or remote object communication.
TypeScript Example 
interface Image { display(): void; }

class RealImage implements Image {
  constructor(private path: string) {
    console.log(`Loading image from disk: ${path}`); // expensive
  }
  display() { console.log(`Displaying: ${this.path}`); }
}

class LazyImageProxy implements Image {
  private real: RealImage | null = null;
  constructor(private path: string) {}
  display() {
    if (!this.real) this.real = new RealImage(this.path); // load on demand
    this.real.display();
  }
}

const img: Image = new LazyImageProxy('photo.jpg');
// Image not loaded yet
img.display(); // loads then displays
img.display(); // only displays (cached)

Behavioral Patterns

Behavioral

13. Chain of Responsibility

Passes a request along a chain of handlers, each deciding to process it or pass it to the next handler.

When to use: Middleware pipelines, event bubbling, approval workflows where multiple handlers may process a request.
TypeScript Example 
abstract class Handler {
  private next: Handler | null = null;
  setNext(h: Handler): Handler { this.next = h; return h; }
  handle(level: number): string {
    if (this.next) return this.next.handle(level);
    return 'Unhandled';
  }
}
class InfoHandler extends Handler {
  handle(level: number) {
    if (level <= 1) return 'INFO handler processed';
    return super.handle(level);
  }
}
class WarnHandler extends Handler {
  handle(level: number) {
    if (level === 2) return 'WARN handler processed';
    return super.handle(level);
  }
}
class ErrorHandler extends Handler {
  handle(level: number) { return `ERROR handler processed level ${level}`; }
}

const info = new InfoHandler();
info.setNext(new WarnHandler()).setNext(new ErrorHandler());
console.log(info.handle(3)); // ERROR handler processed level 3

14. Command

Encapsulates a request as an object, allowing parameterization, queuing, logging, and undoable operations.

When to use: Undo/redo functionality, task queues, transactional operations, macro recording.
TypeScript Example 
interface Command { execute(): void; undo(): void; }

class TextEditor {
  private text = '';
  insert(s: string) { this.text += s; }
  delete(n: number) { this.text = this.text.slice(0, -n); }
  getText() { return this.text; }
}

class InsertCommand implements Command {
  constructor(private editor: TextEditor, private text: string) {}
  execute() { this.editor.insert(this.text); }
  undo() { this.editor.delete(this.text.length); }
}

const editor = new TextEditor();
const cmd = new InsertCommand(editor, 'Hello');
cmd.execute(); console.log(editor.getText()); // Hello
cmd.undo();   console.log(editor.getText()); // (empty)

15. Iterator

Provides a way to sequentially access elements of a collection without exposing its underlying representation.

When to use: Custom traversal logic, lazy iteration over large/infinite sequences, unified traversal of different collections.
TypeScript Example 
class Range implements Iterable {
  constructor(
    private start: number,
    private end: number,
    private step = 1
  ) {}

  [Symbol.iterator](): Iterator {
    let current = this.start;
    const { end, step } = this;
    return {
      next(): IteratorResult {
        if (current <= end) {
          const value = current;
          current += step;
          return { value, done: false };
        }
        return { value: undefined as any, done: true };
      }
    };
  }
}

for (const n of new Range(1, 10, 2)) process.stdout.write(n + ' ');
// 1 3 5 7 9

16. Mediator

Defines an object that encapsulates how a set of objects interact, promoting loose coupling by preventing direct references between them.

When to use: Chat rooms, air traffic control, form validation where many components need to communicate without tight coupling.
TypeScript Example 
interface ChatMediator { send(msg: string, from: User): void; }

class ChatRoom implements ChatMediator {
  private users: User[] = [];
  register(u: User) { this.users.push(u); }
  send(msg: string, from: User) {
    this.users.filter(u => u !== from).forEach(u => u.receive(msg, from.name));
  }
}

class User {
  constructor(public name: string, private mediator: ChatMediator) {}
  send(msg: string) { this.mediator.send(msg, this); }
  receive(msg: string, from: string) { console.log(`${this.name} received from ${from}: ${msg}`); }
}

const room = new ChatRoom();
const alice = new User('Alice', room);
const bob   = new User('Bob', room);
room.register(alice); room.register(bob);
alice.send('Hi Bob!'); // Bob received from Alice: Hi Bob!

17. Memento

Captures and externalizes an object's internal state so the object can be restored to that state later, without violating encapsulation.

When to use: Undo/redo systems, game save states, transactional rollback.
TypeScript Example 
class EditorMemento {
  constructor(private state: string) {}
  getState() { return this.state; }
}

class Document {
  private content = '';
  write(text: string) { this.content += text; }
  save(): EditorMemento { return new EditorMemento(this.content); }
  restore(m: EditorMemento) { this.content = m.getState(); }
  getContent() { return this.content; }
}

const doc = new Document();
doc.write('Hello');
const saved = doc.save();
doc.write(' World');
console.log(doc.getContent()); // Hello World
doc.restore(saved);
console.log(doc.getContent()); // Hello

18. Observer

Defines a one-to-many dependency so that when one object changes state, all dependents are notified and updated automatically.

When to use: Event systems, MVC pattern (model notifying views), reactive programming, pub-sub systems.
TypeScript Example 
type Listener = (data: T) => void;

class EventEmitter {
  private listeners: Listener[] = [];
  subscribe(fn: Listener) { this.listeners.push(fn); }
  unsubscribe(fn: Listener) {
    this.listeners = this.listeners.filter(l => l !== fn);
  }
  emit(data: T) { this.listeners.forEach(l => l(data)); }
}

const store = new EventEmitter<{ count: number }>();
store.subscribe(({ count }) => console.log(`View A: count=${count}`));
store.subscribe(({ count }) => console.log(`View B: count=${count}`));
store.emit({ count: 1 });
// View A: count=1  |  View B: count=1

19. State

Allows an object to alter its behavior when its internal state changes; the object will appear to change its class.

When to use: Traffic lights, vending machines, order processing workflows — anything with distinct modes that change behavior.
TypeScript Example 
interface TrafficState { next(): TrafficState; color(): string; }

class Red    implements TrafficState { next() { return new Green(); }  color() { return 'RED'; } }
class Green  implements TrafficState { next() { return new Yellow(); } color() { return 'GREEN'; } }
class Yellow implements TrafficState { next() { return new Red(); }   color() { return 'YELLOW'; } }

class TrafficLight {
  private state: TrafficState = new Red();
  tick() { this.state = this.state.next(); }
  signal() { console.log(this.state.color()); }
}

const light = new TrafficLight();
light.signal(); // RED
light.tick(); light.signal(); // GREEN
light.tick(); light.signal(); // YELLOW

20. Strategy

Defines a family of algorithms, encapsulates each one, and makes them interchangeable so the algorithm can vary independently from clients that use it.

When to use: Sorting algorithms, payment methods, compression strategies — when you need to switch algorithms at runtime.
TypeScript Example 
type SortStrategy = (arr: number[]) => number[];

const bubbleSort: SortStrategy = (arr) => {
  const a = [...arr];
  for (let i = 0; i < a.length; i++)
    for (let j = 0; j < a.length - i - 1; j++)
      if (a[j] > a[j+1]) [a[j], a[j+1]] = [a[j+1], a[j]];
  return a;
};

const nativeSort: SortStrategy = (arr) => [...arr].sort((a, b) => a - b);

class Sorter {
  constructor(private strategy: SortStrategy) {}
  setStrategy(s: SortStrategy) { this.strategy = s; }
  sort(arr: number[]) { return this.strategy(arr); }
}

const sorter = new Sorter(bubbleSort);
console.log(sorter.sort([3, 1, 4, 1, 5])); // [1,1,3,4,5]
sorter.setStrategy(nativeSort);
console.log(sorter.sort([3, 1, 4, 1, 5])); // [1,1,3,4,5]

21. Template Method

Defines the skeleton of an algorithm in a base class, deferring some steps to subclasses without changing the algorithm's structure.

When to use: Data parsing pipelines, game loops, report generation — when steps are fixed but some details vary by subclass.
TypeScript Example 
abstract class DataImporter {
  // Template method — fixed algorithm skeleton
  import(file: string): void {
    const raw = this.readFile(file);
    const data = this.parse(raw);
    this.validate(data);
    this.save(data);
  }
  protected readFile(f: string): string { return `raw:${f}`; }
  protected abstract parse(raw: string): object[];
  protected validate(data: object[]) { console.log(`Validating ${data.length} rows`); }
  protected abstract save(data: object[]): void;
}

class CsvImporter extends DataImporter {
  protected parse(raw: string) { return [{ type: 'csv', raw }]; }
  protected save(data: object[]) { console.log('Saved CSV data', data); }
}

new CsvImporter().import('data.csv');

22. Visitor

Lets you add further operations to objects without modifying them by separating an algorithm from the object structure on which it operates.

When to use: AST traversal, document export in multiple formats, adding operations to a stable object hierarchy.
TypeScript Example 
interface ASTNode { accept(v: Visitor): number; }
interface Visitor { visitNum(n: Num): number; visitAdd(n: Add): number; }

class Num implements ASTNode {
  constructor(public val: number) {}
  accept(v: Visitor) { return v.visitNum(this); }
}
class Add implements ASTNode {
  constructor(public left: ASTNode, public right: ASTNode) {}
  accept(v: Visitor) { return v.visitAdd(this); }
}

class Evaluator implements Visitor {
  visitNum(n: Num) { return n.val; }
  visitAdd(n: Add) { return n.left.accept(this) + n.right.accept(this); }
}

// 3 + (4 + 5) = 12
const ast = new Add(new Num(3), new Add(new Num(4), new Num(5)));
console.log(ast.accept(new Evaluator())); // 12

23. Interpreter

Defines a grammar for a language and an interpreter that uses the representation to interpret sentences in the language.

When to use: SQL parsers, expression evaluators, scripting engines, DSL implementations — when you need to interpret domain-specific expressions.
TypeScript Example 
interface Expression { interpret(ctx: Map): boolean; }

class Variable implements Expression {
  constructor(private name: string) {}
  interpret(ctx: Map) { return ctx.get(this.name) ?? false; }
}
class AndExpression implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  interpret(ctx: Map) {
    return this.left.interpret(ctx) && this.right.interpret(ctx);
  }
}
class NotExpression implements Expression {
  constructor(private expr: Expression) {}
  interpret(ctx: Map) { return !this.expr.interpret(ctx); }
}

const ctx = new Map([['A', true], ['B', false]]);
const expr = new AndExpression(new Variable('A'), new NotExpression(new Variable('B')));
console.log(expr.interpret(ctx)); // true  (A AND NOT B)

Common Anti-Patterns

God Class

A single class that knows too much or does too much — absorbing responsibilities from across the system into one monolithic blob. It has dozens of methods, hundreds of lines, and direct knowledge of every subsystem.

Fix: Apply Single Responsibility Principle (SRP). Break the class into focused, cohesive classes. Use patterns like Facade (to coordinate), Strategy (to separate algorithms), and Observer (to decouple notifications).

Spaghetti Code

Code with a tangled, unstructured control flow — deeply nested conditionals, global state mutations, long functions that do many things, and no clear separation of concerns. Hard to read, test, or modify.

Fix: Refactor into small functions with single responsibilities. Introduce Chain of Responsibility for sequential checks, State pattern for conditional branches on object mode, and Command pattern to encapsulate actions.

Golden Hammer

"If all you have is a hammer, everything looks like a nail." Over-applying a familiar pattern (e.g. Singleton for every service, Observer for all communication, Factory everywhere) to problems where simpler solutions suffice.

Fix: Understand the intent and trade-offs of each pattern before applying. Evaluate simpler alternatives first. Patterns add indirection — apply them only when they solve a real problem you are currently facing.

Lava Flow

Dead code, vestigial structures, or design decisions from early prototypes that nobody dares to remove because the code path is poorly understood. The system accrues "lava" that has hardened in place.

Fix: Write tests to characterise existing behaviour, then refactor and delete dead paths. Use version control to recover anything accidentally removed.

Premature Optimization

Applying Flyweight, object pooling, or caching before profiling has proven a bottleneck. The added complexity harms readability and maintainability for no measurable gain.

Fix: Write clear, correct code first. Profile before optimizing. Apply structural patterns like Flyweight only when memory profiling confirms object proliferation is the bottleneck.

Q & A — 15 Key Questions

What is the difference between Factory Method and Abstract Factory?
Factory Method uses inheritance — a single factory method in a base class is overridden by subclasses to create one product type. The client code calls the method and gets the object; subclasses decide the concrete type.

Abstract Factory uses composition — a factory interface declares multiple creation methods (one per product in a family). Concrete factories implement the interface to produce a consistent family of related products (e.g. DarkButton + DarkCheckbox). Choose Abstract Factory when products must be used together and you want to enforce family consistency.
When should you avoid the Singleton pattern?
Avoid Singleton when: (1) It carries mutable global state that makes tests order-dependent and hard to isolate. (2) The class needs to be subclassed or mocked in tests — static getInstance() prevents constructor injection. (3) The "one instance" constraint is not a true business requirement but a convenience shortcut. Prefer dependency injection of a shared instance over a static global reference; this preserves testability while still sharing a single object.
What is the difference between Decorator and Proxy?
Both wrap a subject object and implement the same interface, but their intent differs:

Decorator adds behaviour (e.g. logging, validation, compression). The caller typically builds the chain consciously — new LoggingDecorator(new CachingDecorator(realService)).

Proxy controls access to the real object (lazy init, auth, remote call). The caller is often unaware a proxy is present; it looks identical to the real subject. Use Decorator to enrich, Proxy to gate.
How does Strategy differ from State?
Strategy is set by the client and represents an interchangeable algorithm. The context doesn't decide which strategy to use — the client injects it. Strategies rarely know about each other.

State represents an object's current mode and governs behaviour transitions. States are often aware of each other (a state returns the next state). The context follows the state's lead — it doesn't choose the next state externally. Both involve encapsulated behaviour objects, but State transitions are internal while Strategy swaps are external.
What problem does the Bridge pattern solve that inheritance alone cannot?
Inheritance causes a Cartesian product explosion. If you have 3 shapes (Circle, Rectangle, Triangle) and 3 renderers (SVG, Canvas, WebGL), you'd need 9 subclasses. Bridge separates the two hierarchies: shapes hold a reference to a renderer. Adding a new renderer requires one new class, not n new subclasses. The key insight is to "prefer composition over inheritance" when two independent dimensions need to vary.
When is the Builder pattern preferable to a constructor with many optional parameters?
When a class has more than ~4 optional parameters, a single constructor becomes hard to read (new Query(null, null, 'users', null, 50)). Builder solves this by naming each step: .from('users').limit(50).build(). It also enables validation in build() before the object is created, enforces logical ordering of steps (Director pattern), and allows immutable product objects while keeping the build process mutable.
How does Observer relate to the pub-sub pattern?
Classic Observer is a direct, synchronous in-process coupling: the subject holds references to observer objects and calls them directly. Pub-Sub introduces an event bus / message broker between publisher and subscriber so they never reference each other. Pub-Sub is Observer with an intermediary. Benefits of pub-sub: decoupling across modules, async delivery, filtering by topic. Downside: harder to trace the flow of data.
What is the difference between Composite and Decorator?
Composite is about structure — it organises objects into a tree and lets clients treat nodes and leaves uniformly. Each node can have multiple children.

Decorator is about responsibility — it wraps exactly one object to add behaviour. There's always one inner subject. Decorator adds functionality; Composite aggregates and delegates to many children. A Decorator is a Composite with exactly one child.
Why is the Flyweight pattern memory-efficient?
Flyweight separates intrinsic state (shared, immutable, stored in the flyweight — e.g. glyph bitmap, tree texture) from extrinsic state (context-specific, passed at render time — e.g. position, color). By caching and sharing flyweight instances via a factory, you store the intrinsic data once regardless of how many objects "use" it. A game with 10 000 trees of 5 types stores 5 TreeType objects, not 10 000.
What is the Command pattern's role in undo/redo?
Each user action is encapsulated as a Command object with execute() and undo() methods. The application maintains two stacks: an undo stack and a redo stack. On action: execute the command and push it onto the undo stack. On undo: pop from undo stack, call undo(), push onto redo stack. On redo: pop from redo stack, call execute() again. This design also supports macro recording (replaying a list of commands) and transactional rollback.
When would you choose Mediator over direct Observer relationships?
Observer creates a many-to-many web: if 5 components each observe several others, tracking which component reacts to which event becomes complex. Mediator centralises all inter-component communication. Components only know the mediator, not each other. Use Mediator when the interaction logic is complex enough that it deserves its own class (e.g. a form where changing one field enables/disables others, or a chat room routing messages). Use Observer for simpler one-to-many event broadcasting with well-defined event types.
How does the Interpreter pattern differ from the Visitor pattern?
Interpreter defines a grammar and embeds evaluation logic inside the expression nodes themselves. Each node knows how to interpret itself — adding a new operation means modifying all node classes.

Visitor externalises operations: nodes just call accept(visitor); the visitor holds all the logic. Adding a new operation = one new Visitor class; adding a new node type = update all Visitor classes. Visitor is preferable when the node hierarchy is stable but operations vary; Interpreter is simpler for small, self-contained grammars.
What distinguishes Template Method from Strategy?
Both handle algorithm variation, but via different mechanisms:

Template Method uses inheritance: the base class defines the algorithm skeleton with abstract hook methods; subclasses fill in the blanks. The algorithm structure is fixed at compile time.

Strategy uses composition: the algorithm is encapsulated in an interchangeable strategy object injected at runtime. Strategy is more flexible (you can swap at runtime) and more testable (mock the strategy). Template Method is simpler when subclassing is acceptable and behaviour doesn't need to change at runtime.
Why can the Singleton pattern be considered an anti-pattern?
Singleton's global mutable state introduces several problems: (1) Tight coupling — any code can reach getInstance() creating hidden dependencies. (2) Testing difficulty — state bleeds between tests; you can't inject a mock without modifying the class. (3) Violation of SRP — the class manages both its own logic and its own lifecycle. (4) Concurrency bugs — naive implementations are not thread-safe. Prefer registering a single instance in a DI container — you get one instance without the global-state drawbacks.
How do you decide which creational pattern to use?
Use this heuristic:
- Need exactly one instance? → Singleton (carefully).
- Need to create an object but the subclass decides the type? → Factory Method.
- Need to create families of related objects consistently? → Abstract Factory.
- Need to create a complex object step by step with many optional parts? → Builder.
- Need to create objects by copying an existing instance cheaply? → Prototype.

Factory Method and Abstract Factory both defer instantiation; the key differentiator is whether you need one product type (Factory Method) or a coordinated family (Abstract Factory).
