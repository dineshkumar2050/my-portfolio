1What is TanStack Query?

TanStack Query (formerly React Query) is a powerful asynchronous state management library for React (and other frameworks). It handles server state — data that lives on a remote server and must be fetched, cached, synchronized, and updated.

Server State vs Client State

AttributeClient StateServer State
LocationBrowser memory (Redux, Zustand)Remote server/database
OwnershipYou own itMany clients share it
PersistenceResets on refresh (unless stored)Persists on server
StalingNever staleCan become stale at any time
Async operationsSynchronousAsynchronous (loading/error states)
SharingLocal to sessionShared — others can mutate it

Why Not useEffect + useState?

// ❌ The naive approach — full of problems
function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch('/api/users')
      .then(r => r.json())
      .then(data => setUsers(data))
      .catch(e => setError(e))
      .finally(() => setLoading(false));
  }, []);
  // Problems: no caching, no deduplication, race conditions,
  // no background refetch, no stale detection, no retry logic...
}
Problems with useEffect + useState for async data No caching (same data fetched on every mount), no request deduplication (multiple components trigger multiple identical requests), race conditions (if component unmounts before fetch resolves), no background synchronisation, no retry logic, manual loading/error state management in every component.

What TanStack Query Solves

Automatic Caching

Results cached by query key. Same query from multiple components shares one request and one cache entry.

Background Refetching

Stale data shown immediately; fresh data fetched in background and UI updated seamlessly.

Request Deduplication

Multiple components requesting the same query key at the same time only fire one network request.

Automatic Retries

Failed requests are retried automatically (3 times by default) with exponential backoff.

Window Focus Refetch

Data automatically refreshed when user returns to the tab, keeping UI up-to-date.

Pagination & Infinite Scroll

Built-in primitives for paginated and infinite queries including cursor-based pagination.

2Core Concepts

QueryClient

The QueryClient is the central store — it manages the query cache, default options, and provides imperative methods to interact with the cache.

import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

// Create once — outside component to avoid re-creation on renders
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 1000 * 60 * 5,   // 5 minutes
      gcTime: 1000 * 60 * 10,     // 10 minutes (v5 name; was cacheTime in v4)
      retry: 3,
      refetchOnWindowFocus: true,
    },
  },
})

function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <Router />
    </QueryClientProvider>
  )
}

Stale Time vs GC Time (Cache Time)

staleTime

Duration (ms) for which cached data is considered fresh. While fresh, TanStack Query will NOT refetch — it serves cached data immediately. Default: 0 (always stale).

gcTime (was cacheTime)

Duration (ms) that inactive query data stays in cache before garbage collection. An inactive query has no active subscribers (no component mounted). Default: 5 * 60 * 1000 (5 min).

graph LR A[Query fired] --> B{In cache?} B -- No --> C[Fetch from server] B -- Yes --> D{Fresh?} D -- Yes staleTime not exceeded --> E[Return cached data — NO fetch] D -- No stale --> F[Return cached data immediately + refetch in background] C --> G[Store in cache] F --> H[Update UI with fresh data]

Background Refetching

When data is stale and a query is re-observed (e.g., component mounts, window refocuses), TanStack Query serves the stale cached data immediately to avoid UI flicker, then fetches fresh data in the background and updates the UI when it arrives. The isFetching flag (distinct from isLoading) indicates this background activity.

Key insight isLoading is true only when there is NO cached data AND a fetch is in progress (true "loading" state). isFetching is true any time a fetch is in flight — including background refetches. Always show a subtle spinner when isFetching is true, not just isLoading.

3useQuery Hook

import { useQuery } from '@tanstack/react-query'

function TodoList() {
  const {
    data,           // resolved data from queryFn
    error,          // error object if status === 'error'
    status,         // 'pending' | 'error' | 'success'
    isLoading,      // shorthand: status === 'pending' && isFetching
    isError,        // shorthand: status === 'error'
    isSuccess,      // shorthand: status === 'success'
    isFetching,     // true any time a fetch is in progress (including background)
    isPending,      // no data in cache yet (v5 replaces isLoading in some cases)
    refetch,        // manual trigger function
  } = useQuery({
    queryKey: ['todos'],           // unique cache key — MUST be serializable
    queryFn: () => fetchTodos(),   // async function returning data
    staleTime: 1000 * 60 * 2,     // override global default
    gcTime: 1000 * 60 * 10,
    enabled: true,                 // set to false to disable auto-fetching
    retry: 2,                      // override retry count
  })

  if (isLoading) return <Spinner />
  if (isError)   return <Error message={error.message} />
  return <ul>{data.map(t => <li key={t.id}>{t.title}</li>)}</ul>
}

Query Status States

pending — no data, no error
success — data available
error — fetch failed
isFetching — any active fetch
stale — data past staleTime

select Transformer

The select option transforms or selects a subset of data. The selected result is memoized — re-renders only when the selected value changes, not the entire raw data.

const { data: todoCount } = useQuery({
  queryKey: ['todos'],
  queryFn: fetchTodos,
  select: (data) => data.length,   // component only re-renders when count changes
})

const { data: firstTodo } = useQuery({
  queryKey: ['todos'],
  queryFn: fetchTodos,
  select: (data) => data[0],       // same cache, different derived slice
})

4QueryKey Design

Query keys are the cornerstone of TanStack Query's caching. Every unique key represents a separate cache entry. Keys must be serializable arrays.

Key Hierarchy

// Scalar — all todos
['todos']

// With identifier — specific todo
['todos', 42]
['todos', todoId]

// With nested object — filtered/sorted list
['todos', { status: 'done', page: 1 }]

// Scoped under a resource
['users', userId, 'todos']
['users', userId, 'profile']

// Multi-level with filters
['search', 'users', { query: 'john', role: 'admin' }]
Automatic Refetch on Key Change When a key's content changes (e.g., userId changes), TanStack Query automatically treats the new key as a different cache entry and fires a new fetch. This is how you make data reactive to URL params or filter state — just include the variable in the key.

Key Factory Pattern

// Recommended pattern: centralize key definitions
export const todoKeys = {
  all: ['todos'] as const,
  lists: () => [...todoKeys.all, 'list'] as const,
  list: (filters: TodoFilters) => [...todoKeys.lists(), filters] as const,
  details: () => [...todoKeys.all, 'detail'] as const,
  detail: (id: number) => [...todoKeys.details(), id] as const,
}

// Usage
useQuery({ queryKey: todoKeys.detail(id), queryFn: () => fetchTodo(id) })
queryClient.invalidateQueries({ queryKey: todoKeys.lists() }) // invalidate all lists

How Keys Affect Invalidation

// Exact match — only invalidates ['todos', 1]
queryClient.invalidateQueries({ queryKey: ['todos', 1], exact: true })

// Prefix match (default) — invalidates all keys starting with ['todos']
queryClient.invalidateQueries({ queryKey: ['todos'] })
// This invalidates: ['todos'], ['todos', 1], ['todos', {filter}], etc.

5useMutation Hook

Mutations handle data writes — POST, PUT, PATCH, DELETE. Unlike queries, mutations do NOT run automatically; you call mutate() or mutateAsync().

import { useMutation, useQueryClient } from '@tanstack/react-query'

function CreateTodo() {
  const queryClient = useQueryClient()

  const createTodo = useMutation({
    mutationFn: (newTodo: NewTodo) => api.post('/todos', newTodo),

    onMutate: async (variables) => {
      // Fires BEFORE mutationFn — use for optimistic updates (see Section 6)
      console.log('About to create:', variables)
    },

    onSuccess: (data, variables, context) => {
      // data: server response, variables: what you passed to mutate()
      queryClient.invalidateQueries({ queryKey: ['todos'] })
    },

    onError: (error, variables, context) => {
      console.error('Mutation failed:', error)
    },

    onSettled: (data, error, variables, context) => {
      // Always fires — whether success or error
      // Good place for cleanup / final invalidation
    },
  })

  return (
    <form onSubmit={e => {
      e.preventDefault()
      createTodo.mutate({ title: e.target.title.value })
    }}>
      <input name="title" />
      <button disabled={createTodo.isPending}>
        {createTodo.isPending ? 'Creating...' : 'Create'}
      </button>
    </form>
  )
}

6Optimistic Updates

Optimistic updates immediately reflect the intended change in the UI before the server responds, creating a snappy experience. If the server rejects the mutation, you roll back to the snapshot.

sequenceDiagram participant UI participant Cache participant Server UI->>Cache: onMutate: save snapshot, apply optimistic update UI->>Server: mutationFn fires (async) Note over UI,Cache: UI shows updated data immediately alt Success Server-->>UI: 200 OK UI->>Cache: onSuccess: invalidate to sync server truth else Error Server-->>UI: 4xx/5xx UI->>Cache: onError: restore snapshot (rollback) end 
const updateTodo = useMutation({
  mutationFn: (todo: Todo) => api.patch(`/todos/${todo.id}`, todo),

  onMutate: async (updatedTodo) => {
    // 1. Cancel any in-flight queries to avoid overwriting optimistic update
    await queryClient.cancelQueries({ queryKey: ['todos'] })

    // 2. Snapshot the current cache value
    const previousTodos = queryClient.getQueryData(['todos'])

    // 3. Optimistically update the cache
    queryClient.setQueryData(['todos'], (old: Todo[]) =>
      old.map(t => t.id === updatedTodo.id ? { ...t, ...updatedTodo } : t)
    )

    // 4. Return context with the snapshot for rollback
    return { previousTodos }
  },

  onError: (err, updatedTodo, context) => {
    // 5. Rollback to snapshot on error
    queryClient.setQueryData(['todos'], context?.previousTodos)
  },

  onSettled: () => {
    // 6. Always refetch to sync with server truth
    queryClient.invalidateQueries({ queryKey: ['todos'] })
  },
})
Why cancelQueries in onMutate? If a background refetch is in progress when you apply an optimistic update, the refetch result (old data) could overwrite your optimistic update. Cancelling ensures the optimistic data sticks until the mutation resolves.

7Cache Invalidation

invalidateQueries

// Invalidate all queries starting with ['todos'] (prefix match by default)
queryClient.invalidateQueries({ queryKey: ['todos'] })

// Exact match only
queryClient.invalidateQueries({ queryKey: ['todos', 1], exact: true })

// Invalidate all queries in the cache
queryClient.invalidateQueries()

// Invalidate with a predicate function
queryClient.invalidateQueries({
  predicate: (query) =>
    query.queryKey[0] === 'todos' && query.queryKey[1] === userId,
})

setQueryData — Manual Cache Update

Directly write data into the cache — useful after mutations when you already have the updated data from the server response, avoiding an extra round-trip.

// Replace the entire cache entry
queryClient.setQueryData(['todos', todoId], updatedTodo)

// Functional update — safer when current value matters
queryClient.setQueryData(['todos'], (old: Todo[] | undefined) =>
  old ? [...old, newTodo] : [newTodo]
)

removeQueries

// Remove from cache entirely (useful on logout to clear user data)
queryClient.removeQueries({ queryKey: ['user'] })

// Or clear everything
queryClient.clear()

8Prefetching

Prefetching populates the cache before the component that needs the data is rendered, eliminating loading states.

prefetchQuery

// Prefetch in a router loader (e.g., TanStack Router or React Router v6.4+)
export async function loader({ params }) {
  await queryClient.prefetchQuery({
    queryKey: ['user', params.userId],
    queryFn: () => fetchUser(params.userId),
    staleTime: 1000 * 60 * 5,   // don't prefetch if data is fresh
  })
  return null
}

// In the component — data is already in cache, no loading state!
function UserProfile({ userId }) {
  const { data } = useQuery({
    queryKey: ['user', userId],
    queryFn: () => fetchUser(userId),
  })
  return <div>{data.name}</div>  // renders immediately
}

Prefetch on Hover

function TodoItem({ todo }) {
  const queryClient = useQueryClient()

  const prefetchTodo = () => {
    queryClient.prefetchQuery({
      queryKey: ['todos', todo.id],
      queryFn: () => fetchTodo(todo.id),
      staleTime: 10_000,  // don't spam if already fresh
    })
  }

  return (
    <li onMouseEnter={prefetchTodo}>
      <Link to={`/todos/${todo.id}`}>{todo.title}</Link>
    </li>
  )
}
prefetchQuery vs fetchQuery prefetchQuery silently populates the cache and returns void. fetchQuery populates the cache AND returns the data (throws on error) — use it in loaders where you need the data directly.

9Pagination & Infinite Queries

Standard Pagination with keepPreviousData

import { keepPreviousData } from '@tanstack/react-query'

function PaginatedTodos() {
  const [page, setPage] = useState(1)

  const { data, isPlaceholderData } = useQuery({
    queryKey: ['todos', page],
    queryFn: () => fetchTodosPage(page),
    placeholderData: keepPreviousData,  // v5: show previous page while next loads
  })

  return (
    <>
      {data?.todos.map(t => <TodoRow key={t.id} todo={t} />)}
      <button
        onClick={() => setPage(p => p - 1)}
        disabled={page === 1}
      >Previous</button>
      <button
        onClick={() => setPage(p => p + 1)}
        disabled={isPlaceholderData || !data?.hasNextPage}
      >Next</button>
    </>
  )
}

useInfiniteQuery — Infinite Scroll

import { useInfiniteQuery } from '@tanstack/react-query'

function InfiniteTodos() {
  const {
    data,               // { pages: Page[][], pageParams: any[] }
    fetchNextPage,      // trigger to load next page
    fetchPreviousPage,
    hasNextPage,        // true if getNextPageParam returns non-undefined
    hasPreviousPage,
    isFetchingNextPage,
    isFetchingPreviousPage,
    status,
  } = useInfiniteQuery({
    queryKey: ['todos', 'infinite'],
    queryFn: ({ pageParam }) => fetchTodosPage(pageParam),
    initialPageParam: 1,                         // v5: required
    getNextPageParam: (lastPage, allPages) => {  // return undefined to stop
      return lastPage.hasMore ? lastPage.nextCursor : undefined
    },
    getPreviousPageParam: (firstPage) => firstPage.previousCursor,
  })

  // All pages flattened
  const allTodos = data?.pages.flatMap(page => page.todos) ?? []

  return (
    <>
      {allTodos.map(t => <TodoRow key={t.id} todo={t} />)}
      <button
        onClick={() => fetchNextPage()}
        disabled={!hasNextPage || isFetchingNextPage}
      >
        {isFetchingNextPage ? 'Loading more...' : hasNextPage ? 'Load More' : 'No more todos'}
      </button>
    </>
  )
}
Intersection Observer for infinite scroll Combine useInfiniteQuery with an Intersection Observer to automatically call fetchNextPage() when the user scrolls to a sentinel element at the bottom of the list.

10Dependent Queries

Sequential Dependent Query

// Query 2 depends on result of Query 1
function UserPosts({ username }) {
  // Step 1: fetch user to get their ID
  const { data: user } = useQuery({
    queryKey: ['user', username],
    queryFn: () => fetchUserByName(username),
  })

  // Step 2: only fetch posts when user.id is available
  const { data: posts } = useQuery({
    queryKey: ['posts', user?.id],
    queryFn: () => fetchUserPosts(user.id),
    enabled: !!user?.id,  // 🔑 the key pattern for dependent queries
  })

  return <PostList posts={posts} />
}

useQueries — Dynamic Parallel Queries

import { useQueries } from '@tanstack/react-query'

function TodoDetails({ ids }: { ids: number[] }) {
  // Fire one query per ID dynamically
  const todoQueries = useQueries({
    queries: ids.map(id => ({
      queryKey: ['todos', id],
      queryFn: () => fetchTodo(id),
      staleTime: 1000 * 60,

  if (todoQueries.isPending) return <Spinner />
  return <TodoGrid todos={todoQueries.data} />
}

12Global Config, Retry & Backoff

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      // Retry config
      retry: 3,                    // default: 3 attempts total
      retryDelay: attemptIndex =>  // default: exponential, capped at 30s
        Math.min(1000 * 2 ** attemptIndex, 30_000),
      // [attempt 0] = 1000ms, [1] = 2000ms, [2] = 4000ms

      // Custom retry logic — e.g., don't retry on 4xx errors
      retry: (failureCount, error) => {
        if (error.status === 404 || error.status === 403) return false
        return failureCount < 3
      },
    },
    mutations: {
      retry: 0,    // Don't retry mutations by default (could double-submit)
      onError: (error) => toast.error(error.message),  // global mutation error handler
    },
  },
})
Mutations and retry Unlike queries, mutations default to retry: 0. Retrying a POST/PUT/DELETE could cause duplicate submissions or side-effects. Only enable mutation retries when your API is idempotent (e.g., PUT with the same data).

Per-Query Override

// Override defaults at query level
useQuery({
  queryKey: ['critical-data'],
  queryFn: fetchCriticalData,
  retry: 5,
  retryDelay: 500,  // flat 500ms between all retries
})

15Q&A — 15 Questions

Easy What is the difference between isLoading and isFetching?

isLoading (or more precisely in v5, the combination isPending && isFetching) is true only when the query has no cached data and is fetching for the first time — the true "loading spinner" state where there is nothing to show the user.

isFetching is true any time a network request is in flight for this query, including background refetches when stale cached data is already displayed. Always show a subtle indicator (e.g., a small spinner in the corner) when isFetching is true, reserving the full loading skeleton for isLoading.

Easy What happens when staleTime is set to Infinity?

Data cached with staleTime: Infinity is considered permanently fresh. TanStack Query will never automatically refetch it due to window focus, mount, or reconnect triggers. It will serve the cached value indefinitely until the cache is manually invalidated (via invalidateQueries) or the entry is garbage-collected (gcTime expires after all observers unmount).

This is ideal for static reference data like country lists, configuration constants, or any data that is known to never change during a session.

Easy How do you conditionally run a query?

Use the enabled option. When enabled is false, the query will not automatically fetch. The standard pattern for dependent queries is enabled: !!someValue — the double-bang coerces a potentially undefined/null value to a boolean.

const { data: profile } = useQuery({
  queryKey: ['profile', userId],
  queryFn: () => fetchProfile(userId),
  enabled: !!userId,  // won't run until userId is truthy
})

While enabled is false, the query stays in pending status with fetchStatus: 'idle'.

Intermediate Explain query key design best practices and why key structure matters.

Query keys are the fundamental unit of cache identity. Every unique serialized key maps to exactly one cache entry. Key structure matters because:

1. Hierarchical invalidation: By using nested arrays (e.g., ['todos'], ['todos', id], ['todos', {filter}]), you can invalidate an entire resource family with a single prefix invalidation: invalidateQueries({queryKey: ['todos']}) invalidates all of them.

2. Automatic reactivity: Including filter/sort/search variables in the key means TanStack Query automatically detects when the "parameters" of the query change and fires a new fetch — no manual useEffect dependency array needed.

3. The factory pattern (centralized key objects) prevents typos and makes refactoring safe by providing a single source of truth for all key shapes.

Intermediate What is the purpose of select in useQuery and how does it optimize performance?

The select option is a transformation function applied to the raw data returned by queryFn before it reaches the component. Its result is memoized — the component only re-renders when the selected/transformed value changes, not when the entire raw data object changes reference.

This means multiple components can subscribe to the same query (sharing the cache and network request), but each can select a different slice of data and only re-render when their specific slice changes. For example, select: data => data.length means the component never re-renders when a todo's title changes — only when the count changes.

select also accepts a stable function reference (or use with useCallback) to prevent unnecessary re-computation on every render.

Intermediate When should you use initialData vs placeholderData?

initialData is used to pre-populate the cache with real data — typically from Server-Side Rendering or a parent component that already fetched the data. It is persisted in the cache and treated as actual data. Combined with initialDataUpdatedAt, TanStack Query can determine whether to immediately refetch (if the data is older than staleTime) or serve it as fresh.

placeholderData provides temporary UI-only data while the real fetch is in progress. It is NOT stored in the cache and is never persisted. The query always fires a network request immediately. The most common usage is placeholderData: keepPreviousData — while navigating between paginated pages, the previous page's data fills the UI so there's no flash of empty content.

Intermediate How does request deduplication work in TanStack Query?

When multiple components mount simultaneously (or within the same synchronous render cycle) and all call useQuery with the same query key, TanStack Query fires only one network request. All observers share the same cache entry and the same in-flight promise. When the request resolves, all subscribed components update simultaneously.

This is implemented via an internal QueryObserver reference-counting system. As long as at least one observer subscribes to a key, the query is "active." The deduplication is automatic — no special configuration is needed. This is one of the main advantages over useEffect approaches, where each component independently fires its own fetch.

Advanced Walk through a complete optimistic update implementation with rollback.

An optimistic update follows a 5-step pattern in useMutation callbacks:

1. onMutate — Cancel + snapshot + optimistic write: Cancel any in-flight refetches for the affected query (to prevent overwrites), snapshot the current cache value for rollback, and write the expected result directly into the cache with setQueryData. Return the snapshot as context.

2. mutationFn — Fire the real request in the background while the UI already shows the update.

3. onSuccess (optional) — Update with server truth: If the server returns the canonical updated object (e.g., with server-generated fields like updatedAt), call setQueryData again with the precise server value.

4. onError — Rollback: Restore the snapshot saved in context using setQueryData.

5. onSettled — Final invalidation: Always invalidate to sync with server truth regardless of success/error, ensuring eventual consistency even if the optimistic data was slightly wrong.

The cancelQueries step in onMutate is critical — without it, a concurrent background refetch could overwrite the optimistic update before the mutation resolves.

Advanced Explain how useInfiniteQuery manages pages and how getNextPageParam works.

useInfiniteQuery stores data as { pages: PageData[][], pageParams: PageParam[] }. Each call to fetchNextPage() appends a new page to the pages array.

getNextPageParam(lastPage, allPages) is called after each page loads. Its return value becomes the pageParam passed to the next queryFn call. Returning undefined signals that there are no more pages, setting hasNextPage to false.

The function receives the most recently fetched page as lastPage and the full array of all fetched pages as allPages. This gives you flexibility to implement cursor-based (return lastPage.nextCursor), page-number (return lastPage.page + 1), or offset-based (return allPages.flat().length) pagination strategies.

In v5, initialPageParam is required (was auto-inferred in v4) and must match the type expected by queryFn's pageParam argument.

Advanced How would you integrate TanStack Query with SSR (Next.js)?

The recommended approach uses HydrationBoundary (v5) to serialize server-fetched query data and hydrate it into the client cache on first render, avoiding double-fetches.

Server-side (in a Server Component or getServerSideProps): Create a QueryClient, call await queryClient.prefetchQuery() for all needed queries, then serialize with dehydrate(queryClient).

Client-side: Wrap the component tree in <HydrationBoundary state={dehydratedState}>. On first render, TanStack Query finds the pre-populated data in the dehydrated state and injects it into the client QueryClient. Components using useQuery find the data already in cache and render without a loading state.

Key nuance: set staleTime appropriately. With default staleTime: 0, the hydrated data is immediately stale and a client-side refetch fires on mount. Set staleTime to a reasonable value (e.g., 60 seconds) to avoid this immediate refetch while still keeping the data fresh on the client.

Very Advanced What is the gcTime vs staleTime distinction and what are the memory implications of misconfiguring them?

These two timers operate on completely different axes:

staleTime governs when data is considered "fresh" vs "stale." It affects whether TanStack Query will refetch in the background. It has zero impact on memory — stale data stays in the cache.

gcTime governs memory — how long inactive cache entries are kept after the last observer unmounts. An inactive query is one with zero active subscribers (all components using it have unmounted).

Common misconfiguration: Setting gcTime to zero causes cache entries to be immediately garbage-collected as soon as their component unmounts. This breaks the "instant back navigation" feature — navigating back to a page that previously had data will show a full loading spinner again because the cache was cleared. Setting gcTime very high (or Infinity) risks memory leaks in large apps with many distinct query keys.

Important constraint: gcTime must always be greater than or equal to staleTime. If gcTime < staleTime, the data could be garbage-collected while it's still considered "fresh" — a logical contradiction that TanStack Query does not protect against automatically.

Very Advanced Describe the v5 change of removing onSuccess/onError callbacks from useQuery and the correct migration pattern.

In v4, useQuery accepted onSuccess, onError, and onSettled callbacks. These had confusing semantics: they fired per observer (component), not per fetch — so if 3 components subscribed to the same query and the query refetched, all 3 onSuccess callbacks fired. If a component mounted after the data was already cached, its onSuccess fired immediately. This caused bugs like duplicate toast notifications or redundant API calls.

v5 migration pattern:

1. For mutation side effects (toast notifications, navigations after create/update/delete): use onSuccess/onError on useMutation — these fire per mutation, which is the correct semantics.

2. For derived state or side effects based on query data changing: use useEffect watching data:
useEffect(() => { if (data) doSomething(data) }, [data])

3. For global error notifications: configure a QueryCache with an onError callback at the QueryClient level — fires once per failed query fetch, not per observer.

const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error) => toast.error(`Query failed: ${error.message}`),
  }),
})
Very Advanced How does TanStack Query handle window focus refetching and how would you customize it for different environments?

By default, TanStack Query listens for the visibilitychange DOM event. When the document visibility changes from hidden to visible (user returns to the tab), all stale queries with active observers are refetched in the background.

Custom focus manager — useful in non-browser environments (React Native, Electron, Web Workers) or when you want different focus semantics:

import { focusManager } from '@tanstack/react-query'

// React Native — use AppState
import { AppState } from 'react-native'
focusManager.setEventListener((handleFocus) => {
  const subscription = AppState.addEventListener('change', state => {
    handleFocus(state === 'active')
  })
  return () => subscription.remove()  // cleanup
})

// Disable focus refetching entirely
focusManager.setFocused(true)  // always "focused" — no focus-triggered refetches
focusManager.setFocused(undefined)  // restore default browser detection

Similarly, the onlineManager controls network-status detection for refetchOnReconnect and can be customized for React Native's NetInfo API.

Very Advanced Explain the fetchStatus dimension in v5 and how it interacts with status.

In v5, query state has two independent dimensions that combine to describe the full state:

status — describes the data dimension: 'pending' (no data), 'success' (has data), 'error' (last fetch errored). Once data is fetched, status stays 'success' even during background refetches.

fetchStatus — describes the fetch dimension: 'fetching' (request in flight), 'paused' (request queued but paused, e.g., offline), 'idle' (no fetch happening).

Combining these gives you precise states:

  • status: 'pending', fetchStatus: 'fetching' — Initial load (the old isLoading)
  • status: 'success', fetchStatus: 'fetching' — Background refetch with cached data shown
  • status: 'pending', fetchStatus: 'paused' — Offline; query waiting for network
  • status: 'success', fetchStatus: 'idle' — Fully loaded, no active fetch

This two-dimension model eliminates the ambiguity in v4 where isLoading had confusing behavior (it could be false even with no data when enabled: false).

Very Advanced How would you implement a cache persistence layer (persist cache to localStorage across page refreshes)?

TanStack Query provides the @tanstack/query-persist-client-core and @tanstack/react-query-persist-client packages for this pattern.

import { PersistQueryClientProvider } from '@tanstack/react-query-persist-client'
import { createSyncStoragePersister } from '@tanstack/query-sync-storage-persister'

const persister = createSyncStoragePersister({
  storage: window.localStorage,
  key: 'REACT_QUERY_CACHE',
  throttleTime: 1000,  // debounce writes to avoid thrashing
})

function App() {
  return (
    <PersistQueryClientProvider
      client={queryClient}
      persistOptions={{
        persister,
        maxAge: 1000 * 60 * 60 * 24,  // 24 hours — discard cache older than this
        buster: process.env.APP_VERSION,  // change to bust cache on deploy
        dehydrateOptions: {
          shouldDehydrateQuery: (query) =>
            query.state.status === 'success',  // only persist successful queries
        },
      }}
    >
      <Router />
    </PersistQueryClientProvider>
  )
}

Key considerations: The buster string (e.g., app version or build hash) invalidates the entire persisted cache when changed, preventing stale data from a previous deployment from being loaded. For async storage (IndexedDB, AsyncStorage), use createAsyncStoragePersister from @tanstack/query-async-storage-persister.
