Java Comprehensive Reference

Overview

Java is a statically typed, object-oriented, compiled-to-bytecode language that runs on the Java Virtual Machine (JVM). It follows the principle of "Write Once, Run Anywhere".

JVM, JDK, JRE

ComponentFull NameDescription
JVMJava Virtual MachineAbstract machine that executes Java bytecode. Platform-specific but provides platform independence for Java programs.
JREJava Runtime EnvironmentJVM + standard class libraries. Required to run Java applications.
JDKJava Development KitJRE + development tools (javac, javadoc, jdb). Required to develop Java applications.

Bytecode & Platform Independence

Java source code (.java) is compiled by javac into bytecode (.class files). The JVM interprets/JIT-compiles this bytecode into native machine code at runtime. Since bytecode is platform-neutral, any JVM on any OS can run it.

Object-Oriented Programming

Classes & Objects

public class Animal {
    // Instance fields
    private String name;
    private int age;

    // Static field
    private static int count = 0;

    // Constructor
    public Animal(String name, int age) {
        this.name = name;
        this.age = age;
        count++;
    }

    // Getter/setter (encapsulation)
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    // Instance method
    public String describe() {
        return name + " is " + age + " years old";
    }

    // Static method
    public static int getCount() { return count; }

    // toString override
    @Override
    public String toString() {
        return "Animal{name='" + name + "', age=" + age + "}";
    }
}

Abstract Classes

public abstract class Shape {
    protected String color;

    public Shape(String color) {
        this.color = color;
    }

    // Abstract method — subclass must implement
    public abstract double area();

    // Concrete method
    public void printInfo() {
        System.out.println("Shape: " + getClass().getSimpleName()
            + ", Color: " + color + ", Area: " + area());
    }
}

public class Circle extends Shape {
    private double radius;

    public Circle(String color, double radius) {
        super(color);
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle extends Shape {
    private double width, height;

    public Rectangle(String color, double w, double h) {
        super(color);
        this.width = w; this.height = h;
    }

    @Override
    public double area() { return width * height; }
}

Generics

Generic Classes & Methods

// Generic class
public class Box<T> {
    private T value;
    public Box(T value) { this.value = value; }
    public T get() { return value; }
}

// Generic method
public <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) > 0 ? a : b;
}

// Multiple type parameters
public class Pair<A, B> {
    private final A first;
    private final B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
}

Bounded Wildcards & PECS

// Upper bounded wildcard: ? extends T (Producer Extends)
// Use when you only READ from the collection
public double sumList(List<? extends Number> list) {
    return list.stream().mapToDouble(Number::doubleValue).sum();
}

// Lower bounded wildcard: ? super T (Consumer Super)
// Use when you only WRITE to the collection
public void addNumbers(List<? super Integer> list) {
    list.add(1);
    list.add(2);
    list.add(3);
}

// PECS: Producer Extends, Consumer Super
public <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T item : src) dst.add(item);
}

Type Erasure

Type parameters are erased at compile time. List<String> and List<Integer> are both just List at runtime. This means you cannot: instantiate generic types (new T()), use instanceof with generic types, or create generic arrays directly.

List

// ArrayList — dynamic array, O(1) random access, O(n) insert/delete
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
list.add("d");
list.add(0, "z");       // insert at index
list.remove("b");       // remove by value
list.remove(0);         // remove by index
list.set(1, "X");       // replace
list.subList(1, 3);     // view, not copy

// LinkedList — doubly linked, O(1) insert/delete at ends, O(n) random access
LinkedList<Integer> ll = new LinkedList<>();
ll.addFirst(1); ll.addLast(2);
ll.peekFirst(); ll.pollFirst();

// Immutable list (Java 9+)
List<String> immutable = List.of("a", "b", "c"); // no nulls, no modifications
List<String> copy = List.copyOf(list); // defensive copy

Set

// HashSet — O(1) add/remove/contains, no order, allows one null
Set<String> hs = new HashSet<>(Set.of("apple", "banana", "cherry"));

// LinkedHashSet — insertion order preserved
Set<String> lhs = new LinkedHashSet<>();

// TreeSet — sorted order (natural or Comparator), O(log n)
TreeSet<Integer> ts = new TreeSet<>();
ts.add(5); ts.add(1); ts.add(3);
ts.first(); ts.last(); ts.headSet(3); ts.tailSet(3);
ts.floor(4);  // greatest element <= 4
ts.ceiling(4); // smallest element >= 4

Map

// HashMap — O(1) avg, no order, one null key
Map<String, Integer> map = new HashMap<>();
map.put("a", 1);
map.getOrDefault("b", 0);
map.putIfAbsent("a", 99);          // won't overwrite
map.computeIfAbsent("c", k -> k.length()); // compute if missing
map.compute("a", (k, v) -> v == null ? 1 : v + 1); // update
map.merge("a", 1, Integer::sum);    // merge with function

// Iterate
for (Map.Entry<String, Integer> e : map.entrySet()) {
    System.out.println(e.getKey() + "=" + e.getValue());
}
map.forEach((k, v) -> System.out.println(k + "=" + v));

// LinkedHashMap — insertion or access order
Map<String, Integer> lhm = new LinkedHashMap<>(16, 0.75f, true); // access-order

// TreeMap — sorted keys
TreeMap<String, Integer> tm = new TreeMap<>();
tm.firstKey(); tm.lastKey();
tm.subMap("a", "d"); // keys from "a" inclusive to "d" exclusive

// ConcurrentHashMap — thread-safe, no null keys/values
ConcurrentHashMap<String, Integer> chm = new ConcurrentHashMap<>();
chm.putIfAbsent("x", 1);
chm.computeIfPresent("x", (k, v) -> v + 1);

Queue & Deque

// PriorityQueue — heap-based, natural order or Comparator
PriorityQueue<Integer> pq = new PriorityQueue<>(); // min-heap
PriorityQueue<Integer> maxPq = new PriorityQueue<>(Comparator.reverseOrder());
pq.offer(3); pq.offer(1); pq.offer(2);
pq.peek(); // 1 (min), does not remove
pq.poll(); // 1, removes

// ArrayDeque — stack/queue operations, more efficient than LinkedList
Deque<String> deque = new ArrayDeque<>();
deque.push("a");     // addFirst (stack push)
deque.pop();         // removeFirst (stack pop)
deque.offer("b");    // addLast (queue enqueue)
deque.poll();        // removeFirst (queue dequeue)

Streams API

Stream Pipeline

// Source -> Intermediate ops (lazy) -> Terminal op (triggers evaluation)
List<String> names = List.of("Alice", "Bob", "Charlie", "David", "Eve");

// Basic pipeline
List<String> result = names.stream()
    .filter(n -> n.length() > 3)          // intermediate
    .map(String::toUpperCase)             // intermediate
    .sorted()                              // intermediate
    .collect(Collectors.toList());        // terminal

// Method chaining
long count = IntStream.rangeClosed(1, 100)
    .filter(n -> n % 2 == 0)
    .count();

Intermediate Operations

Stream<String> stream = Stream.of("hello", "world", "hello", "java");

stream.distinct();                          // remove duplicates
stream.filter(s -> s.startsWith("h"));      // predicate filter
stream.map(String::toUpperCase);            // transform
stream.flatMap(s -> Arrays.stream(s.split(""))); // flatten
stream.sorted();                            // natural order
stream.sorted(Comparator.comparingInt(String::length));
stream.limit(3);                            // first 3
stream.skip(2);                             // skip first 2
stream.peek(System.out::println);           // debug, doesn't consume
stream.takeWhile(s -> s.length() < 5);     // Java 9+
stream.dropWhile(s -> s.length() < 5);     // Java 9+

Terminal Operations

List<Integer> nums = List.of(1, 2, 3, 4, 5, 6);

// Collection
nums.stream().collect(Collectors.toList());
nums.stream().toList(); // Java 16+, immutable

// Reduction
int sum = nums.stream().reduce(0, Integer::sum);
Optional<Integer> max = nums.stream().max(Integer::compareTo);
Optional<Integer> min = nums.stream().min(Integer::compareTo);
long count = nums.stream().count();

// Short-circuit terminal
Optional<Integer> first = nums.stream().filter(n -> n > 3).findFirst();
Optional<Integer> any   = nums.stream().filter(n -> n > 3).findAny(); // parallel-friendly
boolean allEven = nums.stream().allMatch(n -> n % 2 == 0);
boolean anyEven = nums.stream().anyMatch(n -> n % 2 == 0);
boolean noneNeg = nums.stream().noneMatch(n -> n < 0);

// ForEach
nums.stream().forEach(System.out::println);

Collectors

List<String> words = List.of("apple", "banana", "avocado", "blueberry", "cherry");

// Joining
String joined = words.stream().collect(Collectors.joining(", ", "[", "]"));

// Grouping
Map<Character, List<String>> byFirstLetter = words.stream()
    .collect(Collectors.groupingBy(w -> w.charAt(0)));

// Partitioning
Map<Boolean, List<String>> partition = words.stream()
    .collect(Collectors.partitioningBy(w -> w.length() > 5));

// Counting downstream
Map<Character, Long> countByLetter = words.stream()
    .collect(Collectors.groupingBy(w -> w.charAt(0), Collectors.counting()));

// Mapping downstream
Map<Character, List<Integer>> lengthsByLetter = words.stream()
    .collect(Collectors.groupingBy(
        w -> w.charAt(0),
        Collectors.mapping(String::length, Collectors.toList())));

// Statistics
IntSummaryStatistics stats = words.stream()
    .collect(Collectors.summarizingInt(String::length));

// Teeing collector (Java 12+) — split into two collectors, merge results
Map.Entry<Long, Optional<String>> result = words.stream()
    .collect(Collectors.teeing(
        Collectors.counting(),
        Collectors.minBy(Comparator.naturalOrder()),
        Map::entry));

Optional

// Creation
Optional<String> empty = Optional.empty();
Optional<String> present = Optional.of("hello");       // throws if null
Optional<String> nullable = Optional.ofNullable(null); // wraps null as empty

// Checking
present.isPresent();    // true
present.isEmpty();      // false (Java 11+)

// Retrieval
present.get();                          // throws NoSuchElementException if empty
present.orElse("default");             // return default if empty
present.orElseGet(() -> computeDefault()); // lazy default
present.orElseThrow();                 // throws if empty (Java 10+)
present.orElseThrow(IllegalStateException::new);

// Transforming
Optional<Integer> length = present.map(String::length);
Optional<String> upper = present.filter(s -> s.length() > 3).map(String::toUpperCase);
Optional<Integer> flatMapped = present.flatMap(s ->
    s.isEmpty() ? Optional.empty() : Optional.of(s.length()));

// Side effects
present.ifPresent(System.out::println);
present.ifPresentOrElse(                // Java 9+
    System.out::println,
    () -> System.out.println("empty"));

// Chaining
Optional<String> fallback = empty.or(() -> Optional.of("fallback")); // Java 9+

// Stream
optional.stream().collect(Collectors.toList()); // 0 or 1 element

Lambda & Method References

Lambda Syntax

// No parameters
Runnable r = () -> System.out.println("Hello");

// One parameter (parens optional)
Consumer<String> print = s -> System.out.println(s);

// Multiple parameters
BiFunction<Integer, Integer, Integer> add = (a, b) -> a + b;

// Block body
Function<Integer, String> classify = n -> {
    if (n < 0) return "negative";
    if (n == 0) return "zero";
    return "positive";
};

Four Types of Method References

// 1. Static method reference: ClassName::staticMethod
Function<String, Integer> parseInt = Integer::parseInt;

// 2. Instance method of a particular instance: instance::instanceMethod
String prefix = "Hello, ";
Function<String, String> greet = prefix::concat;

// 3. Instance method of an arbitrary instance of a type: ClassName::instanceMethod
Function<String, String> toUpper = String::toUpperCase;
Comparator<String> compare = String::compareTo;

// 4. Constructor reference: ClassName::new
Supplier<ArrayList<String>> listFactory = ArrayList::new;
Function<Integer, int[]> arrayFactory = int[]::new;

Runnable vs Callable

// Runnable — no return, no checked exception
Runnable task = () -> System.out.println("Task: " + Thread.currentThread().getName());
Thread t = new Thread(task);
t.start();

// Callable — returns result, can throw checked exception
Callable<Integer> computation = () -> {
    Thread.sleep(100);
    return 42;
};

ExecutorService

// Fixed thread pool
ExecutorService executor = Executors.newFixedThreadPool(4);

// Cached thread pool — grows as needed, reuses idle threads
ExecutorService cached = Executors.newCachedThreadPool();

// Single thread executor — sequential execution
ExecutorService single = Executors.newSingleThreadExecutor();

// Scheduled executor
ScheduledExecutorService scheduled = Executors.newScheduledThreadPool(2);
scheduled.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);

// Submit tasks
Future<Integer> future = executor.submit(computation);
Integer result = future.get(); // blocks until done
future.get(5, TimeUnit.SECONDS); // with timeout

// Proper shutdown
executor.shutdown(); // graceful, waits for tasks
executor.shutdownNow(); // interrupts running tasks
executor.awaitTermination(60, TimeUnit.SECONDS);

CompletableFuture

// Basic async
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> {
    // runs on ForkJoinPool.commonPool()
    return "Hello";
});

// Chaining — thenApply (sync transform), thenApplyAsync (async transform)
CompletableFuture<Integer> length = cf.thenApply(String::length);

// thenCompose — flatMap, chain dependent futures
CompletableFuture<String> result = cf.thenCompose(s ->
    CompletableFuture.supplyAsync(() -> s + " World"));

// thenCombine — combine two independent futures
CompletableFuture<String> first = CompletableFuture.supplyAsync(() -> "Hello");
CompletableFuture<String> second = CompletableFuture.supplyAsync(() -> " World");
CompletableFuture<String> combined = first.thenCombine(second, (a, b) -> a + b);

// allOf — wait for all
CompletableFuture<Void> all = CompletableFuture.allOf(first, second);
all.join(); // wait

// anyOf — first to complete
CompletableFuture<Object> any = CompletableFuture.anyOf(first, second);

// Error handling
CompletableFuture<String> safe = cf
    .exceptionally(ex -> "default on error")
    .handle((value, ex) -> ex != null ? "error" : value); // handle both

// thenAccept (consume result), thenRun (run after, no result)
cf.thenAccept(System.out::println);
cf.thenRun(() -> System.out.println("Done"));

// Timeout (Java 9+)
cf.orTimeout(5, TimeUnit.SECONDS);
cf.completeOnTimeout("default", 5, TimeUnit.SECONDS);

Thread vt = Thread.ofVirtual().start(() -> System.out.println("Virtual!"));

Synchronization

synchronized, volatile, Atomic

// synchronized method
public synchronized void increment() { count++; }

// synchronized block (finer granularity)
public void add(int value) {
    synchronized(this) { total += value; }
}

// Class-level lock
public static synchronized void staticMethod() { ... }

// volatile — visibility guarantee, no atomicity
private volatile boolean flag = false;

// Atomic classes — lock-free thread safety
AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet();
ai.compareAndSet(expected, update);
ai.getAndAdd(5);

AtomicReference<String> ar = new AtomicReference<>("initial");
ar.compareAndSet("initial", "updated");

// LongAdder — high-throughput counter

java.util.concurrent.locks

// ReentrantLock — explicit lock with tryLock, fairness
ReentrantLock lock = new ReentrantLock(true); // fair lock
lock.lock();
try {
    // critical section
} finally {
    lock.unlock(); // always unlock in finally
}

// tryLock — non-blocking attempt
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try { /* ... */ } finally { lock.unlock(); }
}

// ReadWriteLock — multiple readers OR one writer
ReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();
try { /* read */ } finally { rwLock.readLock().unlock(); }
rwLock.writeLock().lock();
try { /* write */ } finally { rwLock.writeLock().unlock(); }

// StampedLock — optimistic reads (Java 8+)
StampedLock sl = new StampedLock();
long stamp = sl.tryOptimisticRead();
// read data...
if (!sl.validate(stamp)) {
    stamp = sl.readLock();
    try { /* re-read */ } finally { sl.unlockRead(stamp); }
}

Coordination Primitives

// CountDownLatch — wait for N events
CountDownLatch latch = new CountDownLatch(3);
// worker threads call: latch.countDown()
latch.await(); // main thread waits until count = 0

// CyclicBarrier — all threads meet at a barrier (reusable)
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("All arrived!"));
barrier.await(); // each thread calls this; releases when all arrive

// Semaphore — control concurrent access
Semaphore sem = new Semaphore(5); // allow 5 concurrent
sem.acquire();
try { /* access resource */ } finally { sem.release(); }

// Phaser — flexible multi-phase synchronization (Java 7+)
Phaser phaser = new Phaser(3); // 3 parties
phaser.arriveAndAwaitAdvance(); // sync at phase boundary
phaser.arriveAndDeregister();   // done participating

G1GC — How It Works

Divides heap into equal-sized regions (~1-32MB each). Regions can be Eden, Survivor, Old, Humongous. G1 tracks liveness per region and collects highest-garbage regions first (hence "Garbage First"). Uses concurrent marking to identify live objects while app runs. Young GC evacuates Eden/Survivor regions (STW). Mixed GC also collects some Old regions.

ZGC — How It Works

Fully concurrent GC. Uses colored pointers (load barriers) to track object state. Almost all work happens concurrently with application threads. Only a few short STW pauses for root scanning. Supports heap sizes from 8MB to 16TB.

JVM Internals

Class Loading

Class loading is hierarchical using the parent delegation model:

  1. Bootstrap ClassLoader — loads java.lang.*, core JDK classes from rt.jar / modules
  2. Extension/Platform ClassLoader — loads java.ext.dirs
  3. Application ClassLoader — loads classpath classes

Each loader asks its parent first. Custom loaders (e.g., OSGi, Spring DevTools) can override this for hot-reloading or isolation.

JIT Compilation

HotSpot uses a tiered compilation model:

  • Tier 0 — Interpreter
  • Tier 1 — C1 (client compiler) — simple profiling
  • Tier 2 — C1 with method invocation & backedge counters
  • Tier 3 — C1 with full profiling
  • Tier 4 — C2 (server compiler) — aggressive optimizations

C2 performs: inlining, escape analysis, loop unrolling, dead code elimination, lock elision.

Interview Q&A

What is the difference between JVM, JRE, and JDK? Easy

JVM (Java Virtual Machine) is the runtime engine that executes Java bytecode. It is platform-specific but provides platform independence for Java programs through an abstraction layer.

JRE (Java Runtime Environment) = JVM + standard libraries. Everything needed to run a Java application.

JDK (Java Development Kit) = JRE + development tools (javac compiler, javadoc, jdb debugger, jar, etc.). Everything needed to develop Java applications.

Since Java 11, JDK and JRE are unified — there is no separate JRE download. You use the JDK to run applications too.

Explain the difference between == and equals() in Java. Easy

== compares references for objects (checks if both variables point to the same object in memory). For primitives, it compares values.

equals() compares content/value. The default Object.equals() uses ==, but classes like String, Integer, List override it for logical equality.

String a = new String("hello");
String b = new String("hello");
a == b;       // false — different objects
a.equals(b);  // true — same content

Integer x = 127;
Integer y = 127;
x == y;       // true — Integer cache [-128, 127]

Integer p = 128;
Integer q = 128;
p == q;       // false — outside cache
p.equals(q);  // true

Always override hashCode() when you override equals() — the contract: equal objects must have equal hash codes.

What is the difference between HashMap and ConcurrentHashMap? Easy

HashMap: Not thread-safe. Allows one null key and multiple null values. Better single-threaded performance.

ConcurrentHashMap: Thread-safe. No null keys or values. In Java 8+, uses CAS + synchronized on individual bins (not the whole map), allowing concurrent reads and partial-lock writes. Much better than Hashtable (which locks the whole map).

Use ConcurrentHashMap when multiple threads read/write; otherwise HashMap in single-threaded code.

How does HashMap work internally? Intermediate

HashMap uses an array of buckets (array of Node). On put(key, value):

  1. Compute hashCode() of key, then spread it with a secondary hash
  2. Compute bucket index: (n-1) & hash
  3. If bucket empty: insert new Node
  4. If collision: traverse linked list in bucket, compare via equals()
    • Key found: update value
    • Key not found: append to list
  5. If linked list length ≥ 8 and table size ≥ 64: convert to TreeMap (red-black tree) — O(log n) lookup

Default initial capacity: 16, load factor: 0.75. When size > capacity * loadFactor, rehash doubles the array.

Java 8 improvement: tree bins reduce worst-case from O(n) to O(log n) for bad hash functions.

Explain volatile vs synchronized in Java. Intermediate

volatile: guarantees visibility — changes to a volatile variable are immediately visible to all threads (no CPU cache). Does NOT guarantee atomicity (volatile++ is still read-modify-write).

synchronized: guarantees both visibility and atomicity. Only one thread can execute the synchronized block at a time. Higher overhead than volatile.

// volatile — fine for a simple flag read by one thread, written by another
private volatile boolean running = true;

// synchronized — needed for compound operations
private int count = 0;
public synchronized void increment() { count++; } // safe

Use volatile for simple state flags. Use synchronized (or AtomicXxx) for compound actions like increment.

What is the difference between Comparable and Comparator? Intermediate

Comparable (java.lang): natural ordering. The class itself implements compareTo(T other). Modifies the class. Used by Collections.sort() and sorted data structures by default.

Comparator (java.util): external/custom ordering. A separate object. Does not modify the original class. Can have multiple Comparators for different sort orders.

// Comparable — class defines its natural order
class Student implements Comparable<Student> {
    int gpa;
    @Override public int compareTo(Student other) {
        return Double.compare(this.gpa, other.gpa);
    }
}

// Comparator — external, multiple orderings possible
Comparator<Student> byName = Comparator.comparing(s -> s.name);
Comparator<Student> byGpaThenName = Comparator.comparingDouble((Student s) -> s.gpa)
    .thenComparing(s -> s.name);
Explain Java's Stream API and when to use parallel streams. Intermediate

Streams provide a functional, declarative way to process collections. Pipeline: source → intermediate ops (lazy, stateless/stateful) → terminal op (triggers evaluation).

parallel() splits the stream across ForkJoinPool.commonPool() threads using the Spliterator interface. Beneficial when:

  • Large data (thousands+ elements)
  • Operations are CPU-bound and independent (no shared mutable state)
  • No ordering requirements (or acceptable to ignore)

Avoid parallel streams when: data source is small, operations are I/O-bound (use virtual threads instead), operations are stateful/order-dependent, there is shared mutable state (race conditions).

long sum = LongStream.rangeClosed(1, 1_000_000)
    .parallel()
    .sum(); // good candidate — independent, CPU, large
What is the difference between checked and unchecked exceptions? Intermediate

Checked exceptions: subclasses of Exception (excluding RuntimeException). Must be either caught or declared with throws. Represent recoverable conditions (e.g., IOException, SQLException). The compiler enforces handling.

Unchecked exceptions: subclasses of RuntimeException (or Error). Do not need to be declared or caught (but can be). Represent programming errors (NullPointerException, IllegalArgumentException) or unrecoverable JVM errors (OutOfMemoryError).

Modern practice (especially in frameworks like Spring) favors unchecked exceptions to avoid cluttering APIs with checked exception declarations. Wrap checked exceptions in unchecked when they cannot be meaningfully handled at the call site.

Explain how the Java Memory Model relates to happens-before. Advanced

The Java Memory Model (JMM) defines how threads interact through memory. The happens-before relationship guarantees that if action A happens-before action B, then all memory writes by A are visible to B.

Key happens-before rules:

  • Program order: each action in a thread happens-before subsequent actions in the same thread
  • Monitor lock: unlock happens-before subsequent lock of the same monitor
  • volatile write: a write to a volatile field happens-before subsequent reads of that field
  • Thread start: Thread.start() happens-before any action in the started thread
  • Thread join: all actions in a thread happen-before Thread.join() returns

Without happens-before, the JIT/CPU can reorder instructions, leading to visibility issues. volatile and synchronized establish these relationships.

Explain G1GC internals and when to tune it. Advanced

G1 divides the heap into equal-sized regions (1-32MB). Regions are dynamically assigned to Eden, Survivor, Old, or Humongous (objects > half region size).

Cycle: Young-only phase (minor GC on Eden/Survivor) → Concurrent marking (SATB — snapshot-at-the-beginning) → Space reclaimation (mixed GC — collects young + most-garbage old regions).

Key tuning:

  • -XX:MaxGCPauseMillis=200 — soft pause target. G1 adjusts young gen size to meet it
  • -XX:G1HeapRegionSize — usually let JVM auto-tune; override for very large objects
  • -XX:G1ReservePercent — headroom for evacuation failures
  • -XX:ConcGCThreads — threads for concurrent marking
  • If too many Full GCs: increase heap, tune InitiatingHeapOccupancyPercent
How do Virtual Threads differ from platform threads, and what are their limitations? Advanced

Platform threads map 1:1 to OS threads. Creating thousands is expensive (1MB stack each, OS scheduling overhead).

Virtual threads are lightweight JVM-managed threads. Many virtual threads are multiplexed onto a small pool of carrier (OS) threads. When a virtual thread blocks on I/O, it unmounts from its carrier thread (carrier thread is freed to run other virtual threads). When unblocked, it mounts again on any available carrier thread.

Limitations:

  • Pinning: virtual thread cannot unmount when inside a synchronized block or native method — the carrier thread is pinned. Use ReentrantLock instead of synchronized in virtual-thread-heavy code
  • CPU-bound work: virtual threads don't help — they still need a carrier. Use parallel streams or ForkJoinPool for CPU parallelism
  • ThreadLocal: not an issue for correctness but consider Scoped Values (JEP 446) for cleaner alternatives

Best use: high-concurrency, I/O-bound applications (web servers, database-driven services). Replaces reactive programming boilerplate in many cases.

Explain the SOLID principles with Java examples. Advanced

S — Single Responsibility: A class should have one reason to change. Separate UserRepository (persistence) from UserService (business logic) from UserController (HTTP).

O — Open/Closed: Open for extension, closed for modification. Add new payment methods by implementing PaymentProcessor interface, not modifying existing code.

L — Liskov Substitution: Subtypes must be substitutable for their base types. If a method accepts Shape, passing a Circle or Rectangle must work correctly.

I — Interface Segregation: Clients shouldn't depend on interfaces they don't use. Split a fat interface into ReadableRepository and WritableRepository.

D — Dependency Inversion: Depend on abstractions, not concretions. UserService should depend on UserRepository interface, not JpaUserRepository directly. Enables testing with mocks.

What is type erasure and what are its practical implications? Advanced

Type erasure means generic type parameters are erased at compile time. List<String> becomes List in bytecode. This preserves backward compatibility with pre-Java-5 code.

Implications:

  • Cannot instantiate generic type: new T() illegal — use factory/Supplier<T> instead
  • Cannot use instanceof: obj instanceof List<String> illegal
  • Cannot create generic arrays: new T[10] illegal
  • Cannot catch generic exception types
  • At runtime, all generic types are raw types — heap pollution possible with unchecked casts

Workaround: pass Class<T> type as a token, use TypeToken/ParameterizedType for reflection, use @SuppressWarnings("unchecked") carefully.

Explain StampedLock and its advantages over ReadWriteLock. Very Advanced

StampedLock (Java 8) provides three locking modes:

  1. Writing: exclusive, returns stamp
  2. Reading: non-exclusive shared, returns stamp
  3. Optimistic Reading: does NOT acquire a lock — just checks if a write has occurred since

Optimistic read is the key advantage: if no write happened, no lock overhead at all. Pattern:

StampedLock lock = new StampedLock();
double x, y; // shared state

double distanceFromOrigin() {
    long stamp = lock.tryOptimisticRead();
    double curX = x, curY = y;            // read without lock
    if (!lock.validate(stamp)) {          // check for concurrent write
        stamp = lock.readLock();          // fall back to real read lock
        try { curX = x; curY = y; }
        finally { lock.unlockRead(stamp); }
    }
    return Math.sqrt(curX * curX + curY * curY);
}

Advantages over ReadWriteLock: avoids lock overhead in the common case (no writes). Disadvantage: not reentrant (unlike ReentrantReadWriteLock), more complex API, can cause liveness issues if misused.

How does JIT compilation work with tiered compilation? Very Advanced

HotSpot uses tiered compilation (Java 7+, default in Java 8+):

  • Tier 0 — Interpreter: initial execution, collects method invocation counts and backedge counts (loops)
  • Tier 1 — C1 simple: fast compilation, no profiling code; used for rarely-called code
  • Tier 2 — C1 limited: with invocation and backedge counters
  • Tier 3 — C1 full: full profiling (type profiles, branch profiles)
  • Tier 4 — C2: profile-guided, aggressive optimizations — inlining, escape analysis (stack allocation), loop unrolling, dead code elimination, lock elision, devirtualization

A method starts at Tier 0. Heavily used methods ("hot") get promoted to C1 quickly for fast compilation, then to C2 for maximum optimization. C2 uses profiling data to make speculative optimizations (with deoptimization traps if assumptions are violated — e.g., if a virtual call site becomes polymorphic).

AOT (GraalVM Native Image) compiles ahead-of-time, eliminating JIT warmup at the cost of peak throughput and dynamic features.

Explain Spring Boot auto-configuration mechanism in detail. Very Advanced

Auto-configuration is driven by @EnableAutoConfiguration (included in @SpringBootApplication).

Mechanism:

  1. At startup, Spring Boot reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Spring Boot 2.7+) or spring.factories
  2. These files list hundreds of @AutoConfiguration classes (e.g., DataSourceAutoConfiguration)
  3. Each auto-configuration class uses @Conditional annotations to decide whether to apply:
    • @ConditionalOnClass: only if a class is on the classpath
    • @ConditionalOnMissingBean: only if no bean of that type already defined
    • @ConditionalOnProperty: only if a property has a specific value
    • @ConditionalOnWebApplication: only in web context
  4. If conditions pass, beans are registered

Example: if spring-boot-starter-data-jpa is on classpath, HibernateJpaAutoConfiguration fires, sees DataSource bean, creates EntityManagerFactory, TransactionManager, etc. — but only if you haven't defined your own.

Debug with: --debug flag or logging.level.org.springframework.boot.autoconfigure=DEBUG to see the conditions report.
