Apache Kafka: Architecture, Producers, Consumers, Streams & Connect

Why Kafka?

SystemDescriptionLimitations
Traditional Queue (RabbitMQ, SQS)Once consumed, message is deleted. Push model. No replay.Cannot replay events; single consumer per message; no long-term retention
Pub/Sub (Redis Pub/Sub, SNS)Fan-out to all subscribers. Fire and forget.No persistence; messages lost if consumer offline; no consumer groups
KafkaDistributed commit log. Messages retained for configurable period. Multiple independent consumer groups each at their own offset.Higher operational complexity; not ideal for tiny messages <1ms latency needs

Kafka Key Advantages

  • Durability + Replay: Messages written to disk and replicated. Re-read from any past offset.
  • High Throughput: Sequential disk I/O + zero-copy (sendfile syscall) + batching = millions of msgs/sec.
  • Decoupling: Producers and consumers are independent. Multiple consumer groups read independently.
  • Ordering: Guaranteed ordering within a partition.
  • Scalability: Horizontal scaling via partitions.
  • Stream Processing: Kafka Streams for stateful real-time processing without separate infrastructure.

Core Concepts

ConceptDescription
BrokerKafka server process. Manages topic partitions assigned to it. Handles producer/consumer connections.
TopicLogical channel/category for messages. Split into N partitions.
PartitionOrdered, immutable sequence of records. Basic unit of parallelism and replication. Stored as segment log files on disk.
OffsetMonotonically increasing integer identifying a record's position within a partition. Consumers track their offset.
Consumer GroupSet of consumers cooperating to consume a topic. Each partition assigned to exactly one consumer in the group. Multiple groups consume independently.
RecordKey + Value (bytes) + Timestamp + Headers. Key used for partitioner (null → round-robin/sticky).

ZooKeeper Role vs KRaft Mode

ZooKeeper (Legacy — Pre-Kafka 3.0)

ZooKeeper stored cluster metadata: broker list, topic configurations, partition assignments, controller election, consumer group offsets (moved to Kafka itself in 0.9). Limitations: separate system to operate, ZooKeeper bottleneck for large clusters (thousands of partitions), controller failover time >30s, separate security model.

KRaft Mode (Kafka Raft — Kafka 2.8+)

Replaces ZooKeeper with a built-in Raft-based consensus mechanism. A subset of brokers act as "controllers" (quorum of 3 or 5). Metadata stored in a dedicated internal Kafka topic (@metadata). Controller leader manages all metadata changes; other controllers follow via Raft log replication.

Topic Partitioning

Partitions are the mechanism for both parallelism and ordering. More partitions = more parallelism for consumers, but also more overhead (file handles, replication traffic, leader election work).

Ordering Guarantee: Kafka guarantees ordering ONLY within a partition. If you need messages for customer-42 to be processed in order, use customer_id as the record key — the default partitioner hashes the key to always route to the same partition. 
# Create topic with 6 partitions, replication factor 3
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 6 --replication-factor 3

# Describe topic (see partition → leader → ISR mapping)
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# Increase partitions (cannot decrease)
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 12

Partition Count Guidelines

  • More partitions = higher parallelism but: more open file handles on brokers, longer leader election time, higher replication overhead.
  • Start with: max(target throughput / producer throughput per partition, target throughput / consumer throughput per partition).
  • Practical starting point: 3 × number of brokers. Increase if throughput demands it.
  • Each consumer in a group handles at most 1 partition; consumer count > partition count = idle consumers.

Replication & ISR

Each partition has one leader and N-1 followers. The leader handles all reads and writes. Followers pull (not push) records from the leader.

ISR (In-Sync Replicas)

ISR = set of replicas that are caught up with the leader (within replica.lag.time.max.ms, default 30s). If a follower falls too far behind, it's removed from ISR. A message is committed (visible to consumers) when written to all ISR replicas (with acks=all).

# Check ISR status
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
# Output example:
# Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# If ISR shrinks: Isr: 1,3  → broker 2 fell behind

Unclean Leader Election

If all ISR replicas are down, Kafka can elect an out-of-sync replica as new leader (unclean.leader.election.enable=true — default false). Risk: data loss (uncommitted messages on failed leader are lost). Set to false for durability; accept potential unavailability.

min.insync.replicas

# Require at least 2 in-sync replicas to acknowledge writes
min.insync.replicas=2
# Combined with acks=all: producer gets error if ISR < 2
# Typical production: replication.factor=3, min.insync.replicas=2, acks=all

props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// Transactional producer (exactly-once across topics/partitions)
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-service-txn-1");
producer.initTransactions();
try {
  producer.beginTransaction();
  producer.send(new ProducerRecord<>("orders", orderId, orderJson));
  producer.send(new ProducerRecord<>("inventory", productId, reservationJson));
  producer.commitTransaction();
} catch (Exception e) {
  producer.abortTransaction();
}

Producer Batching & Compression

// Batching configuration
props.put(ProducerConfig.BATCH_SIZE_CONFIG, 32768);       // 32KB batch size (default 16KB)
props.put(ProducerConfig.LINGER_MS_CONFIG, 5);             // wait up to 5ms to fill batch
props.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 33554432);  // 32MB send buffer

// Compression (per-batch)
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4"); // options: gzip, snappy, lz4, zstd
// lz4: best balance of speed + ratio; recommended for most workloads
// zstd: best compression ratio; more CPU; good for bandwidth-constrained links
// gzip: highest ratio, highest CPU; good for archival
// snappy: fast decompression; less CPU than gzip

Batching Mechanics

Kafka producer groups records for the same partition into a batch. batch.size controls the maximum batch size in bytes. linger.ms adds a deliberate delay to allow the batch to fill up — higher linger = more records per batch = better compression + throughput, but more latency. For high-throughput use cases: increase both to 64KB + 20ms. For low-latency: set linger.ms=0.

// Custom partitioner
public class PriorityPartitioner implements Partitioner {
  @Override
  public int partition(String topic, Object key, byte[] keyBytes,
                       Object value, byte[] valueBytes, Cluster cluster) {
    int numPartitions = cluster.partitionCountForTopic(topic);
    // Route VIP orders to partition 0; others distributed
    if (key != null && key.toString().startsWith("VIP")) {
      return 0;
    }
    return Utils.toPositive(Utils.murmur2(keyBytes)) % (numPartitions - 1) + 1;
  }
}

Offset Management

// Auto-commit (at-least-once by default, but can lose messages)
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, true);
props.put(ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG, 5000); // every 5s

// Manual commit — synchronous (blocks until broker ACKs commit)
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

while (true) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
  for (ConsumerRecord<String, String> record : records) {
    processRecord(record); // if this throws, offset not committed
  }
  consumer.commitSync(); // commit after all records processed
}

// Manual async commit (non-blocking, fire-and-forget per batch)
consumer.commitAsync((offsets, exception) -> {
  if (exception != null) log.error("Commit failed", exception);
});

// Commit specific offsets (partition-level control)
Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
offsets.put(new TopicPartition("orders", 0), new OffsetAndMetadata(offset + 1));
consumer.commitSync(offsets);

SemanticHow AchievedRisk

// EXACTLY_ONCE_V2 (Kafka 2.5+): epoch-based fencing, more efficient than EXACTLY_ONCE

consumer.poll(...)
// Process record and produce result
producer.beginTransaction();
producer.send(resultRecord);
// Include consumer offset in transaction so they commit atomically

    Collections.singletonMap(partition, new OffsetAndMetadata(offset + 1)),
    new ConsumerGroupMetadata(groupId)

Consumer Rebalance

Eager Rebalance (Old Protocol)

All consumers revoke ALL their partitions simultaneously → all consumers pause processing → Group Coordinator reassigns → consumers resume. Creates a "stop the world" gap. Bad for high-throughput or stateful consumers.

Cooperative Incremental Rebalance (Kafka 2.4+)

Only partitions that actually need to move are revoked. Other partitions continue processing without interruption. Multiple rounds of rebalance may occur, but each is incremental. No stop-the-world gap. Enabled via CooperativeStickyAssignor.

# Rebalance timing config
session.timeout.ms=45000         # Consumer considered dead after 45s of no heartbeat
heartbeat.interval.ms=3000       # Send heartbeat every 3s (must be < session.timeout.ms / 3)
max.poll.interval.ms=300000      # Max time between polls before consumer considered dead
# If processing takes > max.poll.interval.ms → consumer ejected from group → rebalance

Consumer Performance Tuning

max.poll.records=500                # Records fetched per poll() call
fetch.min.bytes=1048576             # Wait for 1MB of data before returning (reduces CPU, increases latency)
fetch.max.wait.ms=500               # Max time to wait for fetch.min.bytes
fetch.max.bytes=52428800            # Max data per fetch request (50MB)
max.partition.fetch.bytes=1048576   # Max data per partition per fetch (1MB)

Kafka Streams

Kafka Streams is a Java library for building stateful stream processing applications. It reads from Kafka topics, processes records, and writes results back to Kafka. No separate cluster needed — runs within your application process.

KStream vs KTable vs GlobalKTable

AbstractionRepresentsAnalogy
KStreamUnbounded sequence of events — each record is a new eventAppend-only log / event log
KTableChangelog stream — each record represents the latest state for a key (upsert semantics)Database table (partitioned, one partition per shard)
GlobalKTableLike KTable but fully replicated to every instance. All partitions available on every node.Reference table / lookup table

Stateless Operations

StreamsBuilder builder = new StreamsBuilder();

KStream<String, Order> orders = builder.stream("orders",
    Consumed.with(Serdes.String(), orderSerde));

// filter — keep only completed orders
KStream<String, Order> completed = orders
    .filter((key, value) -> value.getStatus().equals("COMPLETED"));

// map — transform key or value
KStream<String, Double> amounts = orders
    .mapValues(order -> order.getTotal());

// flatMap — one record → multiple records
KStream<String, OrderItem> lineItems = orders
    .flatMapValues(order -> order.getItems());

// selectKey — change the key (causes re-partitioning if chained with stateful ops)
KStream<String, Order> byCustomer = orders
    .selectKey((orderId, order) -> order.getCustomerId());

// branch — split stream into multiple streams
Map<String, KStream<String, Order>> branches = orders
    .split(Named.as("by-status-"))
    .branch((k, v) -> "VIP".equals(v.getTier()), Branched.as("vip"))
    .branch((k, v) -> true,                       Branched.as("regular"))
    .noDefaultBranch();

Stateful Operations

// groupBy + count
orders.groupByKey()
    .count(Materialized.as("order-count-store"))
    .toStream()
    .to("order-counts");

// aggregate — running total per customer
orders.groupBy((key, value) -> value.getCustomerId(),
               Grouped.with(Serdes.String(), orderSerde))
    .aggregate(
        () -> 0.0,  // initializer
        (customerId, order, total) -> total + order.getTotal(),  // aggregator
        Materialized.<String, Double, KeyValueStore<Bytes, byte[]>>as("customer-totals")
            .withKeySerde(Serdes.String())
            .withValueSerde(Serdes.Double())
    );

// reduce
orders.groupByKey()
    .reduce((v1, v2) -> v2.getTimestamp() > v1.getTimestamp() ? v2 : v1,
            Materialized.as("latest-order-store"));

Joins & Windowing

// Stream-Table Join (enrich stream with reference data)
KStream<String, Order> orders = ...;
KTable<String, Customer> customers = builder.table("customers");

KStream<String, EnrichedOrder> enriched = orders.join(
    customers,
    (order, customer) -> new EnrichedOrder(order, customer.getName())
);

// Stream-Stream Join (correlate events within a time window)
KStream<String, Click> clicks = builder.stream("clicks");
KStream<String, Purchase> purchases = builder.stream("purchases");

KStream<String, ClickPurchase> attributed = clicks.join(
    purchases,
    (click, purchase) -> new ClickPurchase(click, purchase),
    JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(10))
);

// Table-Table Join (full join of two changelog streams)
KTable<String, OrderDetail> orderDetails = ...;
KTable<String, ShipInfo> shipments = ...;
KTable<String, FullOrder> fullOrders = orderDetails.join(shipments,
    (detail, ship) -> new FullOrder(detail, ship));

orders.groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
    .count()
    .toStream()
    .map((windowedKey, count) -> KeyValue.pair(windowedKey.key(), count))
    .to("order-count-per-minute");

// Session window

    .windowedBy(SessionWindows.ofInactivityGapWithNoGrace(Duration.ofMinutes(30)))
    .count()
    .toStream()
    .to("user-sessions");

Exactly-Once Semantics (EOS)

EOS ensures each message is processed exactly once end-to-end — no duplicates, no loss — using a combination of idempotent producers, transactions, and consumer offset commits inside the transaction.

// Full EOS read-process-write loop
Properties consumerProps = new Properties();
consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed"); // only read committed messages

Properties producerProps = new Properties();
producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "txn-producer-1");
producerProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

KafkaProducer<String, String> producer = new KafkaProducer<>(producerProps);
producer.initTransactions();

while (true) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
  producer.beginTransaction();
  try {
    for (ConsumerRecord<String, String> record : records) {
      String result = processRecord(record.value());
      producer.send(new ProducerRecord<>("output-topic", record.key(), result));
    }
    // Commit consumer offsets AS PART OF the transaction
    Map<TopicPartition, OffsetAndMetadata> offsets = currentOffsets(records);
    producer.sendOffsetsToTransaction(offsets, new ConsumerGroupMetadata(GROUP_ID));
    producer.commitTransaction(); // consumer offset + output records commit atomically
  } catch (Exception e) {
    producer.abortTransaction(); // roll back both output records AND offset commit
  }
}

Interview Q&As — 20+ Questions

Q1. Why is ordering guaranteed only within a partition and not across partitions? Easy

Kafka partitions are independent, ordered logs. Within a partition, records have monotonically increasing offsets and consumers read them sequentially in order. Across partitions, there is no coordination of offsets — different partitions may be on different brokers, consumed at different rates by different consumers in a group. Therefore, if message A goes to partition 0 and message B goes to partition 1, there is no guarantee A is consumed before B. To guarantee ordering for a logical entity (e.g., all events for user-42), always use a consistent key (e.g., the user ID) — the partitioner hashes the key to always route to the same partition, ensuring ordered delivery for that key.

Q2. What is an ISR and why does it matter for producer acks=all? Intermediate

ISR (In-Sync Replicas) is the set of partition replicas that are fully caught up with the leader. A follower is "in sync" if it hasn't fallen more than replica.lag.time.max.ms (default 30s) behind the leader. With acks=all, the producer waits for acknowledgment from ALL ISR members — not necessarily all replicas, just those in the ISR. Combined with min.insync.replicas=2, Kafka requires at least 2 ISR replicas to accept a write. If ISR shrinks to 1 (e.g., one replica is down), the write is rejected, protecting durability. This is the recommended production configuration: RF=3, min.insync.replicas=2, acks=all.

Q3. Explain the difference between at-least-once and exactly-once semantics. Intermediate

At-least-once: Commit consumer offsets only AFTER processing. If the consumer crashes between processing and committing, it restarts from the previous offset and reprocesses — causing duplicates. The processing is idempotent at the application level (e.g., upsert by primary key). Exactly-once: Uses Kafka transactions to atomically write output records AND commit input offsets in a single transaction. If the transaction commits, both succeed; if it aborts, both are rolled back. Kafka Streams achieves this with processing.guarantee=EXACTLY_ONCE_V2. For manual EOS: use producer.sendOffsetsToTransaction() to include consumer offsets in the producer transaction. Cost: ~30% throughput reduction due to transaction protocol overhead.

Q4. What happens during a consumer rebalance? What is cooperative rebalancing? Intermediate

A rebalance is triggered when consumers join/leave a group or new partitions are added to a topic. Eager rebalance (old): All consumers revoke all partitions; stop processing; group coordinator reassigns partitions; consumers resume. Stop-the-world gap, especially harmful for stateful apps. Cooperative incremental rebalance (Kafka 2.4+, CooperativeStickyAssignor): Only partitions that need to move are revoked in each round. Other partitions continue processing. Multiple small rounds converge to the final assignment. No pause for consumers that keep their partitions. This dramatically reduces rebalance disruption and is strongly recommended for production Kafka Streams and consumer applications.

Q5. What is KRaft mode and why was ZooKeeper removed? Intermediate

KRaft (Kafka Raft) is Kafka's built-in consensus mechanism replacing ZooKeeper for metadata management. Problems with ZooKeeper: (1) Separate system to install, operate, secure, and monitor; (2) ZooKeeper becomes a bottleneck for clusters with 200K+ partitions; (3) Controller failover takes 30-60 seconds (ZooKeeper session expiry); (4) Metadata is split between ZooKeeper and Kafka, complicating consistency. KRaft benefits: (1) No external dependency; (2) <1 second controller failover; (3) Supports millions of partitions; (4) Single metadata store; (5) Faster startup. KRaft became GA in Kafka 3.3, ZooKeeper was fully removed in Kafka 4.0.

Q6. How does Kafka achieve high throughput via sequential I/O and zero-copy? Advanced

Sequential I/O: Kafka writes messages to append-only log segments on disk. Sequential disk writes are 10-100x faster than random I/O (even on SSDs). The OS page cache aggressively prefetches sequential reads. Kafka exploits this — consumers reading near the head of the log often serve from page cache, not disk. Zero-copy (sendfile): When a consumer fetches data, the OS copies data from disk to page cache, then from page cache to the network socket using the sendfile syscall — without copying to user-space memory. This eliminates 2 of the 4 data copies in a traditional read-then-send, reducing CPU cycles and memory bandwidth. Combined with batching and compression, Kafka achieves 100MB/s+ per broker.

Q7. When would you use Kafka Streams vs an external stream processor like Flink? Advanced

Kafka Streams: No separate cluster; runs as a library inside your app; auto-scales with Kubernetes/deployments; integrates tightly with Kafka; excellent for simple-to-moderate stateful processing (aggregations, joins, enrichments); RocksDB for local state. Limited by Java-only API, partition count determines parallelism ceiling, stateful operations per topic partition.

Apache Flink: Separate cluster; richer processing model (event time with watermarks, complex windowing, CEP patterns); exactly-once checkpointing with incremental state snapshots; language support (Java, Scala, Python SQL); handles larger state (remote state backends); better for complex pipelines requiring flexible graph topology, massive parallelism independent of Kafka partitions, or non-Kafka sources. Choose Kafka Streams for microservices-embedded, Kafka-only pipelines. Choose Flink for complex analytics, multiple source systems, or independent scaling of compute.

Q8. Explain how consumer group offset management works. What happens on restart? Intermediate

Consumer groups commit offsets to the __consumer_offsets internal Kafka topic (key: groupId+topic+partition, value: offset). On restart: (1) consumer sends JoinGroup request; (2) group coordinator assigns partitions; (3) consumer fetches the committed offset for its assigned partitions; (4) consumer starts reading from that offset. Configuration auto.offset.reset controls behavior when no committed offset exists: latest = start from new messages only; earliest = read all historical messages from offset 0. With enable.auto.commit=true, offsets are committed periodically (every 5s by default) — risk of duplicates (if crash between auto-commit points) or loss (if consumer crashes before first auto-commit). Manual commit + idempotent processing is the standard production pattern.

Q9. What is a KTable and how is it different from a KStream? Intermediate

A KStream treats every record as an independent event appended to the stream. Two records with the same key are two separate events. A KTable treats each record as an upsert — a new record with key K overwrites the previous value for K. It represents the current state (like a database table). Internally, KTable maintains a changelog stream and a materialized state store (RocksDB by default). Operations: if you do KTable.filter(), it emits an update for every key change. KTable.join(KTable) is a materialized join. When to use: KStream for event logs (clicks, orders placed, payments); KTable for current state (account balances, user profiles, inventory levels). A KTable can be created from a topic or derived from a KStream via groupByKey().aggregate().

Q10. What is Debezium CDC and how is it different from a JDBC poll connector? Intermediate

A JDBC poll connector periodically runs queries (SELECT ... WHERE updated_at > last_poll). Limitations: (1) misses hard deletes (no tombstone event); (2) requires an updated_at column; (3) polling interval = minimum latency; (4) increases DB load with frequent queries. Debezium CDC reads the database's binary change log (MySQL binlog, PostgreSQL WAL, MongoDB oplog) at the replication protocol level. It captures every change including deletes, with sub-second latency, and does not increase query load. Debezium events contain the full before/after state of a row. Ideal for replicating tables to Kafka for: event sourcing, search index updates, cache invalidation, cross-service sync, and audit logging.

Q11. How does Kafka Schema Registry prevent deserialization failures? Intermediate

The Schema Registry stores versioned schemas (Avro/Protobuf/JSON Schema). When a producer serializes a message, the serializer: (1) registers the schema (or checks if it exists) with the registry; (2) receives a schema ID; (3) prefixes the serialized message with a 5-byte header: magic byte (0x00) + 4-byte schema ID. When a consumer deserializes: (1) reads the 5-byte header; (2) fetches the writer schema by ID from the registry (cached); (3) deserializes using the writer schema; (4) optionally projects to a reader schema. Compatibility levels (BACKWARD/FORWARD/FULL) prevent breaking schema changes from being registered. This decouples schema evolution from deployment coordination — producers and consumers can be updated independently as long as compatibility rules are respected.

Q12. Explain the idempotent producer. How does it prevent duplicate messages? Advanced

Without idempotence: if the broker receives a message, writes it, but the ACK is lost in the network, the producer retries → duplicate. The idempotent producer assigns each producer a unique Producer ID (PID) and each message a monotonically increasing sequence number per (PID, partition). The broker deduplicates: if it receives a message with a sequence number it has already seen, it discards it and returns a duplicate ACK. This guarantees exactly-once delivery at the producer level within a session (new PID assigned on restart). Enable with enable.idempotence=true — automatically sets acks=all, retries=MAX_INT, and max.in.flight.requests.per.connection=5.

Q13. What is consumer lag and how do you handle consistently growing lag? Intermediate

Consumer lag = LOG_END_OFFSET - CONSUMER_CURRENT_OFFSET per partition. It represents how far behind a consumer group is from the latest messages. Consistently growing lag means consumption rate < production rate — the consumer cannot keep up. Remedies: (1) Add more partitions to the topic and scale up consumer instances (up to partition count). (2) Optimize processing: reduce per-record processing time (async I/O, batching, parallel processing within consumer). (3) Increase max.poll.records and process in batch. (4) Scale consumer group horizontally — one consumer per partition max. (5) Separate slow consumers into dedicated consumer groups with dedicated topics (via separate processing pipelines). Monitor lag with Prometheus + Grafana (kafka_consumergroup_lag metric).

Q14. What is tiered storage in Kafka and when would you use it? Advanced

Tiered storage (GA in Kafka 3.6) offloads older log segments from broker-local disk to cheap object storage (S3, GCS, Azure Blob) while keeping recent segments on broker disk. Benefits: (1) Brokers no longer need large disks for long retention — significant cost reduction; (2) Broker disk only needs to hold the "active" segment plus recent data (hours/days); (3) Historical data can be retained for months/years in S3 at minimal cost; (4) Consumer can still read old segments transparently — Kafka fetches from object storage on demand; (5) Broker recovery is faster (no need to replicate old segments). Use cases: compliance/audit logs with years of retention; replayable event streams; long-term analytics backfill. Trade-off: read latency for old data increases (S3 latency vs NVMe), but for recent data it's unchanged.

Q15. How does Kafka MirrorMaker 2 handle active-active replication without infinite loops? Advanced

MM2's DefaultReplicationPolicy adds a source cluster prefix to replicated topic names: topic orders on cluster A becomes A.orders on cluster B. When B's MM2 replicates back, it would create B.A.orders on A (not orders) — breaking the loop. Additionally, MM2 tracks which records have already been replicated via a provenance header and does not re-replicate them. Consumers in each DC read from their local (non-prefixed) topic; cross-DC writes go to the prefixed topic. MM2 also synchronizes consumer group offsets, allowing consumers to resume from the correct position in the replica cluster during failover. The offset sync mechanism translates local offsets to remote offsets accounting for possible gaps in replication.

Q16. Explain the role of linger.ms and batch.size in producer performance. Intermediate

batch.size (default 16KB) is the maximum number of bytes in a batch for a single partition. The batch is sent when either: it reaches batch.size OR linger.ms elapses. linger.ms (default 0) is an artificial delay added to accumulate more records. At linger.ms=0, the producer sends immediately when a record arrives (minimal latency but small batches). At linger.ms=5, the producer waits up to 5ms, allowing more records to accumulate → larger batches → better compression ratio → less network overhead → higher throughput. For high-throughput pipelines: batch.size=65536 + linger.ms=20 + compression.type=lz4. For low-latency: keep defaults or linger.ms=0.

Q17. What is the difference between KStream.join and KStream.leftJoin with a KTable? Intermediate

KStream.join(KTable): Only produces an output record if the KTable has a non-null value for the stream record's key. If no KTable entry exists → the stream record is dropped. KStream.leftJoin(KTable): Always produces an output record. If no KTable entry exists → the joiner function is called with a null KTable value (you handle the null case). Use join when you only care about stream events that have a matching reference record (e.g., enrich order with customer — skip orders with unknown customers). Use leftJoin when you always want to pass through the stream event even if no enrichment is available (e.g., process the order regardless, just add customer info if available).

Q18. What is Kafka's log compaction and when should you use it? Advanced

Log compaction is an alternative to time/size-based log retention. Instead of deleting old segments, the compactor periodically merges log segments keeping only the latest value for each key. Deleted records are replaced with a tombstone (record with null value) which is itself eventually removed. Result: the topic always retains the current "truth" for each key — even after very long retention. Use cases: (1) Kafka as a system of record (KTable changelog topics use compaction internally); (2) Database cache invalidation topics (keep latest state per entity); (3) Event sourcing where you need the current state of each aggregate, not full history. Compacted topics can be read from the beginning (offset 0) to reconstruct full current state — used by Kafka Streams state store changelog topics for recovery.

Q19. How would you design a Kafka-based order processing system with exactly-once guarantees? Very Advanced

Architecture: Order Service (producer) → orders topic → Order Processor (Kafka Streams) → order-results topic + DB write.

Producer: enable.idempotence=true, transactional.id=order-service-{instanceId}. Each order submitted in a transaction. Order Processor (Kafka Streams): processing.guarantee=EXACTLY_ONCE_V2. Streams handles: read from orders, enrich with inventory KTable, write result to order-results, commit offset — all in one transaction. For DB writes (non-Kafka sink): use the "transactional outbox" pattern — write DB record + Kafka message in the same DB transaction. Debezium reads the outbox table and publishes to Kafka — no two-phase commit needed. Consumers of order-results: use idempotent DB upsert (INSERT ... ON DUPLICATE KEY UPDATE) as the final defense against any duplicates. Isolation level: read_committed on all consumers to avoid reading uncommitted messages from aborted transactions.

Q20. What are the trade-offs between more partitions and fewer partitions? Intermediate

More partitions: Higher parallelism for producers and consumers; more consumers in a group can be active; higher throughput ceiling. Downsides: more open file handles on broker (each partition = files); controller must track more partition states; leader election work during broker failure scales with partition count; end-to-end latency increases slightly (more bookkeeping); Kafka Connect and Streams tasks multiply. Fewer partitions: Less overhead; faster leader election; simpler operations. Downside: throughput ceiling lower; maximum consumer parallelism limited. Rule of thumb: start with a manageable number (3-12), increase when throughput data demands it. You can increase partitions but not decrease — and increasing changes key-to-partition mapping, potentially breaking ordering for existing keys during the transition window.

Q21. What is the Transactional Outbox Pattern and why is it used with Kafka? Advanced

The dual-write problem: writing to a DB and publishing to Kafka in the same "transaction" is impossible without distributed transactions (2PC). If you write DB first and Kafka publish fails, DB has data but event is lost. If Kafka first and DB fails, event published but no DB record.

Transactional Outbox: write DB record + outbox table entry in a single DB transaction. A separate relay process (or Debezium) reads the outbox table via CDC and publishes to Kafka. The DB transaction guarantees atomicity of the business record + outbox entry. The relay delivers the event exactly-once using idempotent producer + deduplication (include a unique event ID in the message; consumers deduplicate). Benefits: no 2PC; DB is the source of truth; events are never lost. Drawback: slight latency (Debezium poll interval); additional outbox table to manage.

Q22. Explain session windows in Kafka Streams with a real-world example. Advanced

Session windows group events with a maximum inactivity gap between them. A session extends as long as events keep arriving within the gap. A new session starts after the gap expires. Example: user session analytics — SessionWindows.ofInactivityGapWithNoGrace(Duration.ofMinutes(30)). If a user clicks at 10:00, 10:05, 10:20, 10:25, then is idle until 11:00 (35 min gap), and clicks again at 11:00 and 11:10 — result: two sessions: Session 1 [10:00-10:25] with 4 events; Session 2 [11:00-11:10] with 2 events. In Kafka Streams, sessions can merge: if a new event arrives within the gap of an existing session, the session extends and previously computed session windows are merged. This requires the state store to hold session boundaries. Challenge: out-of-order events can cause session merges after initial emission — use grace periods carefully.
